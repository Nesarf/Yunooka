# Yunooka（湯の岡）

HMYR 要跑在上面的那个系统。名字取自小一孁こはね所属学寮都市「カピラ」的寮名。

分工写在 HMYR 仓库的 `design/FULLSELF.txt` 第七节：**Hiou Rengo 负责「写」，Yunooka 负责「跑」**。
宿主口归 OS，其余归 SDK。

## 文字

源码、注释、文档、以及程序里的字符串，一律用 Unicode。

- **源码与注释是 UTF-8** —— 这份 `.asm` 里那些中文注释就是
- **程序里的字符串按 HMYR 的底来，是 UTF-16 码元** —— 种子里那几个函数名就是 `letters`、
  `符位` 这样的 UTF-16 串，`read_value` 取串时跳过的也是「字符数乘二」个字节
- **串口输出这一层用 UTF-8**：一个字符先编成字节再出去。这一块还没写，所以现在打出去的
  全是 ASCII —— 而当 `print` 之类的东西要打中文时，缺的就是那一步编码

盘符用希腊字母那一条与这一条是同一个方向：这个系统的文字层面不打算借别人的字母表。

## 盘符

盘符按小写希腊字母从 α 开始：

```
α  β  γ  δ  ε  ζ  η  θ  ι  κ  λ  μ  ν  ξ  ο  π  ρ  σ  τ  υ  φ  χ  ψ  ω
```

这是设计上的选择，不是实现细节。ASCII 的字母在别的系统里已经各有含义（`C:` 是 Windows 的），
而希腊字母在文件名里少见、排序稳定、一眼能看出是 Yunooka 自己的东西。

路径怎么写（`α:\...` 还是 `α:/...`）还没定 —— 那一件事要等有文件系统的时候才说得准。现在这
一条只是把「盘符从哪来」记下来，免得以后随手用了英文字母，而那时改名的成本比现在高。

## 它现在还不是什么

这一条要说在最前面：**Yunooka 现在还不算一个真正的操作系统**，它仍处于依赖 Windows 运行
的阶段。

分两层看：

```
运行那一侧   引导扇区跑在 VirtualBox 的虚拟硬件上，中间没有 Windows。这一层是干净的。
构建那一侧   编它要 nasm、建盘要 node、跑它要 VBoxManage —— 三样都在 Windows 上。
             换一台机器、换一个系统，这三样就没有了。
```

所以它的「能跑」有一半是借来的。真正算数的门槛是**在没有 Windows 的地方也能构建**：
这套引导代码自己能被它自己编出来。那要等 Yunooka 有编译器、有文件系统、有一套工具链，
而那是很远的事。

把这一条写在这里，是因为「能引导、能打印」很容易被当成「已经是 OS 了」。它不是。它是一个
能在虚拟机上说话的最小东西，而它的出生地是一台 Windows。

## 现在有什么

一块能在 VirtualBox 里引导的盘，和一条判据。

```
boot/boot.asm      512 字节的引导扇区：初始化 COM1、打印一行、读十六扇区的第二段、跳过去
boot/stage2.asm    第二段（十六扇区）：打印、读种子、三段位宽、堆自检、读种子头
tools/build.mjs    编两段、各查形状、拼成一块盘、转成 vdi（`--seed` 带种子，`--size` 定盘大小）
tools/run.mjs      挂盘、引导、读串口、比对
```

跑：

```
node tools/build.mjs                                  # 不带宽种子
node tools/build.mjs --seed D:\himeyuri\bootstrap\pack.hmtn
node tools/run.mjs
```

## 判据

**串口里出现四行：`boot ok`、`stage2 ok`、`protected mode ok`、`long mode ok`；种子那一条另报。**

```
Yunooka: boot ok
Yunooka: stage2 ok
Yunooka: seed ok 74594        <- 种子那一条，三选一，不进成败线
Yunooka: protected mode ok
Yunooka: long mode ok
```

种子有三种结果，单独报：

```
Yunooka: seed ok 74594    读完整份种子，前五字节是 HMYRB；数字是种子的真实长度
Yunooka: seed bad         读到了，但前五字节不是 HMYRB（没给 --seed 时就是这一种）
Yunooka: seed unreadable  三批里有一批读不出来
```

种子那一条不进成败线，因为它回答的是「磁盘上那份东西对不对」，而四行成败线回答的是
「这个引导链走不走得通」。两件事分开报，所以不带种子的一趟照样是通的 —— 而种子坏了的
一趟也不会因此被误判成链断了。

走串口而不是屏幕，因为 VBoxManage 能把 COM1 的字节写进主机的一个文件 —— 于是「它说得出
话吗」变成「文件里有没有那段字节」。这件事可以自动比对，不依赖截图、OCR 或者人的眼睛。
屏幕输出照样留着，用来看，不用来判。

`tools/run.mjs` 的退出码：0 四行都在，1 缺至少一行，2 这一台做不了（没有 VirtualBox、
没有盘）。

## 盘的大小

`--size` 给盘的大小（单位 MB），默认 64。

```
node tools/build.mjs --seed <种子> --size 1024     # 1 GB
node tools/build.mjs --seed <种子> --size 4096     # 4 GB
```

现在只用了开头四兆出头，其余是空的。空得体面是有意的 —— 装文件系统、放工具链、塞基本库
都要空间，而一块盘的尺寸定得早，后面就不必为了扩大它去搬分区。

还有一件实测的事：**名义尺寸不等于占用**。64 MB 的盘建出来的 vdi 只有 3 MB ——
VirtualBox 对全零区域是稀疏的。所以 1 G 到 4 G 的盘不必担心在 D 盘上吃掉那么多，
除非真的写满了。

注意 BIOS 的 MBR 那颗路只到 2 TB；1 到 4 G 远在范围内。

## 函数调用

一次最小的调用：把调用者的 pc 与指令流保存起来，切到被调方，跑完再恢复。

```
Yunooka: call -> 512
```

被调方是 `块长`，两条指令就交出 512。这不是在解释「调函数」这条指令 —— 那还要按名字找
函数、传参数、算返回值占哪个槽。它试通的是那条缝：**同一个 exec 能不能跑另一个函数、并且
回到调用者原来那一步**。帧栈的骨架就在那几行 push/pop 里，往后加参数与局部槽，加的是这几
行之间的内容，而不是换一种结构。

## 种子里有重名

`块长` 在种子里出现了**两次**：偏移 50814 的那个返回 256，偏移 65950 的那个返回 512。

这不是异常。数一遍：`main` 出现七次，`is_punct` 两次，`块长` 两次。

这件事把之前两处「看起来像 bug」的东西一起解释了：

- **`find_fn` 卡住**：它按文件顺序数函数，而 HMYR 自己的读取器把重名折进一个 Map、只留
  最后一个。两侧的「第 n 个函数」不是同一个函数 —— 那时遍历到某个位置就再也对不上了。
- **`call -> 256` 与 `call -> 512`**：我脚本按名字找到的是第一个定义，而 `读程序` 给的是
  最后一个。两个数都对，只是看的不是同一个函数。

所以判据跟 `读程序` 那一侧走，用后一个定义。这一条也解释了为什么这一版用硬编码偏移而不
遍历：**在这个种子上，「第几个」不是一个可靠的坐标，而字节偏移是。**

## 条件跳转

求值循环现在认九条指令，其中三条是跳转，于是它能跑种子里那个十一条指令的 `符位`：

```
Yunooka: fn116 -> 2147483648    参数真：不跳，交出 2^31
Yunooka: fn116 -> 0             参数假：跳到 5 那条路，交出 0
```

两行合起来才说明「跳转按条件走」—— 只验一个的话，一个永远不跳的解释器也能过。

栈从一格长到十六格，因为 `取` 与 `常量` 都会压、`假跳` 会弹。跳转的目标是**指令索引**，
而游标是字节位置，所以执行前有一遍预扫把每条指令的字节偏移记下来 —— 没有那张表，每次跳
都得从头发扫一遍。

`假跳` 弹栈，`假跳留` 看栈顶 —— 这一条是从 `src/vm.mjs` 的写法读出来的，而 `符位` 用的是
前者，所以这一版只实现弹栈的那一条。

## 第一次执行

有了指令流，就能执行了。一个只认两条指令的求值循环：

```
常量 "abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ_"   ->  压进一格栈
返回                                                            ->  交出栈顶
```

串口读出来是：

```
Yunooka: letters -> string 53
```

53 是 26 个小写、26 个大写加一个下划线 —— 这个数可以从那一侧独立算出来，所以这一行验的
是「真的执行了」，而不是「打了一行字」。

`letters` 的四条指令里，「常量」与「返回」各出现两次，而入口到第一个「返回」只压过一次，
所以栈只有一格。这不是解释器，是解释器最小的那副骨架 —— 它证明「读一条指令、按它动一下
状态、再读下一条」这条缝是通的。跳转、算术、调用都还不在里面。

## 走完指令流

现在把第一个函数那四条指令全走一遍，而不是只看第一条：

```
Yunooka: fn letters params 0 slots 0 instrs 4
Yunooka: op 5
Yunooka: op 28
Yunooka: op 5
Yunooka: op 28
```

`5` 是「常量」，`28` 是「返回」，所以 `letters` 读作「常量、返回、常量、返回」。用 HMYR 自己的
`读程序` 读同一份文件，给的是同样的四个数。

> 这说明 `letters` 这个函数体是「把某个常量交出去」，两次。中间没有分支、没有调用 —— 这一点与它的名字对得上：它大概是那张字母表的第一个切片。

**走完的关键是立即数形状。** 一条指令占多少字节取决于它带什么：算子类没有立即数，跳转带
四个字节，`名字` 类带一整个 UTF-16 串，`值` 类带一个带标记的可变长编码。所以代码里有一张
34 项的 `imm_shape` 表（操作码到形状），按号排，与 `src/code-file.mjs` 的立即数形状表一致；
`skip_imm` 按形状把剩余字节跳过。不知道形状就只能读第一条 —— 而「只读第一条」与「走完
四条」在第一条上看起来完全一样。

## 读到函数表

跳过文件头之后读第一个函数，并翻出它第一条指令的操作码：

```
Yunooka: fn letters params 0 slots 0 instrs 4
Yunooka: op 5
```

`letters` 是这个种子里第一个函数，参数量 0、槽数 0、四条指令 —— 与 `node` 那边读同一份
文件给出的完全一致。`op 5` 是 `src/code-file.mjs` 那张表里的第六项（表从零数），也就是
「常量」。

操作码的名字由 `tools/run.mjs` 翻译，那张表照抄自 `src/code-file.mjs`。抄在这里是有意的：
判据要独立于被验的那一侧，两边对不上时红的是 Yunooka 而不是那张表。

**没有种子就不读它的头。** 一开始忘了这一步，于是从零填充里读出了「版本 0、0 个函数」，
而那第一条指令的 0 还被翻成了「加」—— 垃圾被翻译成漂亮数字，看起来像真读懂了。判据要的
是「读得懂」，不是「读得出数」。

## 种子读懂了开头

长模式下读种子的前九个字节并报出来：

```
Yunooka: seed v1 202
```

那是 `HMYRB`（五个字节）加版本 u16、函数数 u16 —— 格式记在 HMYR 的 `design/C-VM.txt`。
这一份是版本 1、202 个函数，而用 node 读同一个文件给的也是这两个数，所以这一行是对
「它读懂了格式」的断言，不只是「它读了几个字节」。

**种子没有压缩。** 一开始以为得先写一个解压器才能「解出一点」，查了格式才发现它就是字节码
文件本身：函数表、指令流、全局名，一串往下排。于是「解出一点」其实是「照格式读」，而最便宜
的一段就是文件头。

## 第一个分配器

长模式里有一个 bump 分配器：一个游标从 0x400000 起往上走，每次按 16 字节对齐，返回移走
之前的位置。

```
Yunooka: alloc 0000000000400000
Yunooka: alloc 0000000000400010
Yunooka: alloc 0000000000400040
```

三块请求分别是 16、48、100 字节。第二块落在 0x10，因为第一块 16 字节正好对齐；第三块落在
0x40，因为 48 向上取到 48，0x10 加 0x30 就是 0x40；100 字节那块会再往上取到 0x70。

起点选 0x400000，是因为前 4 MB 已经被引导扇区、第二段与页表占着，种子在 0x20000，而 4 MB
往上是干净且被页表映着的一片。

判据三条：首条正好是 `0000000000400000`、每条末位是零、逐块递增。少了任何一条，一个「能
返回指针」的分配器也可能在返回重叠的地址 —— 而那种错在小程序里完全看不出来。

打印用的是十六位十六进制，不是十进制：地址要对齐看得清，`…0000` 与 `…0010` 比 4194304 与
4194320 一眼就分得出。

## 三段位宽：16、32、64

这一块最大的内容是跨过两种模式。第二段现在跑三个位宽段：

```
[bits 16]  实模式：读种子、验魔数、打前两行
           开 A20（走 BIOS 的 int 0x15），装 GDT，置 CR0.PE
[bits 32]  保护模式：打一行，建四级页表，置 CR4.PAE、EFER.LME、CR0.PG
[bits 64]  长模式：打最后一行
```

三处踩出来的东西写在代码注释里，这里只留结论：

**代码段要两个。** 一开始只有一个 `L=1`（64 位）的代码段，于是刚置完 CR0.PE 就拿它远跳 ——
而 `L=1` 的段在 EFER.LME 还没开时是未定义的，CPU 不报错，直接挂住。现在 `0x08` 是 32 位
代码段，`0x18` 是 64 位代码段，各用各的。

**CR3 指向 PML4，不是 PD。** 写错一次：把 0x3000（PD）放进 CR3，开分页那一瞬间 CPU 把
PD 当 PML4 走，走出来的地址全是垃圾。

**A20 不走 8042。** `out 0x64` / `out 0x60` 那一路在 VirtualBox 上把 `out` 卡住了，症状是
串口停在某个观测字节后面。改用 BIOS 的 `int 0x15, ax=0x2401`。

还有一条不是 bug，是判据的读取时机：`run.mjs` 原先一看到前两行就收工，而那时后面的段还
没跑完，于是「保护模式没到」这个结论其实是「读得太早」。现在它等全程里至少四行出现，
或者给满二十秒。

## 它与 HMYR 的第一次接触

第 3 个扇区往后放的是整份种子（`--seed` 给的那份）。第二段用 BIOS 的 LBA 扩展分三批读它：

```
批 1  64 扇区 -> 0000:8000   物理 0x08000 到 0x10000
批 2  64 扇区 -> 1000:0000   物理 0x10000 到 0x18000
批 3  18 扇区 -> 1800:0000   物理 0x18000 到 0x1A400
```

每批 64 扇区不是 BIOS 的限制，是寻址的便利：64 乘 512 正好 0x8000 字节，正好走完一个段，
于是段与偏移都不用做加法。用 LBA 扩展而不是 CHS 读，因为 CHS 跨磁道时有些 BIOS 会失败。

**这一块的边界要说清**：它读完了 146 个扇区，但判据只验开头五个字节。读了一半与读完，
在 `seed ok` 这个判据上看起来一样 —— 因为三批都成功才会走到检查那一步，而三批里任何一批
失败都会落到 `seed unreadable`，所以「读完」这一半是**靠失败路径反证**的，不是直接验的。
直接验的办法是认种子末尾的几个字节，或者干脆执行它；前者要一个段:偏移的末尾地址，后者
要一个字节码机。两样都留给后面。

这是 Yunooka 第一次去认 HMYR 的东西。它现在还读不懂种子，只认得它开头的 `HMYRB`；而
「认得」这个词在 HMYR 仓库的 `design/FILETYPE.txt` 里有一层更重的意思 —— 那个系统认得
那些扩展名。今天只做到第一层。

## 两段是怎么分的

引导扇区只做三件事：初始化串口、把第二扇区读进 0x7E00、跳过去。往后再加的东西都住在
第二段那一侧，而那一 512 字节从此不必再长大。

读盘用 BIOS 的 `int 0x13`，不自己驱动磁盘 —— 这一层的任务是尽快把下一段交出去，真正的
磁盘驱动属于内核，不属于这里。

两段各写一份串口打印，是重复而不是疏忽：它们将来会独立编译、独立加载，共用要靠链接，
而链接是第三块砖的事。现在重复的代价是二十行，不重复的代价是一层依赖。

## 这一块砖为什么这么起

512 字节是这个国家里最小的入口。它不需要工具链之外的东西（nasm 就够），而它要么打出那行
字、要么打不出 —— 没有中间状态可以含糊过去。GRUB 与 UEFI 是之后的事，那时这块砖还在。

## 还没有的

- 读文件：它还读不到 `.hmtn`，更读不到 `.hmoca`
- 内存管理、中断、进程、驱动（磁盘、键盘、显示、网络）
- HMYR 的字节码机

## 一条踩过的坑

第一版串口打印不等发送器就绪，跑起来只收到 `nooka: boot ok` —— 开头三个字符丢了。十六个
字节的整句在 9600 波特下本来能靠 FIFO 撑过去，而第一个字节偏偏不行。加上 LSR 的 THR 空位
等待之后完整了。

## 与 HMYR 仓库的关系

Yunooka 不依赖 HMYR 仓库里的任何东西，现在连 HMYR 都还不认识。反过来也一样：拿掉 Yunooka，
HMYR 的套件应当全绿 —— 那条层次关系（基础不依赖附加）在 HMYR 的 `design/FULLSELF.txt`
第十节里写着。
