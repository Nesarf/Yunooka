# Yunooka（湯の岡）

HMYR 要跑在上面的那个系统。名字取自小一孁こはね所属学寮都市「カピラ」的寮名。

分工写在 HMYR 仓库的 `design/FULLSELF.txt` 第七节：**Hiou Rengo 负责「写」，Yunooka 负责「跑」**。
宿主口归 OS，其余归 SDK。

## 文字

源码、注释、文档、以及程序里的字符串，一律用 Unicode。

- **源码与注释是 UTF-8** —— 这份 `.asm` 里那些中文注释就是
- **程序里的字符串按 HMYR 的底来，是 UTF-16 码元** —— 种子里那几个函数名就是 `letters`、
  `符位` 这样的 UTF-16 串，`read_value` 取串时跳过的也是「字符数乘二」个字节
- **串口输出这一层用 UTF-8**：一个字符先编成字节再出去。这一块还没写，所以现在打出去的
  全是 ASCII —— 而当 `print` 之类的东西要打中文时，缺的就是那一步编码

盘符用希腊字母那一条与这一条是同一个方向：这个系统的文字层面不打算借别人的字母表。

## 盘符

盘符按小写希腊字母从 α 开始：

```
α  β  γ  δ  ε  ζ  η  θ  ι  κ  λ  μ  ν  ξ  ο  π  ρ  σ  τ  υ  φ  χ  ψ  ω
```

这是设计上的选择，不是实现细节。ASCII 的字母在别的系统里已经各有含义（`C:` 是 Windows 的），
而希腊字母在文件名里少见、排序稳定、一眼能看出是 Yunooka 自己的东西。

路径怎么写（`α:\...` 还是 `α:/...`）还没定 —— 那一件事要等有文件系统的时候才说得准。现在这
一条只是把「盘符从哪来」记下来，免得以后随手用了英文字母，而那时改名的成本比现在高。

## 它现在还不是什么

这一条要说在最前面：**Yunooka 现在还不算一个真正的操作系统**，它仍处于依赖 Windows 运行
的阶段。

分两层看：

```
运行那一侧   引导扇区跑在 VirtualBox 的虚拟硬件上，中间没有 Windows。这一层是干净的。
构建那一侧   编它要 nasm、建盘要 node、跑它要 VBoxManage —— 三样都在 Windows 上。
             换一台机器、换一个系统，这三样就没有了。
```

所以它的「能跑」有一半是借来的。真正算数的门槛是**在没有 Windows 的地方也能构建**：
这套引导代码自己能被它自己编出来。那要等 Yunooka 有编译器、有文件系统、有一套工具链，
而那是很远的事。

把这一条写在这里，是因为「能引导、能打印」很容易被当成「已经是 OS 了」。它不是。它是一个
能在虚拟机上说话的最小东西，而它的出生地是一台 Windows。

## 现在有什么

一块能在 VirtualBox 里引导的盘，和一条判据。

```
boot/boot.asm      512 字节的引导扇区：初始化 COM1、打印一行、读三十二扇区的第二段、跳过去
boot/stage2.asm    第二段（32 扇区、16 KB）：打印、读种子、三段位宽、堆自检、读种子头、
                   指令流、求值、跳转、调用、按名字找、内置、帧与尾调用
tools/build.mjs    编两段、各查形状、拼成一块盘、转成 vdi（`--seed` 带种子，`--size` 定盘大小）
tools/run.mjs      挂盘、引导、读串口、比对
```

跑：

```
node tools/build.mjs                                  # 不带宽种子
node tools/build.mjs --seed D:\himeyuri\bootstrap\pack.hmtn
node tools/run.mjs
```

## 判据

**串口里出现四行：`boot ok`、`stage2 ok`、`protected mode ok`、`long mode ok`；种子那一条另报。**

```
Yunooka: boot ok
Yunooka: stage2 ok
Yunooka: seed ok 74594        <- 种子那一条，三选一，不进成败线
Yunooka: protected mode ok
Yunooka: long mode ok
```

种子有三种结果，单独报：

```
Yunooka: seed ok 74594    读完整份种子，前五字节是 HMYRB；数字是种子的真实长度
Yunooka: seed bad         读到了，但前五字节不是 HMYRB（没给 --seed 时就是这一种）
Yunooka: seed unreadable  三批里有一批读不出来
```

种子那一条不进成败线，因为它回答的是「磁盘上那份东西对不对」，而四行成败线回答的是
「这个引导链走不走得通」。两件事分开报，所以不带种子的一趟照样是通的 —— 而种子坏了的
一趟也不会因此被误判成链断了。

走串口而不是屏幕，因为 VBoxManage 能把 COM1 的字节写进主机的一个文件 —— 于是「它说得出
话吗」变成「文件里有没有那段字节」。这件事可以自动比对，不依赖截图、OCR 或者人的眼睛。
屏幕输出照样留着，用来看，不用来判。

`tools/run.mjs` 的退出码：0 四行都在，1 缺至少一行，2 这一台做不了（没有 VirtualBox、
没有盘）。

## 盘的大小

`--size` 给盘的大小（单位 MB），默认 64。

```
node tools/build.mjs --seed <种子> --size 1024     # 1 GB
node tools/build.mjs --seed <种子> --size 4096     # 4 GB
```

现在只用了开头四兆出头，其余是空的。空得体面是有意的 —— 装文件系统、放工具链、塞基本库
都要空间，而一块盘的尺寸定得早，后面就不必为了扩大它去搬分区。

还有一件实测的事：**名义尺寸不等于占用**。64 MB 的盘建出来的 vdi 只有 3 MB ——
VirtualBox 对全零区域是稀疏的。所以 1 G 到 4 G 的盘不必担心在 D 盘上吃掉那么多，
除非真的写满了。

注意 BIOS 的 MBR 那颗路只到 2 TB；1 到 4 G 远在范围内。

## 函数调用

一次最小的调用：把调用者的 pc 与指令流保存起来，切到被调方，跑完再恢复。

```
Yunooka: call -> 512
```

被调方是 `块长`，两条指令就交出 512。这不是在解释「调函数」这条指令 —— 那还要按名字找
函数、传参数、算返回值占哪个槽。它试通的是那条缝：**同一个 exec 能不能跑另一个函数、并且
回到调用者原来那一步**。帧栈的骨架就在那几行 push/pop 里，往后加参数与局部槽，加的是这几
行之间的内容，而不是换一种结构。

## 种子里有重名

`块长` 在种子里出现了**两次**：偏移 50814 的那个返回 256，偏移 65950 的那个返回 512。

这不是异常。数一遍：`main` 出现七次，`is_punct` 两次，`块长` 两次。

这件事把之前两处「看起来像 bug」的东西一起解释了：

- **`find_fn` 卡住**：它按文件顺序数函数，而 HMYR 自己的读取器把重名折进一个 Map、只留
  最后一个。两侧的「第 n 个函数」不是同一个函数 —— 那时遍历到某个位置就再也对不上了。
- **`call -> 256` 与 `call -> 512`**：我脚本按名字找到的是第一个定义，而 `读程序` 给的是
  最后一个。两个数都对，只是看的不是同一个函数。

所以判据跟 `读程序` 那一侧走，用后一个定义。这一条也解释了为什么这一版用硬编码偏移而不
遍历：**在这个种子上，「第几个」不是一个可靠的坐标，而字节偏移是。**

## 按名字找函数

上一节的调用是硬编码偏移。这一节把那个偏移换成名字 —— `调函数` 这条指令的真实立即数
就是一个名字，没有索引可用。

```
Yunooka: byname -> 512
Yunooka: byname first -> 256
```

两行都要在，因为它们说的是两件事：走完整张函数表、留下最后一个同名定义，交出 512；
第一个匹配就收手，交出 256。同一个名字、同一段代码，只有「怎么找」不同。

先撞上的那个数不是错的，它是另一个函数。`块长` 在种子里两处定义，一个 256 一个 512，
而 HMYR 的 `读程序` 把函数折进 Map 时后写覆盖前写。所以「按名字」在这一侧等于「最后一个
同名定义」—— 一行读数分不开这两种语义，两行可以。

### 一个只读四字节的格子

这一块卡了半天，最后是编译清单一行解决的：

```
949 00000882 4C8B2E    mov r13, [rsi]    ; 指令数，u32
```

`mov r13, [rsi]` 是八字节读，而指令数是 u32 —— 高 32 位吃到的是紧跟着的第一个 opcode，
循环上限于是成了两万多亿。症状不是崩，是「找不到」：跳过指令流那一段一路跑到撞上
10000 条的上限才停，一个函数都没被真正跳过。

同一行在 `find_fn` 里也有一份，但它从不跳过任何指令流（第 0 个就找到了），所以从没露过。
没被跑到的代码不属于「写好了」，只属于「还没被证伪」。

### 这一块还没验的

参数传递。`块长` 是零参，所以槽填充、参数数检查、返回值落回调用者的槽 —— 这三样代码里
有位置，判据还没有。要等下一个真的用得上参数的函数。

## 第一条真的跑起来的程序

`is_digit('7')` 真，`is_digit('a')` 假。

```
Yunooka: is_digit('7') -> true
Yunooka: is_digit('a') -> false
```

这两行比它们看起来重得多。`is_digit` 只有七条指令，但它踩到了解释器的每一样东西：

- 参数落槽（它一参、`in_set` 三参）
- `调函数` —— `digits` 是非尾调用，会压帧再回来
- `调内置 len`
- `索引`，从串里取第 i 个码元
- `等` —— 两个单字符按内容比，不是按指针
- `加` 与 `大等`，f64，走 SSE
- `假跳`，以及 `in_set` 那条十轮的尾递归

**少一样就给不出答案**，而它给出的答案只有两个字。对不上的时候说不清断在哪 ——
这是这条判据的代价，也是它的用处：它不问「某一处对不对」，只问「全都对不对」。
分开验的那些在上面各节里。

### 三个坑，一个比一个安静

**SSE 没有开。** 长模式下 `addsd`、`comisd`、`cvtsi2sd` 要 `CR4.OSFXSR`，而启动那条路
只设了 PAE。没有 IDT，`#UD` 就是三重故障 —— 串口停在上一行，看起来像「后面那段没被
调到」。

**`pop_val` 用 `rcx`。** 参数搬运那个循环把上限也放在 `rcx` 里，于是它永远到不了头。
症状与上面那一条一模一样。

**`find_fn_by_name` 把 `rbx` 用成了自己的计数。** 它按文件顺序走完整张函数表，收工时
`rbx` 是走到的那个 401；而我一直在拿它当调用者的 pc 去判尾调用，于是
`instr_offsets[402]` 出了表，每一处调用都被判成非尾，四帧三两下就用完。

第三个最值得记：**调用者与被调者之间，除了约定好的那几个寄存器，谁都可以改。**
`find_fn_by_name` 的约定里没有「不许碰 rbx」，所以它碰了；而调用它的人以为 `rbx`
还是自己的 pc。

## 长模式下的第一块读盘能力

```
Yunooka: ata same 512
```

文件系统的前提不是路径语法，是「进了长模式之后还读得到盘」。BIOS 的 `int 0x13` 只活在
实模式，所以这一段必须自己碰端口 —— 主通道 `0x1F0` 那一组，LBA28 的 PIO 读。

判据不是「读出来了」，而是「与 BIOS 读的是同一份」：种子已经由 `int 0x13` 读到 `0x20000`，
这里再用 ATA 读同一个扇区（LBA 33，种子在盘上的第一个扇区），512 字节逐字节比。两条完全
不同的路给出同样的字节，才说明这一段对 —— 读错一个扇区也会读出一个结果。

### 控制器必须是 IDE

第一次跑只留下一句 `ata start`，然后就没有下文。原因是这台机器挂在 AHCI 控制器上：
`0x1F0` 那一组端口属于 IDE 兼容模式，AHCI 不映射它们，读 `0x1F7` 一直返回 `0xFF` ——
状态位看着永远「忙」，等待循环转到超时才放手，而串口上什么都没有多出来。

改成 PIIX4（IDE）就通了。`tools/run.mjs` 现在会检查控制器名，不是 IDE 就把机器删了重建：
控制器换不了，只能重来。

## 盘上的第一份布局

```
Yunooka: fs ok v1 root 1025 first hello.txt
```

三个数都来自盘上那份字节：版本、根目录的扇区号、根目录里第一个条目的名字。布局写在
[design/FS.txt](design/FS.txt)，这一块只做它说的第一件事。

超级块像门牌，目录像门牌背后挂着的名册 —— 门牌说这户人家从第几个扇区起住，名册说
住在里头的人叫什么。这一版只把名册第一行念出来，没有人进门。

`tools/build.mjs` 按那份布局写进一个超级块、一个根目录、一份 `hello.txt`；`stage2` 用
上一节那条 ATA 路径把它们读回来。

### 两个让机器停住的坑

**`ata_read` 读完没有等 BSY 落。** 第一次读（LBA 33）照成，第二次（LBA 1024）就停住了：
盘还在忙着收尾，下一条命令被丢掉，而 `insw` 读回的是上一次留在缓冲区里的字节 —— 那
看起来像「读成了，只是读错了扇区」。现在发命令之前等一次、读完之后再等一次。

**`tools/build.mjs` 卸盘还写着 `SATA`。** 控制器早就换成 IDE 了，那一条 `storageattach`
一直失败得很静 —— 盘还挂着，`closemedium` 关不掉，错误要到媒体登记那一步才换一副面目
出现。这种错最难找：它不报错，它只是让后面某一步看起来像坏了。

### 还没做的

路径。`α:/a/b` 怎么被解析、按名字在目录里怎么找、盘符怎么翻译成盘 —— 三件都还空着。
设计里写了它们该长什么样，代码里一行都没有。下一块就是它。

## 按路径打开一份文件

```
Yunooka: open hello.txt -> Yunooka filesystem ok
```

盘符认出来、`α:/` 跳过去、名字在根目录里找到、数据从盘上读回来 —— 四环全对才给得出
这一行，而判据是那二十二个字节的内容本身。

盘符是 UTF-16 里的希腊字，八位串口打不出来，所以这一行打的是名字而不是整条路径。
「盘符被认出来了」由「找到了」间接证明：盘符不认识会走 `unknown drive`，名字不在会走
`not found`，两条都是自己的声音。

### 路径是解析出来的，不是手写的

```
Yunooka: open docs/note.txt -> Yunooka subdirectory ok
Yunooka: open docs/sub/deep.txt -> Yunooka three levels ok
```

`fs_open_path` 从根目录起一段一段查：先认盘符与冒号，然后跳过斜杠、量出这一段的长度、
拿它去查当前目录。找到了就是下一段的目录，没找到就说 `not found`。

**三层那一行才是「路径被解析」的判据。** 两层在旧的写法里也能过 —— 那时是两个手写的
段名各占一个变量（`fs_seg1`、`fs_seg2`），三层就要再加一个，四层再加一个。按斜杠切段
之后，深度只是循环多转了一圈。

「当前在哪一层」是一个寄存器里的扇区号，不是全局的当前目录。绝对路径不需要那种东西 ——
而当前目录要等有进程、有「谁记得自己站在哪」的时候才谈得上。

### 同一个名字，两块盘

```
Yunooka: open hello.txt -> Yunooka filesystem ok
Yunooka: open hello.txt -> Yunooka second disk ok
```

同一个名字，读到两份不同的字节 —— 因为路径前面那个盘符不同。

| 盘符 | 是什么 | 文件系统从 | 预读在 |
| --- | --- | --- | --- |
| α | 主盘 | 第 1024 号扇区 | `0x40000` |
| β | 第二块盘，IDE secondary master，盘号 `0x82` | 第 0 号扇区 | `0x60000` |

**「读哪一块盘」现在不是两段代码，是两个变量的值** —— `fs_base` 与 `fs_start`，
`fs_open_path` 认盘符之后拨它们。两块盘的格式完全一样。

判据要内容不同才分得开：`open` 成功那两行都有。

### 两个都很难看的错

**`"none"` 也算挂上了。** `run.mjs` 判断盘挂没挂用的是「键在不在」，而 `showvminfo`
对空槽位也输出 `IDE-1-0="none"` —— 于是 `attach` 一次也没跑过。盘造出来了、文件也在，
就是没接到机器上。

**拨回得太早。** `fs_open_path` 返回前把基址拨回 α，而读文件在调用者那一侧：
`fs_load(2)` 拿 α 的起点 1024 做减法，借位成一个巨大偏移，表现是 `#PF at 0xA1B4`
而不是「读错了内容」。

一个状态什么时候失效，要由**用完它的人**决定，不是由产生它的人。

## 写一个文件

```
Yunooka: wrote -> Yunooka wrote this
```

造一个不存在的名字 `new.txt`、写一段只有这里才有的字节、再按路径打开它。`files` 的
列表里也多出了 `new.txt`。

`fs_write_file` 算空闲扇区、在根目录追加条目、把数据拷进去。空闲扇区的账是一个减法：

```
新扇区号 = 数据起 + (扇区总数 - 数据起 - 空闲扇区数)
```

这不是分配器。连续分配的意思是「写之前就想清楚它多大」，而这一版不做回收 ——
所以「下一个空扇区永远在最后」这件事暂时成立；一旦删掉一个文件，这个减法就会指到别人身上。

### 判据要两件一起成立

**目录里多了一条**，与**数据落对了地方**。它们各自会坏，而坏的样子不同 —— 只有一条
对的实现看起来很正常，只是读出来的是别的字节。

### 它写的是内存

数据落在**预读区**里，重启就没了。持久化要 PIO 写，那条路还没写出来，记在 `fs-persist`
那一条。把「文件系统这一层的写」与「有没有落到盘上」分开做，是因为混在一起出错时
分不清是哪一层 —— 而那种时候通常会把「没落盘」当成「写错了」。

### 一个同类的坑

`fs_load` 把地址交在 `rsi`，而下一句拿 `rsi` 去打提示词 —— 于是打出来的是数据段里的
字符串（`wrote -> Yunooka: write fail`）。先存进 `fs_buf` 就好了。

这与「`puts64` 的最后一个 `lodsb` 会改 `al`」是同一类：**打印函数会占用它碰到的寄存器**，
而两次都发生在「刚拿到一个地址、马上要打印」的地方。

## 网卡：先证明它在

```
Yunooka: pci dev 3 00000000100E8086
```

网卡从关着变成开了（`nat` + `82540EM`）。第一步不是协议，是 **PCI 枚举**：`0xCF8` 写地址，
`0xCFC` 读数据，扫 0 号总线的 32 个设备槽。

读出来的六个设备里，`8086:100E` 就是 Intel E1000 —— 也就是配给它的那一块。**那两个数由硬件
给出，不由我们解释**；读对了它们，说明「网卡在这台机器上、而这条总线读得通」。

只扫 0 号总线与 func 0：这台机器的设备都在那里，而多扫两级要把「怎么认多功能设备」也
写进来 —— 那一层对「有没有网卡」没有帮助。

**把运输层做好不代表家庭组开始了一行。** 往后 ARP、IP、UDP、TCP 每一步都有它自己的判据，
而它们与家庭组的关系要单独讲。

## 家庭组：先做不需要网络的那两件

设计在 [design/HOMEGROUP.txt](design/HOMEGROUP.txt)。

Windows 的家庭组拆开来是五个部件：**发现、边界、共享、权限、身份**。其中三件依赖网络与
「第二台机器」，而这两样这台机器都没有 —— 网卡刚开、协议栈一个字没写，而且连两台机器
都跑不起来。

所以魔改的结论是：先做那两件不需要网络的。

```
Yunooka: shares docs dir
```

**共享**做成目录条目类型上的一个位（`0x80`），不是一张单独的共享表 —— 表要与目录同步，
而同步总有一个人先动，那个间隙里两边会不一致；位只有一份数据。

**边界**是一个数（超块里的家 ID），不是一段可以说给别人听的密码 —— 后者在没有网络身份
的地方没法验证。

**发现不做**：盘在手里就知道它是哪一块。

### 判据是走两遍

两遍都只该有一条 `docs dir`。**一个「往清单里加一条」的实现走第一遍也是对的** ——
只有第二遍分得开。

### 两个坑，都不是算错

**读错了扇区。** `run_shares` 读的是 `1024`（超块）而不是 `1025`（根目录），清单因此永远
是空的。那一句是照着别处抄的，而那两行连在一起时看着像「读根目录」。

**游标托付给了寄存器。** 列清单的循环用 `r8` 与 `r12` 记位置，而 `put_hex64` 与
`put_utf16_n` 会占用它们碰到的寄存器 —— 循环只转一圈。改放内存变量就好了。

这一条与「`puts64` 改 `al`」「`fs_load` 的地址在 `rsi`」是**同一族**：打印函数会吃掉寄存器。

### 边界是一个数

```
Yunooka: home 00000000594B4E52
Yunooka: beta 0000000011111111 not family
```

超块的偏移 28 放着一个 `u32` 的家 ID。两块盘的号一样，它们就是一家人。

**它不是密码。** 密码在没有网络身份的地方没法验证，而两个数可以比较 —— 这是这台机器现在
唯一能真的做到的边界形式。

主盘写 `0x594B4E52`，β 盘在 `run.mjs` 里**故意写另一个数**。同号的话，「比较过」与
「根本没比较」在串口上完全一样 —— 而那是这一条最该分得开的两件事。

### 加入是一个动作

```
Yunooka: beta 0000000011111111 not family
Yunooka: beta 00000000594B4E52 family
```

`join` 把主盘的家写进第二块盘。**判据是同一个比较的结论翻过来** —— 同一段代码、
同一个读法，只有盘上的数变了。

这比「又打印了一次 `family`」结实得多：一个「总是说 `family`」的实现过不了前半段。

### 共享与边界见面

```
Yunooka: shares 0000000011111111 not family
Yunooka: shares 00000000594B4E52 hello.txt file
```

`fs_shares_at` 先比家 ID，同一家才列，不同一家一条都不列。

判据走三步：先在 β 上标记一个文件、再列 β 的共享（被挡住）、然后 `join`、再列一次
（列得出 `hello.txt file`）。**第三次与第四次之间只发生了一件事** —— 家 ID 被写过去了，
所以两次读数的差别只能来自那里。

**挡住的判据必须是那一行 `not family`**，不能只是「没有条目」：一块盘上本来就可能一条
共享都没有，那种空与这种空看起来一样。

### 门：共享位终于有约束力

```
Yunooka: read blocked by boundary
Yunooka: shared -> Yunooka second disk ok
Yunooka: secret blocked
```

在此之前，β 上的文件**不管共不共享都读得到** —— 那个位只是一句宣言。现在 `fs_gate` 立在
`fs_open_path` 的最后一段上：别的盘上的东西要过两关，**同一个家**，而且**那一条带共享位**。

三次读数各分得开一种坏法：

- 家不同时读不到（不然边界是装饰）
- 同一家共享过的读到（不然它挡住自家人）
- 同一家没共享的读不到（不然共享位是装饰）

**第三条最要紧** —— 一颗「只要同一家就放行」的实现，前两条都对。β 上那第二个文件
`secret.txt` 就是为了这一条而存在的。

### 三个坑，三种形状

**门挡住了标记动作本身。** `share` 要走 `fs_open_path`，而它要标记的那一条在标记之前
过不了门 —— 「要共享才能访问、要访问才能共享」的闭环。解是 `gate_off`：**门只管读取，
管理动作不走它**。

**读主盘的家用了 `fs_load(1024)`。** 而 `fs_load` 用的是「当前盘」那两个数 —— 在 β 上
它算出 `0x60000 + 1024*512`。要先拨到 α 读、读完拨回。

**`fs_open_path` 只交出扇区号。** 「哪一块盘的扇区」那件事被它在结尾拨回了 —— 调用者读
文件时拿 α 的起点去减 β 的扇区号，借位成巨大偏移，症状是 `#PF`。

这是**同一个坑第二次踩**（第一次在 `run_fs_open4`），说明 `fs_open_path` 该把地址一起
交出来；那要改所有调用者，所以先在各处拨，并把这件事记在地图里。

### 还掉一笔债

`fs_open_path` 原来只交出扇区号，而「这是哪一块盘的扇区」被它在结尾拨回了主盘。三个调用者
各自拨一次盘 —— 其中两处踩成了 `#PF`，而且两次看起来都像别的问题。

现在它把地址一起交出来（`last_addr`），三处拨盘代码全删了，**而行为一点没变**，三趟连续
退出码零。

这正是「这是债、不是功能」的证据：**还它不改变任何判据**，只是让下一个读这段的人不必再
踩一次。

### 第二段长到 33 个扇区

「第二段多大」这件事牵着**四个数**：

| 少了哪一处 | 症状 |
| --- | --- |
| `boot.asm` 的 `mov al` | 编不过 |
| `build.mjs` 的上级 | 盘建不起来 |
| stage2 末尾的 `times` | 编不过（`TIMES value negative`） |
| 种子起始扇区（含 `种子偏移` 与 `run_ata_test` 的 LBA） | 种子魔数不对、`ata differ at 0` |

**四个都不一样，这一轮四个都见过。**

### 为什么不需要第二台机器

**β 盘就是「另一台机器的盘」。** 它有自己独立的超块、目录、文件，与一台真机器的盘
没有区别。所以家庭组可以在一块盘上做完整 —— 判据不必等第二台机器。

### 跨机器长什么样

**把盘递过去。** 一块 β 盘拔下来、插到另一台 Yunooka 上，两边的家 ID 一样，那边就看得见
这边共享的目录。

这不是妥协，是这台机器现在唯一能真的做到的形态。它也有好处：把「信任边界」做成了一个
可以检查的数。

## 像素层：屏幕上有了一个点

```
Yunooka: pixel 000000000000002F 000000000000001C
```

实模式里 `int 0x10` 设 VGA `0x13`（320×200×256，一个字节一个像素，帧缓冲在 `0xA0000`），
长模式里往左上角与正中各写一个已知字节，再读回来比。

**这是这台机器第一次把东西放到光里。** 截图里正中那一点是看得见的 —— 那一点就是写进去的
`0x1C`。

### 判据为什么要分两层

串口那一行证明**帧缓冲能写能读**。它证明不了**屏幕上真的有**。

第二层是截图，而截图**不作自动判据**：这台机器 headless，屏幕上有没有东西串口说不了话；
而一张图要被程序判，就得写 PNG 解析 —— 那件事的价值低于它带来的脆弱。

所以那一层留给人，`read_image` 确认过。**「像素层在」这件事有人看过，不是只有一行自述。**

### 为什么是 0x13

它是唯一一个**不需要额外协议、不需要问能力**就能得到的模式 —— 老、小、一定在。

VBE 要在实模式里查模式表、在长模式里再读一遍硬件，那两件事都可以等真的有需要时再做。

而设模式必须在实模式：长模式里没有 BIOS，而这件事只有 BIOS 会做。

### 一条连续的线

```
Yunooka: line 000000000000002F 000000000000002F
```

`draw_line` 是整数 Bresenham，从 `(0,0)` 到 `(319,199)`。读回线上两点（起点与 `x=160` 处）
都是线的颜色 —— 而截图里那条绿线看得见，连续不断，320 个像素一个没漏。

![一条对角线](<D:/Yunooka/build/screen.png>)

**为什么不是「按 x 采样、算 y」**：采样法要么每步一次除法，要么在陡的地方把线断成点。
Bresenham 只用加、减、比，每步恰好落一个像素，而且这条路径上本来没必要碰 `f64`。

判据仍然是两层：读回证明线上有像素，截图证明它连成一条。

### 偶发失败要留下证据

连跑八趟里有一趟红了，而那一趟的输出**没留下** —— 重跑五趟全过，什么也没学到。

现在 `run.mjs` 红了会把完整串口输出写进 `build/failed-run.txt`。

**偶发失败最贵的不是它本身，是撞上之后没有证据。** 而一个没有证据的偶发，下一次还是
只能靠重跑来碰。

## 会算数

```
Yunooka: calc ready
1+1
=2.000000
```

送一个算式进去、回车，它给出结果。这个 `2` **不是常量** —— 是解析、`f64` 加法、六位小数
打印三件事都对才有的。

这一版只到**两级**：乘除先、加减后。不做括号（要递归）、不做幂（要符号表）、不做函数 ——
而 `1+1` 与 `2*3+4` 不碰它们。

求值走已有那两件：`parse_decimal` 读数字，`f64` 的四则运算，`put_f64` 打印。

### 三个坑，都在键盘那一路

**`keymap` 里 `=` 与 `-` 本来是空的。** 所以那一路连这两个字符都收不到。填上就好 ——
一个只有字母数字的表看起来能用，而它缺的正好是算式要用的那两个。

**`+` 与 `=` 不是单个扫描码。** 集 1 里 `=` 是 `0x0D`，而 `+` 是 `Shift(0x2A)` 加 `0x0D`。
所以客人机要处理 Shift 状态，主机要自己拼键。

**四个码不能一次 `keyboardputscancode` 送。** 整个序列会被挤掉 —— 与「整行一次送丢头一个」
同族。一个码一次、中间四十毫秒才行。

### 还没通的一件

等号右边那个名字（`1+1=x` 里的 `x`）。实测**符号后面跟一个字母时那个字母到不了客人机**
（回显是 `1+1=`），原因没查清。

算的那半不依赖它，所以先钉住算。**现在这一步交出的是 `=2`，不是 `x=2`。**

## 签名匹配

```
Yunooka: scan eicar -> FOUND
Yunooka: scan clean -> clean
```

一条规则（EICAR 那 68 字节）、一个子串搜索、两个文件。

**素材选 EICAR 的理由不是它简单，是它合法且可核对** —— 一段公开的、专为测杀毒软件而造的
字符串，打印得出来、命不命中当场看得见。不需要从任何一个病毒库里搬真东西进这台机器。

设计在 [design/SIGNATURE.txt](design/SIGNATURE.txt)。

### 本机有什么，以及为什么第一步不能拿它

四件都在：ClamAV 1.5.4（库 108 MB、362 万条签名）、YARA 4.5.5、YARA-X 1.21.0、Torikago。

而它们的库是 `main.cvd`（89 MB）与 `daily.cld`（86 MB）—— **打包格式**，不是能直接读的
文本，而这个文件系统还不会读压缩。能直接进来的是文本形态：ClamAV 的 `.ndb` / `.hdb`、
YARA 的 `.yar`。

### 「训练」这个词要读准

ClamAV 的库是**签名**，YARA 的规则是**文本** —— 两者都是数据加匹配，不是梯度下降。

所以这一层做的是「**照着签名的形状比字节**」。做对了之后，换成谁的库都只是换数据。

### 判据两条都要

**一个永远报 `FOUND` 的实现过第一条，一个永远报 `clean` 的过第二条。**

### 规则在盘上，不在代码里

```
Yunooka: rules eicar -> FOUND
Yunooka: rules clean -> clean
```

`rules.txt` 一行 `eicar:十六进制`。stage2 找冒号、把后半截 `parse_hex` 解成字节，再拿它扫两个文件。

这一条与上面那条 `scan` **分得开**：`scan` 证明「子串搜索认得这 68 字节」，`rules` 证明
**「规则是数据」** —— 而证明方式是**换掉那个文件、不改一行代码，行为跟着变**。

真的 ClamAV `.ndb` 还有「目标类型」与「偏移」两栏（偏移可写 `*` 表示任意位置）。这一版只
认两栏，但**形状按它来**，所以往后加那两栏是扩这一行，不是推翻它。

### 从一条规则到三行规则

```
Yunooka: rules eicar.txt = eicar
Yunooka: rules clean.txt = none
```

`rules.txt` 三行：一条真的（`eicar`）、两条假的（`never`、`also`）。

**这一层的区别不是数量，是名字。** 一行规则只要能说「命中」，而一个规则库必须说
**「是哪一条命中」** —— 否则五十条规则命中了一条，你只知道有事发生。

两条假规则证明的不是「没命中」，是**「命中不是随手报的」**：一个见到什么都报的实现会把三个
名字一起报出来。

## 把一条曲线画出来

```
Yunooka: plot 000000000000002F 000000000000002F
```

盘上 `plot.txt` 一行写着 `x*x/1000`，读进来，对 320 个 x 各求一次值，点落在屏幕上。

![一条抛物线](<D:/Yunooka/build/screen.png>)

图里从左中向右上爬的那条就是它（另一条斜线是先前 `run_line_test` 的对角线）。

### 设计里那句话被改写了一次

`MATH.txt` 原来说「表达式求值不在这一侧」。画这一层让它必须修正：屏幕要 320 个点，
而把 320 次求值交给 HMYR 那一侧意味着每次跨一层问一次 —— 而这一侧连进程都还没有。

所以求值确实留在了这一侧，**只留「读两三级运算」那么多**：`calc_expr` 认乘除加减两级，
`calc_factor` 认一个变量 `x`。它不算括号、不算幂、不算函数，因为 `x*x/1000` 不需要。

**真求值仍然属于 HMYR。这一侧只做够画一条曲线的那一小块，而它承认自己小。**

### 坐标变换为什么在这一侧

HMYR 那一侧不知道屏幕有多少像素，**也不该知道** —— 把屏幕尺寸写进语言，换一块分辨率就
要求表达式跟着变。

```
屏幕 x = 数学 x（0 到 319）
屏幕 y = 100 - 数学 y（屏幕的 y 往下长）
```

界外的点**被裁掉，不压到边上** —— 压到边上会让一条抛物线的两端看起来像贴了一条直线，而那是假的。

### 判据不靠眼睛

`f(0) = 0` 所以 `(0, 100)` 该有点，`f(160) = 25.6` 所以 `(160, 74)` 该有点 ——
**这两个位置由表达式自己算出来，不是挑了两个看起来对的坐标。**

截图作第二层，留给人看。

## 落盘：关掉再开机，字节还在

```
Yunooka: persist write -> same 512 bytes    第一次启动
Yunooka: persist survived a reboot           第二次启动
```

`ata_write` 是 `ata_read` 的镜像 —— 同一组端口、同一个 LBA 拆分、同一套等 BSY 与 DRQ，
只有两处不同：命令 `0x30` 而不是 `0x20`，方向 `out` 而不是 `in`。

**写完还要再等一次 BSY** —— 写完最后一个 word 时命令并没有结束，它还在往盘上落。
不等这一下就读回来，读到的可能是别的东西，而那种错**看起来像「写丢了」，实际是「没等它写完」**。

### 判据的枢纽：拿盘上留下的字节区分两次启动

60000 号扇区在全新盘上是**零**，写一次之后是 512 个 `0x2A`。

- 第一次启动 → `fresh`（写、读回、比 → `same`）
- 第二次启动 → 读到上一次留下的东西 → `survived`，**不写**

**用「盘上有什么」当依据不是循环** —— 那正是这一条要证明的事。

### 为什么非要跨启动

同一次运行里写下去再读回来，读到的也可能只是内存。而这一条最该否掉的正是那种
**「看起来写成功了」**的实现。

**「跨两次启动」与「一次运行退出码零」是两条不同的纪律** —— 现在它们各自有各自的判据，
而 `exit code` 绑的是两条一起。

第二趟里**没有任何代码去写那 512 个字节**；串口文件先清空，因为 `--uartmode1 file` 是追加写。

### 一个间歇的坏法

`rep insw` 在虚拟机模拟的 IDE 控制器上偶尔会挂住，而挂住只在「前一行的时序稍有不同」
时发生 —— 加一句诊断就好，删掉又坏。这正是时序敏感的坏法，两次绿说明不了什么。

改成逐 word 读的普通循环就稳了：慢一些，但每一步都看得见，也不依赖控制器对 `rep`
的解释。

  要长成的那个样子所依赖的四样东西。
  相川 冥 是从 SilentCrystal 副本长出来的防御工具（会话卫生审计、内容规则、归因与下架）；
  VML 是一个打包发布的监视器、带自己的 web 前端。把这两半并进浏览器这件事，我读出来的
  理由是它们都在「持续看着某些东西」，而浏览器是看着整个网络的那一个 —— 这条理由是我
  读的，不是用户写的。

它们的共同点是都不属于「应用」那一层：一台还没装任何应用的新机器上也要能跑起来，
所以只能住在基础库里。

这一节是清单，不是进度。上面这些现在一个都还没有被编进第二段 —— 它们排在文件系统
之后，而且每一个都要先回答同一个问题：它的哪一部分必须在没有操作系统的机器上就存在。

## 配色

第一标准色组有 22 个色号，存在 [design/palette.json](design/palette.json)。它们按给出的顺序
存，不重排 —— 顺序本身还没有被赋予含义。色号取自那张角色卡的调子（深藏青、红、米白、
木色）。

有一条规则已经定了，而且它反着来：

**容量类的显示里，红色是已用，蓝或蓝黑是告警。**

一般系统是蓝色表示已用、红色表示余量告警。Yunooka 反过来的理由是主色：**这个系统的主色
本来就是红色系**，而最要紧的东西用本色 —— 占用是容量显示里最要紧的那一件，所以它用红。
告警不借本色的声势：它用蓝黑，比主色安静，才像一个「余量不够」的提示而不是又一次强调。

一般系统的主色偏蓝，所以它们把蓝放在已用上、红留给告警。**两边其实是同一条规则，只是
底色不同。**

两个色号是从那 22 个里挑的 —— 红取 `#aa2f32`，告警取 `#293446` —— 不是新加的色。
别的语义（按钮、焦点、错误）还没定，先不要顺手把这两色套过去。

它与 Ichiwatashi 的像素层是一对：色组定颜色，Ichiwatashi 定怎么把颜色画成像素。

## 光标组

静态七个是 64×64 的单尺寸图，动画十个只有 36 宽，而本机把它们都缩到 32 显示。十七个热点
里有两个落在左上角（十字与手写笔），而它们的尖端本该在中心 —— 一条记在方案里，将来要重做。

**暂时**是认真的：它不是最终设计，而是「先有一个十七个槽位都填满的组」。界面还没开始做，

## 第一条命令

```
Yunooka: input from mailbox
Yunooka: shell> files
hello.txt docs cmd.txt repl.txt math.txt
```

盘上有一份 `cmd.txt`，里面写着一行 `files`。`run_shell` 把它找出来、回显、比前五个
字节是不是 `files`，是就列出根目录里的名字。

不过现在默认的来源是**信箱**（见下面「信箱」那一节），盘上那份是退路 —— 第一行
`input from mailbox` 就是「来源是哪一份」的判据。

**认得出与认不出都要有声音。** 一个只会回答的实现看不出「认」这件事发生过；而认不出时
说 `unknown command`，才说明比较那一步是真的在比 —— 这与 `unknown drive`、`not found`
是同一个想法。

### 为什么当初写在盘上

shell 有两半。**解释**那一半是「读到一行、认它、回答」，**交互**那一半是「那一行从键盘
来」。后者要串口能收字节，而那两次尝试后来查清了：不是时序，是客人机的串口 port I/O 在
tcpserver 后端上根本出不去（四条实测记在 `boot/stage2.asm` 的串口一节）。所以命令先写在
盘上：解释路径不变，只是输入的来源换了地方。

来源现在能换了 —— 换成下面那块裸盘。

## 信箱：主机往里送一行

```
Yunooka: mailbox ok
Yunooka: input from mailbox
Yunooka: shell> files
```

**这是第一次有字节从主机进到客人机里。** 串口做不到（它只能往外说），所以路换了一条：
一块 1 MB 的裸盘，挂在 `primary slave`，BIOS 盘号 `0x81`。

「裸盘」的意思是 **VirtualBox 的 RAW medium —— 主机的普通文件就是它的全部内容**。主机用
`fs.writeSync` 往偏移 0 写 512 字节，客人机下一次启动就在第 0 个扇区读到它。

### 头 32 字节

| 偏移 | 内容 |
| --- | --- |
| 0 | 魔数 `YUNOMBX` 加一个 0，共 8 字节 |
| 8 | 版本 u16 |
| 10 | 留白 u16 |
| 12 | 字节数 u32 |
| 16 | 序列号 u32 |
| 32 | 内容，ASCII 字节 |

**内容刻意与 `cmd.txt` 同一个形状**：ASCII、一行一个换行。所以 `run_shell` 里「认命令」
那一段一个字都不用改，变的只是 `r14` 从哪来。

### 为什么判据要两行

`mailbox ok` 只证明魔数对。**盘上 `cmd.txt` 里也是 `files`**，所以只打一个文件列表，看不出
输入是从信箱来的还是从盘上来的。于是多打一行 `input from mailbox` 或 `input from cmd.txt`。

红是这样验的：把信箱里的词换成 `list`，读到

```
Yunooka: input from mailbox
Yunooka: shell> list
Yunooka: unknown command
```

而列目录的答案同时消失 —— 盘上那份仍是 `files`，所以这个红证明了输入真的来自信箱。

### 它不是交互

主机写的时候客人机已经在跑，所以要么先写后启动，要么重启一次让它读。真正边打边算还要
等一个运行时能收到东西的机制，而这块机器现在两样都没有：没有 IDT，也没有能在运行时看见
的共享内存。

它给的是**换一行输入不必重建主盘** —— 这一件已经成立。

### 盘要先造一次

`createmedium` 会注册一个 UUID，重建会让登记里那份失效，所以 `run.mjs` 只在缺的时候造，
造完就只改内容。RAW medium 必须 `--variant Fixed`，动态创建那个格式不支持。


## 命令那一侧的两个小坑

**`put_utf16_ascii` 打到零码元。** 目录条目里名字之后紧跟类型 `u8` 与起始扇区 `u32` ——
类型是 0、扇区是 0x403 时，读出的下一个「码元」是 0x0300，不是零，于是多打出几个看不见
的字节。另写了 `put_utf16_n`，按长度打。

**「卡在八个字符」其实不是这台机器的错。** 那一趟串口停在 `Yunooka:`，我以为是打印断在
半个词上；加了入口标记之后一切正常 —— 真相是 `run.mjs` 读文件读得太早，虚拟机还在写。
**一个看起来像固件故障的现象，根因在主机那一侧的读取时机。**

## 让异常有名字

```
Yunooka: idt ok
Yunooka: trap test
Yunooka: exception 6
```

在这之前，任何一个异常都是三重故障：CPU 找不到处理者，用 `#DF` 再失败一次，然后重启。
症状只有一种 —— **串口停住，什么也不说**。

而这个症状与「还没跑到那里」在串口上长得一模一样。所以这张表的第一价值不是「处理异常」，
是**让错误有名字**。

表在 `0x5000`，256 项只填六个：除零、断点、未定义指令、双重故障、通用保护、页不存在。
其余留零（present=0），访问到会 `#GP` —— 而 `#GP` 已经填了，于是还有话说。

### 判据三件事

`idt ok`（表装上了）、`exception 6`（`ud2` 的 `#UD` 真的被接住）、`handler returned`
**不**出现（处理者没有假装无事发生）。

第三件是前提式的：没有 `trap test` 就算红。否则一条跑不到的路径会白送它 ——
「没出现」这种判据，只要没人走到那里就永远成立。

### 一个错的选择子会废掉整张表

中断门里要 `0x18`（64 位代码段）。写成 `0x08`（32 位那个）之后：`ud2` 触发，CPU 试着
调用那扇门，发现长模式下不能用 32 位代码段，于是 `#GP`；而 `#GP` 走同一张表、同一处写错，
再变成 `#DF`，然后三重故障。

症状是**连异常号都打不出来**。一个错的选择子把整张表一起废掉了。

### 号码被清零

`puts64` 的最后一个 `lodsb` 会读终止符并把 `al` 清成 0，而号码正放在 `rax` 里 ——
于是 `exception 6` 被打成 `exception 0`。

号码改放到 `r15` 就对了。这两件事都不是「哪里算错了」，而是**两处各自正确的东西接在一起
才错**，读代码很难看出来。

### 顺带看见的一件事

装了 IDT 之后才看得见：`run_ata_test` 那条 PIO 偶尔抛异常 —— 连跑两次，一次 `#DF`
一次 `#GP`，第三次又过去了。

以前它稳不住的时候表现是「静默停住」或「重启」；现在知道那大概就是异常变成三重故障的
样子。

### 定位到一条指令

异常处理器改成按号码取 RIP —— `#DF`、`#GP`、`#PF` 带错误码，RIP 在再往上一格。
连跑四趟抓到一次：

```
Yunooka: exception 13 at 0000000000008F67
```

减掉 `org` 的 `0x7e00` 得偏移 `0x1167`，在 `stage2.lst` 里落在一处：

```
00001166 EC      in al, dx
00001167 3CFF    cmp al, 0xFF
```

在 `ata_read` 的等待循环里。**抛异常的是 PIO 轮询**，不是文件系统，也不是别的地方。

### 挪开之后，真凶露头了

PIO 的参数级补丁早试过五轮都失败，所以先把这条测试从主链上拿下来（开关借信箱头偏移 10
那个留白的 `u16`）。主判据立刻稳了，五趟连续退出码零。

**但那只是把症状挪开。** 接着做键盘那一步时，崩溃点跑到了串口那一段 —— 连 `no input`
都打不出来；把轮询次数从五百万降到一千，照崩。

三条不同的路在不同位置抛不同号码的异常，这不是某条指令写错的样子。`long_entry` 从进长模式
起一直没关中断，而 BIOS 装的 PIC 还在送定时器中断，IDT 里 32 号往后全是零（`present=0`）。
于是一次定时器中断就是一次 `#GP`（而向量 8 在老的 16 位映射里正好是双重故障）。

加一句 `cli` 之后：键盘那行成了，ATA 那三趟单独验全是 `same 512`，主判据五趟全绿。

**`ata_read` 从来没坏过**，它只是最常被中断撞上的那一段。ATA 那条测试已经回到主链，
信箱偏移 10 的开关也撤了。

教训是那个形状本身：位置不固定、号码不固定。当时只盯着 ATA，是因为它每次都出现在同一个
位置附近。

## 键盘：运行时收字节的第二条路

```
Yunooka: key 000000000000002B
```

主机用 `VBoxManage controlvm keyboardputscancode 2b` 把扫描码直接注入 8042 —— 不需要
窗口焦点，也不需要客人机装驱动。客人机轮询 `0x64` 的 `bit 0` 看输出缓冲有没有东西，
有就读 `0x60`。

这是三条输入路里唯一一条真正「运行时」的：串口只能往外说，信箱要先写后启动。

### 为什么先轮询而不是中断

先把两件事分开：**先证明「能读到码」**，再把 8259 重映射与 IDT 里的 IRQ1 接上。

顺序反了的话，读不到码时会在中断配置里找问题 —— 而那里本来没问题。

### 只读，不写

只碰 `0x64` 与 `0x60` 的读。当初 A20 那一版是往 `0x64` **写**，把 `out` 卡住了。

### 判据是那个字节，不是「收到了」

```
读盘      ATA -> same 512
键盘      key 000000000000002D
```

**收到的码若不对，说明端口读在别处**，而「收到一个数」这件事仍然成立 —— 两者要分得开。

主机那一侧每轮都送一次，连送十秒：客人机只在一小段窗口里轮询，主机猜不准那一秒。猜一次的
代价是偶尔「没收到」，而那看起来和「键盘不通」一模一样。

客人机那一边有一张 `keymap`：扫描码到 ASCII，只填二十六个字母、0 到 9、空格、回车、
退格。其余留 0 不是偷懒 —— 一张「部分认识」的表比一张猜出来的表诚实。

## 交互：键盘送来的一行

```
Yunooka: shell ready
files
Yunooka: shell> files
hello.txt docs cmd.txt repl.txt math.txt
```

`run_shell_live` 把三样东西接起来了：等键、攒行、解释。

### 先说一句，再送键

主机不知道客人机什么时候开始轮询，而猜错的代价是「没收到」—— 那看起来和「键盘不通」
一模一样。所以客人机先说一句 `shell ready`，主机看到才送键。**时序从猜测变成了握手。**

### 集 1 对集 1

主机用 `keyboardputstring` 逐字符送。这条路上有两个坑，都不是「哪里算错了」：

**`keyboardputstring` 送的是集 1。** 用集 2 的表去读，回显会是 `c3` —— `0x21` 被当成
`c`、`0x26` 被当成 `3`。所以表统一到集 1。

**测试键不能用 `f`。** 前面 `run_key_poll` 用 `keyboardputscancode 21` 按下过 `f` 却从没
放开，VBox 认为它一直按着 —— 于是 `keyboardputstring "f"` 不产生新的按下。送 `gfiles`
得到 `giles`，丢的永远是 `f`。换成 `x`（`0x2D`）就通了。

**整行一次送会丢头一个。** 8042 的缓冲装不下，送 `files` 得到 `iles`。逐字符送、
每个之间留六十毫秒就好了。

### 判据是一条链

`shell ready` 之后接上 `shell> files` 与目录列表 —— 三件事连成一条才能排除「前面从信箱
读的那一次」。那一行也是 `files`，只看「有没有目录列表」分不开它们。

### 这一版没有的

光标、历史、退格之外的行编辑、清屏，以及一个真正的循环：`run_shell_live` 处理完一行就
返回，因为后面还排着别的测试。要做成常驻，得先有一个能跳出来的条件。

## 求一个名字

```
Yunooka: repl> 2 units -> 512
```

盘上的 `repl.txt` 里是一个函数名 —— `块长`，UTF-16 码元，没有换行。`run_repl` 按名字
找到它（重名时留最后那个，与 `读程序` 同一条规矩）、真的跑它、把值打出来并还原成整数。

**那个 512 不是打出来的常量**，是 `exec` 跑了第二个定义的结果。所以这一行同时验了按名字
查找、常量、返回、以及 f64 到整数的还原 —— 少一样就给不出它。

### 为什么打的是码元数

`块长` 两个字的 UTF-16 低字节是 `0x57` 与 `0x7F`：八位串口只会打出一个 `W`，另一个
看不见。所以那一行打的是「2 units」。

**判据没有放在显示上，因为显示在这里有真实的限制。** 名字对不对由 512 间接证明 ——
按错了名，得到的是 256 或者找不到。

## 运行时求一个名字

```
Yunooka: repl ready
letters
Yunooka: repl-live> letters
string 53
```

盘上那份 `repl.txt` 是事先写好的名字。这一行是**运行时打进去的**：`repl ready` 是握手，
主机逐字符送 `letters`，客人机收一行、转成 UTF-16、`find_fn_by_name`、`exec`，再把返回值
打出来。

**那个 53 不是打出来的常量**，是 `exec` 真的跑了种子里第一个函数才算出来的。与盘上那份
的 `512` 各在各的位置：一个是事先写好的名字，一个是运行时打进去的。

### 为什么选 letters

它的返回值是**串**而不是数，于是 `print_value` 的分类那几支里有两支被走到（数、串）。
只测一个数的话，串那一支永远没被执行过。

### 收键那段抽出来了

`read_line_keys`：读 `0x64`、查表、攒缓冲、回车收尾。`shell` 与 `repl` 共用 ——
四步抄两遍，改一处就会漏另一处。

### 回车要补放开码

字符不用补，因为 `keyboardputstring` 自己会拆按下与放开。但回车是 `keyboardputscancode`
直接送的，只送按下码 `1C` 会让 8042 认为它一直按着，重复码追到下一条命令里 ——
症状是 `repl` 收到一个**空行**。补上放开码 `9C` 就好了。

### 求值仍属于 HMYR

Yunooka 这一侧只负责「拿到一个名字」与「打一个值」，中间那一段是种子里已有的 `exec`。

## 盘上的第一个程序

```
Yunooka: prog main -> 7
```

盘上有一份 `prog.hmtn` —— 一个与种子同格式的包：`HMYRB` 头、一个 `u16` 版本、一个 `u16`
函数数，函数表从第九个字节起。里面只有一个函数 `main`，它的指令流是两条：常量 7.0、返回。

`run_program` 把它从文件系统读进预读区，在里面找 `main`、跑它、把返回值打出来。

**那个 7 只存在于那个包的两条指令里**，别处没有 —— 所以读到它就等于「包被读进来、
入口被找到、指令流被跑过」三件事一起成立。

### 让这件事成立的一处小改动

`find_fn_by_name` 原来写死从 `0x20000` 开始扫。改成读 `pkg_base` —— 于是种子与盘上的包
用**同一段查找代码**，差别只在那个变量指哪儿。`run_program` 跑完把它拨回 `0x20000`。

**「程序」与「种子」从此分得开**：种子是启动时就在的那个包，这个是从盘上取的另一个。

### 没有做的

地址空间（包与系统共用同一片内存，没有隔离）、权限、多个程序同时存在、调度。

那些都要先有「一个程序占一块地方」的概念 —— 而那要等进程。

## 一行数学

```
Yunooka: math> sum -> 262.488320
Yunooka: math> average -> 29.165369
Yunooka: curve y -> has x
Yunooka: curve f(x) -> has x
Yunooka: curve f x -> has x
```

盘上的 `math.txt` 是四行，一行一句。`run_math` 逐行切，然后按 [design/MATH.txt](design/MATH.txt)
三节分派：行里有等号就是表达式（左边是名字，右边看有没有 x），否则冒号前是已知运算名
就按具名运算读，都不认得就说 `unknown operation`。

### 三种左边认成一模一样

`y`、`f(x)`、`f x` 是同一个东西。这一条是判据，不是说法：三行读数各自把左边**原样**
打出来 —— 所以 `f(x)` 与 `f x` 的差别看得见，而右边三行都报 `has x`。

括号与空格是给人看的，对读的人没有影响。

### 那个 262.488320 是怎么来的

九个数的和：1、4、19、40、55、29、30.4、6π、24e。一条读数压住五件事 —— 十进制小数、
π 与 e 两个常量、逗号分隔、除法、六位小数的四舍五入。少一样，那串数字就对不上。

真值在 Node 那一侧核过：`(1+4+19+40+55+29+30.4+6*Math.PI+24*Math.E)/9` 是
`29.165368867078595`，六位四舍五入是 `29.165369`。

**判据要一串能比的字**，所以「六位、四舍五入」写进了 MATH.txt 六节。

### 除法为什么单独有一条

```
Yunooka: div -> 1.570796
```

这一行不读盘上的文件：它跑一段四条指令的迷你流（常量 π、常量 2、除、返回）。

理由是：`average` 也走同一份除法，但 `exec` 的分发表若漏了操作码 6，`average` 那两行
**照样是绿的** —— 它们证明的是平均值算得对，不是解释器认得除。两条判据各管一件事。

### 红的验法

把 `30.4` 改成 `30`：`sum` 少正好 `0.4`，`average` 跟着变，判据红。
把 `f(x)=1/x` 的右边改成 `2`：那一行报 `no x`，而另两行仍报 `has x`。

后一次红的用处更大：它证明右边真的被扫描、三行各自独立判断，不是复制第一行的结论。

### 还没有的那半

画图。它要一块能画点的界面，而界面排在像素层之后；画一张图还要定图多大、坐标轴在哪、
取多少个点、x 落在哪一段。表达式求值本身也不在这一侧 —— 那是 HMYR 编译器的活，
这里只认形状、不算值。

## 条件跳转

求值循环现在认九条指令，其中三条是跳转，于是它能跑种子里那个十一条指令的 `符位`：

```
Yunooka: fn116 -> 2147483648    参数真：不跳，交出 2^31
Yunooka: fn116 -> 0             参数假：跳到 5 那条路，交出 0
```

两行合起来才说明「跳转按条件走」—— 只验一个的话，一个永远不跳的解释器也能过。

栈从一格长到十六格，因为 `取` 与 `常量` 都会压、`假跳` 会弹。跳转的目标是**指令索引**，
而游标是字节位置，所以执行前有一遍预扫把每条指令的字节偏移记下来 —— 没有那张表，每次跳
都得从头发扫一遍。

`假跳` 弹栈，`假跳留` 看栈顶 —— 这一条是从 `src/vm.mjs` 的写法读出来的，而 `符位` 用的是
前者，所以这一版只实现弹栈的那一条。

## 第一次执行

有了指令流，就能执行了。一个只认两条指令的求值循环：

```
常量 "abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ_"   ->  压进一格栈
返回                                                            ->  交出栈顶
```

串口读出来是：

```
Yunooka: letters -> string 53
```

53 是 26 个小写、26 个大写加一个下划线 —— 这个数可以从那一侧独立算出来，所以这一行验的
是「真的执行了」，而不是「打了一行字」。

`letters` 的四条指令里，「常量」与「返回」各出现两次，而入口到第一个「返回」只压过一次，
所以栈只有一格。这不是解释器，是解释器最小的那副骨架 —— 它证明「读一条指令、按它动一下
状态、再读下一条」这条缝是通的。跳转、算术、调用都还不在里面。

## 走完指令流

现在把第一个函数那四条指令全走一遍，而不是只看第一条：

```
Yunooka: fn letters params 0 slots 0 instrs 4
Yunooka: op 5
Yunooka: op 28
Yunooka: op 5
Yunooka: op 28
```

`5` 是「常量」，`28` 是「返回」，所以 `letters` 读作「常量、返回、常量、返回」。用 HMYR 自己的
`读程序` 读同一份文件，给的是同样的四个数。

> 这说明 `letters` 这个函数体是「把某个常量交出去」，两次。中间没有分支、没有调用 —— 这一点与它的名字对得上：它大概是那张字母表的第一个切片。

**走完的关键是立即数形状。** 一条指令占多少字节取决于它带什么：算子类没有立即数，跳转带
四个字节，`名字` 类带一整个 UTF-16 串，`值` 类带一个带标记的可变长编码。所以代码里有一张
34 项的 `imm_shape` 表（操作码到形状），按号排，与 `src/code-file.mjs` 的立即数形状表一致；
`skip_imm` 按形状把剩余字节跳过。不知道形状就只能读第一条 —— 而「只读第一条」与「走完
四条」在第一条上看起来完全一样。

## 读到函数表

跳过文件头之后读第一个函数，并翻出它第一条指令的操作码：

```
Yunooka: fn letters params 0 slots 0 instrs 4
Yunooka: op 5
```

`letters` 是这个种子里第一个函数，参数量 0、槽数 0、四条指令 —— 与 `node` 那边读同一份
文件给出的完全一致。`op 5` 是 `src/code-file.mjs` 那张表里的第六项（表从零数），也就是
「常量」。

操作码的名字由 `tools/run.mjs` 翻译，那张表照抄自 `src/code-file.mjs`。抄在这里是有意的：
判据要独立于被验的那一侧，两边对不上时红的是 Yunooka 而不是那张表。

**没有种子就不读它的头。** 一开始忘了这一步，于是从零填充里读出了「版本 0、0 个函数」，
而那第一条指令的 0 还被翻成了「加」—— 垃圾被翻译成漂亮数字，看起来像真读懂了。判据要的
是「读得懂」，不是「读得出数」。

## 种子读懂了开头

长模式下读种子的前九个字节并报出来：

```
Yunooka: seed v1 202
```

那是 `HMYRB`（五个字节）加版本 u16、函数数 u16 —— 格式记在 HMYR 的 `design/C-VM.txt`。
这一份是版本 1、202 个函数，而用 node 读同一个文件给的也是这两个数，所以这一行是对
「它读懂了格式」的断言，不只是「它读了几个字节」。

**种子没有压缩。** 一开始以为得先写一个解压器才能「解出一点」，查了格式才发现它就是字节码
文件本身：函数表、指令流、全局名，一串往下排。于是「解出一点」其实是「照格式读」，而最便宜
的一段就是文件头。

## 第一个分配器

长模式里有一个 bump 分配器：一个游标从 0x400000 起往上走，每次按 16 字节对齐，返回移走
之前的位置。

```
Yunooka: alloc 0000000000400000
Yunooka: alloc 0000000000400010
Yunooka: alloc 0000000000400040
```

三块请求分别是 16、48、100 字节。第二块落在 0x10，因为第一块 16 字节正好对齐；第三块落在
0x40，因为 48 向上取到 48，0x10 加 0x30 就是 0x40；100 字节那块会再往上取到 0x70。

起点选 0x400000，是因为前 4 MB 已经被引导扇区、第二段与页表占着，种子在 0x20000，而 4 MB
往上是干净且被页表映着的一片。

判据三条：首条正好是 `0000000000400000`、每条末位是零、逐块递增。少了任何一条，一个「能
返回指针」的分配器也可能在返回重叠的地址 —— 而那种错在小程序里完全看不出来。

打印用的是十六位十六进制，不是十进制：地址要对齐看得清，`…0000` 与 `…0010` 比 4194304 与
4194320 一眼就分得出。

## 三段位宽：16、32、64

这一块最大的内容是跨过两种模式。第二段现在跑三个位宽段：

```
[bits 16]  实模式：读种子、验魔数、打前两行
           开 A20（走 BIOS 的 int 0x15），装 GDT，置 CR0.PE
[bits 32]  保护模式：打一行，建四级页表，置 CR4.PAE、EFER.LME、CR0.PG
[bits 64]  长模式：打最后一行
```

三处踩出来的东西写在代码注释里，这里只留结论：

**代码段要两个。** 一开始只有一个 `L=1`（64 位）的代码段，于是刚置完 CR0.PE 就拿它远跳 ——
而 `L=1` 的段在 EFER.LME 还没开时是未定义的，CPU 不报错，直接挂住。现在 `0x08` 是 32 位
代码段，`0x18` 是 64 位代码段，各用各的。

**CR3 指向 PML4，不是 PD。** 写错一次：把 0x3000（PD）放进 CR3，开分页那一瞬间 CPU 把
PD 当 PML4 走，走出来的地址全是垃圾。

**A20 不走 8042。** `out 0x64` / `out 0x60` 那一路在 VirtualBox 上把 `out` 卡住了，症状是
串口停在某个观测字节后面。改用 BIOS 的 `int 0x15, ax=0x2401`。

还有一条不是 bug，是判据的读取时机：`run.mjs` 原先一看到前两行就收工，而那时后面的段还
没跑完，于是「保护模式没到」这个结论其实是「读得太早」。现在它等全程里至少四行出现，
或者给满二十秒。

## 它与 HMYR 的第一次接触

第 34 个扇区往后放的是整份种子（`--seed` 给的那份）。第二段用 BIOS 的 LBA 扩展分三批读它：

```
批 1  64 扇区 -> 2000:0000   物理 0x20000 到 0x28000
批 2  64 扇区 -> 2800:0000   物理 0x28000 到 0x30000
批 3  18 扇区 -> 3000:0000   物理 0x30000 到 0x32400
```

读到 0x20000 而不是 0x8000：第二段自己被加载在 0x7E00，16 KB 铺到 0xBE00，而 0x8000 起的
种子会把它覆盖成零。

每批 64 扇区不是 BIOS 的限制，是寻址的便利：64 乘 512 正好 0x8000 字节，正好走完一个段，
于是段与偏移都不用做加法。用 LBA 扩展而不是 CHS 读，因为 CHS 跨磁道时有些 BIOS 会失败。

**这一块的边界要说清**：它读完了 146 个扇区，但判据只验开头五个字节。读了一半与读完，
在 `seed ok` 这个判据上看起来一样 —— 因为三批都成功才会走到检查那一步，而三批里任何一批
失败都会落到 `seed unreadable`，所以「读完」这一半是**靠失败路径反证**的，不是直接验的。
直接验的办法是认种子末尾的几个字节，或者干脆执行它；前者要一个段:偏移的末尾地址，后者
要一个字节码机。两样都留给后面。

这是 Yunooka 第一次去认 HMYR 的东西。它现在还读不懂种子，只认得它开头的 `HMYRB`；而
「认得」这个词在 HMYR 仓库的 `design/FILETYPE.txt` 里有一层更重的意思 —— 那个系统认得
那些扩展名。今天只做到第一层。

## 两段是怎么分的

引导扇区只做三件事：初始化串口、把第二扇区读进 0x7E00、跳过去。往后再加的东西都住在
第二段那一侧，而那一 512 字节从此不必再长大。

读盘用 BIOS 的 `int 0x13`，不自己驱动磁盘 —— 这一层的任务是尽快把下一段交出去，真正的
磁盘驱动属于内核，不属于这里。

两段各写一份串口打印，是重复而不是疏忽：它们将来会独立编译、独立加载，共用要靠链接，
而链接是第三块砖的事。现在重复的代价是二十行，不重复的代价是一层依赖。

## 这一块砖为什么这么起

512 字节是这个国家里最小的入口。它不需要工具链之外的东西（nasm 就够），而它要么打出那行
字、要么打不出 —— 没有中间状态可以含糊过去。GRUB 与 UEFI 是之后的事，那时这块砖还在。

## 还没有的

- 读文件：它还读不到 `.hmtn`，更读不到 `.hmoca`
- 内存管理、中断、进程、驱动（磁盘、键盘、显示、网络）
- HMYR 的字节码机

## 一条踩过的坑

第一版串口打印不等发送器就绪，跑起来只收到 `nooka: boot ok` —— 开头三个字符丢了。十六个
字节的整句在 9600 波特下本来能靠 FIFO 撑过去，而第一个字节偏偏不行。加上 LSR 的 THR 空位
等待之后完整了。

## 与 HMYR 仓库的关系

Yunooka 不依赖 HMYR 仓库里的任何东西，现在连 HMYR 都还不认识。反过来也一样：拿掉 Yunooka，
HMYR 的套件应当全绿 —— 那条层次关系（基础不依赖附加）在 HMYR 的 `design/FULLSELF.txt`
第十节里写着。
