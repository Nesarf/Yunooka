系统文件的保护与补完

用户给的方向（2026 那一轮）：正常情况下无法更改核心运行文件；但要能通过一些「繁文缛节」
的方式解除保护，解除之后是类 Linux 的管理策略；运行出错或缺少文件时，进入「新造界面 /
补完界面」，由系统内置的下载器从服务端取回对应文件并修补。这要求 Yunooka、Hiou Rengo、
HMYR 三者的自我逻辑足够强，并且要为 LLM / API 接入做专门优化。

这一份文件把那条方向拆成可以逐块落地的形状，并把第一块砖指出来。


一、保护与修复是同一件事的两面

一份「不许改」的清单，正好就是一份「该有什么」的清单 —— 前者回答「谁能写」，后者回答
「本来有什么」。而「本来有什么」正是完整性检查要的东西。

所以核心清单只写一份，两层共用：写入时查它、启动时照它校验。两份清单会分家，而分家的
那一天，两边都说得通、结果互相矛盾 —— 那种坏法最难查。

二、四层，从软到硬

第一层 只读位。目录条目的类型字节 bit 6（为 Kohane 第四层加的）。它便宜、跟着文件走、
  而且已经在了。现在 fs_write_file 还不查它 —— 那是第一块要补的砖。
第二层 核心清单。一个名字列表，落在盘上某一个固定位置。清单里的名字默认拒写，不管
  只读位怎么设。这一层管的是「换一块盘插过来也一样」—— 只读位在盘上，清单在系统里。
第三层 完整性校验。清单里每个名字都带一个校验和，启动时算一遍、比一遍。不符就报出
  是哪一个，并进入补完流程（见第四节）。校验和用 CRC32 或 FNV-1a 都行，两条指令的量。
第四层 引导链那一段。第二段与种子不在文件系统里 —— 它们在盘的头几十个扇区。这一层
  没有「只读位」可用，只有「校验」。所以第四层与第三层是同一件事，只是被校验的东西
  不在目录里。

三、「繁文缛节」的力气不在保密，在留下痕迹

这台机器上的「密码」是假的：盘可以拔下来，在别的机器上改。所以解锁的仪式不能靠秘密，
只能靠让它留下痕迹。

具体形状（可改，但要有这几样）：
  一、要读一段说明 —— 说明里写清改的是什么、改了会怎样。
  二、要回答一个问题 —— 一个必须读过说明才答得出的问题，答错就重来。
  三、要写下理由 —— 一句话，进审计日志。
  四、解锁是有期限的 —— 类 Linux 的 sudo timeout，过时自动收回。
  五、任何一次解锁与任何一次受保护的写入都进日志，日志本身是只追加的。

这条设计的判据不是「别人解不开」，而是「解开之后能查出是谁、什么时候、为什么」。
一条查不出痕迹的保护，与没有保护在应急时的价值一样。

四、解锁之后：状态要挂在墙上

用户点的：解除系统保护之后，桌面右下角会出现「开发者模式 / 测试模式 / 全裸模式」这样的
信息标记。

这一条看着是装饰，其实是第三节那个「留下痕迹」的另一半 —— 日志是给事后查的人看的，
标记是给当下用的人看的。两者的内容必须同源：同一个状态，两处显示，一处给事后、
一处给当下。

三种模式各自的含义要能一句话说清：
  开发者模式 —— 可以改、可以读全部、可以装东西。系统文件仍然校验，改了会报。
  测试模式 —— 可以改，而校验失败不拦路。用来试一条改坏的链子。
  全裸模式 —— 连校验都不跑。用来救一台连校验都过不去的机器。

差别只在「校验拦不拦路」这一条轴上，所以三种不是三个功能，是同一个开关的三档。

为什么三种而不是两种：两档（开 / 关）只能表达「保护着」与「没保护」，而修一台坏机器需要
的是「保护着，但允许我弄坏它」这一档 —— 那正是测试模式。少了它，修的时候只剩全裸一条路，
而全裸之后忘了关是这类设计最常见的收场。

标记的判据：它必须与真实状态同源，而不是一个自己画上去的图标。所以标记显示什么，由
「当前模式」那一个数决定，而那个数同时决定校验的行为 —— 一处改，两处显示。
两份分开的状态会在某一次忘记同步的时候说谎，而那一刻标记还亮着、看着比没有更糟。

五、补完界面

启动时按第二节第三层校验，任何一条不符或缺文件，就进入补完界面。界面做三件事：
  一、说清缺什么 —— 名字、期望的校验和、实际算出来的（或缺整个文件）。
  二、说清从哪来 —— 这一版是「从外面的那条通道送进来」，不是网络。
  三、修补之后重新校验，并报修补了几条。

为什么第一版不接网络：信箱盘（一块裸盘，主机写、客人机读）已经是一条能送文件进来的
通道，而且它在的。内置下载器排到网络栈之后 —— 那一条现在是 blocked 的 browser。
一条能送文件的通道 + 一份能校验的清单，已经够把「补完」这件事做成真的；先做成真的，
再谈从远处取。

六、LLM / API 友好的那一条，具体是三件事

一、结构化。人读的散文（Yunooka: fs ok v1 root 1025 ...）改起来成本太高，而且它们已经
   与判据绑在一起了。所以新写的事件行用固定的形状：一行一事件、字段名在前、
   顺序固定、空值显式写成一个记号。旧的散文不动。
二、可判断。每条事件带一个状态词（ok / bad / skipped），而不是让人从散文里猜。
   退出码也属于这一条。
三、不猜。缺的东西显式报「缺」，不要用零代替 —— AHCI 那条路上「控制器还在复位里」与
   「这条线上没有设备」在串口上长得一样的教训，在这里是同一个形状。

七、自我逻辑足够强，最强的那一形态是自举

「能检查自己」是第三层，「能修好自己」是第四节，而「能重建自己缺的那部分」是自举 ——
那与 self-host 是同一条路（HMYR 的编译器要能在字节码里跑）。所以这两条在账上应当相邻，
而且顺序是：先能校验（它便宜），再能修补（要一条通道），最后才是能重建（要编译器在
自己身上跑得起来）。

Hiou Rengo 与 HMYR 那两侧同理，只是它们各自的核心清单不同。三份清单可以不同，
而「清单、校验、修补」这三件的形状应当一样 —— 一样的形状才谈得上互相照应。

八、第一批砖（都不需要新前提）

一、fs_write_file 查只读位。标了只读就拒绝写，并报出来。判据：标只读、写、应当失败；
   而同一个文件在没标只读时写得进去（否则「拒绝」可能只是「写坏了」）。
   状态：已做（run_guard_test）。它同时补了查重名 —— 这个函数原先只找空槽新建，于是
   同名的第二次写会造出第二条同名条目，而目录里两条都算数。所以「只读位一直在，而它
   什么也没挡」这件事，根子在这里。五条判据里最有信息量的是「拒绝时报的是只读而不是
   已存在」：两种拒绝走同一条失败路径，如果报出来的话一样，那「只读」就只是一句
   没人验过的宣告。
二、核心清单与校验和。清单落在盘上（core.bin，二进制：u32 项数，每项 u8 名字长 + 名字
   ASCII + u32 FNV-1a），启动时按它校验，不符就报名字与项数。
   判据：改盘上一个字节，校验必须红；不改则绿。
   状态：已做（run_core_test）。验红的手段是 build.mjs 的 --break：它改的是盘上那份
   字节，而清单仍按原内容算 —— 于是红的时候报的是「内容与清单不符」，不是「清单跟着
   内容一起变了」。实测报的是 guard core bad hello.txt 与 guard core 2 1。
   为什么 FNV-1a 而不是 CRC32：一条异或、一条乘法，两条指令的量，不需要表。它不防碰撞，
   而这一层要防的不是碰撞，是「文件被改过而没人知道」。
   一个副作用值得记：--break 翻的是 hello.txt 的首字节，所以「打开」与「认类型」那两条
   判据也会跟着红（首字节成了 0xEF，identify 认不出来）。验红模式只用来确认判据会红，
   所以没关系 —— 但读那一趟输出的人要知道这是预期的连锁。
三、补完界面的骨架：报出缺什么，不接网络。判据：删掉一个核心文件，界面必须点出它的名字。
   状态：已做（run_repair_screen）。它做三件事：屏幕上画一个窗口（清成暗青、画边框与
   标题栏与内容区，三个原语都是 Kohane 第二层就有的）、串口上报一行结构化的、以及说明
   修补通道是信箱盘而不是网络。
   验红的手段是 build.mjs 的 --drop <名字>：那个名字不进根目录，于是盘上真的缺一份 ——
   补完界面要回答的问题是「该有的东西现在不在」，而这一条造的就是那个处境。实测报的是
   guard core missing hello.txt、guard core 2 1、以及
   event=guard.entry bad=1 repair=mailbox version=1。
   而正常启动那一条判据的形状与别处不同：它验的是「没有」—— 补完界面不该出现。那种判据
   最容易被写成「什么都没读到也算通过」，所以它与「核心清单三项全对上」那条一起看：
   一条要求全对，一条要求全对的时候补完界面不出现。两条合起来才是「该进的时候才进」。
   屏幕那一半是给眼睛的，判据只认串口 —— 截图不是判据。
   真的去修已经接上了（run_repair_patch）：从信箱盘把文件搬进来、重算校验和、再校验一次。这一块做完了。它做的事与三道门：
      一、按名字在补丁包里找到那一条。补丁包的格式是 YUNOPAT：魔数八字节、u32 项数，
          然后每项 u16 名字长、名字 UTF-16、u32 字节数、内容。它写在信箱盘的第 1 到
          第 3 个扇区，而头一个扇区仍是 YUNOMBX 那一行输入 —— 同一次读进来，所以
          长模式里不需要第二套读盘代码。
      二、补丁给的那份字节算出的哈希，必须与清单里记的一致。这是整块砖的门：补丁包
          不是「随便什么字节都能写进去」，它只能把文件恢复成清单记的那一份。少了它，
          这条通道就成了「谁写得了信箱盘，谁就改得动核心文件」。
      三、写进文件系统，再从盘上读回来重算一次。读不到或对不上都不算修好 —— 只报
          fixed 而不报 verified，就是把「写了」当成了「写对了」。
      四、报三个数：fixed 写进去几条、verified 读回来对上几条、refused 补丁里有但
          被校验挡下来几条。三个数分开报，因为它们指向三种处境：写了但没验上、
          验上了但没写、以及根本没有可写的东西。
    位置很要紧：修补在「查到有缺」之后、在补完界面之前。能修的时候不该看见那个界面 ——
    它是「修不了」的地方，不是每次启动都路过的地方。所以两条判据自然分开：有补丁的那一趟
    没有 event=guard.entry，没有补丁的那一趟有。
    而修补之后会把「现在数一遍」重报一次（guard core 3 0）。前一行说的是修补之前的状态，
    判据要的是现在的状态；两行都留在串口上，读的人才看得出修之前是几条。
    补丁包由 build 侧出，不由客人机造：客人机正是缺的那一侧，而 run.mjs 另抄一份会让
    「补丁对不上清单」与「补丁抄错了」看起来一样。build --drop <名字> 时它把那一份的
    原始字节装成 patch-drop.bin；没有 --drop 时那份文件会被删掉，因为上一趟留下的
    那一份会让「没有补丁」这条判据假绿。
四、事件行的结构化。这一条可以最后做，因为它与已有判据有摩擦，而摩擦要一处一处地解。
五、预读区与盘上文件数的同步。这一条是第二块砖撞出来的：core.bin 落在第 1040 号扇区，
   而预读只盖到 1039，于是「清单读到了、项数是零」。那是第三次踩同一个坑（fake.txt 那次
   是第一次）。预读现在十七个扇区。它该由 build 核对 —— 「预读扇区数 >= 盘上文件
   共用的扇区数」是一条能自动查的判据，而现在靠人记得。

第一条最便宜，而且它是第二节第一层唯一的缺口 —— 所以从它开始。第二条与它同一段路上
的下一层，而两条现在都做完了。

九、补完这一块收尾时留下的三件事

一、四条判据，各自先验红再看绿。「修好了」这一条的价值全在它的验红手段上：把补丁包里
    那一项的最后一个字节翻一位，于是补丁里有这一条而哈希对不上 —— 串口上四件事一起变：
    event=guard.repair refused name=hello.txt、fixed=0 verified=0 refused=1、
    event=guard.entry bad=1（进了补完界面）、以及没有重报 guard core 3 0。
    少验这一次红，「修好了」与「永远报修好了」在串口上是一样的。
    四条合起来是：正常启动全对且不进补完界面、删掉一条而给补丁则修好并重报 3 0、
    删掉一条而不给补丁则进补完界面、给了坏补丁则拒绝且仍然进补完界面。
二、修补的语义是「追加」，不是「还原到原位」。fs_write_file 找根目录里的第一个空槽，
    所以修好的 hello.txt 排在目录末尾，第一条成了 docs。这不是错 —— 目录的语义是
    「名字到扇区」，顺序是布局的产物；但它确实改变了三条判据的形状：文件系统的 first、
    wrote 之后那份列表、以及 shell 列出来的名称串。三条都按两种形状写：正常那一趟仍然
    钉住原布局，补丁那一趟只要求「名字在、而且在末尾」。
    一个副作用：修好之后 hello.txt 的起始扇区是新的，索引查出来的数不再是 0x403。
    那一格在补丁模式只要求「查得到且不是零」，而「目录与索引算出同一个数」仍由
    cross same 那条负责 —— 它本来就是为这件事立的。
三、一次没复现的死机。有一趟运行死在「protected mode ok」的第一个字后面：串口停在
    Yunooka: prot，既不报错也不重启，后面什么都没有。同一份代码两次重跑都跑完全程，
    所以当成偶发记着，不当成结论。查过的排除项：0x50000 不与任何东西重叠（GDT 在主体
    里、IDT 在 0x5000、页表在 0x1000 到 0x7000、栈在 0x7C00、种子在 0x20000、预读在
    0x40000、β 盘在 0x60000），四个扇区也在同一个 64 KB 段内、不跨 int 0x13 那条界。
    留给下一次撞上时用：先看串口停在哪一行的第几个字节，再决定要不要往 BIOS 那边查。
