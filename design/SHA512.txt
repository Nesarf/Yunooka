SHA-2：一次压缩全对，两次压缩全错

一份负结果的记录，覆盖 SHA-256 与 SHA-512。写它的理由是这一块已经排掉了十几种可能，
而那十几种里每一种都花过一轮。下次接手的人不该从零开始。

一、结论

两个算法都是同一个形状：消息只需要**一次压缩**时，摘要与标准逐字节相同；需要**两次或
更多次**时，全部不同。

SHA-256（块 64 字节，长度字段 8 字节）：

  长度 0 到 55   一次压缩   全部相同
  长度 56 到 63  两次压缩   全部不同
  长度 64 到 119 两次压缩   全部不同

扫过的九个长度 51、52、53、54、55、56、57、63、64 给出这条分界，而它是精确的：55 加
一字节的 0x80 再加八字节长度正好是 64，装得下；56 就装不下了。

SHA-512（块 128 字节，长度字段 16 字节）的分界在 112，同一个道理。

二、最要紧的不是算法，是判据的覆盖

第二环（sign.bin 里的 SHA-256 清单）之前只对三个文件算过：hello.txt 22 字节、
prog.hmtn 40 字节、cmd.txt 6 字节。**三个都短于 64 字节**，所以那一条判据从落地起就
只走过「一次压缩」的路径，而它的绿没有覆盖多块。

这一轮把 math.txt（118 字节）加进了核心项。判据立刻红了，而且红得正确：

  guard core 4 0                              FNV-1a 那一层是绿的
  item=hello.txt len=22 sha=62C9628437994F6F  与主机相同
  item=prog.hmtn len=40 sha=A9E1A6D3B3F92FA9
  item=cmd.txt   len=6  sha=43807F5B6BD11FA1
  item=math.txt  len=118 sha=99087076C55863FA  与主机不同（主机是 674DAB0D658B7DF8）
  event=onlysign bad name=math.txt

一条判据的覆盖范围与判据本身一样重要。三个短文件让一条只对短输入成立的分支看起来是
通的，而它从来没有被走到过。

三、汇编与一份独立的 Python 给出同一个错值

math.txt 那 118 字节，汇编（boot/stage2.asm 的 sha256）给出 99087076C55863FA，而
一份用 Python 无界整数、结构照抄的实现在同样字节上给出同一个值。两份实现在三种语言、
四种写法下一致：

  JavaScript BigInt（tools/refsha512.mjs）
  JavaScript 双字 32 位、手动进位（tools/sha512words.mjs）
  JavaScript 逐位（tools/shbit.mjs）
  Python 无界整数（tools/sh512.py、E:\~Kohane~Ikkuyoo~\twin.py）

错法一致，说明错在它们共享的那一套理解里，不在字宽、不在进位、不在语言。

四、排除了什么（每一条都实测过）

  一、补齐的字节。两块补齐原样打出来，与标准逐字节相同：块内数据加 0x80 再加零，长度
      落在最末 8 字节（SHA-256）或最末 8 字节而高 8 字节为零（SHA-512）。
  二、补齐的位置。试过九种写法（长度提前八字节、长度写满 16 字节、按字节数、小端、
      0x80 放在别处、补三块、只补一块），全部不符。
  三、常量表。八十个（SHA-512）与六十四个（SHA-256）常量由整数立方根算出，锚点逐个
      对过；而单块路径把它们全部用过一遍，那一条对。
  四、初值。整数平方根算出，0 字节消息的摘要与标准相同 —— 那条路径上初值与末尾加回
      初值都被走过。
  五、W 展开。把展开整段省掉（全零块的 W 恒为零）单独跑八十轮，结果与含展开一致。
  六、轮函数的写法。元组同时赋值与显式中间变量两种写法给出同一个结果。
  七、旋转。rotr 与「把值写成三十二位位串再切片」两种算法在全部位移量与若干边界值上
      一致（0x80000000、0xFFFFFFFF、0x00000001）。
  八、内联。把 56 字节那一例的两块完全铺开、不调用任何函数，结果与调用版相同。
  九、跨调用的状态。先算 55（对）、再算 56（错）、再算 55（仍对）；K 与初值前后不变。
  十、输入块本身。56 字节那一例的两块打印出来是「56 字节数据 + 0x80 + 7 零」与
      「56 零 + 8 字节长度 448」，都对。
  十一、汇编那一边的指针与长度。串口打出每一项的名字与长度，math.txt 报 len=118，
      与盘上一致。

五、还缺什么

一个能单独给出「某一块之后的状态」的第三方参考。上面第三条证明的是四份实现互相一致，
不是它们与标准一致；而 hashlib 与 node 的 crypto 都不暴露中间状态，所以「哪一块开始
错」只能用最终摘要反推。

反推做了，结论是矛盾的：把标准摘要减初值得到「两块之后的状态」，它与我的实现算出的
状态不符 —— 而单块路径又证明压缩函数本身对。两者同时成立就只能是某一步的输入与我以为
的不同，而我已经把输入打印出来逐字节核过。

下一步该试的方向：

  一、自己编一份能打印中间状态的参考实现（比如用 openssl 的 C 源码，或者用一份公开的
     教学实现逐轮打印），拿它对 56 字节那一例的第一块做对照。这是唯一还没试过的路。
  二、把 56 字节那一例的第一块单独当成一条「消息」喂进去，看它的结果与任何标准值是否
     有已知关系。若没有，就只剩上一条。

六、现在的状态

  SHA-256 与 SHA-512 都写在第二段里。SHA-512 还没有接在主链上（第三环的地基），
  它的判据 run_sha512_test 留着但不跑。
  SHA-256 接在第二环上，而第二环现在是**红的** —— 因为清单里第一次有了长过一块的文件。
  这条红是真的，它说的是「多块路径没对」，而不是「第三环还没做」。

一句话：一次压缩的路径通了，多块没通，而多块这件事一直被清单里三个太短的文件挡着。
