SHA-512：单块全对，多块全错，而错在哪还没定

一份负结果的记录。写它的理由是：这一块已经排掉了七八种可能，而那八种里每一种都花过
一轮。下次接手的人不该从零开始。

一、做了什么

第二段里现在有 SHA-512（boot/stage2.asm 的 sha512 与 sha512_block，数据段里的
sha512_h / sha512_w / sha512_pad / sha512_out / sha512_bt / sha512_lens / sha512_k）。
它按 RFC 的写法实现：八十轮、W 展开到 80 项、块 128 字节、补齐末尾 128 位长度字段。

它没有接在主链上（那句 call 被注释掉了，注释里写着原因）。判据 run_sha512_test 留着，
但不跑。

二、验了什么，分界在哪

拿六个长度算摘要，与主机上 node 的 crypto 逐字符比（tools/checksha512.mjs）：

  长度 0、1、111 —— 与标准相同
  长度 112、128、239 —— 与标准不同

再扫一遍 0 到 400（tools/diagsha512.mjs）：0 到 111 全部相同，112 到 400 全部不同。
分界正好在 112。而 112 是「一个 128 字节块装不下 112 字节数据加一个 0x80」的第一点，
也就是「补齐需要第二块」的开始。

所以：一块的消息全对，两块的消息全错。

三、排除了什么（每一条都实测过，不是推测）

  一、补齐的字节。把两块补齐的 hex 原样打出来（tools/trypad2mjs 的基准与
      tools/sh512verbose.py），112 字节消息的补齐块是
      「112 字节数据 + 0x80 + 15 个零」与「120 个零 + 0000000000000380」，
      与 SHA-512 的规定逐字节相同。长度字段写在 248..255（低 8 字节），
      240..247 是高 8 字节的零 —— 这一处曾经写过 240..247，改了以后仍然不同。
  二、补齐的位置。试过九种写法（长度在 240..247、长度写满 16 字节、长度按字节数、
      长度小端、0x80 放 111、补三块、长度放第一块尾部、只补一块），全部不符。
  三、常量表。K 的八十个值用 BigInt 求整数立方根算出（tools/genconst.mjs 的算法），
      前四个与最后一个与已知值逐个对过；而且 K 在「一块」的路径上被完整用过八十次，
      那一条对，所以 K 是对的。
  四、初值。八个 IV 用整数平方根算出，且 0 字节消息的摘要与标准逐字节相同 ——
      而那条路径上 IV 与 final 的加回初值都被走过，所以两者都对。
  五、W 展开。把 W 展开整段省掉（全零块的 W 恒为零），用 tools/sh512min.py 单独跑
      八十轮，结果与含展开的那一份相同 —— 展开没错。
  六、轮函数的两种写法。元组同时赋值与显式中间变量两种写法给出同一个结果，
      所以不是赋值顺序的问题。
  七、四份独立实现。BigInt、双字 32 位（手动进位）、逐位（消息当位串）、
      Python 无界整数 —— 四份在 0 到 111 上全部与标准相同，在 112 起全部错成
      同一个值（389d3586a1a6b4e0...）。四份的错法一模一样，说明它们共享的那套念头
      里有一处错，而那一处不在字宽、也不在进位。
  八、压缩函数的副作用。K 在一次调用前后不变，W 是局部的，两次同样的调用结果相同。
  九、把主机反推出来的中间状态喂回去。用 hashlib 的最终值减初值得到「M1 的两块后
      状态」（M1 是 128 字节的消息），再从这个状态推进一块（256 字节消息的补齐块），
      结果与标准的「M1 与它的补齐块拼起来」的摘要不符。这一条最要紧：它用的初值
      不来自我的实现，而来自标准。

四、还缺什么

一个能单独输出「某一块之后的状态」的第三方实现。第九条已经把标准的中间状态引进来过，
但它只给出两步合成的结果，看不到单独一步。node 与 python 的 hashlib 都不暴露中间状态。

一条先被怀疑、后来被排掉的：长度字段的位置。它在一块的路径上其实被覆盖过 ——
111 字节消息的长度是 888（0x378），非零，写在 120 到 127 与写在 112 到 119 会给出两个
不同的块，而 111 那一条与标准相同。所以「低 8 字节在 120」这个判断是站得住的，不必再
从它查起。真正没被覆盖的只有「长度值小于 2^32」这一侧的对称性，而它们本来就不区分。

下一步该试的方向：

  一、自己编一份能打印中间状态的参考实现，用它把压缩函数对一个具体的（初值、块）逐轮
     对照。上面九条排除的是输入与外围，没被排除的是轮函数本身 —— 而它恰恰是唯一一个
     「一块对、两块错」也能解释的对象：如果它在某个特定初值下的行为不同，那就不是纯
     函数了，而这一点只能靠逐轮对照来证伪。
  二、把第一块（128 个零）的压缩结果与一份手写的六十行 C 实现比。零块的 W 全为零，
     八十轮只依赖 K 与初值，是最好对照的一种输入。

五、一句话

这一块的单块路径是对的，多块路径是错的，而错因还没定。它不该被当成已完成的东西引用。
