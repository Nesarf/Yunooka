谁能写什么：语言归属与 SDK 的边界

用户点的三条（2026 那一轮）：
  一、Himeyuri 是 Yunooka 内默认的计算机语言。所有要进 Yunooka 的系统软件与组件
      （Nanodesu、Torikago、ChuniHydra、Oak Barrels、Ichiwatashi、KID）都要用 Himeyuri
      编写；纯净的 Yunooka 原则上只认识 HMYR 写出来的东西。
  二、Hiou Rengo（HIREN）是 Himeyuri 的 SDK，不是 Yunooka 的 SDK。而 KID 本身包含在
      HIREN 里，同时又被确认为 Yunooka 系统的一部分 —— 所以装 HIREN 时不能把 KID 装两遍。
  三、Yunooka 自己的 SDK 还没想好，可能会并入 HIREN 的计划。
  另有一条上位说法：Yunooka 最终要由完全态的 Himeyuri 编写。

这一份文件把三条摊成分层与判据。它与 design/NAMES.txt 那一份是两条轴：那一份讲「同一个
名字指的是不同的东西」，这一份讲「同一台机器上的东西各由谁写」。


一、四层，谁能写什么

第一层 引导链。引导扇区、第二段、把种子读进来。这一层必须是机器码 —— 总得有人在
  「还没有 HMYR」的时候把第一段字节放进盘的第 0 个扇区。所以它是汇编，而这不是妥协，
  是这一层的定义。

第二层 内核。页表、中断、堆、文件系统、以及那些原语（画一条线、算一个表达式、匹配一条
  签名）。这一层现在也是汇编，而它是要被重写的那一层 —— 用户说 Yunooka 最终由完全态
  的 Himeyuri 写，指的就是这一层往上的全部。剩下的问题是顺序，不是方向。

第三层 系统软件与组件。Nanodesu、Torikago、ChuniHydra、Oak Barrels、Ichiwatashi、KID ——
  全部用 Himeyuri 写。它们不是「Yunooka 的内置功能」，而是跑在 Yunooka 上的包。

第四层 应用。同理，Himeyuri。这一层现在一个都没有。

SDK 不在四层里。HIREN 是 Himeyuri 的 SDK（写东西用的那一侧），Yunooka 只负责跑 ——
这条分工写在 HMYR 仓库的 design/FULLSELF.txt 第七节，而 README 第一节也抄了一句：
「宿主口归 OS，其余归 SDK」。所以「Yunooka 没有自己的 SDK」不是缺口，是那条分工的结果。
将来若真要有，第一件要回答的是「它与 HIREN 的边界在哪」—— 而那要等 HIREN 那边先稳定。

二、「只认识 HMYR」这件事要有一个判据

一句「纯净的 Yunooka 只认识 HMYR 写出来的东西」如果不落到判据上，它就只是一句愿望。
它现在可以落成两条，而两条都能查：

  一、`identify` 对每一个系统组件都要答 package。那个函数已经有了（Kohane 第六层，
     按魔数 HMYRB 判断，不看扩展名）。所以「盘上这几个名字都是包」是一条能跑的判据。
  二、`files` 列出来的系统组件清单，与「那些必须住在基础库里的东西」那份清单要对得上 ——
     而后者在 design/NAMES.txt 与 PLAN 的 system-software 那一条里。

现在这两条都还不成立，因为一个系统组件都还没有。而它们现在就该写下来，理由与
design/GUARD.txt 第一节那句话一样：判据写晚了，实现会先长成别的形状。

三、KID 的两重身份：这条要变成一次安装检查

KID 同时是「Yunooka 系统的一部分」与「HIREN 里的一个成员」。所以：

  装 HIREN 前先查 KID 在不在；在的话，装 HIREN 时要把 KID 那一部分排除掉。

这一条的形状与 GUARD 那两份清单一样 —— 它是一次检查，不是一次小心的操作。「小心别装
两遍」会忘，而「装之前查一遍、查到了就跳过」不会。

而它同时暴露一件事：同一件东西可以同时属于两个集合。所以「安装清单」不能只是
「谁包含谁」的树，它还要有「已经在了就别再装」这一条。树回答「该有什么」，检查回答
「已经有了什么」—— 两个问题都要回答，而后者是运行时的事。

四、与现有实现的张力，以及它怎么解

现在 stage2 里有一批原生实现：Kohane 的六层（列盘、窗口、列条目、详情、分析）、
签名匹配、像素层与画线、表达式求值的一小块。按第二节的说法，这些东西的终点是 HMYR
包，而不是汇编。

那现在这批算什么？脚手架。而这两个字得说清，否则将来有人看到它们会以为方向错了。

它算脚手架的判据有两条，两条都是事实而不是态度：
  一、它们做的是「证明那条路走得通」—— 画一条线证明帧缓冲可写可读，认一个包证明魔数
     那一条路对，列一个目录证明预读区盖得住。证明完之后，真正的实现在 HMYR 那一侧。
  二、它们各自带着一条判据，而那条判据在 HMYR 版本上仍然要成立。所以它们是规格，
     不只是代码：`cross 403 403 same` 那句话在换成 HMYR 实现之后仍然要对。

所以顺序不是「先写汇编再扔掉」，而是「用汇编把判据钉住，再用 HMYR 满足同一批判据」。
钉住判据这件事本身就是产出，而它是唯一不会随着重写而丢掉的东西。

五、还差的

  HMYR 需要的内置：读文件、写文件。没有这两条，系统组件连自己的数据都读不了 —— 而
    它们在 design/FS.txt 第一百零八行那一处已经被提到了，只是还没做。
  Yunooka 需要能跑一个「有输入输出的包」：现在能跑 main 返回 7，而那是没有 I/O 的。
  一个真正的 HMYR 组件：第一批里最容易的是 Ichiwatashi 的一小块（画一个窗口的框），
    因为它的判据已经在 Kohane 第二层钉住了。
  安装检查：装 HIREN 时排除 KID 那一条，要有一次真的安装才有地方落。

六、Myon：宿主口的那一半

用户给了两条，而两条合起来是一件事：
  一、Yunooka 的 shell、terminal、控制台，名字是 Myon。三个词指的是同一件东西。
  二、Myon 可以当 HMYR 的窗口用：输入输出、渲染、桥接。

这句话解掉的是第五节那条「Yunooka 需要能跑一个有输入输出的包」。现在的 shell 是汇编写的、
只认一个词（files）、只回一行；而一个 HMYR 包连「读到一行字、把一段字写回去」都还没有
地方落。Myon 就是那个地方。

为什么这件事值得单独记下来，而不只是改个名字：名字落在哪一层，日后就决定了谁去改它。
若 Myon 只是 shell 的别称，它属于内核那一层，随内核一起被重写；而若它是 HMYR 的窗口，
它属于宿主口 ——
  一、进来的那一行字、出去的那一段字节，是宿主给语言的两条口子；
  二、渲染是第三条：一个 HMYR 包要画东西，不必自己知道帧缓冲在哪；
  三、桥接是第四条：宿主与包之间、或者两个包之间的东西由它转。
这四条都是宿主该提供的，而不是某一个组件该实现的。它与 SDK 那条分工同构：
「宿主口归 OS，其余归 SDK」，而 Myon 是宿主口的那一半。

判据现在还立不全，因为第四层一个包都没有。但形状可以先定下来：
  一、Myon 报出来的每一行仍然是固定形状（event= 开头、键值对、顺序固定）——
     判据只认串口，而串口那一侧正是 Myon 的。
  二、一个 HMYR 包通过 Myon 读一行、写一行。这一条成立之后，第五节的「内置：读文件、
     写文件」就不再是包里唯一的出路 —— 而那两条内置仍然要做，因为包要读自己的数据。
  三、渲染与桥接排在后面，它们要等 Ichiwatashi 那一小块（画一个窗口的框）先进来。

判据的进度：一行不再只有一个词
------------------------------

第二条判据的第一步落地了。

以前 shell 是拿前五个字节与 "files" 比的 —— 于是 "filesx" 也会被当成 files，而「一行
只认一个词、只回一行」那句话就是这样落在代码里的。现在切成「词 + 其余」，按词长与词
分派，而 echo 拿的正是「其余」那一部分。

两趟各测一个，而它们证明的是两件事。第一趟从信箱收到 "echo hello world"：输出里必须
有 hello world，那说明这一行被切开、词之后的部分作为参数传了过去。第二趟没有信箱、
从盘上 cmd.txt 读到 files：目录列表照旧，说明原有的那条没被弄坏。

为什么 echo 值得一条判据：它看着比 files 简单，而它要的不是一个命令名，是一整行字，
而这一整行字必须原样出现在输出里。一个「只认命令名」的实现过不了它。

验红的办法是把参数的起点错开一位：输出变成 "o hello world"，头一个字没了。

剩下的：包那一侧还没接。眼下读与写的两端都在宿主这一侧，而它们就是包将来要接的两个
口子 —— 下一个 HMYR 包应当能调用它们，而不是让汇编替它读。那一步要动 HMYR 的内置表，
排在后面。

写那一半落地了
--------------

第二条判据的「写」那一半走通了：盘上的 prog.hmtn 现在有两个函数 —— main 返 7，
echo 压一个串常量、调内置 write、返回。串口上出现的是那段字本身，而它是包里的字节，
不是宿主里写死的字符串。

内置表原先只有 len。加 write 之后，一个包第一次能往外说一句话，而它不必知道串口在
哪个端口 —— 这就是「出去的那一段字节」那条口子。

判据两条：`event=myon write ok` 必须出现，而且它前面必须有 `myon here`（包里的字）。
两条一起才排掉「一个永远报 ok 的实现」。验红：把 write 里那一次 putc64 拿掉，字不再
出现，判据红。

路径上撞到两个真的结构上限，都记在这里：

一、根目录只有一个扇区，而 fs_lookup 只读一个扇区。加一条 29 字节的条目会让它溢出，
    症状是构建抛 RangeError，不是「少一条」。所以 echo 没有做成独立的包，而是并进
    prog.hmtn 的第二个函数 —— 多函数本来就是包格式支持的东西，所以这不是妥协，是把
    已有的形状用起来。扩根目录要动查找，那是另一件事，不该由一条判据来推动。

二、预读的扇区数是一次又一次被顶上去的：auth.bin 落地时从 23 到 24，这一轮一度到 25，
    并进 prog.hmtn 之后回到 24。这个数由 build 核对，所以它不会悄悄错 —— 但它每次
    都提醒同一件事：盘上每多一份文件，就有三个数要跟着动。

读那一半也落地了，判据二完整
----------------------------

第二条判据走通了：一个包通过 Myon 读一行、写一行。

内置表现在有三个：len、write、readline。readline 把宿主攒的那一行交给包，形状是包里
认的「u16 长度 + 码元」；write 把包给的串打到串口。

盘上 prog.hmtn 的 echo 函数现在是五条指令：压串、write、readline、write、返回。串口上
出现的是：

    myon here
    echo hello world

第一行是包写死的，第二行是这一趟运行时从外面进来的。而第二行才是判据真正的价值 ——
一个「打印固定字符串」的实现过不了它。

判据卡的是顺序而不只是存在：`echo hello world` 在串口上出现两次（shell 的回显，与包
打出来的），只查「有没有这个串」会被前一次满足。所以要的是「`myon here` 之后紧接
`echo hello world`」—— 那个顺序只有包里的那几条指令能给出。

验红：让 shell 不记那一行的位置（把 sh_line_ptr 置零），readline 拿到空，第二个 write
打出一个空行，判据红。

一个内置分派的坑，记在这里：try_write 那一段的长度检查原来直接跳 unknown，于是
readline（长度 8）根本没机会被试到。症状是 `unknown builtin`，而它看起来像「名字写
错了」——分派的出口要一路往下试，而不是一有不对就放弃。

长度截到 255 个码元。超出的部分不交给包，而不是静默截断：这一版没有「包读到一半还想
再要」的机制，所以给它的必须是一整行。

还缺的：渲染与桥接（要等 Ichiwatashi 那一小块），以及「包读到长行」这件事。

渲染的第一步：一个包让宿主画一个框
----------------------------------

第三条判据说「渲染与桥接排在后面，要等 Ichiwatashi 那一小块」。这一轮落的就是那一块的
最小版本：内置 border，零参数，画一个 (10,10) 到 (100,60) 的框，颜色 0x2F。

坐标与颜色写死不是偷懒。这一步要证明的是「包能让宿主画」，而通用绘图是 Ichiwatashi
自己的事，排在它后面。四条边用同一个 draw_line，所以这一条内置换来的是十六个像素，
而不是四段画线代码。

判据读三个点：(10,10)、(50,10)、(100,60)。三个位置隔着三百二十字节的步长，所以它不只
证明「有一个像素亮了」，还证明那个框的尺寸与位置是对的。三个都必须是 0x2F。

验红：把上边的终点从 (100,10) 挪到 (100,20)，那条线斜了，中间那个点不在线上，判据红。

画之前 r12 到 r15 必须先存起来：draw_line 不保存它们，而 exec 用 r12 指指令流、用 r13
数指令数。改坏了它们，症状是「包跑完第一条就乱跳」，与画图毫无关系。

同一个分派的坑出现了第二次
--------------------------

try_readline 的失败出口又跳了 unknown，于是 border（长度 6）没机会被试到，症状还是
`unknown builtin`。

同一个错在一轮里出现两次，说明问题不在某一次手滑，而在那条分派链的形状：每加一个内置，
就要回头改上一个内置的失败出口。现在它有四个出口（len 成功、write、readline、border、
最后 unknown），而它迟早会长到改不过来。

下一轮如果还要加内置，应当先把它换成一张表：名字、长度、处理者三样一起放，循环比。
那时「加一个」是加一行数据，而不是四处跳转。

内置表：一条链换成一行数据
--------------------------

四个内置（len、write、readline、border）现在靠一张表找，不再靠一条跳转链。

换的理由不是抽象的好坏：那个错在一轮里出现了两次。readline 加进去时，write 那一段的
失败出口直接跳 unknown，于是 readline 没机会被试；border 加进去时，readline 那一段也
是同样的毛病。两次的症状都是 `unknown builtin`，而那看起来像名字写错了。

链条的形状才是问题：每加一个内置，都要回头改上一个内置的失败出口。现在它有五个出口，
迟早改不过来。

表项三样：名字长度、名字指针、处理者。循环比，比中了跳过去。加一个内置是加三行数据，
不动任何跳转。

处理者用全名引用（exec.op_len 之类）：它们是 exec 的局部标签，而表在数据段。nasm 接受
这种跨段的引用，这是这张表能在这一版里落地的原因之一。

判据：四个内置都有既有的判据（len 走 is_digit，另外三个走 myon 那一条）。所以这一轮
的验红是「表项的处理者被真的用了」—— 把 len 那一项的处理者改成 op_write，名字还是
len、动作换了，is_digit 立刻坏。

一次重构的判据不该是新的，而该是旧的：四个旧判据全绿，才说明表换对了。

解释器真的能算
--------------

在这之前，包能做的表达只有两样：返回一个常量（main 返 7）、让宿主做事（write /
readline / border / runpkg）。两者都不经过算术。

而「住得下 HMYR」里最要紧的一条是解释器真的能算 —— 一份编译器产出的字节码不会只有
常量与内置调用。

所以 prog.hmtn 加了第三个函数 sum：常量 40、常量 2、add、返回。判据要 `prog sum -> 42`，
而 42 在这个仓库里没有别处出现过 —— 它不可能来自宿主里写死的数，只能来自包里那两条
常量与一次 add。

40 与 2 挑得没有讲究，只要和是 42。验红把它改成 41，和变 43，判据红。

同一个包里的三个函数现在各走一条路：main 走返回值、echo 走宿主口与桥接、sum 走算术。
它们共享一个包头与地址空间 —— 而「两个独立的包」那一条由 docs/myon.hmtn 单独压着。

这几个数与阶段的对应
--------------------

盘上一个包能被执行、能当场算、能用宿主口、能画框、能让宿主跑另一个包 —— 五样都在，
而且各有判据。剩下的是「一份真实的 HMYR 编译产物能在这里跑起来」，而那份东西在上游
仓库里，不在这一侧。

第二段的 128 是三处落点
----------------------

`stage2_sectors` 现在写 117，而上限是 128。那个 128 不是挑的，它有三处落点，而三处
必须同时成立：

一、加载器读两批各 64 扇区：第一批从 0x10000 起，第二批从 0x18000 起，
    而 0x18000 + 64 × 512 = 0x20000。
二、0x20000 是种子 —— `pkg_base` 的默认值就是它。
三、预读区在 0x40000，那还在更后面，轮不到第二段用。

所以「第二段再长一点」要付的代价不是改一个数，而是挪种子。而种子被 `pkg_base` 等着，
挪它要改所有直接读种子区的地方。

那段注释原先写的是「主体住 0x30000，上限 0x40000」—— 两个数都不对。它大概是更早那一版
加载器的记忆，而加载器后来改成了两批。这种注释比没有更坏：它让人以为还有 128 扇区的
余量。

于是 build 现在会在第二段超过 116 个扇区时说一句「只剩 N 个扇区」。116 这个阈值不是
「快到了」的估计 —— 写下这一条的时候第二段占 117，所以它在此刻就说话。一个要等到
明天才响的提醒，与没有提醒差不多。

整张内存地图在 design/MEMORY.txt：它把 0x10000 到 0x400000 之间每一段都数了一遍，
并说明三条挪种子的路各自为什么不通。结论是现在不动 —— 十一格是 5632 字节，而过去二十
几轮的增量大多在数十到数百字节之间。重排内存地图会让所有判据同时受影响，它应当在有
明确需要的时候做，不应当在为了多几格的时候做。

判据的判据：tools/audit.mjs
--------------------------

二十几轮下来，run.mjs 里已经有七十一个判据。而一个判据有两种坏法：它可能算错，也可能
根本没接在链上。前者会被红抓到，后者永远安静。

所以有了 tools/audit.mjs，它查三件与机器无关的事：判据有没有被引用、PLAN 的 after 指不
指着存在的目标、design 是不是纯文本。

它第一次跑就抓出十三处 —— 十三个 design 文件里有八十八处 markdown 加粗。那些星号不会
渲染，只会让读的人在两个星号之间读到一段他以为被强调过的话。信息没丢，而写法在假装有
个渲染器。

它自己也漏过一次：头一版是逐行找星号，而有一对星号跨了两行，于是那一处留了下来，而它
报了「十七个文件都没有」。改成全文找之后才看见。一条检查的第一版也会犯它要查的那种错。

它不进 run.mjs 的那条链：那条链验的是这台机器，这一份验的是我们写下来的东西有没有自相
矛盾。两者都会红，但红的含义不同 —— 混在一起会让「机器坏了」与「文档写歪了」长得一样。

它的第四项方向相反：串口上打了 event= 的行，有没有判据在读它。

第一次跑报出四个：ptmul、ptenc、ptdec、guard.nopatch。前三个是纯仪式 —— 同一个函数
上面已经把读数打出去了（ptm、pte、ptd），而「ok」那一行既不能替换读数，也不能在读数错
的时候变红。删掉。

guard.nopatch 不一样：它说的是「这一趟没有补丁」，而那正是 --drop-nopatch 那一趟要证明
的东西。所以给它加了一个读它的人（无补成），而不是删掉它。

而删那三行正好省下一个整扇区 —— 第二段从 117 落到 116。这件事本身就是一句提醒：那种
「打了没人读」的行不只是噪声，它占着这个仓库最紧的那个资源。









包能决定画在哪里
----------------

内置表加了 rect：五参数（x、y、宽、高、颜色），画一个填充矩形。

这是 border 的下一格。border 的坐标写死在宿主里，那只能证明「包能让宿主画」；rect 证明
的是「包能决定画在哪里、画多大」—— 而后者才是渲染，前者只是一次演示。

判据读四个点：三个来自 border 的 (10,10)、(50,10)、(100,60)，第四个是包那个矩形的中心
(140,30)。前三个是 0x2F，第四个是 0x1C（包自己给的颜色）。

验红试了两个参数，而第一个没红 —— 把 x 从 120 挪到 130，采样点 (140,30) 仍在矩形
（130..170）里，所以串口上一点没变。改宽才有用：宽从 40 收到 10，矩形只到 130，采样点
落在外面，读回 0F。

那一次没红很值得记：判据的采样点在矩形内部，所以它对平移不敏感、对尺寸敏感。一个判据
能过，只说明它采的那几个点对；它不说明别的点也对。


包画出了一个窗口
----------------

prog.hmtn 的第四个函数 win：三个矩形，底色 (60,80,200,90)、标题栏 (61,81,198,12)、
内容区 (61,94,198,75)。一个包画出了一个有结构的东西，而不只是一个盒子。

判据读三个点，各在一个区里：标题栏 0x1C、内容区 0x0F、底色 0x1F。它同时证明三件事：
三个矩形都真的画了、顺序对（后画的盖住先画的）、偏移对（错一格就会读到相邻那一层）。

而它比 rect 那条强：rect 只画一个矩形，一个「永远画同一个矩形」的实现也能过。

第一次跑出的是三个 1F。那不是 rect 坏了，是包里只装了六条指令 —— writeUInt32LE 那里写的
是 窗口矩形.length * 2，而每个矩形是六条指令（五个常量加一次调用），三个该是十八条。
症状是「三次调用拿到同一份参数」，而真相是「后两次调用根本没有指令去执行」。

一个数字差三倍，而那三倍正好是一个「每个矩形六条」的常识。指令数写错时的症状与参数传错
时一模一样 —— 都是「后面那些没有生效」。

验红：把标题栏从 y=81 挪到 y=91，第一个采样点落回底色，读到 1F。


文件读取：内置在，包那一侧的调用还没接上
----------------------------------------

内置表加了 slurp：一个参数（路径，从 α:/ 之后写起），返回那一份文件的内容成一个串。
盘符由内置补上 —— 一个包不该知道盘符。

它是 self-host 的第一块。self-host 的 notes 原先说「读源文件、写目标文件那两件事要的
对象模型与文件写入都还没有」—— 写入早就有了（fs_write_file），缺的是读。而在这之前，
「读」只有一个口子：readline 读的是宿主攒的那一行，不是文件。

一个位置上的坑：fs_open_path 用 rbx 交回字节数，而 rbx 在 exec 里是 pc。所以 slurp 里
必须先把它存起来再调用 —— 否则症状是「包读完了文件就跳到别处」，与读文件毫无关系。

而包那一侧的调用没有留下来。试着让 echo 读 docs/sub/deep.txt 再打出来，结果它断在
readline 之前：串口上 myon here 之后什么都没有，连 echo hello world 都不出现。那不是
「slurp 返回错了东西」，是它把执行流带偏了。

所以包里那条调用撤了，内置与它的注释留着。一条红的判据会有人说点什么，而一条把后面
全部遮住的红会让人先去看别的 —— 后者更贵。


unknown op 100：错位只可能来自扫描
----------------------------------

让 win 调 slurp，串口上是：

    unknown op 100
    Yunooka: exec ran out at 19 21
    Yunooka: win px 1C 1F 1F

op 100 是 0x64 —— 字符 d 的低字节。而编出来的字节里，d 只出现在路径 docs/sub/deep.txt。

上一轮那句「断在 readline 之前」是错的：readline 在 slurp 前面，所以 slurp 不可能是那个
原因。那句话说清了一件更要紧的事 —— 我没读懂自己刚截取的那段输出。

而错位的位置只有一个来源：exec 从 instr_offsets 取每一条指令，而那张表由 scan_instrs
与 imm_shape 建。rsi 怎么前进都影响不到它。

所以下一个要看的是扫描，不是 rsi。下一轮从 scan_instrs 查起：形状 6（名字 + u16）对
builtin 与 call 是同一个形状，而两边只有 builtin 会在这条路上被扫到。


scan op 100：起点已经偏了
-------------------------

在 scan_instrs 里加了一条诊断：opcode 超过形状表长度（34）就报一行。因为 imm_shape 后面
紧跟着 line_letters，越界读到的会是字符 'Y'，而 'Y' 落到「8 tuple」那一支上跳两字节 ——
偏移表会从某一条起全部错位。

把 slurp 的调用加回去之后，串口上是：

    Yunooka: scan op 100
    unknown op 100

所以错位发生在 scan_instrs 之前 —— 也就是 find_fn_by_name 交给 r12 的那个「函数体起点」
已经偏了。scan_instrs 从 r12 起、按 skip_imm 走，它读到 100 说明 r12 本身就在串里。

而 win 与前面三个函数（main、echo、sum）的区别只有一处：它是第四个。

find_fn_by_name 找名字的办法是「跳过前面每一个函数体」—— 用 r13 里的指令数配 skip_imm。
前三个跳得对，第四个就对不上。所以下一轮要在那一段 .skip 循环里找，而不是在 scan_instrs
或 exec 里找。

诊断留着：它在下一次有人调 slurp 的时候会先说话。


判别性实验：slurp 在第一个函数里能工作
--------------------------------------

上一轮说「问题在 find_fn_by_name 跳过前面函数体那一段」，而那只是一种可能。一个实验把它
变成了结论：把 slurp 放进 main —— main 是函数表的第一个，找它时一条函数体都不必跳过。

结果：

    Yunooka: prog main -> 7
    Yunooka: prog sum -> 42
    Yunooka: scan op 100
    unknown op 100

main 跑完了（7 出现），而 scan op 100 出现在 prog sum -> 42 之后 —— 也就是轮到 win
（第四个）的时候。

所以三件事同时成立：slurp 本身没问题，scan_instrs 没问题，而「第四个函数的起点」有问题。

跳过 main(5) + echo(13) + sum(4) = 22 条指令之后，rsi 就偏了。而那 22 条里只有三类形状：
值（常量）、名字加 u16（内置调用）、以及返回。三类都在别处用过。

一句题外话：这个实验花了一次构建与一次运行，而它把「三个可能的桶」缩成一个。前两轮都是
在猜，这一轮是在问 —— 差别在于这一次的问题有一个只会二选一的答案。


差 27 字节：不是一个「跳过算错」
-------------------------------

在 find_fn_by_name 的 .each 里加了一条诊断，打印头五个函数头的位置与名字长度。

prog.hmtn 那一次调用读出来是：

    0x43009 len=4
    0x43043 len=0
    0x4304F len=0
    0x4305B len=0
    0x43067 len=0

第一个是对的：0x43009 是 pkg_base + 9，长度 4 正是 main。而跳过 main 的体之后 rsi 落在
0x43043，名字长度 0 —— 那不是第二个函数头。

算一下正确的那个：main 的头是 2 + 8（名字）+ 2 + 2 + 2 + 4 = 20 字节，指令体是 11 字节
（常量 7 的 1 + 1 + 8，加返回的 1）。所以下一个函数头应当是 0x43009 + 20 + 11 = 0x43028。

而它落在 0x43043 —— 差了 27。

27 既不是 11 的倍数，也不等于任何一段的长度。所以「skip 循环少跳或多跳一条指令」这个
解释对不上。更可能是：读第二个函数头的时候，rsi 已经不是「上一条指令之后」那个位置了。

下一轮要在 .skip 循环里逐条打印 rsi，而不是只看函数头 —— 函数头之间的差是结论，而中间的
每一条才是证据。

那条诊断撤了：它会打一百多行（find_fn_by_name 每次扫到 400 个函数头才放弃），而一个
只在人工读的时候存在的诊断与没有差不多。留下的这一段注释与 design 里的数才是它的产出。


rsi 是对的，r13 是错的
----------------------

上一轮那个「差 27」否定了一个解释。这一轮在 .skip 循环里逐条打印 rsi，拿到了两个数：

    0x4301D  count=3

0x4301D 正是 main 指令流的起点（0x43009 + 20 字节的函数头），所以跳过的起点是对的。

而 r13 读成了 3 —— main 的指令数是 2。

两个数放在一起只说一件事：find_fn_by_name 在 .effed 那里读到的「指令数」不是这个函数的
指令数。多读 1 条之后，跳过的字节数自然对不上，而那个 27 就是从这儿来的。

所以下一轮要查的是 .effed 那几行对 prog.hmtn 的头到底算到了哪里：名字长度、跳名字、
加四（参数量与槽数）、效果数、加二、然后读指令数。build 写头的顺序是名字长度、名字、
参数量、槽数、效果数、指令数 —— 两边应当一致，而那正是要核对的地方。

那个诊断已经撤了，而它给出的这两个数写在这里：一个诊断最大的价值是它留下的数，不是它
打印的每一行。


那 27 是我算错了地址
--------------------

前两轮把「差 27」当成一个待解释的现象。这一轮去盘上读 prog.hmtn 的头，才发现那个地址
根本不是 prog.hmtn。

prog.hmtn 在 数据起 + 5，而 数据起 = 文件系统起 + 3 = 1027，所以它是第 1032 个扇区 ——
预读区里 0x40000 + (1032 - 1024) * 512 = 0x41000。

而诊断过滤的 0x43xxx 是 0x40000 + 24 * 512，也就是第 1048 个扇区 —— 那是 docs/myon.hmtn。

于是那两行「0x4301D count=3」说的是 myon.hmtn：它只有一个函数 echo，指令数正好是 3，
而 0x4301D = 0x43009 + 20 正是 echo 指令流的起点。跳完三条之后落在函数表末尾、读到长度
0 —— 全部正常。

所以 find_fn_by_name 一直是好的，而「差 27」不是 bug 的症状，是我把两个包的位置搞混了。

这一课不是「要小心」，而是「一个地址必须有出处」。0x43xxx 是我从 grep 里顺手拿的一个
数（那是 fs_myon_path 的邻域），而 prog.hmtn 的位置写在 build 的 数据起 + 5 那一行里。
两者差 16 个扇区，而它们在我脑子里是同一种「包地址」。

scan op 100 仍然是真的：那次是 run_win_test 扫 prog.hmtn 找 win，而 win 是第四个函数，
所以要跳过 main(2) + echo(13) + sum(4) = 19 条。下一轮看那 19 条 —— 而这一次地址要先用
0x41000。


地址对了之后：前面三个函数体跳得一点没错
----------------------------------------

用 0x41000（prog.hmtn 真正的地址）重做那个诊断，跳过那十九行全部对得上：

    0x4101D #0  →  0x41027 #1   差 10（常量 7）
    0x4103C #0                   main 不匹配，进 echo
    0x41052 #1   差 22（常量 "myon here"）
    0x41061 #2   差 15（write）
    0x41076 #3   差 21（readline）
    0x41085 #4   差 15（write）
    0x41096 #5   差 17（border）
    0x410A7 #6   差 17（runpkg）
    0x410B1 #7   差 10（常量 120）
    …… 五个常量各差 10，然后差 13 是 rect
    0x410F9 #0                   sum
    0x41121 #0                   win

每一条的相邻差值都等于它该有的长度。所以前面三个函数体跳得一点没错，而 find_fn_by_name
在这一段上是干净的。

问题只在 win 自己的体里：

它的指令流从 0x41121 起、共二十一条（3 + 18），总长应当是 38 + 15 + 15 + 3 × 63 = 257
= 0x101，于是最后一条应当在 0x41221。而诊断打出来的是 0x41205 —— 差 28。

所以不是「从头就错」，是走到了后面的某一段才错。下一轮在第十八条之后那一段找。

一个方法上的收获：同一个诊断、同一个函数，只是把过滤地址从 0x43xxx 换成 0x41000，结论就
从「跳过算错」变成了「跳过完全正确」。上一轮那个错地址让两轮推理都白走 —— 而它们当时
看起来很自洽。


扫描从第零条起就只跳了一个字节
------------------------------

win 的指令流起点是 0x41121。盘上那里的字节是：

    0x121  05 01 00 00 00 00 00 00 00 4E 40
           ↑  opcode 5（常量）  ↑ 种类 1（数）  ↑ 后面八个字节是 60.0 的 f64

所以那是一条完整的常量指令，长 10 字节。

而 scan_instrs 打出来的是：

    0x41121 #0
    0x41122 #1
    0x41124 #2
    0x41124 #3
    0x41124 #4   ← 从 #2 起不动了

第 0 条只前进 1 字节 —— 那正好是 scan_instrs 自己那句 inc rsi（跳过 opcode）。也就是说
skip_imm 收到的是「跳 0」那一支，一个字节都没跳。

于是第 1 条从 0x41122 起 —— 而那里是种类字节 01，被当成 opcode 1（u16），跳 2 字节；
第 2 条从 0x41124 起，那里是 00，opcode 0 的形状是 0 —— 从此原地不动。

所以整条错位链的起点是「第一条常量没有按值编码处理」。imm_shape[5] 是 7，而 7 会走
.value（读种类）再走 .v_num（跳八字节）。下一轮要查的是 skip_imm 在那里到底收到了什么。

两个方法上的收获：一、盘上的字节比任何推理都可靠 —— 这一轮是先把 0x121 那段打出来才看清
「只跳 1」意味着什么的；二、原地不动的那几行（#2 到 #17）本身就是证据：一个「跳 0」的
形状会让游标停在同一处，而它一旦出现，后面的每一条都跟着错。


那十八行「scan at」是误读
-------------------------

上一轮从扫描的位置序列里得出一个结论：第 0 条只前进 1 字节，于是 skip_imm 走了「跳 0」，
整条错位链从那里开始。

这一轮直接量了一次：shape=7，而 rsi 的前后差是 9 字节 —— 正好是「读种类一字节、再跳八个
字节的 f64」。所以 skip_imm 对 win 的第一条完全正确。

那上一轮那十八行是从哪来的？打印条件是 cmp rax, 0x41100 / jb —— 而 rax 在那一行之前已经
被 movzx eax, byte [rsi] 改成了 opcode（5）。5 永远小于 0x41100，所以那个「只打 win 那一段」
的条件从来没有生效过，而打印出来的位置属于别的调用。

一个诊断自己也会犯它要查的那种错。这是第二次：上一次是逐行找星号而漏掉跨行的那一对。

所以现在的结论是：前三个函数体跳得对，win 的第一条也跳得对。scan op 100 仍然是真的
（它只在包调 slurp 时出现），而它不在这两处。

下一轮换一种办法：不猜位置，直接让 scan_instrs 在读到超过 33 的 opcode 时把它前面的
那几个字节打出来 —— 那能说明它落在了什么中间。


win 的体在 0x1DE 结束，之后全是零
--------------------------------

从 0x1DE 往回看那一段：

    0x1d0  40 03 04 00 72 00 65 00    ← 上一条 f64 的尾巴、03（调内置）、名字长度 4、"re"
    0x1d8  63 00 74 00 05 00 1c 00    ← "ct"、参数个数 5、1C（返回）
    0x1e0  00 00 …                     ← 从这里起全是零

所以 win 的最后一条指令是返回，落在 0x1DE。而那之后是 Buffer.alloc 没被写到的部分，
全是零。

一个 opcode 为零的字节，形状也是零 —— skip_imm 会跳零个字节，游标原地不动。所以扫描一旦
走到「体之后的零」，它就会停在那儿，直到 r13 用完。

这和前几轮那些位置都对得上：错位不是发生在某一条指令的长度上，而是发生在体的末尾。而
0x41202 那个 d 属于别处的一个 deep.txt 串 —— 也就是说那次扫描的游标根本不是从 win 的起点
一路走过来的，或者它走到了更后面。

下一轮先把「win 的二十一条到底覆盖到哪个地址」算清楚：从 0x121 起加 38 + 15 + 15 + 18 条
矩形指令，与 0x1DE 比。如果加起来大于 0x1DE，那说明二十一条超过了体的实际长度 —— 而那就
是错位的来源。


一份完整的 prog.hmtn 布局
------------------------

这一轮写了二十行解析器，从包的第九个字节开始，按 build 写头的顺序逐函数走到尾。它给出的
一张表比前面几轮的推算都可靠，因为它不依赖任何一处手算：

    main  @0x1009  头长 20  指令 2   体 0x101d..0x1028（11 字节）
    echo  @0x1028  头长 20  指令 13  体 0x103c..0x10e7（171 字节）
    sum   @0x10e7  头长 18  指令 4   体 0x10f9..0x110f（22 字节）
    win   @0x110f  头长 18  指令 18  体 0x1121..0x11de（189 字节）
    整包到 0x11de

四个函数每一个都自洽：win 的体是 189 字节，而 3 ×（5 × 10 + 13）正好是 189。

所以现在这一版（win 十八条）是干净的，而上面那张表也解释了前几轮那些数为什么对不上：
win 有二十一条的那一版，它的体比现在长六十八字节（路径 38 + slurp 15 + write 15），
起点仍然是 0x1121，而终点就不是 0x11de 了。

于是那个落点 0x1202 —— 它落在二十一条那一版的中段，而那正是「路径串」之后的位置。错了
一步，而错的那一步在二十一条那一版的体里。

下一轮把二十一条那一版也解析一遍：同一段脚本、只改 build 里 win 的指令数，看它的体走到哪
一字节、而第五条之后每一条的位置又是多少。


两套独立规则读到同一个 100
--------------------------

上一轮写的那段解析器（二十行，按 build 写头的顺序走）与固件的 scan_instrs（按 imm_shape
与 skip_imm 走）是两套独立的规则。这一轮把它们放在同一版二十一条的包上，结果：

    !! 未知 opcode 100 在第 19 条
    op=100 at 0000000000041202

同一个位置、同一个 opcode。

两个独立实现给出同一个答案，那说明错的是 build 写出来的那一串字节，不是固件的扫描。这条
推理比前面几轮任何一次都硬 —— 前面的每一次都是在固件内部找原因，而这一次两边互相印证。

而解析器给出的体是 0x1121..0x1203（226 字节），而二十一条按设计应当是 257 字节 —— 少了
31。

所以下一轮的题目很明确：build 在写 win 那二十一条时少写了三十一个字节，而少在哪一段，
把它逐条按设计长度累加一遍就知道。

（那段解析器是临时的，放在 scratch 里。它的价值不在代码，而在于它证明了「build 与固件
用了两套规则」这件事；两套规则同时错的可能性远小于一处错。）


漏掉的那一条是返回
------------------

把 win 的体逐条走一遍（从包内偏移 0x121 起，按 build 的写法），十九行全部合法：

    #0  0x121..0x12b  常量
    #1  0x12b..0x135  常量
    #2  0x135..0x13f  常量
    #3  0x13f..0x149  常量
    #4  0x149..0x153  常量
    #5  0x153..0x160  builtin rect 参5
    …（后面两个矩形同样）
    #17 0x1d1..0x1de  builtin rect 参5
    #18 0x1de..0x1df  ret

十九条，而声明的指令数是十八。少的那一条正是返回。

一个「指令数漏一条」的 bug 而症状很特别：矩形都画了，所以 win px 三个点全对；而 exec 跑完
十八条之后 pc 就等于 r13，直接停下 —— 返回那一条永远不执行，win 从来没有真的返回到调用者。
一个少了返回的函数，看起来与一个正常的函数一模一样。

修法是把声明改成 length * 6 + 1。改完之后解析器与固件给出的都变了：win 十九条、体 190
字节、整包到 0x11df，而串口上 win px 仍是 1C 0F 1F。

顺带记一件自己的错：这一轮我读的是 build/failed-run.txt，而它是上一轮留下的 —— 里面那行
win px 是旧值，于是我把一个正确的运行看成了错的。run.mjs 在失败时写那个文件、成功时不清，
而「先看它」是之前几轮养成的习惯。要看的永远是这一次的 run.log，除非失败。


根因：一个写死的偏移与一个会长大的文件
--------------------------------------

把 slurp 的三条加回 win，包从 479 字节涨到 547，也就是从一个扇区涨到两个。而文件系统里
后面每一个偏移都是「文件系统起 + N」写死的形状：

    子目录2号   = 文件系统起 + 9
    深层文件起  = 文件系统起 + 10
    规则起      = 文件系统起 + 13
    绘图起      = 文件系统起 + 14
    假样本起    = 文件系统起 + 15

于是 docs/sub 正好压在包的第二扇区上。而症状不是「布局冲突」—— 它是扫描在包内偏移 0x202
读到 0x64（字符 d），那是 "deep.txt" 那个目录条目里的码元。

把 子目录2号 改成跟着程序包大小走之后，一次运行里三件事同时变了：

    win px 000000000000001C 000000000000000F 000000000000001F
    （scan op / unknown op 都不再出现）
    Yunooka: open docs/sub/deep.txt -> ...

也就是说：前十几轮追的那个错位，根因就是这一处布局。而它之所以查了这么久，是因为它的
症状（一个落在串中间的 opcode）与它（扇区被目录条目盖掉）之间隔了三层。

而修它不能只改一处：程序包长一个扇区，它后面七个写死的偏移都要加一。所以这一轮退回了
一扇区，并把「重排布局」列成下一件事 —— 那要先有一个能一次算完所有偏移的写法。

一条值得记的教训：一个「长度会变的文件」与一串「写死的偏移」放在一起，那个文件长大的那一天
就是这一串偏移全部错位的那一天。而症状会出现在离布局最远的地方 —— 这一次是解释器读到
一个字符 d。


重排试过一次，卡在「最后一份扇区」
----------------------------------

这一轮把数据区的七个写死偏移换成了「一份清单 + 一次累加」：

    const 数据区清单 = [
      { 名: "hello.txt", 内容: () => 盘上示例, 扇区: 1 },
      ...
    ];
    let 游 = 数据起;
    for (const f of 数据区清单) { f.起 = 游; 游 += f.扇区 ?? ceil(f.内容().length / 512); }

而它一路撞了三件事：内容变量定义在清单之后（要 thunk）、thunk 在累加时求值还是会撞
（要把累加挪到所有定义之后）、以及一条太贪的正则把「码元」函数的头吃掉了。

三件都修好之后 build 通过了，而机器起不来：串口上缺 stage2 ok、protected mode ok、
long mode ok、heap ok。而 build 的输出里那句「最后一份在第 9 号」就是线索 ——
最后一份扇区 算成了九，于是预读区只盖到 1033，而盘上的文件在 1048 附近。

那一处不在清单里：最后一份扇区 来自 外五件 → 签名 → 核心清单 → 假样本起 那条链，
而清单只覆盖到 假样本起。链式的那一半没跟着走。

所以这一轮退回了 build.mjs，而把重排留成下一件事 —— 且这一次它有了一个明确的边界：
清单要覆盖到最后一份文件（外五件与 myon.hmtn 都在链尾），而 最后一份扇区 要从清单的
终点算，不是从链尾的某一个变量。

一条方法上的记录：这次改动连着撞了四个错，而每一个都在不同的层（作用域、求值时机、正则、
以及链尾）。四个都修好才到「build 通过」，而 build 通过之后才暴露第五个（布局的终点）。
一次大改的正确性不会在第一个绿灯处出现。


第二次重排：预读对了，机器还是起不来
------------------------------------

按上一轮定下的两条边界重做了一遍：清单覆盖到链尾（外五件与 myon.hmtn 都在里面），而
最后一份扇区 从清单的终点算。

这一次撞的坑与上次不同，而每一个都能定位：

  一、内容变量定义在清单之后 —— 而这一次清单直接写内容，所以要把清单挪到所有定义之后。
  二、挪到「子目录2 之前」之后，超级块（在它之前）又用不上 示例扇区数 —— 于是再往前提。
  三、提到 超级块 之前之后，子目录2 还没定义 —— 而它只用来算一个扇区，所以换成占位缓冲。
  四、一条正则第二次吃掉「码元」函数的头 —— 与上一轮同一个地方。

四件都修好之后 build 通过，而 build 说「最后一份在第 1048 号 —— 盖得住」—— 那是对的，
上一版算成 9。

而机器起不来：串口只有一行 boot ok，而 stage2 ok 没有出现。引导扇区读到了，加载器没把
第二段带起来 —— 或者带起来了而它没跑。

这一处没查清。两段的位置（引导 1 + 加载器 8 + 主体 121、种子第 130 扇区起）在 build 的
输出里都是对的，所以问题不在那三个数上。

于是又退回了一次。而两次失败的形状值得并排放着看：

  第一次：清单只到 假样本起，最后一份扇区 算成 9，预读盖不住 —— 症状是缺五行。
  第二次：清单覆盖到链尾，最后一份扇区 算成 1048，预读盖得住 —— 症状是只有 boot ok。

同一个改动，两次失败在两个不同的地方。而第二次的那个位置比第一次更早 —— 早到「文件系统
这一层根本没轮到」。这提示一件事：布局改动会先影响启动，再影响文件系统，而这两层之间
隔着加载器与第二段 —— 一个只有一行串口的地方。


第二趟的串口终于留下来了，而它先抓到的是我自己
----------------------------------------------

「落盘」那条判据一直红：第二次启动没有报 persist survived a reboot。而第二趟的串口只存在
内存里，关机之后就没了 —— 所以「第二趟没到」这句话一直没有证据。

这一轮让它落一份文件（build/serial2.log），而第一次读到的第二趟是：

    Yunooka: boot ok
    Yunooka: stage2 ok
    Yunooka: seed unreadable
    Yunooka: fs preread failed
    Yunooka: mailbox ok

两行新东西：seed unreadable 与 fs preread failed。

而这两行来自我这一轮加的那个诊断字符。加载器里为了在 boot ok 之后说一句话，写的是

    mov al, [dbg]
    mov dx, 0x3F8
    out dx, al

而 dx 里的 dl 存着盘号（mov dl, [drive]）。改掉它之后，后面那次 int 0x13 读种子就失败了
—— 症状是 seed unreadable 与 fs preread failed 两行，而它们与「盘号」毫无关系。

回退之后，同一个 serial2.log 上是：

    Yunooka: boot ok
    Yunooka: stage2 ok
    Yunooka: seed ok 74594
    Yunooka: mailbox ok

也就是说「第二趟没到」从来不是布局的问题，而是我这次诊断把盘号弄丢了。

这是第三次「诊断改坏了寄存器」：第一次是 rax（puts64 用 lodsb），第二次是 rbx（fs_open_path
用它交回字节数），这一次是 dl（盘号）。三次的症状都不说「寄存器坏了」：第一次是打印出错的
数，第二次是包跳到别处，这一次是种子读不到。

留下的东西是 serial2.log 那一行 dump：它把「第二趟没到」从一句判断变成了两行证据。


第三次：重排本身让第二段起不来
------------------------------

上一轮那个 dl 的坑让人以为「第二次失败是我的诊断」。这一轮把重排重做了一遍而不碰加载器
—— 结果一样：串口只有一行 boot ok，而 stage2 ok 没有出现。

于是两件事分开了：dl 那个坑是真的（它让第二趟报 seed unreadable），而重排让第二段起不来
也是真的。两者互相掩盖了一轮。

查到的部分：盘上的种子在（偏移 66560 处是 HMYRB），而 build 报的三段（引导 1 + 加载器 8 +
主体 121、种子第 130 扇区起）都对。所以前两段的写入没有问题，而第二段没跑起来。

未查到的：为什么。

而三次失败值得并排放着看：

  第一次  清单只到 假样本起 -> 最后一份扇区 算成 9 -> 预读盖不住 -> 缺五行
  第二次  清单覆盖到链尾 -> 预读 1048 对 -> 而我加的 dl 诊断让第二趟种子读不到
  第三次  同样的重排而不碰加载器 -> 预读对、种子在、而机器只到 boot ok

第三次把第二次那两个原因分开了：dl 是真的，而重排也是真的。而第三次的失败点比前两次都早
—— 早到「文件系统这一层根本没轮到」，早到「只有一行串口」。

所以这个方向现在有一个未知：一次只改数据区布局的修改，为什么会影响到第二段能不能跑起来。
在弄清它之前，第四次重排没有意义 —— 而三次失败都发生在同一个改动上，那说明这里有耦合，
不是运气。

退回到已知良好状态。而下一件是把那个耦合找出来：从「第二段的第一条指令是什么、它在什么
条件下不执行」开始，而不是再从布局那一侧推。


对比：diff 里只有布局，而启动不读布局
------------------------------------

这一轮不再试第四次，而是把重排重做一遍然后看 diff。

删掉的 22 行全是那串写死的偏移与旧的多行 示例扇区数；新增的 63 行全是清单块。也就是说
那四个脚本没有碰别的地方 —— 没有误改、没有多余的删除。

于是三件事摆在一起，两两矛盾：

  一、diff 里只有布局。
  二、启动不读超级块，也不读数据区 —— 引导扇区读加载器，加载器读第二段，第二段读种子。
  三、而机器只到 boot ok。

如果一与二对，那么三不该发生。而三发生了三次。

所以有一个假设是错的。可能的错处：

  - 布局那次改动并不只影响布局（比如 示例扇区数 的求值顺序让某个模块级副作用提前或推后）；
  - 或者「启动不读布局」这句话是错的（比如某个地址被算在启动路径上）；
  - 或者串口那一行「boot ok」之后其实还有东西，只是没被读出来（比如加载器换了输出端口）。

第三条最容易验证而我一直没有验：串口的读取是 run.mjs 那一侧做的，而「只有 boot ok」是
它读到的。如果加载器在 boot ok 之后把字符写到了别处，串口上就会是干净的 —— 而那种干净与
「没跑」长得一样。

三种可能里，第三条最便宜。下一轮先验它：在 0x3F8 之外再读一遍（或者直接看 VBox 的串口文件
在 boot ok 之后有没有增长），而不是先怀疑布局。


第三条候选被否掉了：串口真的不再增长
------------------------------------

上一轮把三件事摆成一个矛盾，并说最便宜的那一条是「那行之后串口是否真的没再增长」——
因为串口是 run.mjs 那一侧读的，而「只有 boot ok」也许只是「读不到」。

这一轮直接量：清空串口、起机器、每半秒看一次文件大小，看二十秒。结果是

    0.5s   0
    3s    18
    之后不再变化

而 18 字节的内容就是 Yunooka: boot ok 那一行。

所以第三条候选不成立：加载器没有把字符写到别处，它就是。

而「卡住」这个判断比「没跑」更具体：加载器的失败路径会打 line_fail 加错误码加批号，
而串口上没有那一行。也就是说它既没走成功路径（那会跳进第二段并打 stage2 ok），也没走
失败路径（int 0x13 返回进位的那种）。它停在 int 0x13 里面，或者停在两批之间。

所以下一个问题很窄：为什么同一份加载器、同一份盘布局的数字，在重排之后会在 int 0x13
里停住。

一个附带的东西：watchserial.mjs 这个脚本现在留下了 —— 它做一件 run.mjs 不做的事：把
「串口的大小随时间怎么变」摊开。而这一轮正是靠它把「读不到」与「没写」区分开的。


重排成了，而它缺的是链尾那五个
------------------------------

三次失败的最后一次把范围收窄到「加载器停在 int 0x13 里」。这一轮换了一个办法：不跑机器，
只比盘。

取重排前后的 disk.img 前 64 KB（加载器只读那一块）各存一份，比 sha256 —— 不同。再找第一个
不同的字节：偏移 0x200，也就是第 1 个扇区的开头。

    好：  fa 31 c0 8e d8 ...      ← 加载器的第一条指令
    坏：  04 00 00 00 09 68 65 6c 6c 6f 2e 74 78 74 ...

坏的那一边是核心清单：4 条 item、第一条名字长度 9、内容是 hello.txt。

而核心清单应当写在 核心清单起，那个值是「假样本起 + 1」。问题是那一行是 const：

    const 核心清单起 = 假样本起 + 1;

而 假样本起 在这一版里改成了 let，由数据区清单赋值 —— 赋值发生在这行之后。所以 const 捕获的
是它的初始值 0，于是 核心清单起 = 1。

链尾那五个全都一样：核心清单起 = 1、签名起 = 2、外五起 = 3、auth起 = 8、myon起 = 9。

于是核心清单被写到偏移 512 —— 那是加载器的地方。加载器在盘上只剩前 512 字节的引导扇区，
而它自己被覆盖成了「4 条 item」。

：引导扇区在、能打印，而加载器已经不是加载器了。int 0x13
读进来的是别的字节，跳到 0x1000 之后什么都没有 —— 既不打 stage2 ok，也不打 line_fail，
因为它们都不在。

修法是把那五个也改成 let、并在清单之后赋值。改完之后盘的前 64 KB 与「好」那一版 sha256
完全相同，而全套判据回到绿。

一条值得记的：这一轮的诊断顺序是「比字节」而不是「再跑一次」。三次跑机器都没有给出新东西，
而一次 static 的 diff 直接指出了偏移。当症状离原因三层远的时候，静态比较比动态实验便宜。


slurp 终于接上了，而它接上靠的是布局那一修
------------------------------------------

把三条加回 win 之后，一次运行里四件事同时成立：

    win 的指令数 22、体 0x1121..0x1223（258 字节）
    scan op 与 unknown op 都不再出现
    win px 1C 0F 1F（三个采样点都对）
    Yonooka three levels ok —— 那是 slurp 读出来的 deep.txt

而 build 报了一件新事：预读只盖 25 个扇区（1024 到 1048），而盘上最后一份文件在第 1050 号。
于是 dap_count 从 25 改成 27。

这件事本身值得记：prog.hmtn 涨到两个扇区之后，最后一份文件往后挪了两格，而预读那条数还停在
旧位置。build 那条检查把它抓住了 —— 那一条不是判据（判据在 run.mjs 里），而是构建期的核对。
如果没有它，症状会是「读到了、内容是零」，而那与「文件不存在」完全不同。

所以这一轮的三件改动是一条链：

    链尾那五个 const 在 假样本起 还是 0 时算定了 -> 核心清单写到扇区 1、盖掉加载器
    修好之后 prog.hmtn 可以涨到两个扇区
    而它涨了两格之后，预读那条数要跟着改（25 -> 27）

三件都做完，slurp 读文件这件事才第一次真的是那个意思：一个包读了一个盘上的文件，而那文件
的位置由清单算出来，不由一串写死的偏移。


filesize 试过一次：slurp 在第五个函数里读不到
---------------------------------------------

想给「slurp 的返回值参与计算」做最小的一步，所以加了第五个函数 filesize：常量路径、
slurp、len、返回。判据应当是 prog size -> 24（deep.txt 是 24 字节）。

而它跑出来是 prog size -> 0。

先怀疑的是顺序：win 自己也 slurp 一次，也许第二次 miss。于是把 filesize 排到 win 之前
—— 仍然是 0。所以与顺序无关。

再用解析器看布局：五个函数的位置、头长、指令数、体长全都自洽，filesize 在 0x1223、头长
28（名字八个码元）、四条指令、体 65 字节（38 + 15 + 11 + 1）。所以定位与编码都对。

所以是 slurp 在那一次调用里真的失败了 —— fs_open_path 返回零，走了 slurp_miss，交出空串，
而 len(空串) = 0。

而同一个路径在 win 里是成功的。两者的差别现在还不知道。

这一轮把它退回了：一个不工作的函数加上一条红判据，比没有更贵 —— 而那条判据会盖住别的。
留下的现象是这一个：

    win  里的 slurp 成功（打出 Yonooka three levels ok）
    filesize 里的 slurp 失败（prog size -> 0）
    两者读同一个路径，而顺序不是原因

下一轮要查的是「两次 slurp 之间有什么不同」—— 一个可能的方向是 fs_open_path 的
last_addr 与 fs_base 在两次调用之间被谁改过；另一个是 slurp_buf 与 myon_line 相邻，
而某个 call 写过了头。


更正：slurp 从来没有成功过
-------------------------

上一轮说「slurp 接上了」，依据是串口上出现了 Yunooka three levels ok。

这一轮给 slurp 的两条失败路径各加了一个标记（1 = 路径太长、2 = fs_open_path 返回零），
然后跑了一次。结果是：

    Yunooka: slurp miss at 0000000000000002

也就是说 fs_open_path 返回零 —— 而它出现了（win 一次、filesize 一次）。把 filesize
撤回之后还剩一次，那就是 win 的。

而 win 里那三条指令是「常量路径、slurp、write」。slurp 失败时交出一个空串，而 write 打一个
空串 —— 在串口上就是一个空行。而那个空行我当时看成了别的东西：run_fs_open3 那一条打的
Yunooka three levels ok 就在附近，而我把那一行当成了 slurp 的成果。

所以「接上了」是误读。真实情况是：slurp 每次都 miss，而它的唯一痕迹是一个空行。

这一轮留下的东西是那两条标记 —— 它们把「读不到」拆成两种，而这一次直接指向第二种：
路径拼好了，而 fs_open_path 没找到那个文件。

下一轮从 fs_open_path 在这一条路径上的行为查起：同一个路径在 run_fs_open3 里成功，而在
exec 内部（slurp 是内置，它在 exec 里跑）失败。两者之间的差别是这一轮没有查的部分。

一条方法上的记录：那一轮我把「串口上有一行正确的输出」当成了成功，而没有确认那一行是谁
打的。而这一轮加的两个标记，把一个「看起来成功」直接变成了「两次都失败」。


一段能读、三段不能
------------------

上一轮把 slurp 的失败确认到 fs_open_path 返回零。这一轮继续拆：把 win 里 slurp 的路径从
三段（docs/sub/deep.txt）换成一段（hello.txt），其余一个字不动。

结果：

    slurp miss 的次数 0
    Yunooka filesystem ok

也就是说 slurp 读到了 hello.txt，并把它的内容打了出来。

所以问题不在 slurp 自己、不在 fs_open_path 的第一步（盘符与冒号）、也不在寻址那两块：
fs_base 与 fs_start 都对着。问题在 —— 而它只在 exec 内部出现，因为同样的三段
路径在 run_fs_open3 里是成功的。

两边的差别是可数的：exec 内部多两样东西在寄存器里 —— r12 指指令流、r13 数指令数。
fs_open_path 自己 push/pop 了它们，所以它们在那之后是干净的。而段循环里还用了 rdi、rcx 与
机器栈（.at_slash 里 push rax / pop rdi），那三样在 exec 内部与外面没有区别。

所以下一轮要在段循环里打点：每过一段打一次段名与 fs_lookup 的返回值。两段之后就看得出来
是哪一段给了零。

一条方法上的记录：这一轮没有读代码，只做了一次「换一个输入」的实验，而它把范围从
「fs_open_path 与 slurp」缩到「段循环」。前几轮读代码读了三处，每一处都看不出问题 ——
而一次只改输入的实验直接给了一个二选一的答案。

=== 段循环打点：假设被证实，结论却被推翻 ===

上一轮记的下一步是「在段循环里打点，看哪一段给了零」。打点做出来了，两行：

    Yunooka: seg 4 1 1026      docs 命中，扇区 1026
    Yunooka: seg 3 0 1026      sub 在同一个扇区里返回零

所以「第二段给了零」这个假设是对的。但它指向的结论错了 —— 真因不在段循环里。

错在哪一步是看得出来的：如果段循环写错了，那么它每次都会错。而它没有 —— 同一个
fs_lookup(1026, "sub", 3)，在 run_fs_open3 那一次成功（seg 3 1 1034），在 slurp
那一次失败。同一段代码、同一个扇区、同一天里两种结果。

一个函数时而对时而错，指向的不是「函数写错」，而是「它读的那份东西被改过」。

于是换了一个完全静态的做法：按盘上格式把根目录走一遍，量出每条的起点。十九条静态
条目，最后一条 dex.bin 在偏移 480，自己有二十五字节，下一个可用位置 505。扇区 512。

第一次写文件要二十五个字节（new.txt）。505 加 25 是 530 —— 它跨过 512。

跨过去的 18 个字节落在第 1026 号扇区，而 1026 那时是 docs 的条目区。docs 的头三条是
note.txt、sub、myon.hmtn。sub 的条目就在新字节下面。

修法两件：根目录占两个扇区（超块偏移 16 一直是 1，而这个字段本来就是干这个的），
以及 fs_write_file 找空槽时带一个从超块读的上界，写到自己的页之外就返回失败。

修完 slurp 通，同时回来的还有写、共享、共享见面、门、此电脑、系统保护、详情、索引
这几族 —— 它们原先红着，而在此之前没有人知道它们与目录容量有关。

方法上两条：

  一、这一次的决定性证据来自一个静态脚本，不来自第二次机器运行。前一轮跑了三趟虚拟
      机，每趟三分之二分钟，而三次都只说明「还是红」。量根目录那一次花了不到一秒，
      直接给出了 505 这个数。
  二、先试的那条快路（让 fs_lookup 每次重读那一页）让 slurp 通了，但把「写之后读回
      自己写的东西」打红。它被撤掉了 —— 撤的时机是判据红的那一刻，不是发现它的第二天。
      留着一条「通了但它弄坏了别的」的改动，比原样红着更贵。
=== 目录边界是各自的：一条判据问对了方向，而余量不够走完 ===

上一轮修的那个 bug 是「目录条目区没有边界，写越界吃掉了隔壁目录」。修法是：根目录占两页，
fs_write_file 的条目上界从超块那个字段读，写到自己的页之外就拒绝。

而那条修法有一面没有验：拒绝只该发生在满的那一个目录上，不该是一个全局状态。最省事的
实现（一个 bool，或者干脆不听 write_dir）会让「根目录满了」挡住所有目录，而在串口上
这与「写对了」长得一样 —— 文件确实写进去了，只是写错了地方。

所以写了 run_docs_after_full：dirfull 之后往 docs 里写一份 late.txt，然后按完整路径查它。

它第一趟就红，而红得很具体：

    Yunooka: dirfull wrote 29 refused 11
    Yunooka: dirfull docs lost
    1027

那个 1027 是两个出口的分水岭。它等于 docs 的扇区号，所以不是「根目录里没有 docs」——
fs_lookup 找到了它。而 fs_write_file 也说了成功（否则会打 blocked，而不是 lost）。
于是剩下的只有一种：条目写进去了，而按 α:/docs/late.txt 查不到。

三个方向留给下一轮，按便宜程度排：
  一、fs_write_file 到底把条目写进了哪个扇区 —— 打 [write_dir] 与 [last_dir_sec]，
      两个数一比就知道 write_dir 有没有被传进去。
  二、docs 那时有没有空槽。它有三条静态条目，加上 save 写的 inner.txt 是四条。
      第四条之后应当是零，也就是空槽；若那里不是零，fs_write_file 会一直走到上界才失败，
      而失败会走 blocked —— 所以这一条与串口不符，但值得确认。
  三、fs_open_path 第二段查的地址：docs 的扇区是 1027，而 fs_load(1027) 是 0x40600，
      与 fs_write_file 写的是同一处。

而这一轮没有余量走完它：第二段到了 128 扇区，实到 65324 字节，余 212。上一次改动
（把 lost 的 r15 打出来）花了 88 字节。再往下每一次试探都要先腾地方。

所以它从主链上摘下来了，代码留着 —— 与 run_health_test、run_smart_test 同一个处理：
一条已经问对了方向的失败，不该继续占着串口。判据本身留在 run.mjs 里（晚成），
只是暂时不在链上。

那条纪律因此又多一面：红的形状本身就是进度。它这一趟给出的不是「不对」，而是「在哪一段
不对」，而后者才是下一轮能接着用的东西。
=== 答案：一个终止零码元，而三个聪明的方向全错了 ===

上一节列了三个方向，按便宜程度排：写进哪个扇区、docs 有没有空槽、查找第二段的地址。
三个全错。而它们错得有理 —— 每一个都能从「写成功而查不到」这句话推出来，而且每一个
听起来都比「数据的定义少了一个零」更像回事。

真因：fs_late_name 那八个码元后面没有终止零。它后面紧跟的是 fs_late_data 的两个字节，
于是在 fs_write_file 的 .count_name 看来名字还没完 —— 它一路数下去，直到撞见某个零码元，
然后按那个长度写下一条条目。确实写了，写的不是 late.txt，所以按 late.txt 查当然查不到。

第六个数才指出来：docs 页里「四条之后」那一格的名字长度是 9，不是 8。

六个数的顺序与它们各自排除了什么：

    0      write_dir   —— 清过之后的零，什么都不说明，而它第一眼看起来最像答案
    1027   last_dir_sec—— 写入确实进了 docs，把「走错了目录」这一支砍掉
    1085   last_write_sec
    0      late_probe  —— 直接查那一页也失败，把「fs_open_path 的第二段」砍掉
    1027   probe 的扇区—— 上一个数失败时的残留
    9      第 5 条的名字长度 —— 既不是 8（写入成功）也不是 0（空槽），于是问题在名字本身

有一处没有查到底，记在这里：按 .count_name 的走法，名字长度超过 64 会走 .fail，而 .fail
会让 fs_write_file 返回零，于是串口该是 blocked 而不是 lost。实际是 lost，说明它在 64
之内撞见了零码元。哪一个零、为什么那个位置恰好有零，没有查 —— 判据绿了，而那条路不值得
再花一次两分钟的运行。不确定的地方写出来，比补一个听起来合理的解释好。

方法上留着两条：

  一、把「三个数一次打出来」比「一次打一个数、跑三趟」省两趟。前者的代价是那个零会被
      误读（write_dir 打的是清理之后的值），而后者的代价是六分钟与两次可能被别的东西
      带偏的判断。
  二、判据红着的时候，找一个能把它二分掉的数，比找一个能解释它的理论便宜。第五个数把
      「查的那一侧」砍掉之后，第六个数几乎是自动指到名字上的。
=== 删除：三次尝试，而它仍然不工作 ===

包 API 的最后一格是「删」。这一段写了 remove 内置与它的判据，而它不工作 ——
包删完之后 list 仍是 33，说明 docs 里那四条还在。这一节记的是走过的路，与下一轮
该从哪儿接。

判据先写下了，而它红得对：prog remove -> 33（应当是 24）。所以「没删掉」这件事本身
是确定的，不是猜的。

路上遇到的四件事，按它们各自的价值排：

一、build 的返回字节自检救了一次。加第八个函数时又复制了一个 0x1c，而这一次不是靠把
    字节摊开发现的 —— 自检直接说「返回字节写了 9 次，而包声明了 8 个函数」。那条三行的
    检查是这一段里最划算的一笔。

二、savetest 的返回位置错了，而它的症状是「第七、第八个函数都找不到」。原因是那个返回
    留在了第二次 save 之前，于是扫描器数完十一条指令就落到下一个函数的头上，把名字长度
    读成了 opcode。walkscan（在主机上照 find_fn_by_name 的算术走一遍）一次就定位到了：
    savetest 的体 ends 0xdb85，越过包尾。那个工具这一轮值得第二次用。

三、fs_delete 第一次插在了 exec 内部 —— 一个全局标签出现在 .op_list 之前，于是它后面
    所有 .op_* 都变成了它的局部标签，nasm 报 exec.op_index 未定义。挪到 fs_write_file
    之前就好了。exec 的内部标签不能从中间插一个全局标签进去。

四、包涨到 1083 字节（三扇区），于是数据区后移、预读窗口从 28 涨到 30。这一条是 build
    自己说的，不是猜的。

而最后那个红，红的不是 remove：是写盘（存成）。串口里 save survived docs/inner.txt
1058 6 出现在第一趟，说明第一趟 run_save_test 走的是「第二趟」那个分支 —— 也就是说
第一趟启动时盘上已经有 docs/inner.txt。这一条没有查清，而它是下一轮的第一个问题：
若第一趟的盘不干净，那么「save 只落过一次」这个前提就不成立，而那会影响别的判据。

下一轮的第一件事：先确认第一趟的盘上有没有 inner.txt。build 从 disk.img 生成 vdi，
而 disk.img 应当是干净的 —— 所以要么 build 没有重建 vdi，要么上一趟的 vdi 被复用了。
那是一个可以在主机上查清的问题（读 vdi 的 1027 扇区），不必花一次两分钟的运行。
=== 删除第二次：它能工作，而它把盘写坏了 ===

remove 这一轮做到了：串口里 prog remove -> 23，也就是 docs 里少掉 inner.txt 之后剩下的
那三个名字。判据的数第一版写成 24，而 8+1+3+1+9+1 就是 23 —— 红的那一趟会去查固件，
而固件是对的，所以那个错本身也是一条：判据里的数要能自己算一遍。

但同一次运行的第二趟坏了：

    第二趟：boot ok / stage2 ok / seed ok 38072 / mailbox ok / pro（断在这里）

38072 是第二段里 seed_bytes 那一格，它应当是 40。也就是说第二趟读到的 stage2 不是 build
写的那一份 —— 盘上 LBA 9..138 被改过。而第一趟自己的 seed ok 是 40，所以写坏发生在
第一趟运行期间。

三处已经修好、而且是真的：

一、fs_delete 那个全局标签原先插在 exec 内部，把它后面所有 .op_* 变成自己的局部标签。
二、op_remove 拼父路径用的是 rsi，而 fs_load 会把它改成算出来的地址（第六次寄存器对）。
三、fs_delete 比较名字时多跳了两个字节 —— r12 是没有长度前缀的裸串，而数长度那一处
    已经按这个约定改了，比较那一处还留着 +2。这一个是靠四个诊断数收进来的：
    返回 0、页 1027、首码元 1053（也就是 'i'）、数出来的长度 9。

而这第四个症状没有解释：只有 ata_write 能写到预读区之外，而它的三个调用点是 persist
（60000）与 save 的两页（目录页与数据页）。save 的数据扇区在第一趟里约 1053..1086，
目录页是 1025 与 1026 —— 没有一处靠近 9..138。

所以下一轮的第一件事是：在第一趟结束之后读盘上的 LBA 9 与 138，看它们是不是真的变了。
那可以在主机上做（把 vdi 转成 raw），不必先跑虚拟机。若它们没变，那么问题在「第二趟
读的是别处」，而不是「有人写了那里」。

这一段因此回滚了：代码与判据都撤掉，因为一条把盘写坏的胜利不算胜利。
=== 两趟读到同一份 stage2：一条有真实红的判据，与一个没解释的数 ===

上一轮 remove 那一趟，第二趟死在「没有 persist survived」这一句话上，而串口只多给了一行：
seed ok 38072，而占位种子是四十字节。那与「第二趟根本没起来」在串口上长得一样，而两者的
修法完全不同。所以加了一条：两趟的种子字节数必须相同。

它不是想出来的判据 —— 那个错先发生，然后才有它。所以它的红有据可查：上一轮的串口就是
40 与 38072 这一对。

而查它的时候撞见另一件事，没有解释：

    两趟现在都报 seed ok 4218691752。

盘上是对的：LBA 138 偏移 296 处是 40，而那是第二段偏移 66344（seed_bytes 那一格）。
而 loader 的第三批从 LBA 137 读 512 字节到 0x20000，所以 LBA 138 的偏移 296 落在 0x20328。
而实模式那一段从头到尾 ds 都是 0x1000，所以 [seed_bytes] 这个绝对地址 0x10328 指的正是
0x20328。三件事都指向「读对了」。

而串口给的是 4218691752，也就是 0xFB7C0008。

所以上面那三件事里有一件是假的，而我没有查出来。记在这里而不是补一个听起来合理的解释：
那种解释会让下一轮从错的地方开始。

下一轮最便宜的一步：把 put_num 与那条 mov eax, [seed_bytes] 的机器码从 stage2.lst 里
抄出来对一遍。那不必跑虚拟机 —— 若 lst 里那条指令的地址不是 0x10328，那么「ds 0x1000
所以它指 0x20328」这句话就已经不成立了，而 4218691752 也就不用再解释。

顺带记一个教训：seed ok 的数一直被我当成「种子读到了」的标志，而现在它连自己的数都报
不准。一条判据的读数里，那个数字与那句话是两个断言 —— 这一轮之前只验了前者。

=== 真种子接管：七万四千字节一直在本机，而判据侧一个字没改 ===

种子族那九项（函数、操作码、求值、跳转、调用、按名、数字、求值活、曲线）长期以
「跳过」的样子存在。理由写在 run.mjs 里：它们的前提是种子里有 letters 这个函数，
而四十字节的占位包只有 main。跳过是诚实的 —— 它明说自己没验 —— 于是它一直没被当成
待办，直到有人问「为什么 Yunooka 里没有真东西可跑」。

答案是那份东西一直在本机：上游语言仓库的构建产物，74594 字节、版本 1、
202 个函数，与占位包只差规模不差格式。头五个字节同样是 HMYRB。所以这一段的动作只有
一次复制，加一条 build 的 --seed。

换上之后串口给的是：seed ok 74594、seed v1 202、种子里有 letters 那九族照验。九项
一次全过 —— 求值 2 units -> 512、除法 div -> 1.570796、数学 sum -> 262.488320 与
average -> 29.165369、表达式 f x -> has x、曲线 f(0) 与 f(160) 都在 2F。第二次启动
报的是同一个数：74594 / 74594。

值得单独记的是判据侧一个字没改。守卫写的是「串口里有没有 fn letters」而不是「有没有
种子」—— 当初选这个形状是为了不误伤占位包，而副作用是它把「前提不成立」写成了一句
看得见的话。前提一成立，那九项自己就上岗了。一个跳过要是写清了前提，它就不需要有人
记得回来改它。

顺带查出两处注释错，都是那次「种子从 0x20000 搬到 0x70000」留下的：

一、stage2 里第三批种子读的注释还写着「目标是 0x30000、18 个扇区铺到 0x32400、
主体上限 0x30000」。那是旧布局的账，而 seg 从 0x2000 改成了 0x7000，数字没跟着算。
它读起来仍然自洽（0x32400 与 146 个扇区对得上），三段地址却全错。真正的三个地址是
0x70000 / 0x78000 / 0x80000，铺到 0x82400。

二、loader 开头的注释说「上限 0x20000，种子在那里」，而同一个文件第六十六行的注释
已经在说「种子搬到 0x70000 之后这里能一直往上数」。同一个文件里两条注释互相矛盾，
而它们都在同一个提交里。

两处都不影响运行 —— 注释不进 .bin。而这正是它们的危险：一个自洽的错注释不会让人去核，
它只在下一个改这里的人身上收钱。这与「过时的注释比没有注释更坏」是同一条，只是这次的
过时来自一次全局替换：0x20000 改成 0x70000 的时候，命中了代码里的 0x200000（页表那
个 2 MB 步长，为此红过一次），而注释里的派生数字（0x32400）既不在替换表里，也没人重算。

一条可带走的：地址搬完要重新算一遍注释里的派生数，不能只跟着替换 —— 替换只改它认得的
那一个字面量。

=== hmgk 的头：认出只要四个字节，读懂要走完整个头 ===

identify 的第十六格答 hmgk，而那一格只用头四个字节。所以「认得出」与「读得懂」是两件
事，这一段补的是后一件：run_hmgk_test 按 design/HMGK.txt 的偏移把版本、BPM、结构段
字节数、pattern 数读出来，打成

    Yunooka: hmgk v1 bpm 120500 struct 40 pattern 3

判据要求四个数与样本里写死的一致。

判据侧的形状：三个数（BPM 120500、结构段 40、pattern 3）都不是「恰好非零」能凑出来的。
尤其 120500 —— 它放在偏移 28，四个字节的小端整数。魔数对了之后随便挑一个偏移去读，
得到的会是一个小于四位的数，或者两个相邻 u16 拼起来的东西，凑不出 120500。

验红的办法与它证明的东西：把 BPM 的偏移从 28 改成 24，读出来是 327682，判据点名不符、
退出码一。327682 这个数值得单独看一眼 —— 它是 2 加 5 乘 65536，而偏移 24 上正是 track
（2）与 loop（5）两个 u16。所以那个红不只是「值不对」，它还顺带把「这两个字段在偏移
24、26」这句话验了一遍：错位一格读到的两个字段拼成了预期之外的一个数，位置关系因此
不是被声明的，是被测出来的。

改回 28 就又绿了。一红一绿两步都在这一轮里走过，所以这一格不是「建起来就绿」的那一种。

代价：第二段从 130 个扇区到 131，余量从六十二格到六十一格。新的上限仍是 192，而种子的
落点跟着从第 139 个扇区到第 140 —— build 的三处交叉核对把这一串一起核了，所以搬动它们不会各自跑偏。

还没做的那一件留在 design/HMGK.txt 末尾：嵌入形态。魔数在偏移 0 这个假设在「嵌进任意
可执行文件」之后不成立，而那一天要先有一条判据（一个 PE 头后面跟着一份 hmgk，该报出
两样东西）。

=== hmgk 的第三种活法：魔数不在偏移 0 ===

前两格（认出、读懂头）都建立在「魔数在偏移 0」这个前提上。而用户给的规范里有一句
「它可以被嵌进任意可执行文件」，那句话把这个前提打破了：一份 hmgk 进了别的程序之后，
它的魔数可能在第 200 个字节，也可能在第 200000 个。

所以加的是一段扫描：scan_magic 在 [起点, 起点 + 长度) 里找四字节魔数，返回偏移或负一。
上界写成长度减四 —— 最后一个合法起点要能读满四个字节，否则会读出边界外，而在实地址
空间里读边界外通常不会报错，只会给出一个巧合相等的值。

判据只写一样东西不够。判据的形状是「两样」：样本是一条 PE 头加一份落在偏移 256 的
hmgk，所以那一行要答 pe（外面那层被认出来了）并且给出 256（里面那份被扫出来了）。只答
pe 的实现根本不知道里面有东西；只答 hmgk 的实现把外面那层漏了。两样都要，是因为这两种
错在串口上长得不一样，而判据要能分开报。

这一格见红的办法与前两格不同：把样本里的落点从 256 挪到 200，判据不动。那一行于是报
「在偏移 200」，判据点名「应当 256」，退出码一。这个红证明的是偏移真的被扫出来 —— 若
实现里写着一个常量 256，挪样本之后它仍会报 256，红不起来。

三种红至此凑齐，而它们的意义各不相同：
  错值（BPM 读出 327682）—— 判据在读那个数，而不是在读某个恰好非零的东西。
  错位（落在 200 而不是 256）—— 偏移是被测出来的，不是被声明的。
  格式不匹配（少一个空格，报「没扫到」）—— 判据按写下的形状在匹配，而不是模糊地找子串。

第三种红是这一轮唯一一次「先红后绿」的意外：put_ident_kind 打的名字后面已经有一个空格，
而内层那段文字又以空格开头，于是串口上是 "pe  hmgk"，而判据写的是单空格。修的是固件
（去掉那个前导空格），不是判据 —— 判据先写下了形状，固件去对上它。这条与 STATUS 里
第八条记的是同一件事：形状一旦写下来，对不上的那一侧就该改。

代价：第二段从 131 个扇区到 132，余量从六十一格到六十格，种子从第 141 个扇区起。

=== 屏幕上的第一个字母，以及「擦」不能用「画」来实现 ===

到这一格之前，屏幕上有过像素、线、框、矩形与整窗，而从没出现过一个字母。而窗口那一层
若不能写字就不算窗口 —— 一份界面最先要能说人话。所以加了 8x8 单色位图：帧缓冲是
320x200、每像素一字节的调色板索引，一个字符于是就是「六十四次写或不写」。每行一字节、
最高位在左边，比存六十四个字省八倍，而「第几行第几列」这个关系在移位里是明摆着的 ——
左移 r11 位之后原来第 (7-列) 位就到了最高位。

判据是四个点，不是四个点随便挑的：把 H 铺在 (100,60)，读左上、右上、中间、第四行左端。
前两个与该亮（两竖），第三个该暗（两竖之间），第四个该亮（中间那一横）。一个把最高位
当成最右位的实现写出来的是镜像字，而镜像字在一个左右对称的字模上看不出来 —— 所以真正
分开方向的是「两端各读一次」这个形状，不是点的个数。

这一格红过两次，两次都值得记。

第一次是这整段唯一一次真正的设计错：抹背景用的是「画一份全零的位图」。而位图里的 0 表示
「这个像素不写」—— 全零位图画完什么也没发生，于是「该暗」那一点读到了前面测试留在屏幕
上的 0x0F。这不是算错，是把两件事混成了一件：「不写」与「写成背景色」。位图表达的是
前者，而擦需要后者。修法是单独写一段 clear_block，把 64 个像素真的写成给定颜色。
症状的形状也值得记 —— 它没有报「什么都没画」，它报的是「第三个点读到 0F」；如果没有
那第四个点、只读一个「该亮」的点，这个错会让判据一直绿着，而屏幕上那块地方是脏的。

第二次是主动验红：把字模第一行改成 0x00，四个点变成 00 00 00 2F。第四点仍是 2F 是因为
它读的是第 4 行（那一行是 0xFF，没动），于是这个红同时说明四件事：前两个点各读第一行的
最左与最右、第三个点读两竖之间、第四个点读的是另一行。四个点分别落在四个不同的位置，
这一点是被测出来的。

代价：第二段从 132 个扇区到 133，余量五十九格，种子从第 142 个扇区起。判据 82 到 83。

=== 一行字：字距这个数，只有两个字并排时才被问到 ===

一个字到一行字，中间隔的是「字模成表」与「字距」两件事。字模 0 到 9 做成连续表，于是
draw_text 里「字符减 0x30、乘八、加到表头」就是全部的位置计算。字距八像素 —— 与字模
宽度相同，所以相邻两个字之间没有空隙；加空隙是排版的事，等有排版再说。

判据写「01」，读五个点。前三点验字模（0 的左上角该暗、顶边该亮、左竖该亮），后两点
验字距。而验字距这两点必须成对，这是这一格唯一的难点：

  1 的顶边是 0x18，两个连续亮位。只读 111（字距为八时它落在 1 顶边的右边那个亮位上）
  的话，把字距改成七，同一个像素就落到左边那个亮位上 —— 读出来还是 2F，判据照样绿。

第一版就是只读了 111。验红时才发现它不变，于是老实地承认：那一个点只能测出「字距偏大」，
测不出「偏小」。加上 110（字距为八时它落在 1 顶边左边的空位上）之后，偏小会让它变亮、
偏大会让 111 变暗，两个方向才都被问到。

这个形状值得记住：一个字模里连续两个亮位，就把「位置偏一格」这件事盖住了一半。要让一个
判据对「偏移」敏感，读的必须是边界上的像素 —— 亮位与空位的交界，而不是亮的中间。

顺带发现的一件事，与字无关而与流程有关：这一轮有一次没 build 就直接跑了 run，于是盘上
带着上一次第二趟存下的 docs/inner.txt，run_save_test 走了「第二趟」那个分支、打了
save survived 而不是 save，而「包写文件」那条判据因此报红 —— 报的是「要么包没读回那行
字，要么目录里查不到 out.txt」，一个看起来像缺陷的红。

而它是脏盘。run 会写盘，而 build 的镜像是唯一干净的起点；两趟启动之间共用同一块盘是
有意的（第二趟要验持久化），两次 run 之间共用则不是。所以「先 build 再 run」不是一个
习惯问题，它是判据的前提。记在这里，因为下一个红在写盘那一条上出现时，先问的应当是
「这一趟的盘是新的吗」，而不是去读 run_save_test。

代价：第二段从 133 个扇区到 134，余量五十八格，种子从第 143 个扇区起。判据 83 到 84。

=== 一帧的起点：清屏，以及一个白读的判据点 ===

屏幕上有过像素、线、框、矩形、整窗、一个字母、一行字，而「把它们擦掉」从来没有过。
没有清屏就没有一帧 —— 两次画的东西叠在一起，谁也分不开谁是谁。

clear_screen 把六万四千个字节（320 x 200）写成给定颜色。不用 rep stosb 的理由写在代码
里：它要三个寄存器同时就位，而小段上的启动开销随处理器不同；这一版要的是「一定能跑、
数得清」。

判据先画一个 H 在 (10,10)，把整屏写成 05，再读四个点：(10,10)、(17,10)、(10,11)、
(0,0)。前三落在画过、而且本来亮的位置上，第四个从没画过。四个都该是 05。

而这一格的验红带出一条比清屏本身更值得记的东西。第一次把清屏范围从六万四缩到三百二十
（只清第一行），红出来的串口是 2F 00 2F 05 —— 第二个点是 00。第二个点当时读的是
(11,10)，那是 H 顶边 0x81 的中间六个零之一：它本来就该是 0。也就是说，那个点无论清屏
做没做都读 0，它一点也没在测。

判据照样红了（另外三个点报了），但那是运气。一个白读的点会一直在那里，而它一旦成为
唯一读「正常值」的那个，整条判据就会在真问题面前保持绿色 —— 更糟的是它看起来像被验过
的，因为同一个函数里别的点确实报过红。改成 (17,10)（顶边右端，本该是 2F）之后再验红，
四个点变成 2F 2F 2F 05，三个都在说「没清」。

一条可带走的：判据点要落在「本该非零」的地方。读一个本来为 0 的位置，绿色的含义只是
「它还是 0」，而红的含义根本不成立 —— 因为那里没有东西可以被清掉。

判据 84 到 85。第二段仍是 134 个扇区，因为这一格的代码是从注释里省出空间的。

=== 大写字母：两张表，与一个错一格的验红 ===

数字之后是字母。font_letters 收二十六个大写字母，行 0 到 6 是字形、行 7 留空 ——
所以字与字之间竖直方向有一行空隙，水平方向没有（字距就是字宽）。

为什么不与 digit 合成一张从 0x30 到 0x5A 的连续表：合成的话中间那七个标点（: ; < = > ? @）
要占位置填空白，而空白字模在判据里与「这个字符不存在」长得一样。两张表各有入口，多一个
分支换掉七格假数据。

判据写「HO」。挑这两个字母是因为它们顶边形状不同：H 是 0x66（亮位在中间偏两端），O 是
0x3C（亮位在正中）。四个点都落在亮位与空位的交界上，而不是亮的中间 —— 这是上一轮学到的
形状：读亮的中间，位置偏一格仍会读到亮；读交界，偏一格就翻面。

期望 00 2F 00 2F。验红把字母表基址从 'A' 错到 'B'，于是 H 的位置画出来的是 G，而 G 的
顶边是 0x3C：它的 bit6 是空的，第二点从 2F 变 0，串口给出 00 00 00 2F，判据红、退出码一。
这个红说明的事比「值不对」多一点：四点一起落到别的字上，而那个字在这一位恰好是空的 ——
基址错一格是整表平移，不是单个字模坏掉，而平移在这四个点上留下的痕迹就是这个。

顺带记一句 font_H 与表里的 H 不同，那是有意的：font_H 是单字铺绘那一格的样本，验的是
「把八字节位图铺到屏幕上」这个机制；表里的 H 是字体的一部分。

判据 85 到 86。第二段从 134 到 135 个扇区，余量五十七格，种子从第 144 个扇区起。

=== 多行：换行交给谁，以及一个专门测行距的点 ===

draw_text 的入参只有一个 x —— 它不知道「下一行从哪里重新起头」，那是调用者的事。所以
这一格把它拆成两层：draw_one 画一个字符（x、y、字符、颜色），draw_lines 管换行与行距。
拆分不是为了好看：多行文本必须按字符画，因为换行处要在中途重新起头，而「把一行串从头
画到尾」做不到这一点。

行距十像素（字高八，空两行）。换行字符是 0x0A。

判据写「H 换行 0」，读四个点：H 顶边最左列（该暗）与它右邻（该亮）、第二行 0 顶边的
中段（该亮）、以及第二行那个 0 的最后一行（行 7 也是 0x3C，该亮）。期望 00 2F 2F 2F。

第四点是这一格里唯一测得出行距的点，而它的理由要看位图：那个 0 的行 0 到行 6 分别是
0x3C 与 0x66，只有行 0 与行 7 是 0x3C 那种窄的形状。行距改成八时第二行落在 y=28，
y=37 已经在字的外面（28 + 8 = 36 是下一格的起点），读出来是 00。而第三点 (12,30) 在
两种行距下都亮 —— 十的时候它是行 0、八的时候它是行 2，而 0x3C 的 bit5 与 0x66 的 bit5
都是 1。

验红给出的就是这一对：00 2F 2F 00。第三点没动、第四点掉了，所以那个掉下来的位置确实
只与行距有关。

这条与前一格是同一条原则的第二次应用：一个判据点要落在「两种候选实现会有不同答案」的
地方。第八格的四个点里，前三个回答「换行有没有发生」，第四个回答「行距是几」—— 两个
问题两种答案，四点才不浪费。

顺带一处重构：draw_text 现在只剩一个循环调 draw_one，它自己的分派逻辑跟着搬了过去。
所以数字与字母两张表的入口现在只有一个地方在读。

判据 86 到 87。第二段从 135 到 136 个扇区，余量五十六格，种子从第 145 个扇区起。

=== 包第一次在屏幕上说话：内置 text ===

到这一格为止，屏幕上出现过的东西全是宿主画的 —— 坐标或者写死、或者由包指定，而画出来的
内容由宿主决定。这一条换了方向：串是包里的常量，宿主管的只是「把它铺到哪」。

固件侧三件：内置表加一项（名字 text、处理者 exec.op_text）、op_text 取三个参数（x、y、
串）、以及 draw_utf16。包里侧加第九个函数 textline，五条指令：两个坐标常量、一个串常量
OK、调内置 text、返回。

draw_one 的入参在这一格从 8 位字节放宽到 16 位码元。理由不是洁癖：包里的串是 UTF-16
（u16 长度 + 码元），而固件自己那几条测试用的是以 0 结尾的 8 位串。让绘制那一层吃码元，
两条路就共用同一份 —— 字符集、字距、未知字符的处理三样都只有一份，而这三样都已经有了
判据。若分成两份，下一次改字体就要改两处，而漏掉的那一处不会红。

判据读三个点：(40,120) 是 O 顶边最左列该暗，(42,120) 该亮，(50,120) 是 K 起点右边第二位
该亮。后两点在同一个 y 上、两个不同的字上，所以字距八也一并被问到 —— 若串被读成零长，
或者绘制时忘了推进 x，第三点会落到 O 的末尾而不是 K 上。

验红的办法是改包：把 textline 里的 x 从 40 挪到 44。三点于是全灭（O 到了 44、K 到了 52），
判据报 00 00 00。这个红证明的是「坐标来自包」—— 一个把坐标写死在宿主里的实现改包不会
有任何变化，而它照样能让判据绿。

路上踩到一个自检，值得记：build.mjs 里有一条计数式自检，它数源码里行首的
「程序包[位++] = 28;」出现次数，要求与包头声明的函数数相等（一个函数恰好一个返回字节）。
我新加的那一段在花括号里，于是那一行带了两格缩进，正则匹配不到 —— 自检报「写了 8 次而
声明了 9 个函数」。改的是缩进，不是自检：那条自检存在的理由正是「多一个或少一个返回字节
会让后面每个函数都找不到」，而它这次抓的是它自己该抓的东西。

判据 87 到 88。第二段从 136 到 137 个扇区，余量五十五格，种子从第 146 个扇区起。

=== 颜色：最后一处宿主替包决定的东西 ===

text 上一版把颜色固定成 0x2F，写的理由是「参数表已经三项」。那个理由站不住：位置与内容
都归包了，颜色没有理由留在宿主手里 —— 一个界面里深浅两种字是常态，不是特例。

所以参数从三项变四项（x、y、串、颜色），固件从栈顶往下读，第一个拿到的是最后压进去的
颜色。包里那个函数随之从五条指令变六条：三个常量（x、y、颜色）、一个串常量、调内置、
返回。

判据的期望值也跟着改：从 2F 变 1C。这个改动本身是判据的一部分 —— 只要与宿主曾经写死的
那个值不同，「这个像素是谁给的」就能从串口上分开。若沿用同一个值，一个仍然写死 0x2F 的
实现会与正确的实现一模一样，而那种绿是假的。

验红用了更硬的一手：把固件里那一行从 mov r8b, al 改回 mov r8b, 0x2F（也就是忽略包传来
的颜色）。串口给出 00 2F 2F，判据报「应当是 00 1C 1C」，退出码一。这一手比「改包里的
颜色」更硬，因为它动的正是宿主那一侧，而它证明的是宿主不能替包决定颜色 —— 改包只证明
判据在读那个值。

于是这两格合起来是同一件事的两半：包能决定画在哪（坐标）、也能决定画成什么样子（颜色）。
一个有坐标没颜色的界面只能有两种字 —— 正文与背景，而背景还得靠画矩形拼出来。

判据仍是 88 条：这一格改的是已有判据的期望值，不是加一条新的。第二段仍是 137 个扇区。

=== 包写一段话：换行，以及两种验红里更该学的那一种 ===

draw_utf16 认了 0x0A，行距十像素 —— 与 draw_lines 同一套约定。这不是抄一份，而是理由：
两条路最后都落到 draw_one，所以「一段话长什么样」不该因为串的来源不同而不同。若这里用
八像素、那里用十像素，同一个串从包里来与从固件里来会长得不一样，而那种差别没有任何人
需要。

状态量三个：rbx 是行首 x（换行时回到这里），r9 是当前 x，r10 是当前 y。用 rbx 而不另找
一个不参与传参的寄存器，是因为 draw_one 一路下去不碰它（draw_glyph 自己会保存 rbx）。

包里 textline 的串改成「O、换行、K」，判据读三个点：(42,120)、(42,130)、(42,140)，
期望 1C 1C 00。第二点验换行真的发生了，第三点验没有多出一行 —— 后者防的是「每行都在
同一个 y 上累加」这种错法，它与正确的实现只在第三行上分得开。

验红在这一次分成了两步，而第一步是错的，值得完整记：

  第一步把 je .newline 改写成 je .loop。想的是「跳过换行、继续画下一格」，而实际效果是
  跳回循环顶 —— 那里既没有推进 r11 也没有减 ecx，码元还是 0x0A，于是永远跳回去。串口上
  那一行变成「(没跑到)」，而诊断列出一长串没通过的项（异常、尺、写盘、目录列、目录满、
  隔壁目录、删除、myon写、桥接、字、字串、上、行、包字）。一次死循环把一个格子的问题
  扩散成十三个格子的红。

  第二步改成「把那两行判断整个删掉」，也就是让 0x0A 走未知字符那条路 —— 那才是「换行
  没有实现」该有的样子。串口给出 1C 00 00：K 被画到 40 + 8 = 48 上，落回第一行。
  诊断只有一项。

两种红都在说同一件事，但价值差得远：后一种把故障定在一个判据上，前一种把整个后半段拖
下水。而前一种的错法很普通 —— 「跳过这个字符」与「在循环里跳过这个字符」差着的就是那
两个推进语句，而少写它们不会编译报错，只会让程序原地转。

所以下次要验「某个分支不存在时会怎样」，最省的办法是把分支的判断删掉，让它走默认路径；
不要改写成「跳到别处」，因为跳转的目标在那条路径上没被设计过。

判据仍是 88 条（这一格改的是期望值）。第二段仍是 137 个扇区。

=== 小写折成大写：折在绘制层，而不是每个调用者手里 ===

字体只有大写 26 个。而进来的串可能带小写 —— 紧接下一格要做的输入回显就是这样：信箱里
那一行是 echo hello world，全小写。

三种做法：给字体加 26 个小写（多二百多字节，而这一版只为了一处用途）；让每个调用者自己
转（每处都要记得，漏掉的那处只画出一片空白、不报错）；在绘制层折（一处，且它的位置
正确 —— 一个只有大写的字体把 a 画成 A，是字体该做的决定）。

选了第三种：draw_one 在查表之前，码元落在 a 到 z 就减 0x20。

判据写 "ab"，读三个点：(10,40) 是 A 顶边最左列该暗、(13,40) 是 A 顶边的 bit4 该亮、
(19,40) 是第二个字符（b 折成 B）顶边的 bit6 该亮。后两点各自守着一个小写字母，而它们
之间隔着八像素 —— 字距也顺带被问到。

验红删掉 sub ax, 0x20 那一行：两个小写字母于是通不过后面那条大写检查、走未知字符的路，
三个点全 0，判据红、退出码一，诊断只列一项。

这一格本身很小，但它的位置在链条上很关键：它是输入回显的前一步。回显要画的那一行是
哪里来的、内容是什么形状，只有查清之后才知道「先得有折叠」—— 而这一步查的是 run.mjs
里信格那一段：内容是 "echo hello world"，ASCII 字节，一行一个换行。

判据 88 到 89。第二段仍是 137 个扇区（折叠是三行代码）。

=== 输入回显：宿主递进来的那一行出现在屏幕上 ===

上一格画的是包里的常量；这一格画的是运行时从外面进来的东西。这是「界面对话」的前一半
—— 一个只能显示自己写死内容的界面，与一块牌子没有区别。

链条很短，因为两头都已经有了：包里加第十个函数 echo2text（六条指令：两个坐标常量、调
内置 readline、一个颜色常量、调内置 text、返回），固件一个字没改。压栈顺序有讲究 ——
readline 必须在颜色之前，因为固件从栈顶往下读，而 text 要的顺序是 x、y、串、颜色。

那一行来自信箱盘：内容 "echo hello world"，ASCII 字节，一行一个换行。全小写，而字体只有
大写 —— 所以这一条同时验着上一格做的折叠：折叠若没有，屏幕上是空白，而 readline 那边
一切正常。

判据读三个点：(40,150) 是 E 顶边最左列该暗、(41,150) 是它右边一位该亮、(129,150) 是
第十一个字符（w 折成 W）顶边的 bit6 该亮。第三点离起点八十八像素 —— 只读开头两点的话，
一个画完第一个字就停的实现照样能过，而那种实现在屏幕上看起来像「只显示了一个字母」，
很难说清是哪里错。

验红把包里那次 readline 换成一份常量串 AAAAAAAAAAAA：三个点全 0，判据红、退出码一、
诊断一项。A 的顶边是 0x18，比 E 的 0x7E 窄得多，所以它在那三格上都读不到东西 —— 这也
说明判据选的三个位置不是「随便什么字母都亮」的位置。

路上踩到一个很普通的错，值得记：包里那个函数名，我照抄了 textline 那一行的名字长度 8，
而 echo2text 是九个码元。于是包头里写的是长度 8，而 find_fn_by_name 按长度 9 去找，
永远找不到 —— 串口只留一行 "Yunooka: progecho missing"，没有别的线索。一个长度字段与
它描述的串不一致，症状是「这个名字不存在」，而不是「长度写错了」。

判据 89 到 90。第二段从 137 到 138 个扇区，余量五十四格，种子从第 147 个扇区起。

=== 带标题的窗口：包里的函数与内置长得一样，但走的是两条路 ===

win 画三层矩形（底色 0x1F、标题栏 0x1C、内容区 0x0F），text 写字。把这两样合起来，屏幕上
第一次出现一个「窗口」而不是一块画布 —— 一个框加上它自己说的话。

包里第十一个函数 titlewin，七条指令：调 win、两个坐标常量（70、84）、一个串常量
（MYON）、一个颜色常量（0x0F）、调 text、返回。标题的 y 是 84：标题栏从 81 到 92，字高八，
所以 84 到 91 都在栏内，上下各留三像素。

判据读三个点：(70,84) 是 M 顶边最左列，0x63 的 bit7 是 0，那里该露出标题栏底色 0x1C；
(71,84) 是它右边一位，该是字色 0x0F；(80,84) 是第二个字符 Y 的 bit5，也该是 0x0F。第一点
与后两点是同一件事的两面：字画上去了，而它周围的底色没被吃掉 —— 只读后两点的话，一个把
整条标题栏刷成字色的实现照样能过。

这一格的红不是「值不对」，而是一个概念错，值得完整记：

  第一版把 win 当成内置调了（opcode 3）。而 win 是包里自己的一个函数 —— 它在包头的函数表
  里，要用 opcode 4 调用。串口上留下的是两行：「unknown builtin」，与「exec ran out at 0 7」。
  那个 0 是 pc，7 是这条函数的指令数 —— pc 停在 0 说明它在第一条就退出了，而窗口因此
  没有画、标题也没有画，判据读到 1C 1C 1C（屏幕上原本就有的东西，与这一格无关）。

  「包里的函数」与「宿主的内置」在字节码里长得几乎一样：都是一段名字（u16 长度 + 码元）
  加一个 u16 参数个数。差别只有一个字节 —— 指令码 3 还是 4。而那一字节写错之后的症状是
  「这个名字不存在」，不是「你调错了对象」。

验红用了另一个方向：把标题的 y 从 84 挪到 96（内容区）。三点于是全变 1C —— 因为字挪走了，
84 那一行只剩标题栏底色。这证明第一点确实在测「底色与字的关系」，而不是在测某个恰好为 1C
的位置。

判据 90 到 91。第二段从 138 到 139 个扇区，余量五十三格，种子从第 148 个扇区起。

=== 裁剪：左闭右开的一条界线，以及为什么只裁文字 ===

上一格把窗口与文字合起来了，但内容会溢出去：画到窗口外的字照画不误，两个窗口挨着就互相
脏。这一格补的是那条界线。

内置 clip 设一个矩形（四参：x0、y0、x1、y1），左闭右开 —— x 落在 [x0, x1) 才算在里面。
右开是为了让相邻两块窗口共用一条边而不重叠：前一块的 x1 就是后一块的 x0，一个点只会属于
一边。四参全零表示关闭，因为那个矩形本身没有意义（宽高都是零），不会有人真想用它，于是
省掉一个 unclip 的名字。

draw_glyph 在写像素之前比一次。裁剪关着的时候这一段的代价只是两条 cmp，而它挡住的是
「一个窗口的字画到隔壁窗口身上」—— 那种错在屏幕上看得出，在串口上看不出。

只裁文字。矩形与线不裁，因为它们现有的判据都画在窗口里面；而「需要被裁的矩形」要到拖动
窗口那天才出现，那时再给它们同样的检查，位置写在 op_clip 的注释里。

包里第十二个函数 clipped：设 (60,80)-(260,170)，在 (240,84) 写 LONG，再关掉裁剪。四个
字符占 240 到 271，越过右边界的部分该消失。

判据读两个点：(241,84) 是 L 顶边的 bit6，该是字色 0x0F；(261,84) 是 N 顶边的 bit2。
第二点前面先被固件写成 0x05 —— 只有这样「没被覆盖」才是有内容的断言：屏幕那一格本来是
零，而零与「裁掉了」在串口上分不开。这是第五格（清屏那个白读的点）之后第二次用到同一条
原则：判据点要落在「本来有东西」的位置上。

验红让 op_clip 里那个 clip_on 永远为 0。越界那一格于是被涂成 0F，判据报 0F 0F、退出码一。

这一格连带修了两件事，都不是逻辑错而是账要跟着动：

  一、程序包从 1083 字节涨到 1543 字节（三个扇区变四个），把盘上最后一份文件推到第 1055
     号，而预读只盖到 1053。build 的自检先报出来：「预读只盖 30 个扇区，而盘上最后一份
     文件在第 1055 号」。改成 32 就好 —— 而这条自检存在的理由，正是这三种症状（认成
     unknown、清单项数是零、读到的是零）看起来都像别的东西。

  二、cvttsd2si 的第二操作数必须是 xmm 寄存器，不能直接给通用寄存器。第一版写成
     cvttsd2si rax, rdx，nasm 报四处 invalid combination of opcode and operands。改成先
     movq xmm0, rdx 再转换。

判据 91 到 92。第二段从 139 到 140 个扇区，余量五十二格，种子从第 149 个扇区起。
预读区 α 与 β 各从 30 到 32 个扇区。

=== 窗口里的第三个内容来源：磁盘上的文件 ===

到上一格为止，窗口里的字有两个来源 —— 包里的常量，与宿主递进来的一行。这一格是第三个：
磁盘上的文件。三个来源合起来，一个文本查看器的形状就齐了。

而这一格只加包，固件一个字没改。理由是上下两头早就接好了：slurp 返回的串形状是「u16
长度 + 码元」，正是 draw_utf16 吃的那一种；而 text 那个内置已经把 draw_utf16 接在后面。
所以「能显示文件」这件事在上一格就已具备，只差有人连起来。

连起来的那一句是压栈顺序：x、y、路径三个常量先压，slurp 的返回值直接压在它们上面，再压
颜色 —— 栈上依次就是 x、y、串、颜色，而 text 从栈顶往下读正好是这个顺序的倒序。中间不
需要任何暂存寄存器，因为「函数返回值压在自己那一步的栈顶上」这条规矩让三层调用能直接串。

包里第十三个函数 showfile，七条指令。坐标 (70,100) 落在窗口的内容区里（内容区从 (61,94)
起、198 宽 75 高）。颜色用 0x2F 而不是内容区的 0x0F —— 同色的话字画上去也看不见，而那
在屏幕上看起来像「什么都没画」。

判据读三个点：(70,100) 是 Y 顶边最左列，该露出内容区底色 0x0F；(72,100) 是 bit5，该是
字色 0x2F；(80,100) 是第二个字符（u 折成 U）顶边的 bit5，从 70 + 8 = 78 起、78 + 2 = 80，
也该是 0x2F。后两点隔着八像素 —— 「一个字」与「一整行」在这里分得开。

验红把路径指向 docs/nosuch.txt。slurp 读不到时交一个空串（而不是「空」），于是屏幕上只
剩底色，三点全变 0F，判据红、退出码一、诊断一项。那个「交空串而不是空」的选择在这一格
显出好处：包不需要为「文件不存在」写一条分支，它照常调用 text，画出来就是没有。

顺带两件账要跟着动：程序包从 1543 涨到 1653 字节，所以 Buffer.alloc 从 1600 放到 2048
（否则 writeUInt16LE 抛 ERR_OUT_OF_RANGE，而那个错来自 node 而不是来自这一格）；第二段
从 140 到 141 个扇区，余量五十一格，种子从第 150 个扇区起。

判据 92 到 93。

=== 写槽：包里第一次能改自己的状态，以及加一条 opcode 其实要改三处 ===

在 opcode 34 之前，包里的所有函数都是「读参数、算、返回」—— 一个计数器都写不出来，也就
一个循环都写不出来。所以这一条比它看起来重要：它是「包能有状态」与「包只能算一次」之间
的分界。

实现与 .op_get 共用同一段地址算术（帧基址加槽号），所以「写」与「读」看到的一定是同一个
格子 —— 那正是这一格要验的东西。写槽从运算栈弹一个值，读槽压一个值，两者之间没有任何
缓存。

两处选号上的教训，都是踩出来的。

一、不要占 HMYR 那 34 条里已有的号。第一版把写槽放在 17，理由是「17 现在空着」。而 17
    在 HMYR 的表里是另一个指令、形状也不同 —— 种子是 HMYR 产的，里面就有 17，于是形状表
    一改，种子族的解析全错：写槽那一项自己绿着，而种子族那九项一起红。追加在末尾、旧号
    不动，是 design/INSTR-MAP.txt 写下过的纪律，而它这次是被违反之后才想起来的。

二、加一条 opcode 其实要改三处，不是两处：
    形状表（imm_shape）加一项；
    分派链（exec 的 .loop）加两行；
    scan_instrs 里那个硬上限 —— 它写着 cmp eax, 34 才把新号放进来。
    第三处最贵：漏掉它不报编译错，只是扫描提前停下，而 instr_offsets 里剩下的那几格是
    上一个函数留下的旧偏移，于是这个函数跑到别人的代码上去。串口上看到的是
    「exec ran out at 4 4」与一个 kind=0 的返回值 —— 两条都不指向真正的原因。

包里第十四个函数 slotwrite，四条指令：常量 42、写槽 1、读槽 1、返回。它短得几乎不像
一课，而那是刻意的：这一条验的是「写与读看到同一个格子」，掺进循环或条件就分不清是哪一环
坏的。槽 1 而不是槽 0，是为了顺手把「槽号从 0 数」这个约定也钉住。

判据的力气在分辨力上：若写槽是空操作，读槽读到的是一格初始值「空」而不是数字 42，于是
返回的东西种类变了。验红删掉写回那两行，串口给出 progset 后面跟着 kind=0 —— 判据红、
退出码一、诊断一项。

判据 93 到 94。第二段仍是 141 个扇区（这一条的实现不到二十行）。

=== 包里第一次转起来：二十六条指令，没有改一行固件 ===

上一格给了包「写槽」，这一格把那件事用起来。二十六条指令，形状是任何一门语言的第一个
循环：

    槽 0 数次数、槽 1 记当前的 x
    i = 0、x = 40
  顶: i >= 3 ? 是就跳出去
    画一个 8x8 的方块在 (x, 170)
    x = x + 20
    i = i + 1
    跳回顶
    返回 i

三样零件都已在：写槽（34）、真跳（16）、大等（9）。所以这一格没有改一行固件 —— 它是
前面几格攒出来的第一件「程序」，而不是又一条指令。这一条值得单独说：前面十几格都是
「加一条指令、加一个内置」，而这一格是那些零件第一次一起工作。

没有乘法：x 用槽累加而不是 i 乘二十。这一版的算术只有加、除、等与大等四条，而加乘是为了
一个能被累加替代的算式。

判据读四个点：三个方块的中心该是 0x2F，第四个方块本该在的位置该是零。返回值与第三个方块
是两条独立的证据 —— 一个说循环转了三轮，一个说三轮都画了。

验红带出一条比循环本身更值得记的东西。把上限从三改成二之后，串口给出「计数 2」与
「2F 2F 28 00」—— 第三点是 0x28，而不是零。那个 28 是屏幕上原本就有的东西：第三个方块
没被画，于是底下的旧像素露了出来。

它这次红了，因为 0x28 不是 0x2F。但若那格底下恰好是 0x2F，一个「只画了两个方块」的实现
会与正确的实现一模一样。也就是说，那三个判据点当时验的是「方块盖住了那格」，而不是
「方块画在了那格」—— 两者在干净背景上是同一件事，在脏背景上不是。

所以那一格现在先把四格抹成零再跑。这是第五格（清屏那个白读的点）之后第三次用到同一条
原则：判据点要落在「本来有东西、且那个东西是这一格说了算」的位置上。第一次是白读的点，
第二次是裁剪那一格先写 05 打底，这一次是背景本身要归这一格管。

判据 94 到 95。第二段从 141 到 142 个扇区，余量五十格，种子从第 151 个扇区起。

=== 全局：比一次调用更长寿的那一格，以及两次 exec 才能验出来的差别 ===

槽随帧生死，全局不随。这个差别在同一个函数里看不出来 —— 槽也能写完再读，上一格已经证过。
所以这一格的判据必须跨两次 exec：先跑 globalset 把 7 写进第 3 号，再跑 globalget 把它读
回来。若「全局」其实落在了槽里，第二次读到的是空，因为那时已经是另一帧、另一次 exec 了。

两次之间不清扫，这是有意的：全局的意思正是「不清扫也还在」，而清扫一下再读，判据就变成
「它在清扫之后被留住」而不是「它跨调用活着」。

固件侧三样：一块十六格的两张表（种类与内容）、两条指令（35 取、36 存）、形状表加两项与
扫描上限抬到 36。第二段因此从 142 到 144 个扇区 —— 涨了两个，而这一格加的东西按行数算
不到四十行，多的那部分是那张表本身（十六格乘八字节乘两张）。

路上踩到一个自查就能避免的错，值得记：第一次 exec 之后，我按前几格的惯性把 pkg_base 拨回
0x70000（那是种子的地址，前几格用它当「默认值」恢复）。而这一次后面还有一次
find_fn_by_name —— 它于是在种子里找 globalget，报 missing。

那个 missing 与「全局没生效」毫无关系：一个实现如果全局是假的，第二次读到的是空；而这里
是根本没找到那个函数。两种红在串口上都只是一行，而修法完全不同。把 pkg_base 拨回去那个
动作在前几格是对的（每个测试用完要还原），在这一格是错的（同一个测试里还要再用它一次）。
惯性的代价就是这一处。

验红把全域存改成空操作：第二次读到空，判据报「没跑到」，退出码一，诊断一项。

判据 95 到 96。第二段 142 到 144 个扇区，余量四十八格，种子从第 153 个扇区起。

=== 拖动：同一个函数画在两个地方，位置是状态而不是常量 ===

全局有了之后，窗口位置就能跨调用活下来。这一格是那件事的第一个用处，也是这一条线上第一次
出现「同一个东西在两帧之间变化」。

包里三个函数分工，而它们各自要被单独调用一次：

    resetpos   把全局 5 设成 40、全局 6 设成 180
    mark       读全局 5、6，在那一点画一个 8x8 的方块
    right60    把全局 5 加六十

判据的形状就是「同一个 mark 画在两处」：resetpos + mark 之后读第一处，right60 + mark 之后
读第二处，两点都得 0x2F。若 mark 忽略全局、把坐标写死，第二次读到的是零 —— 验红正是这么
做的（把第一个全域取换成常量 40），串口给出 2F 00。

这就是「界面」与「一幅画」的分界：前者同一个东西在两帧之间会变，而变的是它的状态、不是
画它的那串指令。到这一格为止，包里第一次出现「改一个数就换一个样子」。

三次 find_fn_by_name 都在同一个包里，所以 pkg_base 从头到尾不拨 —— 上一格刚踩过这个坑，
这一格是照着改的。

  三、mark 的指令数我写成 6，而它实际是 8（两个全域取、三个常量、rect、弃、返回）。

=== 一帧：擦、改、画三步，以及一个不需要新内置的橡皮 ===

上一格证明「同一个 mark 能画在两个地方」，但旧的那个留在屏幕上 —— 拖过去就是一路撒方块。
这一格补的是顺序。

包里加的 erase 与 mark 逐条一样，只有最后一个常量不同：颜色 0 而不是 0x2F。所以橡皮没有
引入任何新机制 —— rect 本来就是「填充一个矩形」，把一块地方涂成背景色就是擦除。加一个
fill 内置会让「擦」成为一个独立动词，而这一层还不需要那个区别。这是一个先量再定的判断，
不是省事：两条路都能走，而省下来的那一条少一个内置表项、少一份判据。

判据读四个点，顺序本身就是这一格的内容：

    mark 之后读旧位置              0x2F
    erase 之后读同一处             0x00      擦真的发生了
    right60 + mark 之后读新位置     0x2F
    再看旧位置                     0x00      擦掉的东西没被谁画回去

验红用的是「把橡皮的颜色改成 05」。四个点于是变成 2F 05 2F 05，判据红、退出码一。

这个红值得单独说，因为它验证的不是「值不对」而是「这个点在读什么」。第二点与第四点本来
读的是 0，而 0 有两种可能：橡皮画下 0，或者那里本来就空着。改一个颜色就把两种可能分开
了 —— 若它们是「本来空着」，改颜色不会让它们变 05。这与裁剪那一格先写 05 打底是同一个
手法：让一个「没有」变成可以被验证的「有」。

路上一个小错：这一格的测试函数写完了、名字加了、判据也加了，却漏了在主链上挂 call，
于是串口里根本没有 progfrm 那一行，判据报「没跑到」。那种红最容易被误读成「函数写错了」，
而实际上它连跑都没跑。挂链这一句没有检查，也没有任何东西会因为漏了它而报错 —— 记在这里，
因为这一格不是第一次（前面每一格都要手动加那一行）。

判据 97 到 98。第二段从 145 到 146 个扇区，余量四十六格，种子从第 155 个扇区起。

=== 重绘：同一个函数，两帧不同的字 ===

前二十一格里，屏幕上的东西只有两种：一块方块换个地方（拖动、一帧），或者一个函数画同一幅
画面（titlewin 的 MYON 写死在指令里）。两种都不是「内容会变」—— 前者变的是位置，后者连
位置都不变。这一格要的是包能把一幅画重画成另一幅。

包里加的第二十二个函数 retitle 在一个函数里做三步：把整个标题栏重刷一遍（矩形 61,81,198,12
涂成标题栏自己的底色 0x1C）、读全局 9 当选择子、按它选一个字画在标题的位置上。

擦的是矩形，不是「上一个字占的那几个像素」：包不知道上一个字有多宽，也不需要知道。一个窗口
重绘自己的某一块区域，本来就是把那块区域整个刷掉再画。

判据取两个像素，各落在一个字的关键位置上。字体是 8x8、每字节一行、最高位是最左像素：

    'O' 的顶横 0x3C 亮在 x+2..x+5，所以 (x+3, y+0) 亮
    'X' 的顶行 0x66 亮在 x+1,x+2,x+5,x+6，同一处是空的
    'X' 的中心 0x18 亮在 x+3,x+4，所以 (x+3, y+3) 亮
    'O' 的第四行 0x66 在那两格是空的

两个字在这两点上正好互换，于是读数 0F 1C 1C 0F 的顺序本身就是「先 O 后 X」。第三个数同时
钉住一件单独的事：擦出来的那一格是标题栏底色，不是零 —— 若重绘只画新字不刷旧字，第三个数
会读到 0F（旧的 O 还在）。

选择子用全局 9 而不是早就存在的全局 3：全局 3 已经被 globalset 那一格写成了 7，而串口的判据
是按顺序跑的。一条判据若依赖另一条判据留下的状态，它红了也说不清为什么红。

这一格踩到一个只有跑起来才会露头的错：全局那一格存的是 double 的位模式，而测试里直接写了
整数 1。解释器按 double 读出来是 4.9e-324（最小次正规数），于是「大于等于 1」仍然是假，
两帧都画 O。屏幕上看起来像「重绘没生效」，其实是那个数根本不是我写进去的那个数。改成存
1.0 的位模式 0x3FF0000000000000 之后四点一次全对。

还踩到一次串口顺序：三层路径那一行的输出偶发延迟，一次落在本行之前、一次落在行头与数字之间
（两次运行各一种），判据因此先红了一次。四个连续的数才是这一条的内容，所以正则允许行头与数
之间夹着别的输出，窗口取八十字符、并要求四个数之后有回车换行 —— 万一插进来的恰好是另一条
带十六进制的读数，非贪婪也不会把它当成这一条。

判据 98 到 99。第二段从 146 到 147 个扇区，余量四十五格，种子从第 156 个扇区起。

=== 过桥：让值也过桥，以及一个从桥接落地那天就在的缺口 ===

桥接那一条判据落地时只证明了一半。runpkg 能让内层跑起来，而内层的返回值永远是空 ——
它保存状态、跑内层、恢复状态、然后压一个 null。内层是用 write 说话的，话说完就完，没人
看返回值，所以「一半的桥」照样能让判据绿。

这一格补另一半。三处改动：

    docs/myon.hmtn 的 echo 从三条指令变成四条：打完那行字再返回 7
    prog.hmtn 加第二十三个函数 bridge：两条指令，调 runpkg、返回它
    runpkg 不再丢返回值：把内层 exec 停下时的 rax 与 rdx 存到内存，恢复完再压回去

判据是 progbridge 7。三端对得上才叫桥：内层返回什么、外层带回什么、宿主读到什么。少一端，
「桥没接上」与「接上了而值被丢掉」在读数上就是一样的。

这一格挖出一个从桥接落地那天就存在的缺口。指令偏移表是全局的，内层 exec 把它换成了内层
函数的那一份，而 runpkg 只保存与恢复了 r12 与 r13（字节流与条数），没有重算表。原来的
调用者从桥上回来就收尾，恰好没露头；而 bridge 的返回语句在桥之后，于是 exec 按内层的偏移
去外层的字节里取，跳进一串乱字节。

症状值得单独记：异常报的是 exception 13 at 0000000000010D96，而那个地址落在 write 内置的
第二条指令上 —— 看起来像串口或字符串的错。实际是 write 被一个不是串的值调用了，而 rsi 是
7 的位模式；非规范地址解引用给的是 13（通用保护）而不是 14（缺页），这一点也让第一眼误判
成「段的问题」。治法是在恢复 r12 与 r13 之后重调一次 scan_instrs。

诊断手法也记一笔：第一版只读了 RIP，半天都在猜。后来在 call exec 之后与状态恢复之后各打
一行标记，一次运行就把三种可能分开了 —— 内层没回来、回来了而恢复坏了、恢复好了而后面的
取指崩了。串口上两行标记都出现、异常在它们之后，于是范围收到「恢复之后」。

判据 99 到 100。第二段从 147 到 148 个扇区，余量四十四格，种子从第 157 个扇区起。

=== 送值：桥的两头都要通，以及一个「槽不清理」带来的取数约束 ===

上一格让值能带回来，这一格让它能送过去 —— 而且内层真的用了它。

三处改动：

    新内置 runpkg1：与 runpkg 同一条路，多一步先弹参数
    docs/myon.hmtn 的第二个函数 bump：读槽 0、常量 1、加、返回
    prog.hmtn 的第二个桥 bridge1：常量 7、调 runpkg1、返回它

参数落在哪里是这一格唯一的新知识：槽就是值栈最前面那八格，帧 0 的槽 0 就在第 0 格。
外层在起跑前把值写进 stack_kinds[0] 与 stack_vals[0]，内层第一条「读槽 0」就读得到。
而 exec 从不清理槽区 —— 这一点到验红时才显出分量。

为什么另起一个内置而不是给 runpkg 加参数：runpkg 已经有两个调用者，改它的参数表会把
两处一起动过，而这一格要说的是新的一句话。

判据是 progbump 8。三个可能的读数各排除一种情况：1 是参数没到（槽是空），7 是到了而
内层没加一，8 只有一个来路。所以一个读数同时钉住方向、位置与算术三件事。

验红是拿掉写槽那两行。读到的是 4，不是预想的 1 —— 槽区不清理，上一格跑 loopthree 时
留在槽 0 的 3 还在那里，加一得 4。这个红比「空槽」更有信息：残留可以是任何一个旧值，
所以判据必须挑一个不会被残留碰到的数（7），而不是挑 0 —— 0 加一与没送到加一，在读数上
一样是 1。

判据 100 到 101。第二段从 148 到 149 个扇区，余量四十三格，种子从第 158 个扇区起。

=== 重画：窗口第一次是一个东西，而不是三笔分开的画 ===

前面的格子各证明一件事：retitle 能重画标题栏、titlewin 能画骨架加一句话、echo2text 能把
输入的那一行画到屏幕上。而窗口本身从来没有被整体重画过 —— 三样各画各的，谁也擦不掉谁。
屏幕上那些窗口碎片是叠出来的，不是画出来的。

redraw 把它们收进一次调用：擦掉整块窗口、按全局 9 选标题（O 或 X）、把 readline 送进来的
那一行画进内容区。二十五条指令。

擦不需要另写一段代码。win 的第一个矩形就是整块底色 (60,80,200,90)，盖住的正好是另外两层

画用的是同一组坐标 —— 改位置时不可能只改一边。

判据三点各问一件不同的事：

    (73, 84)   'O' 顶横的中央。titlewin 画的 MYON 里这一格是 M 的空位，
               所以它只在真的画了新标题时是 0F
    (71, 100)  内容区第一个字符 'e' 的笔画，只在 readline 拿到那行字并画出来时是 2F
    (74, 154)  重画之前宿主人为涂的一块 2F。字只占 y 100..107，所以它回到 0F
               只能是被底色盖掉 —— 这一点读的是「擦真的发生了」

验红把调 win 那一条换成一条「弃」：指令数与后面所有跳转目标都不动。读数从 0F 2F 0F 变成
0F 2F 2F，只有第三点翻。这顺带说明前两点不依赖 win —— 它们读的是新画上去的东西，而擦是

这一格也是程序包第一次把预读区顶宽。包涨到 2751 字节，盘上最后一份文件推到第 1059 号，
预读从 34 个扇区改成 36。两次都是 build 的自检先报出来的 —— 它说的是「预读只盖 34 个扇区
而最后一份在 1059」，而不是「读不到」。判据若只表达「读到了」，那种失败会以「读到了、内容
是零」的样子出现，而那是另一种红。

=== 移位：位置从常量变成参数，以及一个选错的判据点 ===

win 把三层写死在 (60,80)，而窗口若不能移动就只是一幅画。这一格把位置搬出来。

两个函数：

    winat      接受 x 与 y 两个参数，三层的相对偏移与 win 完全一致，三十条指令
    shiftwin   零参，四条：读全局 10、读全局 11、调 winat 两参、返回

要一个零参外壳，是因为宿主调用包函数时压不了参数。宿主直接 exec，没有「调用者」那一层；
实参是从运算栈搬进新帧的槽的，而宿主的栈是空的。所以「参数从哪来」只能由函数自己去取，
全局就是那个来源。winat 的两参形态留给包内的调用者用。

位置放在全局 10 与 11 而不是 5 与 6：5 与 6 是拖动那一格的方块位置。两件事混在同一组格子上，
红起来会分不清是谁的。

判据三点：(100,60) 新窗口左上角是底色 1F、(110,70) 新窗口标题栏是 1C、(60,80) 旧窗口左上角
是 00。测试先清屏再画，所以三点都只可能来自这一次调用。

第三点第一次挑的是 (160,86)，那是旧窗口标题栏的中央 —— 可它同时也在新窗口的内容区里。两个
位置互相重叠：新窗口从 (100,60) 起、宽两百高九十，盖住了 (160,86)。于是正确实现的读数也是
0F，判据红在一个选错的点上。改到 (60,80) 之后才成立，那里隔着四十列，两个窗口不相交。

=== 两值：桥一次送两个数，以及一个靠残留才看得清的验红 ===

上一格把位置搬进全局，winat 于是有两个参数 —— 但那是包内的调用，而桥还只会送一个值。

这一格让两个值一起过桥：

    新内置 runpkg2   与 runpkg1 同一条路，差别是弹两个实参
    内层 sum2        四条指令：读槽 0、读槽 1、加、返回
    外层 bridge2     四条指令：常量 30、常量 13、调 runpkg2 两参、返回

顺序是这一条唯一的难点。栈顶是最后那个实参，所以先弹出来的是第二个值；而槽 0 必须是第一个
实参。于是先弹的那个要先放下（rp_b 与 rp_kb），等第一个也弹出来、写进槽 0 之后再写槽 1。

挑 30 与 13 而不是 0 与 43：只送到一个时，结果是「某个数加上残留」。若用 0 与 43，只送到 43
也能读出 43，那种失败就与成功分不开。

加法交换，所以这一格测不出顺序错 —— 它测的是「两个值都到了」。顺序要留到减法那一格。

验红是只写槽 0、不写槽 1。读数变成 90，也就是「第一个实参 30 加槽 1 里的残留 60」。两个值
缺一不可，而 90 这个数还说明了另一件事：第一个实参真的到了它该到的那一格 —— 若两个都没写，
读数会是残留加残留，那就看不出第一个到了。

路上踩了两个上限，都是这一格自己的体积造成的：

    内层包的 Buffer 128 字节放不下第三个函数，ERR_OUT_OF_RANGE 落在 writeUInt32LE
    程序包涨到 3084 字节，把盘上最后一份文件推到 1061，预读从 36 改成 38

判据 103 到 104。第二段从 151 到 152 个扇区，余量四十格，种子从第 161 个扇区起。

=== 合成：两半各做一半的路，合成一条 ===

这一格之前有两半各做各的。redraw 能整体重画窗口，可它调的是坐标写死的 win；winat 能按参数
画，可它只被 shiftwin 用过一次，画完就没人管。两半都在，而「窗口能边移动边重画」这件事一次
也没有发生过。

合成之后 redraw 是这样：读全局 10 与 11 存进自己的槽 0 与 1、调 winat 两参画三层（那就是擦）、
标题画在 (x+10, y+4)、内容画在 (x+10, y+20)。三十七条指令，从二十五条长出来的十二条里有十条
是「坐标改成相对位置」的算术。

位置存进槽而不是每次重读全局：这一格里它要用六次。槽与全局在同一帧里没有别人改，存下来读的
是同一个数。

判据从三点变四点。测试先清屏，位置设到 (100,60)：

    (113, 64)   标题 'O' 顶横的中央
    (111, 80)   内容第一个字符的笔画
    (150, 120)  宿主事先涂上去的一块 2F，字占不到那里
    (60, 80)    旧窗口的左上角，清屏之后没人往那里画

第四点的界限要说清：它证明的不是「旧位置被擦」。移动的两步是擦旧、画新，而 redraw 现在只做
后者 —— 擦旧要等它也知道旧位置在哪。把「没画在旧位置」说成「旧位置被擦」，是这一格最容易
写出的一句假话。

验红把两条读全局换成常量 60 与 80，读数从 0F 2F 0F 00 变成 00 1F 0F 1F。第一、第二、第四点
都翻，第三点不翻 —— 因为旧窗口的内容区恰好盖住 (150,120)，人为涂的那块 2F 照样被刷成 0F。
三个点翻已经够分开两种实现；这也说明「每个点单独看都可靠」不等于「每个点在每种反例下都翻」。

顺手两件小事。一是写字节的帮手挪到了文件前面：redraw 也要用那一套，而模块顶层的 const 按
顺序生效，留在原处就晚了 —— 这类错在 JS 里报的是 ReferenceError，症状清楚，不费时间。

二是发现一件没有判据盯着的事：程序包的头里那个函数个数还写着 21，而包里现在有二十八个
函数。没有任何代码读它，所以一直没人报，也没有任何判据会因为它错而红。这正好是那条老规矩的
又一个例子 —— 一个没有判据的行为，等于不存在。

判据仍是 104 条：这一格换强的是已有的那一条，不是加了一条。

第二段仍是 152 个扇区（实到 77604 字节，余 20700），种子仍在第 161 个扇区起。

=== 顺序：减法是判据，而判据自己漏了一个减号 ===

上一格用加法验证「两个值都到了」，可加法测不出顺序 —— 顺序反了，和还是那个和。这一格补的
是减法。

两件事一起做：

    减是 opcode 30，形状表里本来就有（无立即数），可分派链上一直没接
    新内置 runpkg3 与 runpkg2 逐条一样，只把内层函数从 sum2 换成 sub2

于是「加一条 opcode 是三处」这句话在这里只是两处 —— 形状表那一处本来就不缺。这是它第一次
不是三处。

内层加第四个函数 sub2（读槽 0、读槽 1、减、返回），外层加第二十九个函数 bridge3（常量 50、
常量 8、调 runpkg3 两参、返回）。判据是 progsub 42。

挑 50 与 8：差与和都清楚，而顺序反了得 -42。若用 8 与 8，顺序反了也还是 0，那一种就白挑。

验红第一次没有红。读数从 42 变成 42 —— 我把两个实参的落槽顺序调过来，串口上什么也没变。
查下去发现 print_value 的 .num 走 f64_to_int，而那个函数只看指数与尾数、不看符号位，所以
负数一律以绝对值回来：-42 打印成 42。

于是这个反例在串口上与正确实现一模一样，判据根本红不了。修法是在打印之前看符号位、置位就
打一个减号再把那一位清掉。修完再交换一次，读数变成 -42，判据才红。

这条比这一格本身值钱。判据的形状里漏了一个字，而那个字恰好是这一格唯一要证明的东西 ——
一个判据看不见的差别，等于不存在。前面几格的教训都是「点选错了」，这一次是「数字的写法盖
住了差别」，而后者更难发现：串口上有读数、有数值、看起来完全正常，只是少了一个负号。

顺带两个上限：第二段从 152 涨到 154 个扇区（sub2 与符号修复各占一点），种子移到第 163 个
扇区起。预读区没动，仍是 38 个扇区。

=== 落点：桥送过去的不再是数，而是坐标 ===

前三格送进内层的值都被拿去算数 —— 加一、相加、相减。这一格让它们变成坐标。

新内置 runpkg4 与 runpkg3 逐条一样，只把内层函数换成 drawat。内层加第五个函数 drawat
（七条指令：读槽 0、读槽 1、常量 "A"、常量 0x2F、调 text 四参、弃、返回）；外层加第三十
个函数 bridge4（读全局 12、读全局 13、调 runpkg4 两参、返回）。

于是「桥」这件事从「能把数送过去」变成「能让对方在你指定的位置做事」。后者才是两个组件
真的接上 —— 前者的每一个判据，都还能由一个只做算术的内层满足。

位置走全局 12 与 13 而不是写死在 bridge4 里，是因为判据要调它两次、每次一组不同的位置。
若坐标写在 bridge4 里，两次就会落在同一处，「位置真的送过去了」与「内层自己知道画在哪」
就分不开。

三点，第二点最要紧。'A' 的顶行是 0x18，只在中间两格亮：

    (x+3, y)    字的笔画，2F
    (x,   y)    同一行左边的空位，00 —— 两点挨着，一次调用就同时证明「画了」与「画在哪儿」
    (183, 160)  第二次调用的另一组位置，2F —— 它只证明坐标真的从槽里来

验红把 drawat 的两条读槽换成常量 100 与 120：读数从 2F 00 2F 变成 2F 00 00。只有第三点翻，
正合预期 —— 前两点读的是第一次调用，内层写不写死坐标都画在那儿。这一格的验红因此只覆盖
「位置是参数」这一半，而「字画在了那个位置」是前两点在覆盖。一个验红只翻一个点不是缺点，
只要那个点正好问的是这一格要证明的事。

判据 105 到 106。第二段从 154 涨到 155 个扇区，种子移到第 164 个扇区起。

=== 尺寸：位置之后，尺寸也进全局 —— 以及一个越界写 ===

位置进全局之后，尺寸还写死在 winat 里（200x90）。这一格把宽高也搬出来：全局 7 是宽、8 是
高，winat 改成四个参数。

三层按参数算：

    底色    (x, y, w, h)
    标题栏  (x+1, y+1, w-2, 12)
    内容区  (x+1, y+14, w-2, h-14)

w-2 与 h-14 用减 —— opcode 30 是上一格才接上的，这里第一次用上。

判据用一个非默认尺寸 160x70，读窗口的两只角：(259,129) 是内角、(260,130) 是外角。只读内角
的话，一个画成 200x90 的实现照样能过，因为它盖住了内角；外角才是这一条的判据。

越界写不会报错 —— .op_getglobal 那一处的注释早就写着「上限不做检查：越界读到的会是自己那两

而这两个判据与窗口毫无关系，所以第一轮的目光全落在文件系统上：先怀疑 fs_write_file 的上界，

教训与前面几格同源，但形态不同：前几次是「点选错了」「数字的写法盖住差别」「两个几何区域
重叠」，这一次是「一个沉默的越界让远处的判据变红」。一个越界写不报错，它只会让一串与它无关
的判据同时红，而红的样子指向另一个子系统的深处。这也是「全局十六格」这条约束第一次被真正
踩到。

=== 标志：第一帧没有「旧」可擦 ===

上一格的 redraw 每次进来都擦旧。而第一帧的「旧位置」是全局 14 与 15 的初值 —— (0,0)。
那一擦会盖掉别人画在左上角的像素。

加一格全局 4：「画过了」的标志。它是假就跳过擦旧，画完置一。redraw 从五十条涨到五十四条。

判据的形状换了。上一格读的是「旧位置空了、新内容在」，这一格要读的是「第一次不擦、第二次
擦」—— 而后者只有先放一个「别人的东西」才问得出来：

    清屏之后宿主在 (0,0) 画一块 2F
    位置 (100,60) 调第一次 —— 标志是 0，不该擦，所以记号还在
    位置 (140,90) 调第二次 —— 标志已是 1，先擦 (100,60)

三点：2F 00 1F。

第一点与第二点合起来才是这一格的话。只读「旧位置空了」的话，一个「每帧都擦」的实现照样
能过 —— 它擦掉了 (0,0)，但那个点没人看。

测试里必须显式把全局 4 清零。同一趟里前面的测试可能已经调过 redraw，把它置成过 1；而一个
「恰好是 1」的初值会让第一点假绿。

验红把那个假跳换成一条「弃」：指令数与后面所有目标都不动，只让每一帧都擦。读数从 2F 00 1F
变成 00 00 1F，第一点翻。这也是换一条等长指令的又一次用法 —— 删掉两条再重算索引，红的形状
会与「标志没生效」混在一起。

一个编号上的修正：goal 里写的是全局 18。而全局区只有十六格，上一格刚用一次越界写把 save
判据弄红过。标志用的是空闲的 4。这句话写在这里，是因为下一个要加全局的人也会先想一个好记的
编号，而好记的编号往往已经出了界。

判据仍是 107 条：这一格换强的是已有的那一条。

第二段仍是 157 个扇区（实到 79916 字节，余 18388），种子仍在第 166 个扇区起。

=== 擦旧：移动的另一半 ===

上一格让 redraw 走 winat，窗口能边移动边重画 —— 可它只画新位置。旧位置留在屏幕上，移动就
变成「一路盖窗口」：每经过一个地方就留一个框。

这一格把上一帧的位置留在全局 14 与 15。每次进来：

    一、rect(旧x, 旧y, 200, 90, 0) —— 把那一块涂成背景色
    二、取新位置进槽、调 winat 画三层
    三、画标题与内容
    四、把新位置写回全局 14 与 15

擦旧用 rect 涂 0，而不是再画一遍 winat 的框：背景色就是索引色 0，与清屏同色，所以第一次
调用（全局 14 与 15 还是 0）擦的是一块空白 —— 无害。加一个标志位跳过第一次会更准确，但那
要多一格全局加一次判断，而这一层还不需要它。这是一句要写下来的取舍：现在这个实现是「第一次
会多擦一块空白」，而不是「第一次不会擦」。

判据从四点变三点，测试调两次：第一次 (100,60)，第二次先把全局位置改到 (140,90) 再调。

    (100, 60)   第一帧的左上角 —— 该是背景色 00
    (153, 94)   第二帧标题 'O' 顶横的中央 —— 0F
    (151, 110)  第二帧内容第一个字符的笔画 —— 2F

第一点正是这一格比上一格多出来的那一条。上一格的第四点读 (60,80)，只证明「没画在旧位置」；
这一格的第一点读 (100,60)，那里确实有东西（第一帧的窗口底色），所以读 00 只能是「被擦了」。
同一个位置，前一格问不出的话，这一格问得出 —— 因为前一格调一次、这一格调两次。

验红把擦除矩形的宽改成 0：读数从 00 0F 2F 变成 1F 0F 2F，只有第一点翻。改宽而不删指令，
是为了不动后面的指令索引与两个跳转目标 —— 七条指令一旦删掉，假跳与跳的立即数都要重算，
而算错的话红的样子会与「擦没发生」混在一起。

判据仍是 106 条：这一格换强的是已有的那一条。

第二段仍是 155 个扇区（实到 79316 字节，余 18988），种子仍在第 164 个扇区起。

=== 扩表：全局区从十六格到三十二格 ===

（这一节的追加点落在上面「擦旧」那一节的结尾，所以位置在它之后；时间上它接在「尺寸」与

十六格在现在的用量下快见底了：位置、尺寸、选择子、标志、上一帧、落点位置，用掉大半。而

=== 两窗：屏幕上第一次有两个窗口 ===

（这一节接上面「扩表」那一节。）

到这一格为止，屏幕上的窗口永远只有一个：redraw 的位置在全局 10 与 11、尺寸在 7 与 8、
旧位置在 14 与 15、标志在 4。它画得再完整，也只是「那一个」。

最省事的做法是给 redraw 加参数。可宿主调用包函数时压不进参数 —— 它直接 exec，没有调用者
那一层 —— 于是参数只能从全局来，而「从哪一组全局来」就得由函数名分开。所以第二个窗口是
一个新函数 redraw2，包里第三十二个。

它与 redraw 的差别只有四处：读哪一组格子、标题字母是 2、没有内容行、用了自己一组旧位置与
标志。三层矩形的相对关系一个数都没改 —— 那部分由 winat 管着，两份窗口共用它。

格子这么分：位置 16 与 17、尺寸 18 与 19、旧位置 24 与 25、标志 21。不复用 10..15 与 4，
因为那几格是第一窗口的。两件事混在同一组格子上，红起来先要花时间分辨是谁的 —— shiftwin
那一处为同样的理由把位置从 5 与 6 挪到了 10 与 11。

判据三点，各占一区，互不重叠：

    (100, 60)   第一窗口的左上角。它必须在第二个窗口画过、挪过之后仍是 1F。
    (20, 20)    第二窗口的旧左上角。挪走之后该回到背景色 00。

=== 移窗：窗口第一次自己走 ===

（这一节接上面「两窗」那一节。）

前面每一格挪窗口，都是测试改全局 10/11 或 16/17 —— 窗口没有动过，是别人替它动了。这一格
要的是「挪」这个动作来自一次真的按键。

输入这一侧早就通了：主机能用 VBoxManage controlvm keyboardputscancode 把扫描码直接注入，
固件轮询 8042 的 0x64 / 0x60 就能读到，不需要窗口焦点也不需要在 guest 里装驱动。这一格
只是把那条路接到窗口上。

路分三段：主机送扫描码 → 宿主读 0x60、把方向键的第二个字节写进全局 22 → 包里的 keymove
判「这是右键」、把全局 16 加八、再调 redraw2 重画。策略在包里，键码在全局，宿主只管读。
这条分工与「输入是宿主口、渲染与策略归包」是同一条，而这一格是它第一次落到指令上。

方向键不是单字节的键。集 1 里它由前缀 0xE0 加一个方向字节组成，而 8042 的输出缓冲一次只
放一个字节 —— 不把 0xE0 读走，后面那个就进不来。所以「读一次 0x60」在这里不够，而它的
症状很有欺骗性：读到的永远是 0xE0，看起来像主机根本没送键。

两次按键，两次握手。串口只能往外说，所以「现在轮到按键了」必须由客人机自己报出来：先打
move ready，主机看到才送第一个右方向键；挪完打 move again，主机再送一个。靠时间猜的话，
送早了键还躺在缓冲里、送晚了这个测试已经超时，而两种坏法在串口上都只表现为「progmove
后面没有数」。

这一格连红了三次，每一次的红都是真的：

一、放开码被数成了按键。右方向键按下是 E0 4D、放开是 E0 CD，两者都带 0xE0 前缀。第一版
在读到前缀之后就把第二字节原样交出去，于是同一个键的按下与放开被数成了两次 —— 窗口只挪
了一次，判据第二点读到 1F 而不是 00，而擦旧本身没有坏。

二、判据点选得太软。第一版第一点读 (36,20)，可窗口宽六十，起点 28 时 36 落在窗口里面，
于是「没挪」「只挪一次」「挪了两次」三种情况里前两种给出同一个读数，验红读到 1F 1F 1F，
等于没有问。换成 (90,20) —— 窗口的右边界内侧，起点 20 时边界 79、28 时 87，两者都盖不到
九十 —— 才真的在问「位置到没到 36」。改完再验红，读数 00 1F 1F。

三、第二趟跑不完。第二趟只等串口、不送按键，于是移窗那一条会在两个等待窗口里各自耗到
预算用完才往下走。六十秒的窗口加上这两个空等就挤到了边界上，症状是「第二趟没有 save
survived」—— 而它红的样子与「落盘失败」一模一样，读的人会去查持久化。把等键预算从
五百万降到两百万、第二趟的窗口从六十秒放宽到七十五秒，这个红才回到它该有的样子。

第三点值得单独记：一条判据红在别处，比判据红在自己身上贵得多 —— 它不占去查错的时间，
它占去「以为那里坏了」的时间。

=== 事件行：一次按键成为一行带源与目标的记录 ===

（这一节接上面「移窗」那一节。）

「复数控制器」那一批设计在 design/INPUT.txt 里写了十二节，而它们一行固件都没有。这一格取

这一格还顺手定下了「事件」这个词在 YNOK 里的形状：一行文本、四个字段、顺序固定。这个选择
有代价（文本比二进制宽、要解析），而它换来的是「判据只认串口」这条一直守着的规矩 —— 以及

=== 未登记被拒：一张清单，与一次被挡下的按键 ===

（这一节接上面「事件行」那一节。）

上一格把「一次按键成为一行事件」写在一处。这一格把它拆成两件事 —— 发射一行，与决定要不要
发射；拆的理由是判据，而不是整洁：一个「打了拒绝行却照样把事件放过去」的实现，在只有发射的
时候完全看不出来，因为它打的那一行每个字段都对。

三个例程，照依赖排：register_source 填清单（四格，0 是空位，满了什么都不做 —— 那是这一格里
唯一没有人读的分支，等第二个源再说）；emit_event 只管形状，六个字段一行结束，那六条指令是
上一格原样搬来的，一个字节没改；arbitrate 读全局 26 的源 id、线性查四格、查到就尾跳到
emit_event，查不到就打一行拒绝。查表不建哈希：四格的表用哈希只是把「查什么」藏进一个函数里。

判据取自 design/INPUT.txt 第十二节第二条，而它的力气在后一半 —— 一个否证：整份串口里不该
出现任何 event src=2。前一半（有一行 input src=2 rejected=unregistered）单独是不够的，因为
一个「打了拒绝行、但仍然把事件放过去」的实现打的那一行与真的拒绝一模一样。所以两次按键送的
是同一个键，只差源 id 一格：源 1 那一行进事件行，源 2 那一行只留拒绝。同一个东西、两种待遇，
在串口上直接看得见。

拒绝行的理由做成字段而不是散文，这一处值得单独记。这一层后面还要区分「未绑定」与「工程
失活」，三种拒绝的修法各不相同 —— 没有绑定是材料不全，工程失活是主体不被信任 —— 而串口上
分不开就等于没分。做成字段之后，加一种拒绝是加一个值；写成散文的话，加一种拒绝是改一次句子
的形状，而形状一改，前面那些判据的正则就全要跟着改。

验红用的是那条判据的假想敌人本身：把 reject 分支的尾跳改成「照打拒绝行，然后也去发射」。
读数里紧跟着就是 event src=2 kind=key payload=000000000000004D target=2，退出码 1 —— 而拒绝
那一行完好无损。这一种红比「拒绝行不见了」贵得多：后者一眼看得出是没打，前者只有把整份输出
读完才分得开，而那正是判据要问的问题。

第二趟的账也要记一笔：这一格多了两个等待窗口，而第二趟没有人送键，所以它多等约六秒。等键
预算两百万次约三秒，五次窗口约十五秒，七十五秒的窗口还有余量 —— 上一格就是在这个地方红的，
红的样子像落盘坏了。

判据 111 到 112。第二段从 162 涨到 163 个扇区（实到 82948 字节，余 15356），种子移到第
172 个扇区起。


=== 未绑定被拒：说得出名字，却说不出主人 ===

（这一节接上面「未登记被拒」那一节。）

上一格把拒绝的理由做成了字段，理由是「这一层后面还要区分未绑定」。这一格兑现那一句：
登记与绑定分成两张表，同下标，0 是空位。

分开放，是因为它们回答两个不同的问题 —— 登记回答「这个源存在吗」，绑定回答「它属于谁」。
合成一张表也跑得动（把一个空位当「没主人」用），但那样「登记过」与「有主人」就再也分不
开了，而这一层的判据问的正是这两件事之间的那个差。

次序是这一格真正的判断：先问存在，再问主人。一个没有 id 的源连查绑定表的下标都没有，而
「说不出你是谁」比「说不出你属于谁」更原始。反过来做的话，没登记的源会先撞上绑定表的一个
空位、报出「未绑定」，于是查错的人会去翻绑定表，而问题在登记表里 —— 两种拒绝的修法不同，
这一条就是「修法不同」在代码里的样子。

理由做成字段的收益也在这一格显出来：两种拒绝的差别只是各给 r11 装一个字符串地址，拒绝行
本身一个字节没动。写成散文的话，这里要改的是一句话的形状，而读过那句话的正则全要跟着改。

判据用同一个源 id 做两次拒绝：上一格那次源 2 没有名字，这一次源 2 有名字却没有主人。把
「谁被拒」那一格固定住，两行字就只差理由一格 —— 这比换一个源结实，因为换源的话，两行字
的差别有两处，红的理由也就有两处。判据要三样：两行都在、理由不同、整份串口里没有
event src=2。验红把那一边的理由串换成 unregistered，两行合成一行字，判据红。

这一格撞出一件事，值得单独记。两张表一分，上一格那条测试的前提就变了：它只登记源 1、
没给它主人，而仲裁现在要两样都有才放行，于是 reject ready 之后那一行变成
input src=1 rejected=unbound。那不是判据错，是它依赖的前提变了 —— 修的是测试的前提，
不是判据。一条判据依赖的前提一变就自己红，正是它在链上的证据；没有判据的话，这次改动
会在没人注意的地方把「放行」悄悄变成「拒绝」。

判据 112 到 113。第二段仍是 163 个扇区（实到 83276 字节，余 15028），种子仍是第

=== 工程失活：主体的状态与一次事件的判决 ===

（这一节接上面「未绑定被拒」那一节。）

前三格判的都是一次事件：这个源在不在清单上、它有没有主人。这一格判的是一个主体的状态，
而状态与判决的差在这里可测 —— 一个逐次查清单的实现在第二次请求上会再报一次「不在清单里」，
正确的实现在第二次报「失活」。两行字不同，而那不是措辞的差别，是两种实现的差别。

工程表四格、三态：0 空位（从没见过）、1 失活、2 信任。要第三态，正因为「没见过」与
「见过而失活」必须分开 —— 合成两态的话，第一次与第二次请求会给出同一行读数，而这一格的
判据问的正是它们的不同。

四种结局在串口上是四行：没名字、失活、被信任、接受。判据把四行当成一条序列读，而不是
四个独立的正则 —— 一个「每次都报 untrusted」的实现，四行里有三行单看都像个正常答案。
「接受」也有一个可读的后果：控制器真的被登记，编号是工程 id 加十，所以最后那一行带
src=13。一条只说「接受了」而什么也没建的读数，与一个真的建了的读数长得一样。

验红用等宽替换（立刻数 1 改成 0，字节数不变）：第一次撞门不再写成失活，于是第二行退回
untrusted，判据红。这一次红证明的是「那一行来自状态」，而不是「那一行来自又一次查表」——
两者的实现都对，错的只是其中一个记得住、一个记不住。

撤销的传递（工程到操作员到控制器）这一格没做，理由写在 PLAN 里：控制器还不带工程 id，
先做传递会让这一格的红理由落在一个不存在的链上。先有链环，才有传递。

=== 伪装可被识破：名字不算数，签名才算 ===

（这一节接上面「工程失活」那一节。）

前四格里，改一个值就能让判据红。这一格不同：它换的是查找用的键，而那一换就把整张表的
意义换掉了 —— 一个按名字判断的实现，在名字与签名没有人故意撞在一起的场合，与正确的实现
一行指令都不差。

三列同下标：签名（主键）、状态、名字。名字能记下来，却不能当主键 —— 这一格要的正是这个
区别。名字在这里是一个编号，因为这一层只需要比较两个名字是否相同，不需要它的字节；
真名进来的时候这一列会换成指针，而查找仍然走签名。

三行成对读：名字 1 属于签名 7（基准），签名 7 请求被接受（控制器编号 17），签名 8 顶着
名字 1 被挡下。第一行是基准 —— 少了它，剩下两行看不出「名字 1 只属于 7」。而判据要求
三行的名字相同，否则那只是两个无关工程的结论。

验红做了两次，第二次才是这一条要的形状。

第一次把名字值传进签名查找，读数变成 7/trusted、7/untrusted、8/inactive —— 三行全变。
它证明了三行都依赖那个查找键，但也仅此而已：那不是「按名字判断」，那是一个查错列的实现。

第二次让「名字在清单里就算数」，读数变成 7/trusted、7/accepted、8/accepted src=18 ——
签名 8 顶着名字 1 混了过去，判据红在两个不同的签名带着同一个名字。这一次才是判据原文
那句话的实体：一个按名字判断的实现过不了它。

而两次验红之间那一步值得记下来：按名字判断不是改一行，是换一张表的主键。正因为如此，
它在正确的表结构下无法用最小改动模拟 —— 要造出那个坏实现，得另写一段按名字扫的代码。
一条判据的力气，往往就体现在「要让坏实现出现，得费多大劲」上。

判据 114 到 115。第二段从 165 涨到 166 个扇区（实到 84572 字节，余 13732），种子移到第
175 个扇区起。


=== 注册：两道缺项，同一行字 ===

（这一节接上面「伪装可被识破」那一节。）

前五格测的都是「会不会拒绝」，这一格测的是「拒绝说不说得清」。材料是三个位：源、操作员、
签名，只有 7 算完整 —— 多出来的位也不合格，因为一份材料不该带着它没声明的字段，那与缺项
是同一个问题的另一面。

两道不同的缺项（缺签名位的 3、缺源位的 6）都落到同一句字上。判据要的比较是逐字节相等，
不是「两行都以 denied 开头」—— 一个把缺项写进那一行的实现完全能拒绝，而它送出的正是一个
可以逐项收敛的信号：改一位、看行变不变，几十次之后就凑齐了。这正是这一条把「不说明缺
什么」从承诺变成比对的地方。

判据的三个条件缺一不可：三行都在；第一行与后两行不同（否则一个「全都说同一句话」的实现
也能过）；后两行逐字节相同。

验红就演那个坏实现：失败行带上材料值，读数变成 denied 3 与 denied 6，两行不同，判据红。
这一次红的价值在于它演的正是那类「看起来更友好」的实现 —— 告诉用户缺了什么，通常被当成
善意，而在这里它是把搜索空间从「全或无」变成「逐项」。

这一格不需要按键，也不占等待窗口：它是纯固件的一次判断，而它读的三行都在同一次调用里写完。

判据 115 到 116。第二段仍是 166 个扇区（实到 84756 字节，余 13548），种子仍是第
175 个扇区起。


=== 不锁定：两次失败之后，完整的一份仍然成功 ===

（这一节接上面「注册」那一节。）

前六格读的都是一行或一对行，这一格读的是一串：denied、denied、ok。因为它测的是两条时间
线上的性质，而时间线上的东西一行装不下。

第一行与第三行合起来是「不锁定」：连着两次失败之后，完整的一份仍然成功。这条容易过 ——
一个什么都不记的实现天然满足它。

第二行是这一格真正的重量，而它比第一半难测得多。「不让下一次变短」在串口上不显形：
没有任何一行会说「我记住了你上次对了前两位」。它的可测形式是造一个具体的情形：第一次给
缺签名位的材料，第二次只给签名位 —— 一个记住了「前两位已经对了」的实现会让第二次成功，
而一个每次从头比 7 的实现会拒绝它。所以第二行必须是 denied。

行首用 nolock 而不是 register 是有意的。两条判据测的是两种东西：一条是一份材料的结果，
一条是一条时间线。合成一套行首的话，两条判据会按位置切同一股串口流，而位置是这个项目里
最容易错位的东西 —— 加一行、动一行，切点就移了，而错的判据看起来像对的。

验红就演那个记住上一次的实现：第二次变成 ok，判据红。这一种红比前几格的都温和 ——
它不改变任何一行的形状，只让一行在错误的时候出现。而那正是「状态」这种漏洞的样子：
它不写出任何异常，只是让某个本该失败的东西成功。

至此 design/INPUT.txt 第十二节那七条能立的判据全绿，剩下「同级」与「每源一个焦点」两条
仍等第二条运行时输入路 —— 而那条路不该用「同一路改个名字」去凑。

判据 116 到 117。第二段仍是 166 个扇区（实到 84932 字节，余 13372），种子仍是第
175 个扇区起。


=== 信箱升级：空转时问一次盘 ===

（这一节接上面「不锁定」那一节。）

这一批的七条判据都是「同一路输入上的不同判决」。这一格加的是第二条路：信箱盘不再只在
启动时读一次，而是在 wait_arrow 的空转里每 4096 轮读第 4 个扇区一次。序列号变了就是一条
新输入，而它走的是与键盘同一个 wait_arrow、同一个 arbitrate —— 差别只在源那一格。

三处撞出来的东西，每一处都会再咬人。

第一处：ata_read 的设备字节写死成 0xE0（primary master），所以它以前读不了信箱盘 ——
读是成功的，读回来的是主盘同一号扇区的字节。症状很安静：轮询读到了字节、比对失败、
返回「没有新输入」，看起来像信箱没东西。加了 ata_dev 之后才有从盘，而它平时是 0 ——
文件系统那一整套读的都是主盘，只有 mbox_poll 临时置 0x10。

第二处比第一处贵：wait_arrow 的等键预算原本放在 r10，而 ata_read 用 r10 做忙等计数器，
于是每一轮轮询都把预算重置成 200000，那个循环永远耗不完。症状是「mbox ready 之后串口
静住」—— 不是崩溃、不是报错，是安静。一个会安静地不返回的循环，比一个会挂住的测试更
难看见，因为它什么都不说。

第三处是我自己写出来的：wait_arrow 的键盘那一路也设了一次源，于是「设源 2、等键、仲裁」
变成了「设源 2、等键、源被改回 1、仲裁」，读数从 input src=2 变成 event src=1。判据当场
红了。「这次是谁送的」这件事只有 wait_arrow 知道，但「该记成哪个源」是调用者的意思 ——
信箱那一路要改源，因为调用者不知道这次是信箱；键盘那一路不该碰。

还有一笔账：空转时轮询是有代价的，而代价落在没有键可送的那一趟上。第二趟里每个等待
窗口都耗满预算，而每一个都变慢了一秒左右，八个窗口就是三十多秒。窗口从一百五十轮放宽到
两百轮。这种放宽要写在注释里，因为「窗口不够」与「那一块坏了」在串口上是同一种样子。

这一格为什么不是「宿主在运行中写」：实测 VBox 在客户机运行时独占锁着盘文件，宿主 open r+
直接 EBUSY。所以这一格证明的是「运行时读盘」与「序列号消费」，而消息是启动前沿序放进
第 4 个扇区的 —— 「随时可写」要另一条通道，那条路与盘无关。

判据 117 到 118。第二段从 166 涨到 168 个扇区（实到 85996 字节，余 12308），种子移到第
177 个扇区起。至此第二条运行时输入路成立，「同级」与「每源一个焦点」两条判据的前提到位。


=== 同级：一条挂起来的判据，与它缺的那样东西 ===

（这一节接上面「信箱升级」那一节。）

第八条判据要的是「同一个窗口被两条路各操作一次，两趟读数完全相同，而事件行只在源 id 那
一格不同」。代码写了，判据也立了，读数一直是一半：第二趟对，第一趟的 payload 全零。

第一趟必须由键盘送，而键盘键要等宿主「看到握手之后再送」—— 宿主每 150 毫秒读一次串口
文件，而 wait_arrow 的等待预算在虚拟机上跑完只要几十毫秒。于是键总是在这一边放手之后才到。
读数看起来像「键没送到」，实测是「等待已经结束」。

把预算调大是第一个念头，而它花了三次往返：200 万、2000 万、2 亿。读数没有变好，只把第一趟
从几十毫秒拉成几十秒，最后连第二趟都没跑到。这是这一格真正学到的东西：在没有时钟的一层，
用猜去对齐两边的时序，那个猜不是判据。

所以它挂起，而不是留一条永远红的判据 —— 一条永远红的判据比没有更糟，它会把「红」这个
信号本身用掉。代码留在原处，调用注释掉，判据摘出成败链，理由写在三处（stage2 的调用点、
run.mjs 的形状留档、这里）。

它要落地的条件很具体：客人机能读到「现在过去了多久」，或者串口变成双向的（那样客人机可以
自己说「我还没等到」，而不是靠宿主猜它等了多久）。第一件比第二件便宜一个数量级。

判据 118 条（摘下同级之后回到这个数）。第二段 171 个扇区（实到 87140，余 11164），种子从
第 180 个扇区起。

=== 时钟：等键的预算是墙钟，不是循环次数 ===

这一格补的是这台机器一直没有的一样东西：现在过去了多久。

在此之前，「等一个键」的预算是循环次数 —— 而循环次数什么也不算。同一个数字在这台机器上
可能是二十五毫秒，在另一台上是半秒，因为每一轮里可能有一次真实的 ATA 读。于是「宿主看到
握了手、再把键送进来」能不能赶上，完全取决于机器今天跑多快。同级那一条判据就卡在这里：
它挂起过一轮，而那一轮留下的最值钱的一句是 —— 在没有时钟的一层，用猜去对齐两边的时序，
那个猜不是判据。

落地的是 rdtsc。三个理由：不需要端口（RTC 与 PIT 都要，而且一个是 BCD 秒、一个是
五十五毫秒绕回一次的十六位计数）；不需要中断（这一层从 long_entry 起就 cli）；不需要校准
也能用 —— 它的绝对频率是宿主的，而这一层从来不问「现在几点」，只问「从刚才到现在走了多少」。

先立的是「它在走」这一条，位置在堆自检之后、种子之前，因为这件事与种子无关。判据钉的不是
值（同一个四千轮循环在不同机器上读出几千到几万个计数），而是三件事：这一行在、数是正的、
而且没有大到不像计数。第三条不是形式主义：若高半截拼错了，读出来会是一个巨大的数，而
「巨大」正好是「拼错」与「时钟走得快」之间唯一还看得见的区别。第一趟读到的是四千轮之后
五千三百七十六个计数，也就是大约一圈一个计数 —— rdtsc 跟的是核频，不是某个固定晶振。

然后 wait_arrow 换了单位：起点与终点都是它读出来的数，默认预算放在 [wait_budget] 里，为的
是让某个调用点能临时加长 —— 等一个要经过宿主的键，和「看看有没有键」不是同一件事。两次
问信箱之间的间隔也换成了它（poll_ticks），因为「每四千零九十六轮问一次」在有了时钟之后是
个没有意义的单位：真正该管的是「多久问一次」。硬上界留着（r8 里那个十亿轮），它不是预算，
是保险丝：万一这台机器上 rdtsc 不动（某些虚拟化配置会冻结它），那条比较永远不成立，而它
至少还能转完就放手。

超时的时候串口现在会说等掉了多少个计数。这一行是这一格真正的收获，因为它把「没等到」分成
两件完全不同的事：预算太短（那就把数调大），或者根本没人在送（那调多大都一样）。在它出现
之前，这两种在串口上长得一模一样 —— 而这正是同级那一条挂起时踩的坑。

而加上这一行之后，同级给出了第二个答案：把预算加大十倍，仍然等满；而同一段代码、同一个
送法在相邻的「事件行」那一处，用默认预算就等到了。所以这一次不是时钟的事。这一格因此没有
把同级救回来，但它把「不知道卡在哪」换成了「卡在宿主那一侧的一个数」—— 从看到 same ready
到 vbox 返回之间有多少毫秒。那是一个能用时间戳量出来的数，不是猜。

顺带修掉的三处，都在 wait_arrow 里，都是「静悄悄返回 0」的形状：

  一、第二字节没等到时，以前直接 xor eax, eax 返回，与「一个字节都没来」一模一样。现在它
      跳到同一个超时出口，于是那两种情形在串口上分开。
  二、「读到 E0 之后重设预算」去掉了：总预算只有一份。重设会把一次等待变成两次，而两次
      加起来仍然超时的时候，日志里看不出是哪一个先到。
  三、「不是方向键的按下」时补预算也去掉了，理由同上。

第二段从 171 涨到 172 个扇区（实到 87612 字节，余 10692），种子从第 181 个扇区起。
判据 118 到 119。


=== 补记：宿主那一侧的量出来了 ===

同级挂起之后，剩下的是一个能测的数。测法是让宿主在送键前后各记一次时间，并把它返回的
状态码一起打出来。得到的三个数是：四十五毫秒、一百七十五毫秒、两次都返回 0。也就是说
VBoxManage 确实把那一串扫描码收下了，而且很快。

客人机那一侧在同一段时间里只读到一次字节，还是 0x00 —— 输出缓冲的标志位亮过一次，而
里面没有一个真正的扫描码。为了拿到这一行，wait_arrow 里临时加了一句「读到了什么就打
出来」，而它给出的答案把怀疑从「键被丢掉」改成了「键没到」。这一句侦查完就收了，因为
它会让每一次等键都多两行噪声。

这两件事放在一起，这一格能说清的是：不是预算、不是送法、也不是客人机把字节吃掉了，
而是那一次注入没有落到 8042 的输出缓冲里。相邻的「事件行」那一处确实拿到过一个迟到的
4D（它自己的等待只有默认预算），说明通路整体是通的，落空是间歇的。

所以这一格到此为止，而它留下的比它解决的更值钱：三个数、一行侦查的结论，以及一个
写清楚了的下一个动作 —— 让等待与送键在时间上对齐，而不是继续动预算。


=== 换算：把计数换成秒，以及它顺手拽出来的两个缺陷 ===

上一格留下了两个没法比的数：宿主四十五毫秒送完，客人机三乘十的十次方个计数等满。
这一格补上中间那一步 —— 拿 RTC 的秒字段校准。等秒变三次，那之间恰好两秒，同一个跨度
里读两次 TSC，商就是每秒多少个计数。读出来是二十九亿到四十亿之间（每次跑都不一样，
因为那是宿主的核频，而它会随负载漂）。

第一版等的是五次（四秒），四秒就把「算数」那一条推红了。红的样子很有价值：calc ready
之后读到的输入是「xxxxxxx1+1」，算出 0。那不是算错，是先前送出去、没被当场读走的键盘
字节积在输入流里，时序一变就挤进了 shell。整趟测试对时序敏感，所以校准取两秒。

追那十五个 x，追出两个真缺陷。

一、宿主的键盘分支用一个上一轮的串口快照判断「有没有 key 行」，于是送出去的那一次
还没被看见，下一轮又送一次。一个条件用旧快照判断，就会在一次真实动作上重复执行很多次。
修法是把读串口提到循环开头，并且给这一段加一个握手 —— run_key_poll 现在先打一行
key ready，宿主听到才送，只送一次。

二、run_key_poll 的等待原先数的是轮次。而「in」是一条要退出虚拟化的指令，一千万轮在
真实机器上是几十毫秒，在虚拟机上能是几分钟。八亿轮试过一次，第二趟（重启验证）没有人
送键，于是它停在那一条上直到宿主的窗口用完，串口停在 key ready 就再没有下文 —— 症状是
「第二趟没有 persist survived」，读起来像落盘坏了。现在它也按时钟等，半秒。

这两条是同一个主题的两个侧面：能等多久要用时钟说，不能用轮次说；而握手要由等待的一方
先说，不能让送上的一方去猜。

判据 119 到 121（多出「换算」那一条）。第二段 172 个扇区不变。

=== 第三趟：一点四秒也等不到，而这一趟排掉了「时间」 ===

换算率到手之后回到同级那一条，把预算从十倍（七点七秒）降到四乘十的九次方（一点四秒），
因为宿主的重复送键已经修好，不需要那么长的窗口。结果一样：等满，没有键。

而宿主同时报的是四十六毫秒加一百六十六毫秒、两次都返回 0。所以这件事与等待长度无关、
与送法无关、也与那十五个 x 无关 —— VBoxManage 说它收下了，而 8042 的输出缓冲一次都没亮。
相邻的「事件行」用的是同一段代码与同一种送法，它在默认预算里拿到了键。

三次挂起，一次比一次窄：第一次是「不知道卡在哪」，第二次排掉了「预算」，这一次排掉了
「时间」。剩下的是「那一次注入有没有落到控制器上」，而那不是这一层能看见的东西。
判据仍是 121，因为这一条没有挂进链。

=== 第四趟：清场，以及它给出的否证 ===

想到的下一个解释是「键其实到了，只是在等待开始之前就到了，躺在缓冲里挡住了后来的那个」。
这个解释能同时说明两件事：宿主说送出去了、而客人机说没等到。它还可以验：在每次等待之前
把输出缓冲读空，并报出读到了几个字节。

wait_arrow 开头因此多了一段 drain_keys。它跑完整趟只亮了一次 —— 其余每一次等待开始时
缓冲都是空的，而 same ready 那一次也是零。

所以那个解释被否掉了：键不是被旧字节挡住的，是真的没有落进控制器。这一条第四次挂起，
四次挂起一次比一次窄：不知道卡在哪、排掉预算、排掉时间、排掉缓冲。剩下一条路要看，
而它在这一层之外 —— 宿主那一次 controlvm 调用在 VBox 自己的日志里是什么结果。

drain_keys 留着不删：它平时不说话，只在真读到残留时打一行，而那一行以后会有用（任何
一次「等不到」的排查都要先问「缓冲里是不是有东西」）。

=== 第五趟：读盘干扰，也排掉了 ===

VBox 没有留下日志，所以「问虚拟机那一侧」这条路暂时是空的。换一个更便宜的可能：等待
期间每五毫秒读一次信箱（一次 ATA 读），而每次 in 都是一次虚拟机退出 —— 会不会是读盘
把键盘的注入挡住了。轮询间隔放到五十毫秒，键仍然没有进来。

五次挂起，一次比一次窄：不知道卡在哪、预算、时间、缓冲、读盘干扰。剩下的只有 VBox
那一侧，而它没有日志 —— 再往下走得先让虚拟机把日志写出来，那是下一格的事。

轮询间隔那一处留下了：五十毫秒是更合理的一个数（原先五毫秒问一次信箱，而信箱里明明
只有一条消息）。它没有救回这一条，但它让每一次等待少问一百来次盘。

=== 第六趟：日志，以及「不挂链的测试照样能弄坏链」 ===

这一层能问的已经问完了：预算、时间、缓冲、读盘干扰，四项都是否证。剩下的是 VBox 自己
把那次注入当成了什么，于是下一步是让虚拟机写日志。VBOX_LOG_DEST 与 VBOX_LOG 是这条路
的标准做法，而它们在这一版 VBox 上没有生效 —— 跑完 build/ 里没有 vbox.log。两行留着，
旁边注明没生效：下一次换版本、或者改用 setextradata 时，那是起点。

这一趟还留下第二个事实，而它比日志更值钱：不挂链的测试照样能弄坏链。把这一条重新接上
之后，别的判据红了 —— 它自己换队头，消耗了信箱里一条消息，而那一条是后面几个测试等的。
被判据忽略，与被机器忽略不是同一件事。

=== 第七趟：日志给出了答案，而答案不在这一层 ===

VM 建在默认机器目录里，日志住在它的 Logs 子目录下（VBox 7 换了位置，所以前几趟一直
往上一级找，找到的是空）。unregistervm --delete 会把整个目录连日志一起删，于是日志
每趟都写了、从来没留下过。现在在删之前先复制一份到 build/。

日志里那一行是决定性的：

  /PDM/Queue/Keyboard/Insert   0 calls

整趟运行里，虚拟机的键盘队列一次插入都没有。也就是说宿主那些返回 0 的
keyboardputscancode 调用，从来没有变成队列里的一个键。客人机那一侧读到零个字节是对的，
它不是漏读，是没有东西可读。

而这条通路以前是通的 —— 事件行、移窗、未登记那几处都拿到过 4D。所以不是「这条路不通」，
是「这一次它没被当成一次键盘输入」。这一层再往下已经问不出东西了：从客人机看，这是一个
空队列；从宿主看，这是一个返回 0 的调用。两边都诚实，而中间那一段不在这个仓库里。

同级那一条因此第七次挂起，也是第一次挂在一个具体的外部事实上 —— 以前挂的是「我们不知道」，
现在挂的是「VBox 没把那次注入插进队列」。下一步要查的是 controlvm keyboardputscancode
在这一版上需要什么条件才真正入队。

=== 假红：那条 stderr 不是 node 说的话 ===

好几轮里运行的退出码一直是 1，而终端上只有一句「另一个程序正在使用此文件」。追到最后
发现它不来自这一层：命令写的是 cmd /c "node tools/run.mjs > build\run.log 2>&1"，而
cmd 自己写不动那个日志文件，于是把它自己的退出码 1 与那句 Windows 错误交给了外面。
node 其实跑完了，而且是通过的 —— 换成 PowerShell 的 Out-File 之后，同一份代码退出码是 0。

这件事的代价要说清楚：中间有六七轮，每一次红都被归因到「盘锁」与「VBox 残留」上，
而真正的错在测量工具。一条读数如果来自一层不可信的中介，它就不该被当成机器的结论。
这也是这一层反复学到的那句话的另一面：判据要问「这个数是谁给的」。

顺带补齐的三处锁，每一处都是同一条规则：poweroff，然后等状态真的变成 poweroff。

  一、build 删旧盘之前 —— 跑的顺序是先 build，而执行 build 的时候上一次 run 留下的
      VM 可能还握着盘的写锁。
  二、开工之前 —— run 自己的入口。
  三、第一趟结束到第二趟之间 —— 不等的话，第二趟 startvm 会说同一句话，而它出现在
      第一趟跑完之后，读起来像「第一趟把盘弄坏了」。

再加上清空串口文件时对 EBUSY 的重试：VBox 的 uartmode file 后端在机器关掉之后还会短暂
握着那个文件，而未捕获的那一次会把整趟掐在「五行都在」那一行，连「落盘」都不打。

修完之后两趟都通了：落盘读到 survived，包写的那一份也 survived。
