谁能写什么：语言归属与 SDK 的边界

用户点的三条（2026 那一轮）：
  一、Himeyuri 是 Yunooka 内默认的计算机语言。所有要进 Yunooka 的系统软件与组件
      （Nanodesu、Torikago、ChuniHydra、Oak Barrels、Ichiwatashi、KID）都要用 Himeyuri
      编写；纯净的 Yunooka 原则上只认识 HMYR 写出来的东西。
  二、Hiou Rengo（HIREN）是 Himeyuri 的 SDK，不是 Yunooka 的 SDK。而 KID 本身包含在
      HIREN 里，同时又被确认为 Yunooka 系统的一部分 —— 所以装 HIREN 时不能把 KID 装两遍。
  三、Yunooka 自己的 SDK 还没想好，可能会并入 HIREN 的计划。
  另有一条上位说法：Yunooka 最终要由完全态的 Himeyuri 编写。

这一份文件把三条摊成分层与判据。它与 design/NAMES.txt 那一份是两条轴：那一份讲「同一个
名字指的是不同的东西」，这一份讲「同一台机器上的东西各由谁写」。


一、四层，谁能写什么

第一层 引导链。引导扇区、第二段、把种子读进来。这一层必须是机器码 —— 总得有人在
  「还没有 HMYR」的时候把第一段字节放进盘的第 0 个扇区。所以它是汇编，而这不是妥协，
  是这一层的定义。

第二层 内核。页表、中断、堆、文件系统、以及那些原语（画一条线、算一个表达式、匹配一条
  签名）。这一层现在也是汇编，而它是要被重写的那一层 —— 用户说 Yunooka 最终由完全态
  的 Himeyuri 写，指的就是这一层往上的全部。剩下的问题是顺序，不是方向。

第三层 系统软件与组件。Nanodesu、Torikago、ChuniHydra、Oak Barrels、Ichiwatashi、KID ——
  全部用 Himeyuri 写。它们不是「Yunooka 的内置功能」，而是跑在 Yunooka 上的包。

第四层 应用。同理，Himeyuri。这一层现在一个都没有。

SDK 不在四层里。HIREN 是 Himeyuri 的 SDK（写东西用的那一侧），Yunooka 只负责跑 ——
这条分工写在 HMYR 仓库的 design/FULLSELF.txt 第七节，而 README 第一节也抄了一句：
「宿主口归 OS，其余归 SDK」。所以「Yunooka 没有自己的 SDK」不是缺口，是那条分工的结果。
将来若真要有，第一件要回答的是「它与 HIREN 的边界在哪」—— 而那要等 HIREN 那边先稳定。

二、「只认识 HMYR」这件事要有一个判据

一句「纯净的 Yunooka 只认识 HMYR 写出来的东西」如果不落到判据上，它就只是一句愿望。
它现在可以落成两条，而两条都能查：

  一、`identify` 对每一个系统组件都要答 package。那个函数已经有了（Kohane 第六层，
     按魔数 HMYRB 判断，不看扩展名）。所以「盘上这几个名字都是包」是一条能跑的判据。
  二、`files` 列出来的系统组件清单，与「那些必须住在基础库里的东西」那份清单要对得上 ——
     而后者在 design/NAMES.txt 与 PLAN 的 system-software 那一条里。

现在这两条都还不成立，因为一个系统组件都还没有。而它们现在就该写下来，理由与
design/GUARD.txt 第一节那句话一样：判据写晚了，实现会先长成别的形状。

三、KID 的两重身份：这条要变成一次安装检查

KID 同时是「Yunooka 系统的一部分」与「HIREN 里的一个成员」。所以：

  装 HIREN 前先查 KID 在不在；在的话，装 HIREN 时要把 KID 那一部分排除掉。

这一条的形状与 GUARD 那两份清单一样 —— 它是一次检查，不是一次小心的操作。「小心别装
两遍」会忘，而「装之前查一遍、查到了就跳过」不会。

而它同时暴露一件事：同一件东西可以同时属于两个集合。所以「安装清单」不能只是
「谁包含谁」的树，它还要有「已经在了就别再装」这一条。树回答「该有什么」，检查回答
「已经有了什么」—— 两个问题都要回答，而后者是运行时的事。

四、与现有实现的张力，以及它怎么解

现在 stage2 里有一批原生实现：Kohane 的六层（列盘、窗口、列条目、详情、分析）、
签名匹配、像素层与画线、表达式求值的一小块。按第二节的说法，这些东西的终点是 HMYR
包，而不是汇编。

那现在这批算什么？脚手架。而这两个字得说清，否则将来有人看到它们会以为方向错了。

它算脚手架的判据有两条，两条都是事实而不是态度：
  一、它们做的是「证明那条路走得通」—— 画一条线证明帧缓冲可写可读，认一个包证明魔数
     那一条路对，列一个目录证明预读区盖得住。证明完之后，真正的实现在 HMYR 那一侧。
  二、它们各自带着一条判据，而那条判据在 HMYR 版本上仍然要成立。所以它们是规格，
     不只是代码：`cross 403 403 same` 那句话在换成 HMYR 实现之后仍然要对。

所以顺序不是「先写汇编再扔掉」，而是「用汇编把判据钉住，再用 HMYR 满足同一批判据」。
钉住判据这件事本身就是产出，而它是唯一不会随着重写而丢掉的东西。

五、还差的

  HMYR 需要的内置：读文件、写文件。没有这两条，系统组件连自己的数据都读不了 —— 而
    它们在 design/FS.txt 第一百零八行那一处已经被提到了，只是还没做。
  Yunooka 需要能跑一个「有输入输出的包」：现在能跑 main 返回 7，而那是没有 I/O 的。
  一个真正的 HMYR 组件：第一批里最容易的是 Ichiwatashi 的一小块（画一个窗口的框），
    因为它的判据已经在 Kohane 第二层钉住了。
  安装检查：装 HIREN 时排除 KID 那一条，要有一次真的安装才有地方落。

六、Myon：宿主口的那一半

用户给了两条，而两条合起来是一件事：
  一、Yunooka 的 shell、terminal、控制台，名字是 Myon。三个词指的是同一件东西。
  二、Myon 可以当 HMYR 的窗口用：输入输出、渲染、桥接。

这句话解掉的是第五节那条「Yunooka 需要能跑一个有输入输出的包」。现在的 shell 是汇编写的、
只认一个词（files）、只回一行；而一个 HMYR 包连「读到一行字、把一段字写回去」都还没有
地方落。Myon 就是那个地方。

为什么这件事值得单独记下来，而不只是改个名字：名字落在哪一层，日后就决定了谁去改它。
若 Myon 只是 shell 的别称，它属于内核那一层，随内核一起被重写；而若它是 HMYR 的窗口，
它属于宿主口 ——
  一、进来的那一行字、出去的那一段字节，是宿主给语言的两条口子；
  二、渲染是第三条：一个 HMYR 包要画东西，不必自己知道帧缓冲在哪；
  三、桥接是第四条：宿主与包之间、或者两个包之间的东西由它转。
这四条都是宿主该提供的，而不是某一个组件该实现的。它与 SDK 那条分工同构：
「宿主口归 OS，其余归 SDK」，而 Myon 是宿主口的那一半。

判据现在还立不全，因为第四层一个包都没有。但形状可以先定下来：
  一、Myon 报出来的每一行仍然是固定形状（event= 开头、键值对、顺序固定）——
     判据只认串口，而串口那一侧正是 Myon 的。
  二、一个 HMYR 包通过 Myon 读一行、写一行。这一条成立之后，第五节的「内置：读文件、
     写文件」就不再是包里唯一的出路 —— 而那两条内置仍然要做，因为包要读自己的数据。
  三、渲染与桥接排在后面，它们要等 Ichiwatashi 那一小块（画一个窗口的框）先进来。

判据的进度：一行不再只有一个词
------------------------------

第二条判据的第一步落地了。

以前 shell 是拿前五个字节与 "files" 比的 —— 于是 "filesx" 也会被当成 files，而「一行
只认一个词、只回一行」那句话就是这样落在代码里的。现在切成「词 + 其余」，按词长与词
分派，而 echo 拿的正是「其余」那一部分。

两趟各测一个，而它们证明的是两件事。第一趟从信箱收到 "echo hello world"：输出里必须
有 hello world，那说明这一行被切开、词之后的部分作为参数传了过去。第二趟没有信箱、
从盘上 cmd.txt 读到 files：目录列表照旧，说明原有的那条没被弄坏。

为什么 echo 值得一条判据：它看着比 files 简单，而它要的不是一个命令名，是一整行字，
而这一整行字必须原样出现在输出里。一个「只认命令名」的实现过不了它。

验红的办法是把参数的起点错开一位：输出变成 "o hello world"，头一个字没了。

剩下的：包那一侧还没接。眼下读与写的两端都在宿主这一侧，而它们就是包将来要接的两个
口子 —— 下一个 HMYR 包应当能调用它们，而不是让汇编替它读。那一步要动 HMYR 的内置表，
排在后面。

写那一半落地了
--------------

第二条判据的「写」那一半走通了：盘上的 prog.hmtn 现在有两个函数 —— main 返 7，
echo 压一个串常量、调内置 write、返回。串口上出现的是那段字本身，而它是包里的字节，
不是宿主里写死的字符串。

内置表原先只有 len。加 write 之后，一个包第一次能往外说一句话，而它不必知道串口在
哪个端口 —— 这就是「出去的那一段字节」那条口子。

判据两条：`event=myon write ok` 必须出现，而且它前面必须有 `myon here`（包里的字）。
两条一起才排掉「一个永远报 ok 的实现」。验红：把 write 里那一次 putc64 拿掉，字不再
出现，判据红。

路径上撞到两个真的结构上限，都记在这里：

一、根目录只有一个扇区，而 fs_lookup 只读一个扇区。加一条 29 字节的条目会让它溢出，
    症状是构建抛 RangeError，不是「少一条」。所以 echo 没有做成独立的包，而是并进
    prog.hmtn 的第二个函数 —— 多函数本来就是包格式支持的东西，所以这不是妥协，是把
    已有的形状用起来。扩根目录要动查找，那是另一件事，不该由一条判据来推动。

二、预读的扇区数是一次又一次被顶上去的：auth.bin 落地时从 23 到 24，这一轮一度到 25，
    并进 prog.hmtn 之后回到 24。这个数由 build 核对，所以它不会悄悄错 —— 但它每次
    都提醒同一件事：盘上每多一份文件，就有三个数要跟着动。

读那一半也落地了，判据二完整
----------------------------

第二条判据走通了：一个包通过 Myon 读一行、写一行。

内置表现在有三个：len、write、readline。readline 把宿主攒的那一行交给包，形状是包里
认的「u16 长度 + 码元」；write 把包给的串打到串口。

盘上 prog.hmtn 的 echo 函数现在是五条指令：压串、write、readline、write、返回。串口上
出现的是：

    myon here
    echo hello world

第一行是包写死的，第二行是这一趟运行时从外面进来的。而第二行才是判据真正的价值 ——
一个「打印固定字符串」的实现过不了它。

判据卡的是顺序而不只是存在：`echo hello world` 在串口上出现两次（shell 的回显，与包
打出来的），只查「有没有这个串」会被前一次满足。所以要的是「`myon here` 之后紧接
`echo hello world`」—— 那个顺序只有包里的那几条指令能给出。

验红：让 shell 不记那一行的位置（把 sh_line_ptr 置零），readline 拿到空，第二个 write
打出一个空行，判据红。

一个内置分派的坑，记在这里：try_write 那一段的长度检查原来直接跳 unknown，于是
readline（长度 8）根本没机会被试到。症状是 `unknown builtin`，而它看起来像「名字写
错了」——分派的出口要一路往下试，而不是一有不对就放弃。

长度截到 255 个码元。超出的部分不交给包，而不是静默截断：这一版没有「包读到一半还想
再要」的机制，所以给它的必须是一整行。

还缺的：渲染与桥接（要等 Ichiwatashi 那一小块），以及「包读到长行」这件事。

渲染的第一步：一个包让宿主画一个框
----------------------------------

第三条判据说「渲染与桥接排在后面，要等 Ichiwatashi 那一小块」。这一轮落的就是那一块的
最小版本：内置 border，零参数，画一个 (10,10) 到 (100,60) 的框，颜色 0x2F。

坐标与颜色写死不是偷懒。这一步要证明的是「包能让宿主画」，而通用绘图是 Ichiwatashi
自己的事，排在它后面。四条边用同一个 draw_line，所以这一条内置换来的是十六个像素，
而不是四段画线代码。

判据读三个点：(10,10)、(50,10)、(100,60)。三个位置隔着三百二十字节的步长，所以它不只
证明「有一个像素亮了」，还证明那个框的尺寸与位置是对的。三个都必须是 0x2F。

验红：把上边的终点从 (100,10) 挪到 (100,20)，那条线斜了，中间那个点不在线上，判据红。

画之前 r12 到 r15 必须先存起来：draw_line 不保存它们，而 exec 用 r12 指指令流、用 r13
数指令数。改坏了它们，症状是「包跑完第一条就乱跳」，与画图毫无关系。

同一个分派的坑出现了第二次
--------------------------

try_readline 的失败出口又跳了 unknown，于是 border（长度 6）没机会被试到，症状还是
`unknown builtin`。

同一个错在一轮里出现两次，说明问题不在某一次手滑，而在那条分派链的形状：每加一个内置，
就要回头改上一个内置的失败出口。现在它有四个出口（len 成功、write、readline、border、
最后 unknown），而它迟早会长到改不过来。

下一轮如果还要加内置，应当先把它换成一张表：名字、长度、处理者三样一起放，循环比。
那时「加一个」是加一行数据，而不是四处跳转。

内置表：一条链换成一行数据
--------------------------

四个内置（len、write、readline、border）现在靠一张表找，不再靠一条跳转链。

换的理由不是抽象的好坏：那个错在一轮里出现了两次。readline 加进去时，write 那一段的
失败出口直接跳 unknown，于是 readline 没机会被试；border 加进去时，readline 那一段也
是同样的毛病。两次的症状都是 `unknown builtin`，而那看起来像名字写错了。

链条的形状才是问题：每加一个内置，都要回头改上一个内置的失败出口。现在它有五个出口，
迟早改不过来。

表项三样：名字长度、名字指针、处理者。循环比，比中了跳过去。加一个内置是加三行数据，
不动任何跳转。

处理者用全名引用（exec.op_len 之类）：它们是 exec 的局部标签，而表在数据段。nasm 接受
这种跨段的引用，这是这张表能在这一版里落地的原因之一。

判据：四个内置都有既有的判据（len 走 is_digit，另外三个走 myon 那一条）。所以这一轮
的验红是「表项的处理者被真的用了」—— 把 len 那一项的处理者改成 op_write，名字还是
len、动作换了，is_digit 立刻坏。

一次重构的判据不该是新的，而该是旧的：四个旧判据全绿，才说明表换对了。

解释器真的能算
--------------

在这之前，包能做的表达只有两样：返回一个常量（main 返 7）、让宿主做事（write /
readline / border / runpkg）。两者都不经过算术。

而「住得下 HMYR」里最要紧的一条是解释器真的能算 —— 一份编译器产出的字节码不会只有
常量与内置调用。

所以 prog.hmtn 加了第三个函数 sum：常量 40、常量 2、add、返回。判据要 `prog sum -> 42`，
而 42 在这个仓库里没有别处出现过 —— 它不可能来自宿主里写死的数，只能来自包里那两条
常量与一次 add。

40 与 2 挑得没有讲究，只要和是 42。验红把它改成 41，和变 43，判据红。

同一个包里的三个函数现在各走一条路：main 走返回值、echo 走宿主口与桥接、sum 走算术。
它们共享一个包头与地址空间 —— 而「两个独立的包」那一条由 docs/myon.hmtn 单独压着。

这几个数与阶段的对应
--------------------

盘上一个包能被执行、能当场算、能用宿主口、能画框、能让宿主跑另一个包 —— 五样都在，
而且各有判据。剩下的是「一份真实的 HMYR 编译产物能在这里跑起来」，而那份东西在上游
仓库里，不在这一侧。

第二段的 128 是三处落点
----------------------

`stage2_sectors` 现在写 117，而上限是 128。那个 128 不是挑的，它有三处落点，而三处
必须同时成立：

一、加载器读两批各 64 扇区：第一批从 0x10000 起，第二批从 0x18000 起，
    而 0x18000 + 64 × 512 = 0x20000。
二、0x20000 是种子 —— `pkg_base` 的默认值就是它。
三、预读区在 0x40000，那还在更后面，轮不到第二段用。

所以「第二段再长一点」要付的代价不是改一个数，而是挪种子。而种子被 `pkg_base` 等着，
挪它要改所有直接读种子区的地方。

那段注释原先写的是「主体住 0x30000，上限 0x40000」—— 两个数都不对。它大概是更早那一版
加载器的记忆，而加载器后来改成了两批。这种注释比没有更坏：它让人以为还有 128 扇区的
余量。

于是 build 现在会在第二段超过 116 个扇区时说一句「只剩 N 个扇区」。116 这个阈值不是
「快到了」的估计 —— 写下这一条的时候第二段占 117，所以它在此刻就说话。一个要等到
明天才响的提醒，与没有提醒差不多。

整张内存地图在 design/MEMORY.txt：它把 0x10000 到 0x400000 之间每一段都数了一遍，
并说明三条挪种子的路各自为什么不通。结论是现在不动 —— 十一格是 5632 字节，而过去二十
几轮的增量大多在数十到数百字节之间。重排内存地图会让所有判据同时受影响，它应当在有
明确需要的时候做，不应当在为了多几格的时候做。

判据的判据：tools/audit.mjs
--------------------------

二十几轮下来，run.mjs 里已经有七十一个判据。而一个判据有两种坏法：它可能算错，也可能
根本没接在链上。前者会被红抓到，后者永远安静。

所以有了 tools/audit.mjs，它查三件与机器无关的事：判据有没有被引用、PLAN 的 after 指不
指着存在的目标、design 是不是纯文本。

它第一次跑就抓出十三处 —— 十三个 design 文件里有八十八处 markdown 加粗。那些星号不会
渲染，只会让读的人在两个星号之间读到一段他以为被强调过的话。信息没丢，而写法在假装有
个渲染器。

它自己也漏过一次：头一版是逐行找星号，而有一对星号跨了两行，于是那一处留了下来，而它
报了「十七个文件都没有」。改成全文找之后才看见。一条检查的第一版也会犯它要查的那种错。

它不进 run.mjs 的那条链：那条链验的是这台机器，这一份验的是我们写下来的东西有没有自相
矛盾。两者都会红，但红的含义不同 —— 混在一起会让「机器坏了」与「文档写歪了」长得一样。

它的第四项方向相反：串口上打了 event= 的行，有没有判据在读它。

第一次跑报出四个：ptmul、ptenc、ptdec、guard.nopatch。前三个是纯仪式 —— 同一个函数
上面已经把读数打出去了（ptm、pte、ptd），而「ok」那一行既不能替换读数，也不能在读数错
的时候变红。删掉。

guard.nopatch 不一样：它说的是「这一趟没有补丁」，而那正是 --drop-nopatch 那一趟要证明
的东西。所以给它加了一个读它的人（无补成），而不是删掉它。

而删那三行正好省下一个整扇区 —— 第二段从 117 落到 116。这件事本身就是一句提醒：那种
「打了没人读」的行不只是噪声，它占着这个仓库最紧的那个资源。









包能决定画在哪里
----------------

内置表加了 rect：五参数（x、y、宽、高、颜色），画一个填充矩形。

这是 border 的下一格。border 的坐标写死在宿主里，那只能证明「包能让宿主画」；rect 证明
的是「包能决定画在哪里、画多大」—— 而后者才是渲染，前者只是一次演示。

判据读四个点：三个来自 border 的 (10,10)、(50,10)、(100,60)，第四个是包那个矩形的中心
(140,30)。前三个是 0x2F，第四个是 0x1C（包自己给的颜色）。

验红试了两个参数，而第一个没红 —— 把 x 从 120 挪到 130，采样点 (140,30) 仍在矩形
（130..170）里，所以串口上一点没变。改宽才有用：宽从 40 收到 10，矩形只到 130，采样点
落在外面，读回 0F。

那一次没红很值得记：判据的采样点在矩形内部，所以它对平移不敏感、对尺寸敏感。一个判据
能过，只说明它采的那几个点对；它不说明别的点也对。


包画出了一个窗口
----------------

prog.hmtn 的第四个函数 win：三个矩形，底色 (60,80,200,90)、标题栏 (61,81,198,12)、
内容区 (61,94,198,75)。一个包画出了一个有结构的东西，而不只是一个盒子。

判据读三个点，各在一个区里：标题栏 0x1C、内容区 0x0F、底色 0x1F。它同时证明三件事：
三个矩形都真的画了、顺序对（后画的盖住先画的）、偏移对（错一格就会读到相邻那一层）。

而它比 rect 那条强：rect 只画一个矩形，一个「永远画同一个矩形」的实现也能过。

第一次跑出的是三个 1F。那不是 rect 坏了，是包里只装了六条指令 —— writeUInt32LE 那里写的
是 窗口矩形.length * 2，而每个矩形是六条指令（五个常量加一次调用），三个该是十八条。
症状是「三次调用拿到同一份参数」，而真相是「后两次调用根本没有指令去执行」。

一个数字差三倍，而那三倍正好是一个「每个矩形六条」的常识。指令数写错时的症状与参数传错
时一模一样 —— 都是「后面那些没有生效」。

验红：把标题栏从 y=81 挪到 y=91，第一个采样点落回底色，读到 1F。


文件读取：内置在，包那一侧的调用还没接上
----------------------------------------

内置表加了 slurp：一个参数（路径，从 α:/ 之后写起），返回那一份文件的内容成一个串。
盘符由内置补上 —— 一个包不该知道盘符。

它是 self-host 的第一块。self-host 的 notes 原先说「读源文件、写目标文件那两件事要的
对象模型与文件写入都还没有」—— 写入早就有了（fs_write_file），缺的是读。而在这之前，
「读」只有一个口子：readline 读的是宿主攒的那一行，不是文件。

一个位置上的坑：fs_open_path 用 rbx 交回字节数，而 rbx 在 exec 里是 pc。所以 slurp 里
必须先把它存起来再调用 —— 否则症状是「包读完了文件就跳到别处」，与读文件毫无关系。

而包那一侧的调用没有留下来。试着让 echo 读 docs/sub/deep.txt 再打出来，结果它断在
readline 之前：串口上 myon here 之后什么都没有，连 echo hello world 都不出现。那不是
「slurp 返回错了东西」，是它把执行流带偏了。

所以包里那条调用撤了，内置与它的注释留着。一条红的判据会有人说点什么，而一条把后面
全部遮住的红会让人先去看别的 —— 后者更贵。


unknown op 100：错位只可能来自扫描
----------------------------------

让 win 调 slurp，串口上是：

    unknown op 100
    Yunooka: exec ran out at 19 21
    Yunooka: win px 1C 1F 1F

op 100 是 0x64 —— 字符 d 的低字节。而编出来的字节里，d 只出现在路径 docs/sub/deep.txt。

上一轮那句「断在 readline 之前」是错的：readline 在 slurp 前面，所以 slurp 不可能是那个
原因。那句话说清了一件更要紧的事 —— 我没读懂自己刚截取的那段输出。

而错位的位置只有一个来源：exec 从 instr_offsets 取每一条指令，而那张表由 scan_instrs
与 imm_shape 建。rsi 怎么前进都影响不到它。

所以下一个要看的是扫描，不是 rsi。下一轮从 scan_instrs 查起：形状 6（名字 + u16）对
builtin 与 call 是同一个形状，而两边只有 builtin 会在这条路上被扫到。


scan op 100：起点已经偏了
-------------------------

在 scan_instrs 里加了一条诊断：opcode 超过形状表长度（34）就报一行。因为 imm_shape 后面
紧跟着 line_letters，越界读到的会是字符 'Y'，而 'Y' 落到「8 tuple」那一支上跳两字节 ——
偏移表会从某一条起全部错位。

把 slurp 的调用加回去之后，串口上是：

    Yunooka: scan op 100
    unknown op 100

所以错位发生在 scan_instrs 之前 —— 也就是 find_fn_by_name 交给 r12 的那个「函数体起点」
已经偏了。scan_instrs 从 r12 起、按 skip_imm 走，它读到 100 说明 r12 本身就在串里。

而 win 与前面三个函数（main、echo、sum）的区别只有一处：它是第四个。

find_fn_by_name 找名字的办法是「跳过前面每一个函数体」—— 用 r13 里的指令数配 skip_imm。
前三个跳得对，第四个就对不上。所以下一轮要在那一段 .skip 循环里找，而不是在 scan_instrs
或 exec 里找。

诊断留着：它在下一次有人调 slurp 的时候会先说话。


判别性实验：slurp 在第一个函数里能工作
--------------------------------------

上一轮说「问题在 find_fn_by_name 跳过前面函数体那一段」，而那只是一种可能。一个实验把它
变成了结论：把 slurp 放进 main —— main 是函数表的第一个，找它时一条函数体都不必跳过。

结果：

    Yunooka: prog main -> 7
    Yunooka: prog sum -> 42
    Yunooka: scan op 100
    unknown op 100

main 跑完了（7 出现），而 scan op 100 出现在 prog sum -> 42 之后 —— 也就是轮到 win
（第四个）的时候。

所以三件事同时成立：slurp 本身没问题，scan_instrs 没问题，而「第四个函数的起点」有问题。

跳过 main(5) + echo(13) + sum(4) = 22 条指令之后，rsi 就偏了。而那 22 条里只有三类形状：
值（常量）、名字加 u16（内置调用）、以及返回。三类都在别处用过。

一句题外话：这个实验花了一次构建与一次运行，而它把「三个可能的桶」缩成一个。前两轮都是
在猜，这一轮是在问 —— 差别在于这一次的问题有一个只会二选一的答案。


差 27 字节：不是一个「跳过算错」
-------------------------------

在 find_fn_by_name 的 .each 里加了一条诊断，打印头五个函数头的位置与名字长度。

prog.hmtn 那一次调用读出来是：

    0x43009 len=4
    0x43043 len=0
    0x4304F len=0
    0x4305B len=0
    0x43067 len=0

第一个是对的：0x43009 是 pkg_base + 9，长度 4 正是 main。而跳过 main 的体之后 rsi 落在
0x43043，名字长度 0 —— 那不是第二个函数头。

算一下正确的那个：main 的头是 2 + 8（名字）+ 2 + 2 + 2 + 4 = 20 字节，指令体是 11 字节
（常量 7 的 1 + 1 + 8，加返回的 1）。所以下一个函数头应当是 0x43009 + 20 + 11 = 0x43028。

而它落在 0x43043 —— 差了 27。

27 既不是 11 的倍数，也不等于任何一段的长度。所以「skip 循环少跳或多跳一条指令」这个
解释对不上。更可能是：读第二个函数头的时候，rsi 已经不是「上一条指令之后」那个位置了。

下一轮要在 .skip 循环里逐条打印 rsi，而不是只看函数头 —— 函数头之间的差是结论，而中间的
每一条才是证据。

那条诊断撤了：它会打一百多行（find_fn_by_name 每次扫到 400 个函数头才放弃），而一个
只在人工读的时候存在的诊断与没有差不多。留下的这一段注释与 design 里的数才是它的产出。


rsi 是对的，r13 是错的
----------------------

上一轮那个「差 27」否定了一个解释。这一轮在 .skip 循环里逐条打印 rsi，拿到了两个数：

    0x4301D  count=3

0x4301D 正是 main 指令流的起点（0x43009 + 20 字节的函数头），所以跳过的起点是对的。

而 r13 读成了 3 —— main 的指令数是 2。

两个数放在一起只说一件事：find_fn_by_name 在 .effed 那里读到的「指令数」不是这个函数的
指令数。多读 1 条之后，跳过的字节数自然对不上，而那个 27 就是从这儿来的。

所以下一轮要查的是 .effed 那几行对 prog.hmtn 的头到底算到了哪里：名字长度、跳名字、
加四（参数量与槽数）、效果数、加二、然后读指令数。build 写头的顺序是名字长度、名字、
参数量、槽数、效果数、指令数 —— 两边应当一致，而那正是要核对的地方。

那个诊断已经撤了，而它给出的这两个数写在这里：一个诊断最大的价值是它留下的数，不是它
打印的每一行。


那 27 是我算错了地址
--------------------

前两轮把「差 27」当成一个待解释的现象。这一轮去盘上读 prog.hmtn 的头，才发现那个地址
根本不是 prog.hmtn。

prog.hmtn 在 数据起 + 5，而 数据起 = 文件系统起 + 3 = 1027，所以它是第 1032 个扇区 ——
预读区里 0x40000 + (1032 - 1024) * 512 = 0x41000。

而诊断过滤的 0x43xxx 是 0x40000 + 24 * 512，也就是第 1048 个扇区 —— 那是 docs/myon.hmtn。

于是那两行「0x4301D count=3」说的是 myon.hmtn：它只有一个函数 echo，指令数正好是 3，
而 0x4301D = 0x43009 + 20 正是 echo 指令流的起点。跳完三条之后落在函数表末尾、读到长度
0 —— 全部正常。

所以 find_fn_by_name 一直是好的，而「差 27」不是 bug 的症状，是我把两个包的位置搞混了。

这一课不是「要小心」，而是「一个地址必须有出处」。0x43xxx 是我从 grep 里顺手拿的一个
数（那是 fs_myon_path 的邻域），而 prog.hmtn 的位置写在 build 的 数据起 + 5 那一行里。
两者差 16 个扇区，而它们在我脑子里是同一种「包地址」。

scan op 100 仍然是真的：那次是 run_win_test 扫 prog.hmtn 找 win，而 win 是第四个函数，
所以要跳过 main(2) + echo(13) + sum(4) = 19 条。下一轮看那 19 条 —— 而这一次地址要先用
0x41000。


地址对了之后：前面三个函数体跳得一点没错
----------------------------------------

用 0x41000（prog.hmtn 真正的地址）重做那个诊断，跳过那十九行全部对得上：

    0x4101D #0  →  0x41027 #1   差 10（常量 7）
    0x4103C #0                   main 不匹配，进 echo
    0x41052 #1   差 22（常量 "myon here"）
    0x41061 #2   差 15（write）
    0x41076 #3   差 21（readline）
    0x41085 #4   差 15（write）
    0x41096 #5   差 17（border）
    0x410A7 #6   差 17（runpkg）
    0x410B1 #7   差 10（常量 120）
    …… 五个常量各差 10，然后差 13 是 rect
    0x410F9 #0                   sum
    0x41121 #0                   win

每一条的相邻差值都等于它该有的长度。所以前面三个函数体跳得一点没错，而 find_fn_by_name
在这一段上是干净的。

问题只在 win 自己的体里：

它的指令流从 0x41121 起、共二十一条（3 + 18），总长应当是 38 + 15 + 15 + 3 × 63 = 257
= 0x101，于是最后一条应当在 0x41221。而诊断打出来的是 0x41205 —— 差 28。

所以不是「从头就错」，是走到了后面的某一段才错。下一轮在第十八条之后那一段找。

一个方法上的收获：同一个诊断、同一个函数，只是把过滤地址从 0x43xxx 换成 0x41000，结论就
从「跳过算错」变成了「跳过完全正确」。上一轮那个错地址让两轮推理都白走 —— 而它们当时
看起来很自洽。


扫描从第零条起就只跳了一个字节
------------------------------

win 的指令流起点是 0x41121。盘上那里的字节是：

    0x121  05 01 00 00 00 00 00 00 00 4E 40
           ↑  opcode 5（常量）  ↑ 种类 1（数）  ↑ 后面八个字节是 60.0 的 f64

所以那是一条完整的常量指令，长 10 字节。

而 scan_instrs 打出来的是：

    0x41121 #0
    0x41122 #1
    0x41124 #2
    0x41124 #3
    0x41124 #4   ← 从 #2 起不动了

第 0 条只前进 1 字节 —— 那正好是 scan_instrs 自己那句 inc rsi（跳过 opcode）。也就是说
skip_imm 收到的是「跳 0」那一支，一个字节都没跳。

于是第 1 条从 0x41122 起 —— 而那里是种类字节 01，被当成 opcode 1（u16），跳 2 字节；
第 2 条从 0x41124 起，那里是 00，opcode 0 的形状是 0 —— 从此原地不动。

所以整条错位链的起点是「第一条常量没有按值编码处理」。imm_shape[5] 是 7，而 7 会走
.value（读种类）再走 .v_num（跳八字节）。下一轮要查的是 skip_imm 在那里到底收到了什么。

两个方法上的收获：一、盘上的字节比任何推理都可靠 —— 这一轮是先把 0x121 那段打出来才看清
「只跳 1」意味着什么的；二、原地不动的那几行（#2 到 #17）本身就是证据：一个「跳 0」的
形状会让游标停在同一处，而它一旦出现，后面的每一条都跟着错。


那十八行「scan at」是误读
-------------------------

上一轮从扫描的位置序列里得出一个结论：第 0 条只前进 1 字节，于是 skip_imm 走了「跳 0」，
整条错位链从那里开始。

这一轮直接量了一次：shape=7，而 rsi 的前后差是 9 字节 —— 正好是「读种类一字节、再跳八个
字节的 f64」。所以 skip_imm 对 win 的第一条完全正确。

那上一轮那十八行是从哪来的？打印条件是 cmp rax, 0x41100 / jb —— 而 rax 在那一行之前已经
被 movzx eax, byte [rsi] 改成了 opcode（5）。5 永远小于 0x41100，所以那个「只打 win 那一段」
的条件从来没有生效过，而打印出来的位置属于别的调用。

一个诊断自己也会犯它要查的那种错。这是第二次：上一次是逐行找星号而漏掉跨行的那一对。

所以现在的结论是：前三个函数体跳得对，win 的第一条也跳得对。scan op 100 仍然是真的
（它只在包调 slurp 时出现），而它不在这两处。

下一轮换一种办法：不猜位置，直接让 scan_instrs 在读到超过 33 的 opcode 时把它前面的
那几个字节打出来 —— 那能说明它落在了什么中间。


win 的体在 0x1DE 结束，之后全是零
--------------------------------

从 0x1DE 往回看那一段：

    0x1d0  40 03 04 00 72 00 65 00    ← 上一条 f64 的尾巴、03（调内置）、名字长度 4、"re"
    0x1d8  63 00 74 00 05 00 1c 00    ← "ct"、参数个数 5、1C（返回）
    0x1e0  00 00 …                     ← 从这里起全是零

所以 win 的最后一条指令是返回，落在 0x1DE。而那之后是 Buffer.alloc 没被写到的部分，
全是零。

一个 opcode 为零的字节，形状也是零 —— skip_imm 会跳零个字节，游标原地不动。所以扫描一旦
走到「体之后的零」，它就会停在那儿，直到 r13 用完。

这和前几轮那些位置都对得上：错位不是发生在某一条指令的长度上，而是发生在体的末尾。而
0x41202 那个 d 属于别处的一个 deep.txt 串 —— 也就是说那次扫描的游标根本不是从 win 的起点
一路走过来的，或者它走到了更后面。

下一轮先把「win 的二十一条到底覆盖到哪个地址」算清楚：从 0x121 起加 38 + 15 + 15 + 18 条
矩形指令，与 0x1DE 比。如果加起来大于 0x1DE，那说明二十一条超过了体的实际长度 —— 而那就
是错位的来源。


一份完整的 prog.hmtn 布局
------------------------

这一轮写了二十行解析器，从包的第九个字节开始，按 build 写头的顺序逐函数走到尾。它给出的
一张表比前面几轮的推算都可靠，因为它不依赖任何一处手算：

    main  @0x1009  头长 20  指令 2   体 0x101d..0x1028（11 字节）
    echo  @0x1028  头长 20  指令 13  体 0x103c..0x10e7（171 字节）
    sum   @0x10e7  头长 18  指令 4   体 0x10f9..0x110f（22 字节）
    win   @0x110f  头长 18  指令 18  体 0x1121..0x11de（189 字节）
    整包到 0x11de

四个函数每一个都自洽：win 的体是 189 字节，而 3 ×（5 × 10 + 13）正好是 189。

所以现在这一版（win 十八条）是干净的，而上面那张表也解释了前几轮那些数为什么对不上：
win 有二十一条的那一版，它的体比现在长六十八字节（路径 38 + slurp 15 + write 15），
起点仍然是 0x1121，而终点就不是 0x11de 了。

于是那个落点 0x1202 —— 它落在二十一条那一版的中段，而那正是「路径串」之后的位置。错了
一步，而错的那一步在二十一条那一版的体里。

下一轮把二十一条那一版也解析一遍：同一段脚本、只改 build 里 win 的指令数，看它的体走到哪
一字节、而第五条之后每一条的位置又是多少。


两套独立规则读到同一个 100
--------------------------

上一轮写的那段解析器（二十行，按 build 写头的顺序走）与固件的 scan_instrs（按 imm_shape
与 skip_imm 走）是两套独立的规则。这一轮把它们放在同一版二十一条的包上，结果：

    !! 未知 opcode 100 在第 19 条
    op=100 at 0000000000041202

同一个位置、同一个 opcode。

两个独立实现给出同一个答案，那说明错的是 build 写出来的那一串字节，不是固件的扫描。这条
推理比前面几轮任何一次都硬 —— 前面的每一次都是在固件内部找原因，而这一次两边互相印证。

而解析器给出的体是 0x1121..0x1203（226 字节），而二十一条按设计应当是 257 字节 —— 少了
31。

所以下一轮的题目很明确：build 在写 win 那二十一条时少写了三十一个字节，而少在哪一段，
把它逐条按设计长度累加一遍就知道。

（那段解析器是临时的，放在 scratch 里。它的价值不在代码，而在于它证明了「build 与固件
用了两套规则」这件事；两套规则同时错的可能性远小于一处错。）


漏掉的那一条是返回
------------------

把 win 的体逐条走一遍（从包内偏移 0x121 起，按 build 的写法），十九行全部合法：

    #0  0x121..0x12b  常量
    #1  0x12b..0x135  常量
    #2  0x135..0x13f  常量
    #3  0x13f..0x149  常量
    #4  0x149..0x153  常量
    #5  0x153..0x160  builtin rect 参5
    …（后面两个矩形同样）
    #17 0x1d1..0x1de  builtin rect 参5
    #18 0x1de..0x1df  ret

十九条，而声明的指令数是十八。少的那一条正是返回。

一个「指令数漏一条」的 bug 而症状很特别：矩形都画了，所以 win px 三个点全对；而 exec 跑完
十八条之后 pc 就等于 r13，直接停下 —— 返回那一条永远不执行，win 从来没有真的返回到调用者。
一个少了返回的函数，看起来与一个正常的函数一模一样。

修法是把声明改成 length * 6 + 1。改完之后解析器与固件给出的都变了：win 十九条、体 190
字节、整包到 0x11df，而串口上 win px 仍是 1C 0F 1F。

顺带记一件自己的错：这一轮我读的是 build/failed-run.txt，而它是上一轮留下的 —— 里面那行
win px 是旧值，于是我把一个正确的运行看成了错的。run.mjs 在失败时写那个文件、成功时不清，
而「先看它」是之前几轮养成的习惯。要看的永远是这一次的 run.log，除非失败。


根因：一个写死的偏移与一个会长大的文件
--------------------------------------

把 slurp 的三条加回 win，包从 479 字节涨到 547，也就是从一个扇区涨到两个。而文件系统里
后面每一个偏移都是「文件系统起 + N」写死的形状：

    子目录2号   = 文件系统起 + 9
    深层文件起  = 文件系统起 + 10
    规则起      = 文件系统起 + 13
    绘图起      = 文件系统起 + 14
    假样本起    = 文件系统起 + 15

于是 docs/sub 正好压在包的第二扇区上。而症状不是「布局冲突」—— 它是扫描在包内偏移 0x202
读到 0x64（字符 d），那是 "deep.txt" 那个目录条目里的码元。

把 子目录2号 改成跟着程序包大小走之后，一次运行里三件事同时变了：

    win px 000000000000001C 000000000000000F 000000000000001F
    （scan op / unknown op 都不再出现）
    Yunooka: open docs/sub/deep.txt -> ...

也就是说：前十几轮追的那个错位，根因就是这一处布局。而它之所以查了这么久，是因为它的
症状（一个落在串中间的 opcode）与它（扇区被目录条目盖掉）之间隔了三层。

而修它不能只改一处：程序包长一个扇区，它后面七个写死的偏移都要加一。所以这一轮退回了
一扇区，并把「重排布局」列成下一件事 —— 那要先有一个能一次算完所有偏移的写法。

一条值得记的教训：一个「长度会变的文件」与一串「写死的偏移」放在一起，那个文件长大的那一天
就是这一串偏移全部错位的那一天。而症状会出现在离布局最远的地方 —— 这一次是解释器读到
一个字符 d。


重排试过一次，卡在「最后一份扇区」
----------------------------------

这一轮把数据区的七个写死偏移换成了「一份清单 + 一次累加」：

    const 数据区清单 = [
      { 名: "hello.txt", 内容: () => 盘上示例, 扇区: 1 },
      ...
    ];
    let 游 = 数据起;
    for (const f of 数据区清单) { f.起 = 游; 游 += f.扇区 ?? ceil(f.内容().length / 512); }

而它一路撞了三件事：内容变量定义在清单之后（要 thunk）、thunk 在累加时求值还是会撞
（要把累加挪到所有定义之后）、以及一条太贪的正则把「码元」函数的头吃掉了。

三件都修好之后 build 通过了，而机器起不来：串口上缺 stage2 ok、protected mode ok、
long mode ok、heap ok。而 build 的输出里那句「最后一份在第 9 号」就是线索 ——
最后一份扇区 算成了九，于是预读区只盖到 1033，而盘上的文件在 1048 附近。

那一处不在清单里：最后一份扇区 来自 外五件 → 签名 → 核心清单 → 假样本起 那条链，
而清单只覆盖到 假样本起。链式的那一半没跟着走。

所以这一轮退回了 build.mjs，而把重排留成下一件事 —— 且这一次它有了一个明确的边界：
清单要覆盖到最后一份文件（外五件与 myon.hmtn 都在链尾），而 最后一份扇区 要从清单的
终点算，不是从链尾的某一个变量。

一条方法上的记录：这次改动连着撞了四个错，而每一个都在不同的层（作用域、求值时机、正则、
以及链尾）。四个都修好才到「build 通过」，而 build 通过之后才暴露第五个（布局的终点）。
一次大改的正确性不会在第一个绿灯处出现。


第二次重排：预读对了，机器还是起不来
------------------------------------

按上一轮定下的两条边界重做了一遍：清单覆盖到链尾（外五件与 myon.hmtn 都在里面），而
最后一份扇区 从清单的终点算。

这一次撞的坑与上次不同，而每一个都能定位：

  一、内容变量定义在清单之后 —— 而这一次清单直接写内容，所以要把清单挪到所有定义之后。
  二、挪到「子目录2 之前」之后，超级块（在它之前）又用不上 示例扇区数 —— 于是再往前提。
  三、提到 超级块 之前之后，子目录2 还没定义 —— 而它只用来算一个扇区，所以换成占位缓冲。
  四、一条正则第二次吃掉「码元」函数的头 —— 与上一轮同一个地方。

四件都修好之后 build 通过，而 build 说「最后一份在第 1048 号 —— 盖得住」—— 那是对的，
上一版算成 9。

而机器起不来：串口只有一行 boot ok，而 stage2 ok 没有出现。引导扇区读到了，加载器没把
第二段带起来 —— 或者带起来了而它没跑。

这一处没查清。两段的位置（引导 1 + 加载器 8 + 主体 121、种子第 130 扇区起）在 build 的
输出里都是对的，所以问题不在那三个数上。

于是又退回了一次。而两次失败的形状值得并排放着看：

  第一次：清单只到 假样本起，最后一份扇区 算成 9，预读盖不住 —— 症状是缺五行。
  第二次：清单覆盖到链尾，最后一份扇区 算成 1048，预读盖得住 —— 症状是只有 boot ok。

同一个改动，两次失败在两个不同的地方。而第二次的那个位置比第一次更早 —— 早到「文件系统
这一层根本没轮到」。这提示一件事：布局改动会先影响启动，再影响文件系统，而这两层之间
隔着加载器与第二段 —— 一个只有一行串口的地方。


第二趟的串口终于留下来了，而它先抓到的是我自己
----------------------------------------------

「落盘」那条判据一直红：第二次启动没有报 persist survived a reboot。而第二趟的串口只存在
内存里，关机之后就没了 —— 所以「第二趟没到」这句话一直没有证据。

这一轮让它落一份文件（build/serial2.log），而第一次读到的第二趟是：

    Yunooka: boot ok
    Yunooka: stage2 ok
    Yunooka: seed unreadable
    Yunooka: fs preread failed
    Yunooka: mailbox ok

两行新东西：seed unreadable 与 fs preread failed。

而这两行来自我这一轮加的那个诊断字符。加载器里为了在 boot ok 之后说一句话，写的是

    mov al, [dbg]
    mov dx, 0x3F8
    out dx, al

而 dx 里的 dl 存着盘号（mov dl, [drive]）。改掉它之后，后面那次 int 0x13 读种子就失败了
—— 症状是 seed unreadable 与 fs preread failed 两行，而它们与「盘号」毫无关系。

回退之后，同一个 serial2.log 上是：

    Yunooka: boot ok
    Yunooka: stage2 ok
    Yunooka: seed ok 74594
    Yunooka: mailbox ok

也就是说「第二趟没到」从来不是布局的问题，而是我这次诊断把盘号弄丢了。

这是第三次「诊断改坏了寄存器」：第一次是 rax（puts64 用 lodsb），第二次是 rbx（fs_open_path
用它交回字节数），这一次是 dl（盘号）。三次的症状都不说「寄存器坏了」：第一次是打印出错的
数，第二次是包跳到别处，这一次是种子读不到。

留下的东西是 serial2.log 那一行 dump：它把「第二趟没到」从一句判断变成了两行证据。


第三次：重排本身让第二段起不来
------------------------------

上一轮那个 dl 的坑让人以为「第二次失败是我的诊断」。这一轮把重排重做了一遍而不碰加载器
—— 结果一样：串口只有一行 boot ok，而 stage2 ok 没有出现。

于是两件事分开了：dl 那个坑是真的（它让第二趟报 seed unreadable），而重排让第二段起不来
也是真的。两者互相掩盖了一轮。

查到的部分：盘上的种子在（偏移 66560 处是 HMYRB），而 build 报的三段（引导 1 + 加载器 8 +
主体 121、种子第 130 扇区起）都对。所以前两段的写入没有问题，而第二段没跑起来。

未查到的：为什么。

而三次失败值得并排放着看：

  第一次  清单只到 假样本起 -> 最后一份扇区 算成 9 -> 预读盖不住 -> 缺五行
  第二次  清单覆盖到链尾 -> 预读 1048 对 -> 而我加的 dl 诊断让第二趟种子读不到
  第三次  同样的重排而不碰加载器 -> 预读对、种子在、而机器只到 boot ok

第三次把第二次那两个原因分开了：dl 是真的，而重排也是真的。而第三次的失败点比前两次都早
—— 早到「文件系统这一层根本没轮到」，早到「只有一行串口」。

所以这个方向现在有一个未知：一次只改数据区布局的修改，为什么会影响到第二段能不能跑起来。
在弄清它之前，第四次重排没有意义 —— 而三次失败都发生在同一个改动上，那说明这里有耦合，
不是运气。

退回到已知良好状态。而下一件是把那个耦合找出来：从「第二段的第一条指令是什么、它在什么
条件下不执行」开始，而不是再从布局那一侧推。


对比：diff 里只有布局，而启动不读布局
------------------------------------

这一轮不再试第四次，而是把重排重做一遍然后看 diff。

删掉的 22 行全是那串写死的偏移与旧的多行 示例扇区数；新增的 63 行全是清单块。也就是说
那四个脚本没有碰别的地方 —— 没有误改、没有多余的删除。

于是三件事摆在一起，两两矛盾：

  一、diff 里只有布局。
  二、启动不读超级块，也不读数据区 —— 引导扇区读加载器，加载器读第二段，第二段读种子。
  三、而机器只到 boot ok。

如果一与二对，那么三不该发生。而三发生了三次。

所以有一个假设是错的。可能的错处：

  - 布局那次改动并不只影响布局（比如 示例扇区数 的求值顺序让某个模块级副作用提前或推后）；
  - 或者「启动不读布局」这句话是错的（比如某个地址被算在启动路径上）；
  - 或者串口那一行「boot ok」之后其实还有东西，只是没被读出来（比如加载器换了输出端口）。

第三条最容易验证而我一直没有验：串口的读取是 run.mjs 那一侧做的，而「只有 boot ok」是
它读到的。如果加载器在 boot ok 之后把字符写到了别处，串口上就会是干净的 —— 而那种干净与
「没跑」长得一样。

三种可能里，第三条最便宜。下一轮先验它：在 0x3F8 之外再读一遍（或者直接看 VBox 的串口文件
在 boot ok 之后有没有增长），而不是先怀疑布局。


第三条候选被否掉了：串口真的不再增长
------------------------------------

上一轮把三件事摆成一个矛盾，并说最便宜的那一条是「那行之后串口是否真的没再增长」——
因为串口是 run.mjs 那一侧读的，而「只有 boot ok」也许只是「读不到」。

这一轮直接量：清空串口、起机器、每半秒看一次文件大小，看二十秒。结果是

    0.5s   0
    3s    18
    之后不再变化

而 18 字节的内容就是 Yunooka: boot ok 那一行。

所以第三条候选不成立：加载器没有把字符写到别处，它就是。

而「卡住」这个判断比「没跑」更具体：加载器的失败路径会打 line_fail 加错误码加批号，
而串口上没有那一行。也就是说它既没走成功路径（那会跳进第二段并打 stage2 ok），也没走
失败路径（int 0x13 返回进位的那种）。它停在 int 0x13 里面，或者停在两批之间。

所以下一个问题很窄：为什么同一份加载器、同一份盘布局的数字，在重排之后会在 int 0x13
里停住。

一个附带的东西：watchserial.mjs 这个脚本现在留下了 —— 它做一件 run.mjs 不做的事：把
「串口的大小随时间怎么变」摊开。而这一轮正是靠它把「读不到」与「没写」区分开的。


重排成了，而它缺的是链尾那五个
------------------------------

三次失败的最后一次把范围收窄到「加载器停在 int 0x13 里」。这一轮换了一个办法：不跑机器，
只比盘。

取重排前后的 disk.img 前 64 KB（加载器只读那一块）各存一份，比 sha256 —— 不同。再找第一个
不同的字节：偏移 0x200，也就是第 1 个扇区的开头。

    好：  fa 31 c0 8e d8 ...      ← 加载器的第一条指令
    坏：  04 00 00 00 09 68 65 6c 6c 6f 2e 74 78 74 ...

坏的那一边是核心清单：4 条 item、第一条名字长度 9、内容是 hello.txt。

而核心清单应当写在 核心清单起，那个值是「假样本起 + 1」。问题是那一行是 const：

    const 核心清单起 = 假样本起 + 1;

而 假样本起 在这一版里改成了 let，由数据区清单赋值 —— 赋值发生在这行之后。所以 const 捕获的
是它的初始值 0，于是 核心清单起 = 1。

链尾那五个全都一样：核心清单起 = 1、签名起 = 2、外五起 = 3、auth起 = 8、myon起 = 9。

于是核心清单被写到偏移 512 —— 那是加载器的地方。加载器在盘上只剩前 512 字节的引导扇区，
而它自己被覆盖成了「4 条 item」。

：引导扇区在、能打印，而加载器已经不是加载器了。int 0x13
读进来的是别的字节，跳到 0x1000 之后什么都没有 —— 既不打 stage2 ok，也不打 line_fail，
因为它们都不在。

修法是把那五个也改成 let、并在清单之后赋值。改完之后盘的前 64 KB 与「好」那一版 sha256
完全相同，而全套判据回到绿。

一条值得记的：这一轮的诊断顺序是「比字节」而不是「再跑一次」。三次跑机器都没有给出新东西，
而一次 static 的 diff 直接指出了偏移。当症状离原因三层远的时候，静态比较比动态实验便宜。


slurp 终于接上了，而它接上靠的是布局那一修
------------------------------------------

把三条加回 win 之后，一次运行里四件事同时成立：

    win 的指令数 22、体 0x1121..0x1223（258 字节）
    scan op 与 unknown op 都不再出现
    win px 1C 0F 1F（三个采样点都对）
    Yonooka three levels ok —— 那是 slurp 读出来的 deep.txt

而 build 报了一件新事：预读只盖 25 个扇区（1024 到 1048），而盘上最后一份文件在第 1050 号。
于是 dap_count 从 25 改成 27。

这件事本身值得记：prog.hmtn 涨到两个扇区之后，最后一份文件往后挪了两格，而预读那条数还停在
旧位置。build 那条检查把它抓住了 —— 那一条不是判据（判据在 run.mjs 里），而是构建期的核对。
如果没有它，症状会是「读到了、内容是零」，而那与「文件不存在」完全不同。

所以这一轮的三件改动是一条链：

    链尾那五个 const 在 假样本起 还是 0 时算定了 -> 核心清单写到扇区 1、盖掉加载器
    修好之后 prog.hmtn 可以涨到两个扇区
    而它涨了两格之后，预读那条数要跟着改（25 -> 27）

三件都做完，slurp 读文件这件事才第一次真的是那个意思：一个包读了一个盘上的文件，而那文件
的位置由清单算出来，不由一串写死的偏移。


filesize 试过一次：slurp 在第五个函数里读不到
---------------------------------------------

想给「slurp 的返回值参与计算」做最小的一步，所以加了第五个函数 filesize：常量路径、
slurp、len、返回。判据应当是 prog size -> 24（deep.txt 是 24 字节）。

而它跑出来是 prog size -> 0。

先怀疑的是顺序：win 自己也 slurp 一次，也许第二次 miss。于是把 filesize 排到 win 之前
—— 仍然是 0。所以与顺序无关。

再用解析器看布局：五个函数的位置、头长、指令数、体长全都自洽，filesize 在 0x1223、头长
28（名字八个码元）、四条指令、体 65 字节（38 + 15 + 11 + 1）。所以定位与编码都对。

所以是 slurp 在那一次调用里真的失败了 —— fs_open_path 返回零，走了 slurp_miss，交出空串，
而 len(空串) = 0。

而同一个路径在 win 里是成功的。两者的差别现在还不知道。

这一轮把它退回了：一个不工作的函数加上一条红判据，比没有更贵 —— 而那条判据会盖住别的。
留下的现象是这一个：

    win  里的 slurp 成功（打出 Yonooka three levels ok）
    filesize 里的 slurp 失败（prog size -> 0）
    两者读同一个路径，而顺序不是原因

下一轮要查的是「两次 slurp 之间有什么不同」—— 一个可能的方向是 fs_open_path 的
last_addr 与 fs_base 在两次调用之间被谁改过；另一个是 slurp_buf 与 myon_line 相邻，
而某个 call 写过了头。


更正：slurp 从来没有成功过
-------------------------

上一轮说「slurp 接上了」，依据是串口上出现了 Yunooka three levels ok。

这一轮给 slurp 的两条失败路径各加了一个标记（1 = 路径太长、2 = fs_open_path 返回零），
然后跑了一次。结果是：

    Yunooka: slurp miss at 0000000000000002

也就是说 fs_open_path 返回零 —— 而它出现了（win 一次、filesize 一次）。把 filesize
撤回之后还剩一次，那就是 win 的。

而 win 里那三条指令是「常量路径、slurp、write」。slurp 失败时交出一个空串，而 write 打一个
空串 —— 在串口上就是一个空行。而那个空行我当时看成了别的东西：run_fs_open3 那一条打的
Yunooka three levels ok 就在附近，而我把那一行当成了 slurp 的成果。

所以「接上了」是误读。真实情况是：slurp 每次都 miss，而它的唯一痕迹是一个空行。

这一轮留下的东西是那两条标记 —— 它们把「读不到」拆成两种，而这一次直接指向第二种：
路径拼好了，而 fs_open_path 没找到那个文件。

下一轮从 fs_open_path 在这一条路径上的行为查起：同一个路径在 run_fs_open3 里成功，而在
exec 内部（slurp 是内置，它在 exec 里跑）失败。两者之间的差别是这一轮没有查的部分。

一条方法上的记录：那一轮我把「串口上有一行正确的输出」当成了成功，而没有确认那一行是谁
打的。而这一轮加的两个标记，把一个「看起来成功」直接变成了「两次都失败」。


一段能读、三段不能
------------------

上一轮把 slurp 的失败确认到 fs_open_path 返回零。这一轮继续拆：把 win 里 slurp 的路径从
三段（docs/sub/deep.txt）换成一段（hello.txt），其余一个字不动。

结果：

    slurp miss 的次数 0
    Yunooka filesystem ok

也就是说 slurp 读到了 hello.txt，并把它的内容打了出来。

所以问题不在 slurp 自己、不在 fs_open_path 的第一步（盘符与冒号）、也不在寻址那两块：
fs_base 与 fs_start 都对着。问题在 —— 而它只在 exec 内部出现，因为同样的三段
路径在 run_fs_open3 里是成功的。

两边的差别是可数的：exec 内部多两样东西在寄存器里 —— r12 指指令流、r13 数指令数。
fs_open_path 自己 push/pop 了它们，所以它们在那之后是干净的。而段循环里还用了 rdi、rcx 与
机器栈（.at_slash 里 push rax / pop rdi），那三样在 exec 内部与外面没有区别。

所以下一轮要在段循环里打点：每过一段打一次段名与 fs_lookup 的返回值。两段之后就看得出来
是哪一段给了零。

一条方法上的记录：这一轮没有读代码，只做了一次「换一个输入」的实验，而它把范围从
「fs_open_path 与 slurp」缩到「段循环」。前几轮读代码读了三处，每一处都看不出问题 ——
而一次只改输入的实验直接给了一个二选一的答案。

=== 段循环打点：假设被证实，结论却被推翻 ===

上一轮记的下一步是「在段循环里打点，看哪一段给了零」。打点做出来了，两行：

    Yunooka: seg 4 1 1026      docs 命中，扇区 1026
    Yunooka: seg 3 0 1026      sub 在同一个扇区里返回零

所以「第二段给了零」这个假设是对的。但它指向的结论错了 —— 真因不在段循环里。

错在哪一步是看得出来的：如果段循环写错了，那么它每次都会错。而它没有 —— 同一个
fs_lookup(1026, "sub", 3)，在 run_fs_open3 那一次成功（seg 3 1 1034），在 slurp
那一次失败。同一段代码、同一个扇区、同一天里两种结果。

一个函数时而对时而错，指向的不是「函数写错」，而是「它读的那份东西被改过」。

于是换了一个完全静态的做法：按盘上格式把根目录走一遍，量出每条的起点。十九条静态
条目，最后一条 dex.bin 在偏移 480，自己有二十五字节，下一个可用位置 505。扇区 512。

第一次写文件要二十五个字节（new.txt）。505 加 25 是 530 —— 它跨过 512。

跨过去的 18 个字节落在第 1026 号扇区，而 1026 那时是 docs 的条目区。docs 的头三条是
note.txt、sub、myon.hmtn。sub 的条目就在新字节下面。

修法两件：根目录占两个扇区（超块偏移 16 一直是 1，而这个字段本来就是干这个的），
以及 fs_write_file 找空槽时带一个从超块读的上界，写到自己的页之外就返回失败。

修完 slurp 通，同时回来的还有写、共享、共享见面、门、此电脑、系统保护、详情、索引
这几族 —— 它们原先红着，而在此之前没有人知道它们与目录容量有关。

方法上两条：

  一、这一次的决定性证据来自一个静态脚本，不来自第二次机器运行。前一轮跑了三趟虚拟
      机，每趟三分之二分钟，而三次都只说明「还是红」。量根目录那一次花了不到一秒，
      直接给出了 505 这个数。
  二、先试的那条快路（让 fs_lookup 每次重读那一页）让 slurp 通了，但把「写之后读回
      自己写的东西」打红。它被撤掉了 —— 撤的时机是判据红的那一刻，不是发现它的第二天。
      留着一条「通了但它弄坏了别的」的改动，比原样红着更贵。
=== 目录边界是各自的：一条判据问对了方向，而余量不够走完 ===

上一轮修的那个 bug 是「目录条目区没有边界，写越界吃掉了隔壁目录」。修法是：根目录占两页，
fs_write_file 的条目上界从超块那个字段读，写到自己的页之外就拒绝。

而那条修法有一面没有验：拒绝只该发生在满的那一个目录上，不该是一个全局状态。最省事的
实现（一个 bool，或者干脆不听 write_dir）会让「根目录满了」挡住所有目录，而在串口上
这与「写对了」长得一样 —— 文件确实写进去了，只是写错了地方。

所以写了 run_docs_after_full：dirfull 之后往 docs 里写一份 late.txt，然后按完整路径查它。

它第一趟就红，而红得很具体：

    Yunooka: dirfull wrote 29 refused 11
    Yunooka: dirfull docs lost
    1027

那个 1027 是两个出口的分水岭。它等于 docs 的扇区号，所以不是「根目录里没有 docs」——
fs_lookup 找到了它。而 fs_write_file 也说了成功（否则会打 blocked，而不是 lost）。
于是剩下的只有一种：条目写进去了，而按 α:/docs/late.txt 查不到。

三个方向留给下一轮，按便宜程度排：
  一、fs_write_file 到底把条目写进了哪个扇区 —— 打 [write_dir] 与 [last_dir_sec]，
      两个数一比就知道 write_dir 有没有被传进去。
  二、docs 那时有没有空槽。它有三条静态条目，加上 save 写的 inner.txt 是四条。
      第四条之后应当是零，也就是空槽；若那里不是零，fs_write_file 会一直走到上界才失败，
      而失败会走 blocked —— 所以这一条与串口不符，但值得确认。
  三、fs_open_path 第二段查的地址：docs 的扇区是 1027，而 fs_load(1027) 是 0x40600，
      与 fs_write_file 写的是同一处。

而这一轮没有余量走完它：第二段到了 128 扇区，实到 65324 字节，余 212。上一次改动
（把 lost 的 r15 打出来）花了 88 字节。再往下每一次试探都要先腾地方。

所以它从主链上摘下来了，代码留着 —— 与 run_health_test、run_smart_test 同一个处理：
一条已经问对了方向的失败，不该继续占着串口。判据本身留在 run.mjs 里（晚成），
只是暂时不在链上。

那条纪律因此又多一面：红的形状本身就是进度。它这一趟给出的不是「不对」，而是「在哪一段
不对」，而后者才是下一轮能接着用的东西。
=== 答案：一个终止零码元，而三个聪明的方向全错了 ===

上一节列了三个方向，按便宜程度排：写进哪个扇区、docs 有没有空槽、查找第二段的地址。
三个全错。而它们错得有理 —— 每一个都能从「写成功而查不到」这句话推出来，而且每一个
听起来都比「数据的定义少了一个零」更像回事。

真因：fs_late_name 那八个码元后面没有终止零。它后面紧跟的是 fs_late_data 的两个字节，
于是在 fs_write_file 的 .count_name 看来名字还没完 —— 它一路数下去，直到撞见某个零码元，
然后按那个长度写下一条条目。确实写了，写的不是 late.txt，所以按 late.txt 查当然查不到。

第六个数才指出来：docs 页里「四条之后」那一格的名字长度是 9，不是 8。

六个数的顺序与它们各自排除了什么：

    0      write_dir   —— 清过之后的零，什么都不说明，而它第一眼看起来最像答案
    1027   last_dir_sec—— 写入确实进了 docs，把「走错了目录」这一支砍掉
    1085   last_write_sec
    0      late_probe  —— 直接查那一页也失败，把「fs_open_path 的第二段」砍掉
    1027   probe 的扇区—— 上一个数失败时的残留
    9      第 5 条的名字长度 —— 既不是 8（写入成功）也不是 0（空槽），于是问题在名字本身

有一处没有查到底，记在这里：按 .count_name 的走法，名字长度超过 64 会走 .fail，而 .fail
会让 fs_write_file 返回零，于是串口该是 blocked 而不是 lost。实际是 lost，说明它在 64
之内撞见了零码元。哪一个零、为什么那个位置恰好有零，没有查 —— 判据绿了，而那条路不值得
再花一次两分钟的运行。不确定的地方写出来，比补一个听起来合理的解释好。

方法上留着两条：

  一、把「三个数一次打出来」比「一次打一个数、跑三趟」省两趟。前者的代价是那个零会被
      误读（write_dir 打的是清理之后的值），而后者的代价是六分钟与两次可能被别的东西
      带偏的判断。
  二、判据红着的时候，找一个能把它二分掉的数，比找一个能解释它的理论便宜。第五个数把
      「查的那一侧」砍掉之后，第六个数几乎是自动指到名字上的。
=== 删除：三次尝试，而它仍然不工作 ===

包 API 的最后一格是「删」。这一段写了 remove 内置与它的判据，而它不工作 ——
包删完之后 list 仍是 33，说明 docs 里那四条还在。这一节记的是走过的路，与下一轮
该从哪儿接。

判据先写下了，而它红得对：prog remove -> 33（应当是 24）。所以「没删掉」这件事本身
是确定的，不是猜的。

路上遇到的四件事，按它们各自的价值排：

一、build 的返回字节自检救了一次。加第八个函数时又复制了一个 0x1c，而这一次不是靠把
    字节摊开发现的 —— 自检直接说「返回字节写了 9 次，而包声明了 8 个函数」。那条三行的
    检查是这一段里最划算的一笔。

二、savetest 的返回位置错了，而它的症状是「第七、第八个函数都找不到」。原因是那个返回
    留在了第二次 save 之前，于是扫描器数完十一条指令就落到下一个函数的头上，把名字长度
    读成了 opcode。walkscan（在主机上照 find_fn_by_name 的算术走一遍）一次就定位到了：
    savetest 的体 ends 0xdb85，越过包尾。那个工具这一轮值得第二次用。

三、fs_delete 第一次插在了 exec 内部 —— 一个全局标签出现在 .op_list 之前，于是它后面
    所有 .op_* 都变成了它的局部标签，nasm 报 exec.op_index 未定义。挪到 fs_write_file
    之前就好了。exec 的内部标签不能从中间插一个全局标签进去。

四、包涨到 1083 字节（三扇区），于是数据区后移、预读窗口从 28 涨到 30。这一条是 build
    自己说的，不是猜的。

而最后那个红，红的不是 remove：是写盘（存成）。串口里 save survived docs/inner.txt
1058 6 出现在第一趟，说明第一趟 run_save_test 走的是「第二趟」那个分支 —— 也就是说
第一趟启动时盘上已经有 docs/inner.txt。这一条没有查清，而它是下一轮的第一个问题：
若第一趟的盘不干净，那么「save 只落过一次」这个前提就不成立，而那会影响别的判据。

下一轮的第一件事：先确认第一趟的盘上有没有 inner.txt。build 从 disk.img 生成 vdi，
而 disk.img 应当是干净的 —— 所以要么 build 没有重建 vdi，要么上一趟的 vdi 被复用了。
那是一个可以在主机上查清的问题（读 vdi 的 1027 扇区），不必花一次两分钟的运行。
=== 删除第二次：它能工作，而它把盘写坏了 ===

remove 这一轮做到了：串口里 prog remove -> 23，也就是 docs 里少掉 inner.txt 之后剩下的
那三个名字。判据的数第一版写成 24，而 8+1+3+1+9+1 就是 23 —— 红的那一趟会去查固件，
而固件是对的，所以那个错本身也是一条：判据里的数要能自己算一遍。

但同一次运行的第二趟坏了：

    第二趟：boot ok / stage2 ok / seed ok 38072 / mailbox ok / pro（断在这里）

38072 是第二段里 seed_bytes 那一格，它应当是 40。也就是说第二趟读到的 stage2 不是 build
写的那一份 —— 盘上 LBA 9..138 被改过。而第一趟自己的 seed ok 是 40，所以写坏发生在
第一趟运行期间。

三处已经修好、而且是真的：

一、fs_delete 那个全局标签原先插在 exec 内部，把它后面所有 .op_* 变成自己的局部标签。
二、op_remove 拼父路径用的是 rsi，而 fs_load 会把它改成算出来的地址（第六次寄存器对）。
三、fs_delete 比较名字时多跳了两个字节 —— r12 是没有长度前缀的裸串，而数长度那一处
    已经按这个约定改了，比较那一处还留着 +2。这一个是靠四个诊断数收进来的：
    返回 0、页 1027、首码元 1053（也就是 'i'）、数出来的长度 9。

而这第四个症状没有解释：只有 ata_write 能写到预读区之外，而它的三个调用点是 persist
（60000）与 save 的两页（目录页与数据页）。save 的数据扇区在第一趟里约 1053..1086，
目录页是 1025 与 1026 —— 没有一处靠近 9..138。

所以下一轮的第一件事是：在第一趟结束之后读盘上的 LBA 9 与 138，看它们是不是真的变了。
那可以在主机上做（把 vdi 转成 raw），不必先跑虚拟机。若它们没变，那么问题在「第二趟
读的是别处」，而不是「有人写了那里」。

这一段因此回滚了：代码与判据都撤掉，因为一条把盘写坏的胜利不算胜利。
=== 两趟读到同一份 stage2：一条有真实红的判据，与一个没解释的数 ===

上一轮 remove 那一趟，第二趟死在「没有 persist survived」这一句话上，而串口只多给了一行：
seed ok 38072，而占位种子是四十字节。那与「第二趟根本没起来」在串口上长得一样，而两者的
修法完全不同。所以加了一条：两趟的种子字节数必须相同。

它不是想出来的判据 —— 那个错先发生，然后才有它。所以它的红有据可查：上一轮的串口就是
40 与 38072 这一对。

而查它的时候撞见另一件事，没有解释：

    两趟现在都报 seed ok 4218691752。

盘上是对的：LBA 138 偏移 296 处是 40，而那是第二段偏移 66344（seed_bytes 那一格）。
而 loader 的第三批从 LBA 137 读 512 字节到 0x20000，所以 LBA 138 的偏移 296 落在 0x20328。
而实模式那一段从头到尾 ds 都是 0x1000，所以 [seed_bytes] 这个绝对地址 0x10328 指的正是
0x20328。三件事都指向「读对了」。

而串口给的是 4218691752，也就是 0xFB7C0008。

所以上面那三件事里有一件是假的，而我没有查出来。记在这里而不是补一个听起来合理的解释：
那种解释会让下一轮从错的地方开始。

下一轮最便宜的一步：把 put_num 与那条 mov eax, [seed_bytes] 的机器码从 stage2.lst 里
抄出来对一遍。那不必跑虚拟机 —— 若 lst 里那条指令的地址不是 0x10328，那么「ds 0x1000
所以它指 0x20328」这句话就已经不成立了，而 4218691752 也就不用再解释。

顺带记一个教训：seed ok 的数一直被我当成「种子读到了」的标志，而现在它连自己的数都报
不准。一条判据的读数里，那个数字与那句话是两个断言 —— 这一轮之前只验了前者。

=== 真种子接管：七万四千字节一直在 D 盘，而判据侧一个字没改 ===

种子族那九项（函数、操作码、求值、跳转、调用、按名、数字、求值活、曲线）长期以
「跳过」的样子存在。理由写在 run.mjs 里：它们的前提是种子里有 letters 这个函数，
而四十字节的占位包只有 main。跳过是诚实的 —— 它明说自己没验 —— 于是它一直没被当成
待办，直到有人问「为什么 Yunooka 里没有真东西可跑」。

答案是那份东西一直在本机：D:\himeyuri\bootstrap\pack.hmtn，74594 字节、版本 1、
202 个函数，与占位包只差规模不差格式。头五个字节同样是 HMYRB。所以这一段的动作只有
一次复制，加一条 build 的 --seed。

换上之后串口给的是：seed ok 74594、seed v1 202、种子里有 letters 那九族照验。九项
一次全过 —— 求值 2 units -> 512、除法 div -> 1.570796、数学 sum -> 262.488320 与
average -> 29.165369、表达式 f x -> has x、曲线 f(0) 与 f(160) 都在 2F。第二次启动
报的是同一个数：74594 / 74594。

值得单独记的是判据侧一个字没改。守卫写的是「串口里有没有 fn letters」而不是「有没有
种子」—— 当初选这个形状是为了不误伤占位包，而副作用是它把「前提不成立」写成了一句
看得见的话。前提一成立，那九项自己就上岗了。一个跳过要是写清了前提，它就不需要有人
记得回来改它。

顺带查出两处注释错，都是那次「种子从 0x20000 搬到 0x70000」留下的：

一、stage2 里第三批种子读的注释还写着「目标是 0x30000、18 个扇区铺到 0x32400、
主体上限 0x30000」。那是旧布局的账，而 seg 从 0x2000 改成了 0x7000，数字没跟着算。
它读起来仍然自洽（0x32400 与 146 个扇区对得上），三段地址却全错。真正的三个地址是
0x70000 / 0x78000 / 0x80000，铺到 0x82400。

二、loader 开头的注释说「上限 0x20000，种子在那里」，而同一个文件第六十六行的注释
已经在说「种子搬到 0x70000 之后这里能一直往上数」。同一个文件里两条注释互相矛盾，
而它们都在同一个提交里。

两处都不影响运行 —— 注释不进 .bin。而这正是它们的危险：一个自洽的错注释不会让人去核，
它只在下一个改这里的人身上收钱。这与「过时的注释比没有注释更坏」是同一条，只是这次的
过时来自一次全局替换：0x20000 改成 0x70000 的时候，命中了代码里的 0x200000（页表那
个 2 MB 步长，为此红过一次），而注释里的派生数字（0x32400）既不在替换表里，也没人重算。

一条可带走的：地址搬完要重新算一遍注释里的派生数，不能只跟着替换 —— 替换只改它认得的
那一个字面量。

=== hmgk 的头：认出只要四个字节，读懂要走完整个头 ===

identify 的第十六格答 hmgk，而那一格只用头四个字节。所以「认得出」与「读得懂」是两件
事，这一段补的是后一件：run_hmgk_test 按 design/HMGK.txt 的偏移把版本、BPM、结构段
字节数、pattern 数读出来，打成

    Yunooka: hmgk v1 bpm 120500 struct 40 pattern 3

判据要求四个数与样本里写死的一致。

判据侧的形状：三个数（BPM 120500、结构段 40、pattern 3）都不是「恰好非零」能凑出来的。
尤其 120500 —— 它放在偏移 28，四个字节的小端整数。魔数对了之后随便挑一个偏移去读，
得到的会是一个小于四位的数，或者两个相邻 u16 拼起来的东西，凑不出 120500。

验红的办法与它证明的东西：把 BPM 的偏移从 28 改成 24，读出来是 327682，判据点名不符、
退出码一。327682 这个数值得单独看一眼 —— 它是 2 加 5 乘 65536，而偏移 24 上正是 track
（2）与 loop（5）两个 u16。所以那个红不只是「值不对」，它还顺带把「这两个字段在偏移
24、26」这句话验了一遍：错位一格读到的两个字段拼成了预期之外的一个数，位置关系因此
不是被声明的，是被测出来的。

改回 28 就又绿了。一红一绿两步都在这一轮里走过，所以这一格不是「建起来就绿」的那一种。

代价：第二段从 130 个扇区到 131，余量从六十二格到六十一格。新的上限仍是 192，而种子的
落点跟着从第 139 个扇区到第 140 —— build 的三处交叉核对把这一串一起核了，所以搬动它们不会各自跑偏。

还没做的那一件留在 design/HMGK.txt 末尾：嵌入形态。魔数在偏移 0 这个假设在「嵌进任意
可执行文件」之后不成立，而那一天要先有一条判据（一个 PE 头后面跟着一份 hmgk，该报出
两样东西）。

=== hmgk 的第三种活法：魔数不在偏移 0 ===

前两格（认出、读懂头）都建立在「魔数在偏移 0」这个前提上。而用户给的规范里有一句
「它可以被嵌进任意可执行文件」，那句话把这个前提打破了：一份 hmgk 进了别的程序之后，
它的魔数可能在第 200 个字节，也可能在第 200000 个。

所以加的是一段扫描：scan_magic 在 [起点, 起点 + 长度) 里找四字节魔数，返回偏移或负一。
上界写成长度减四 —— 最后一个合法起点要能读满四个字节，否则会读出边界外，而在实地址
空间里读边界外通常不会报错，只会给出一个巧合相等的值。

判据只写一样东西不够。判据的形状是「两样」：样本是一条 PE 头加一份落在偏移 256 的
hmgk，所以那一行要答 pe（外面那层被认出来了）并且给出 256（里面那份被扫出来了）。只答
pe 的实现根本不知道里面有东西；只答 hmgk 的实现把外面那层漏了。两样都要，是因为这两种
错在串口上长得不一样，而判据要能分开报。

这一格见红的办法与前两格不同：把样本里的落点从 256 挪到 200，判据不动。那一行于是报
「在偏移 200」，判据点名「应当 256」，退出码一。这个红证明的是偏移真的被扫出来 —— 若
实现里写着一个常量 256，挪样本之后它仍会报 256，红不起来。

三种红至此凑齐，而它们的意义各不相同：
  错值（BPM 读出 327682）—— 判据在读那个数，而不是在读某个恰好非零的东西。
  错位（落在 200 而不是 256）—— 偏移是被测出来的，不是被声明的。
  格式不匹配（少一个空格，报「没扫到」）—— 判据按写下的形状在匹配，而不是模糊地找子串。

第三种红是这一轮唯一一次「先红后绿」的意外：put_ident_kind 打的名字后面已经有一个空格，
而内层那段文字又以空格开头，于是串口上是 "pe  hmgk"，而判据写的是单空格。修的是固件
（去掉那个前导空格），不是判据 —— 判据先写下了形状，固件去对上它。这条与 STATUS 里
第八条记的是同一件事：形状一旦写下来，对不上的那一侧就该改。

代价：第二段从 131 个扇区到 132，余量从六十一格到六十格，种子从第 141 个扇区起。

=== 屏幕上的第一个字母，以及「擦」不能用「画」来实现 ===

到这一格之前，屏幕上有过像素、线、框、矩形与整窗，而从没出现过一个字母。而窗口那一层
若不能写字就不算窗口 —— 一份界面最先要能说人话。所以加了 8x8 单色位图：帧缓冲是
320x200、每像素一字节的调色板索引，一个字符于是就是「六十四次写或不写」。每行一字节、
最高位在左边，比存六十四个字省八倍，而「第几行第几列」这个关系在移位里是明摆着的 ——
左移 r11 位之后原来第 (7-列) 位就到了最高位。

判据是四个点，不是四个点随便挑的：把 H 铺在 (100,60)，读左上、右上、中间、第四行左端。
前两个与该亮（两竖），第三个该暗（两竖之间），第四个该亮（中间那一横）。一个把最高位
当成最右位的实现写出来的是镜像字，而镜像字在一个左右对称的字模上看不出来 —— 所以真正
分开方向的是「两端各读一次」这个形状，不是点的个数。

这一格红过两次，两次都值得记。

第一次是这整段唯一一次真正的设计错：抹背景用的是「画一份全零的位图」。而位图里的 0 表示
「这个像素不写」—— 全零位图画完什么也没发生，于是「该暗」那一点读到了前面测试留在屏幕
上的 0x0F。这不是算错，是把两件事混成了一件：「不写」与「写成背景色」。位图表达的是
前者，而擦需要后者。修法是单独写一段 clear_block，把 64 个像素真的写成给定颜色。
症状的形状也值得记 —— 它没有报「什么都没画」，它报的是「第三个点读到 0F」；如果没有
那第四个点、只读一个「该亮」的点，这个错会让判据一直绿着，而屏幕上那块地方是脏的。

第二次是主动验红：把字模第一行改成 0x00，四个点变成 00 00 00 2F。第四点仍是 2F 是因为
它读的是第 4 行（那一行是 0xFF，没动），于是这个红同时说明四件事：前两个点各读第一行的
最左与最右、第三个点读两竖之间、第四个点读的是另一行。四个点分别落在四个不同的位置，
这一点是被测出来的。

代价：第二段从 132 个扇区到 133，余量五十九格，种子从第 142 个扇区起。判据 82 到 83。

=== 一行字：字距这个数，只有两个字并排时才被问到 ===

一个字到一行字，中间隔的是「字模成表」与「字距」两件事。字模 0 到 9 做成连续表，于是
draw_text 里「字符减 0x30、乘八、加到表头」就是全部的位置计算。字距八像素 —— 与字模
宽度相同，所以相邻两个字之间没有空隙；加空隙是排版的事，等有排版再说。

判据写「01」，读五个点。前三点验字模（0 的左上角该暗、顶边该亮、左竖该亮），后两点
验字距。而验字距这两点必须成对，这是这一格唯一的难点：

  1 的顶边是 0x18，两个连续亮位。只读 111（字距为八时它落在 1 顶边的右边那个亮位上）
  的话，把字距改成七，同一个像素就落到左边那个亮位上 —— 读出来还是 2F，判据照样绿。

第一版就是只读了 111。验红时才发现它不变，于是老实地承认：那一个点只能测出「字距偏大」，
测不出「偏小」。加上 110（字距为八时它落在 1 顶边左边的空位上）之后，偏小会让它变亮、
偏大会让 111 变暗，两个方向才都被问到。

这个形状值得记住：一个字模里连续两个亮位，就把「位置偏一格」这件事盖住了一半。要让一个
判据对「偏移」敏感，读的必须是边界上的像素 —— 亮位与空位的交界，而不是亮的中间。

顺带发现的一件事，与字无关而与流程有关：这一轮有一次没 build 就直接跑了 run，于是盘上
带着上一次第二趟存下的 docs/inner.txt，run_save_test 走了「第二趟」那个分支、打了
save survived 而不是 save，而「包写文件」那条判据因此报红 —— 报的是「要么包没读回那行
字，要么目录里查不到 out.txt」，一个看起来像缺陷的红。

而它是脏盘。run 会写盘，而 build 的镜像是唯一干净的起点；两趟启动之间共用同一块盘是
有意的（第二趟要验持久化），两次 run 之间共用则不是。所以「先 build 再 run」不是一个
习惯问题，它是判据的前提。记在这里，因为下一个红在写盘那一条上出现时，先问的应当是
「这一趟的盘是新的吗」，而不是去读 run_save_test。

代价：第二段从 133 个扇区到 134，余量五十八格，种子从第 143 个扇区起。判据 83 到 84。

=== 一帧的起点：清屏，以及一个白读的判据点 ===

屏幕上有过像素、线、框、矩形、整窗、一个字母、一行字，而「把它们擦掉」从来没有过。
没有清屏就没有一帧 —— 两次画的东西叠在一起，谁也分不开谁是谁。

clear_screen 把六万四千个字节（320 x 200）写成给定颜色。不用 rep stosb 的理由写在代码
里：它要三个寄存器同时就位，而小段上的启动开销随处理器不同；这一版要的是「一定能跑、
数得清」。

判据先画一个 H 在 (10,10)，把整屏写成 05，再读四个点：(10,10)、(17,10)、(10,11)、
(0,0)。前三落在画过、而且本来亮的位置上，第四个从没画过。四个都该是 05。

而这一格的验红带出一条比清屏本身更值得记的东西。第一次把清屏范围从六万四缩到三百二十
（只清第一行），红出来的串口是 2F 00 2F 05 —— 第二个点是 00。第二个点当时读的是
(11,10)，那是 H 顶边 0x81 的中间六个零之一：它本来就该是 0。也就是说，那个点无论清屏
做没做都读 0，它一点也没在测。

判据照样红了（另外三个点报了），但那是运气。一个白读的点会一直在那里，而它一旦成为
唯一读「正常值」的那个，整条判据就会在真问题面前保持绿色 —— 更糟的是它看起来像被验过
的，因为同一个函数里别的点确实报过红。改成 (17,10)（顶边右端，本该是 2F）之后再验红，
四个点变成 2F 2F 2F 05，三个都在说「没清」。

一条可带走的：判据点要落在「本该非零」的地方。读一个本来为 0 的位置，绿色的含义只是
「它还是 0」，而红的含义根本不成立 —— 因为那里没有东西可以被清掉。

判据 84 到 85。第二段仍是 134 个扇区，因为这一格的代码是从注释里省出空间的。

=== 大写字母：两张表，与一个错一格的验红 ===

数字之后是字母。font_letters 收二十六个大写字母，行 0 到 6 是字形、行 7 留空 ——
所以字与字之间竖直方向有一行空隙，水平方向没有（字距就是字宽）。

为什么不与 digit 合成一张从 0x30 到 0x5A 的连续表：合成的话中间那七个标点（: ; < = > ? @）
要占位置填空白，而空白字模在判据里与「这个字符不存在」长得一样。两张表各有入口，多一个
分支换掉七格假数据。

判据写「HO」。挑这两个字母是因为它们顶边形状不同：H 是 0x66（亮位在中间偏两端），O 是
0x3C（亮位在正中）。四个点都落在亮位与空位的交界上，而不是亮的中间 —— 这是上一轮学到的
形状：读亮的中间，位置偏一格仍会读到亮；读交界，偏一格就翻面。

期望 00 2F 00 2F。验红把字母表基址从 'A' 错到 'B'，于是 H 的位置画出来的是 G，而 G 的
顶边是 0x3C：它的 bit6 是空的，第二点从 2F 变 0，串口给出 00 00 00 2F，判据红、退出码一。
这个红说明的事比「值不对」多一点：四点一起落到别的字上，而那个字在这一位恰好是空的 ——
基址错一格是整表平移，不是单个字模坏掉，而平移在这四个点上留下的痕迹就是这个。

顺带记一句 font_H 与表里的 H 不同，那是有意的：font_H 是单字铺绘那一格的样本，验的是
「把八字节位图铺到屏幕上」这个机制；表里的 H 是字体的一部分。

判据 85 到 86。第二段从 134 到 135 个扇区，余量五十七格，种子从第 144 个扇区起。
