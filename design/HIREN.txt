HIREN 在 Yunooka 里的规划

用户点下一整套（2026 那一轮）。这一份把它摊成有顺序的几块，并写下三条判断 ——
那三条判断是为了让其中几块不与 design/LAYERS.txt 已经定下的东西打架。

原文的几块：
  已经定下来的：KPB 进 KID。
  第一件：把 C / C++ / Java / C# / Lua / Rust / Python / JavaScript / Go 等语言做成整合包
    装到 Yunooka，并让 win / mac / linux / android 的文件与程序在 Yunooka 里可辨认与读写。
  第二件：把 lineweight 与魔改后的 SAI、PS、AI 优化之后做成 Ichiwatashi 的扩展件。
  第三件：把 RhinoCeros 与 Keil 一并魔改优化，整合成名为 Miketsukami 的软件。
  剩下的：参考各种 SDK 的经验，用 HMYR 把用于优化平台开发的工具、工具链、子语言做出来。
  另有：OnlySign 也要做到 Yunooka 的系统层里，而 Yunooka / HIREN / HMYR 未来出包时都用
    S.M.Y.T. 签名。


一、判断一：整合包本身是 HMYR 包

design/LAYERS.txt 说「纯净的 Yunooka 原则上只认识 HMYR 写出来的东西」，而这一块要把别的
语言装进来 —— 两句会打架，除非把「装进来」读清楚。

读法只有一种能同时成立：**整合包本身是一个 HMYR 包**。它里面是「用 HMYR 写的那个语言的
实现」—— 解释器、或者编译器、或者运行时。所以 Yunooka 认识的仍然是 HMYR；而那些语言是被
**解释**的，不是被原生装载的。

另一种读法（把 gcc 或 CPython 的二进制原样装进来）会立刻破掉上一轮刚定的东西，而且技术上
也不成立：那些二进制是 ELF 或 PE，而 Yunooka 没有它们的装载器。

所以这一块的形状是：一个语言一个包，包里是 HMYR 写的实现，判据是「那个语言的某个程序在
这个包上跑出正确的结果」。而用户最后那句「子语言」正指向这条路 —— 那些语言在这里是
HMYR 的**子语言**，不是与它并列的东西。

一条现实的话：这一块的工作量是「一个语言一个实现」，而它与 main 返回 7 之间隔着 HMYR 的
读文件、写文件、以及一个有 I/O 的包 —— 那三件还没有。所以它是方向，不是下一块砖。

二、判断二：「可辨认与读写」不等于「可执行」

win / mac / linux / android 的程序在 Yunooka 里可辨认、可读写 —— 按字面读，那是三件事：

  辨认：认得那个格式的头。PE（MZ 加 PE\0\0）、ELF（7F 45 4C 46）、Mach-O（FEEDFACE 一族
    与 FAT 的 CAFEBABE）、APK（PK 的 zip 头加 AndroidManifest）、DEX（dex\n）。这一层与
    Kohane 第六层的 identify 是同一件工具，只是表更长。
  读写：能读它的节表、资源、导入表；能改它的某一段并写回去。这一层要的是「结构知道得
    够细」，而它不需要对方能跑。
  执行：完全是另一件事 —— 要 PE 装载器、要 Win32 的 API 表面、要 Mach-O 的 dyld。
    用户没有说这一条，而它比前两条贵一个数量级。

所以这一块按字面落：**能认、能读、能改**。而这样落还有实用上的理由：Nanodesu 与 Torikago
（安防那两件）要的正是「认得出、读得懂」—— 判断一个文件是什么，不需要跑它。

三、判断三：「魔改」指的是照能力自研，不是改别人的二进制

SAI、PS、AI、RhinoCeros、Keil 都是别人的产品，而这个是一台自研的机器。所以「魔改优化后
做成扩展件 / 整合成新软件」只有一种读法成立：**照着它们的能力做自己的实现**。

改它们的二进制这条路在这台机器上不成立（没有它们的运行时），在别的地方也不该走。

所以这两块的落法是「能力清单」而不是「产品移植」：
  Ichiwatashi 的扩展件：lineweight（线条重量，那一件已经在计划里）、以及从 SAI / PS / AI
    里挑出来的能力 —— 画笔引擎的压感与混色、图层与蒙版、矢量路径与变换。挑哪些要按
    「像素画工具的日常」来定，不是按「那个软件有什么」来定。
  Miketsukami：RhinoCeros 给的是几何（NURBS、布尔、网格），Keil 给的是固件工具链
    （编译器、链接器、调试器、烧写）。两件看起来无关，而共同点是**把一个设计变成一件
    实物** —— 一个给形状，一个给让它动起来的代码。所以 Miketsukami 是「造物」那一侧的
    软件，它与 Ichiwatashi（画）和 KID（找文件）不在同一层。

四、签名：OnlySign 与 S.M.Y.T. 是两侧

一句分工：**S.M.Y.T. 是签的那一侧，OnlySign 是验的那一侧。**
  S.M.Y.T. 在出包时用，三个仓库（Yunooka、HIREN、HMYR）都签。
  OnlySign 住在 Yunooka 的系统层，负责在装载或更新之前验。

而它与 design/GUARD.txt 第三层的关系要写清，因为两层容易被当成一层：
  校验和（FNV-1a，已经在跑）防的是**误改** —— 一个字节变了就报。它便宜，所以每次启动
    都跑。
  签名防的是**故意** —— 有人改了，并且把校验和也重算了。它贵，所以只在安装与出包时验。
两层都要，而它们回答的不是同一个问题。现在 GUARD 只有第一层，而「只有校验和」这件事
在有人故意改的时候是零防护。

五、顺序

这一块里能先动的不多，而顺序有理由：

  一、HMYR 的读文件与写文件。没有这两条，上面每一块都落不了地 —— 一个语言实现要读源、
    要写目标。
  二、OnlySign 的验那一侧。它现在就能做，因为它验的是「盘上那份字节」，而读盘已经有了。
    判据也现成：把核心清单里一个 hash 换掉，验必须红。
  三、文件格式辨认。identify 的表从三种扩到十几种，判据是「给一个 PE 头，它答 PE」。
    这一条比第一、二条都便宜，而它立刻能用（安防那两件在等它）。
  四、其余三块（整合包、Ichiwatashi 扩展、Miketsukami）都要 HMYR 先能读能写，所以排在
    那之后；而它们的判据现在就能写下来 —— 写判据不需要实现。

六、还差的

  HMYR 的读文件与写文件（第 108 行的 FS.txt 已经提到过，还没做）。
  Yunooka 能跑一个有 I/O 的包（现在只能跑 main 返回 7）。
  OnlySign 的验：一个签名格式、一个验的例程、一条判据。
  identify 的表：PE、ELF、Mach-O、APK、DEX 五个头。
