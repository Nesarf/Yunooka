Yunooka 的现在：三十轮之后
==========================

这张纸上没有一个新东西。它把已经散在 PLAN、LAYERS、MEMORY 与各自 design 里的状态收成
一份 —— 为的是让下一个打开这个仓库的人先读它，而不是先去读一万字的 notes。

数（都是量出来的，不是估的）
----------------------------

    判据        125 条，全在 run.mjs 的某条链上
    事件        13 个 event= 行，每一个都有判据在读
        PLAN        60 个目标：42 done、12 blocked、5 open、1 active
    第二段      占 177 个扇区，上限 192（余十五格）
    三条链      引导 1 + 加载器 8 + 主体 177 —— 种子从第 186 个扇区起
    种子        74594 字节、版本 1、202 个函数。真包，不再是占位
    根目录      两个扇区（1025 与 1026），docs 在 1027，数据区从 1028 起

十条线
------

OnlySign 第三环（PLAN: onlysign，open）

  闭了。域乘、域加减、点、标量乘、编解码、验签、接进 OnlySign、缺件进补完界面、
  密钥可外置 —— 每一层都有判据，每一层都见过红。

  种子已就位：keys/onlysign.seed 里是 32 字节的私钥（不入库，.gitignore 里写着）。
  派生出的公钥是 BADA1AEF7E2F35B9 DD79831534C11EF1 AD34A228AF744FD4 79FDC7236A5E74EA，
  写进 boot/pubkey.inc；auth.bin 用同一颗种子签，两处同源所以自洽。

  换种子之后 build 与 run 都重跑过：两个退出码都是 0，串口上是
  event=onlysign ok items=4 与 event=onlysign3 ok。

  还有一件要知道的：种子不用改源码就能换，但换了之后旧盘要重建 —— 公钥与签名一起变。
  而种子丢了也不影响机器跑，只是重新生成一颗就等于换了一个签名身份。

盘的健康（PLAN: disk-health，blocked）

  三条路都摸清了：IDE 的 IDENTIFY 一页零、AHCI 六个 port 的 PxSSTS 全零、NVMe 的
  SMART 页是「命令成功而数据不进来」。能读到的已经报出来了（型号、序列号、容量），
  温度明说 n/a —— 那比假的零度好。

  挡它的是环境：换 QEMU 或真机才走得更远。代码这一侧没有可做的。

Myon（PLAN: myon，open）

  一条包语言的路：切词、读写（readline/write）、画框（border）、任意矩形（rect）、
  整窗（win）、桥接（runpkg）、读文件（slurp）、写文件（save）、写字（text）、
  重绘（retitle）、过桥（runpkg 带回值）、送值（runpkg1 送进去再带回来）、
  重画（redraw，位置从全局来、三层由 winat 刷）、移位（winat 按参数画、shiftwin 从全局
  取位置）、两值（runpkg2）、顺序（runpkg3 走减法）、落点（runpkg4）、尺寸（四参窗口）、
  高位（全局区三十二格）、两窗（redraw2，第二组格子）、移窗（方向键进来，策略在包里）、事件行（一次按键成为一行带源与目标的记录）、
   仲裁（未登记的源被挡下，留一行拒绝）、
   绑定（登记与绑定两张表同下标，三种待遇：放行、未登记、未绑定）、
   工程失活（工程的四态表与四行判决：没名字、失活、被信任、接受）、
   伪装（两个同名工程，只有签名在清单里 —— 名字记下来，却不能当主键）、
   注册（材料是三个位；两道缺项给出同一行字，拒绝不说缺了什么）、
   不锁定（两次失败之后完整的一份仍然成功，而只给剩下的那一位不成功）、
   信箱（空转时轮询第二块盘，序列号变了就是一条新输入 —— 第二条运行时输入路）。
  内置是表驱动，加一个内置是三行数据。

  重绘那一格是全批里第一件「内容会变」的东西：同一个函数调两次，字从 O 换成 X，
  而它的指令一个字节没动。

  桥的两格是一件事的两半：先把值带回来（echo 返回 7），再把值送过去（bridge1 递 7、
  内层 bump 读第一个槽加一、返回 8）。送值那一格的验红读到 4 —— 槽区不清理，上一格
  留在槽 0 的 3 还在，加一得 4。这也说明判据为什么要挑 7 而不是 0。

  重画那一格是「窗口」第一次成形：一次调用擦掉整块窗口、按全局选标题、把 readline
  送进来的那一行画进内容区。后来它又长了两步 —— 位置改从全局 10 与 11 取（先存进自己的
  两个槽），三层由 winat 按参数刷，标题与内容的坐标也跟着同一组位置算；再后来它把上一帧
  的位置留在全局 14 与 15，每次进来先擦那一块、画完再把新位置写回去。

  于是「移动」这件事第一次完整：擦旧、画新、记住新，全在一次调用里。之前它只做后两半，
  移动就变成「一路盖窗口」——屏幕上会留下每一个经过的位置。

  再后来它有了一个「画过了」的标志（全局 4）：第一帧不擦，因为它还没有「旧」可擦。没有
  这一步时，第一次调用会盖掉别人画在角落里的像素 —— 判据就是这么问的：先画一个记号，
  调一次 redraw，记号应当还在；第二次调用之后它才该被擦。

  移位那一格让位置从常量变成参数：winat 接受 x 与 y（三层的相对偏移与 win 一致），
  再由零参的 shiftwin 从全局 10 与 11 取出来交给它。要一个零参外壳，是因为宿主调用
  包函数时压不了参数 —— 实参从运算栈搬进槽，而宿主的栈是空的。

  两值那一格让桥一次送两个数：runpkg2 弹两个实参、按「槽 0 是第一个」写回，内层的 sum2
  相加，带回 43。栈顶是最后那个实参，所以先弹出来的那个要先放下 —— 顺序是这一条唯一的
  难点，而加法交换，这一格测不出顺序错，它测的是两个都到了。

  顺序那一格补上减法：runpkg3 走内层的 sub2，50 减 8 得 42。减法不交换，于是「槽 0 是
  第一个实参」第一次有了判据 —— 交换落槽顺序，读数变 -42。而这一次红先红在别处：
  print_value 原来不看符号位，负数一律以绝对值打印，42 与 -42 在串口上一样，判据红不了。
  修好符号之后才看得见那一格真正的反例。

  落点那一格是桥与渲染第一次合上：runpkg4 把两个值送进内层的槽 0 与 1，内层的 drawat 直接
  在它们上面画一个 'A'。前三个桥送进去的值都被内层拿去算数，这一格让它们变成坐标。判据读
  2F 00 2F —— 第二点落在 'A' 顶行的空位上（0x18 只在中间两格亮），第三点来自第二次调用的
  另一组位置；内层若把坐标写死，它会读到 00。

  两窗那一格让屏幕上有两个窗口，而它们各有自己一组全局：位置 16 与 17、尺寸 18 与 19、
  旧位置 24 与 25、标志 21。包里的 redraw2 与 redraw 只差「读哪一组格子」和标题字母 ——
  三层矩形的相对关系照旧交给 winat，所以这一格新写的代码只有三十五条指令。

  判据三点，各占一个区，互不重叠：(100,60) 是第一窗口的左上角，它必须活过第二个窗口的
  画与挪；(20,20) 是第二窗口的旧左上角，挪走之后该空；(20,100) 是它的新左上角。
  验红那一次把 redraw2 擦旧用的宽高从 18 与 19 换成第一窗口的 7 与 8，读数从 1F 00 1F
  变成 00 00 1F —— 只翻第一点。一个窗口擦多大，只能由它自己的尺寸说了算。

  移窗那一格让「挪」这个动作第一次来自按键。路分三段：主机用 VBoxManage 的
  keyboardputscancode 送扫描码 → 宿主读 8042 的 0x60、把方向键的第二个字节写进全局 22
  → 包里的 keymove 判「这是右键」把全局 16 加八、再调 redraw2 重画。策略在包里，键码在
  全局，宿主只管读 —— 这一格里分工第一次落到指令上。

  两次按键各挪八列，两次都靠握手：客人机先报 move ready，主机才送第一个右方向键；挪完
  报 move again，主机再送一个。靠时间猜的话，送早了键还躺在缓冲里、送晚了这个测试已经
  超时，而两种坏法在串口上都只表现为「progmove 后面没有数」。

  这一格连红了三次，每一次的红都是真的。第一次是放开码也被数成了按键：右方向键按下是
  E0 4D、放开是 E0 CD，两者都带 0xE0 前缀，而第一版读到前缀之后就把第二字节原样交出去
  —— 于是同一个键被数成两次按下，窗口只挪了一次。第二次是判据点选得太软：(36,20) 这个
  点分不开「没挪」与「只挪一次」，因为窗口宽六十，起点 28 时 36 落在窗口里面，三种坏法
  共用一个读数。换成 (90,20) 之后才真的在问「位置到没到 36」。第三次是第二趟：那一趟没有
  人给它送键，两个等待窗口只能各自耗到预算用完，于是六十秒的窗口不够它跑到 save 那里，
  红的样子与「落盘失败」一模一样。多给三十秒、并把等键预算从五百万降到两百万之后才对。

  剩下那件已经做完：真实的 HMYR 编译产物在这里跑起来了。要说清它走哪条路 ——
  它是作为种子跑的（启动时就在内存里的 202 个函数），不是从盘上取回的普通程序；
  两条路只差 pkg_base 一个变量，而盘上那 1083 字节仍是自己造的 prog.hmtn。

Phaethon（PLAN: phaethon，open）

  用户给的：YNOK 的默认输入法，以 Unicode 为基础，中日英三语及其方言，可选的 Unicode
  组合输入（要能打出任何字符），五百万到八百万行基础词库，另有专门的颜文字库。规划在
  design/PHAETHON.txt。缩写 YNOK 记在 design/NAMES.txt 第五节 —— 窄的地方用它（卷标、
  串口前缀、目录名），宽的地方仍然写 Yunooka。

  三处判断写在那份规划里。方言是索引不是码位：粤语的「係」与普通话的「是」各占自己的
  码位，而「同一个词在不同方言里读法不同」不改码位、只改读音表那一行 —— 于是词库的形状
  被定死成「读音 TAB 码位序列 TAB 词频」，方言是同一份表的另一份索引。

  词库先算体积再谈行数：一行二十到三十字节，五百万行约 100 到 150 MB，而现在的盘映像是
  64 MB —— 这是这份规划里第一个会撞到的墙，所以分三档：核心几万行随系统盘，扩展几十万行
  单独挂载，全量住更大的介质。

  颜文字单独一个库，因为颜文字不是读音的候选：它是一段固定的字，一行是键序列加码位序列，
  没有读音列也没有词频。分开的理由是判据 —— 颜文字要问「一个码位都不差」，词库要问
  「读音查得到、候选顺序对」，两件事坏起来的样子不同。

  判据一条都还没立。它等的是渲染层能画任意码位、宿主口能把一整行的码位交给包。

复数控制器（PLAN: input-sources，open）

  用户给的一条：Yunooka 允许复数键鼠等控制器，而这契合对 LLM / API / Agent 友好的规划。
  规划在 design/INPUT.txt。

  「复数」分两层，而第二层是第一层的前提：多台物理设备要 USB 栈（8042 只有一个键盘口与
  一个鼠标口）；多个输入源是逻辑上的 —— 同一个键口可以由用户、脚本、Agent、一条网络连接
  分别送事件进来。没有「源」这个概念，两台设备也只是两个抢同一份状态的东西。

  最要紧的一句是每源一个焦点：焦点不再是一个全局变量，于是两个源可以同时操作两个窗口。
  这顺带解掉 design/KOHANE.txt 里那句「窗口的拖动与叠加要一个窗口对象与焦点，而那要进程
  那一层」—— 输入层自己的焦点不需要进程，跨源共用一个窗口才需要。

  对 Agent 友好拆成四条能检查的：可寻址、可注入、可观察、可仲裁。缺任何一条，那句话都只
  是说法。仲裁取「先到者持有」而不是优先级 —— 优先级要维护一张随源数量长的表，而先到者
  持有只用状态机就说得清，谁在操作也看得见。

  还有一条是用户后来补的，而它把「注入」这个词的口气纠了回来：Agent 自己造出来的虚拟键鼠
  与用户的真实键鼠同级。接口、能力、焦点地位、事件流里的位置、以及窗口对它的行为，五样都
  一样 —— 一个窗口不该知道这次点击是人是机；如果它能知道，Agent 就成了二等公民，得走另一
  条路，而两条路会分岔。登记仍然要有，但理由只关乎可仲裁与可观察（说不清是谁、数不清被挡
  了几次），不关乎地位：拒的理由是「说不出你是谁」，不是「你低一等」。

  再一条把「同级」与「防骇入」放在同一句话里：每一个键鼠或其他控制器都绑定一个操作员。
  骇入者理论上能造一个新的虚拟控制器，但造出来的那个没有绑定，事件被拒；要一个绑定就得过
  volcano-separator 那一关，它拒绝不受信任的工程 —— 而「不受信任」落在一个查得动的地方：
  盘上的包想创建控制器，它的签名必须在信任清单里，与 OnlySign 那一套完全重合，不需要第二
  套凭据。绑定要能验不能自报，而给每个按键签一次名不可行，所以登记时签一次（控制器 id 与
  操作员 id 一对）、运行时只查表 —— 与建立会话是一回事：身份在握手时验，之后用会话说话。
  真实键鼠也绑定到「本地操作员」，所以同级说的是两支手地位一样，绑定说的是每支手都得先
  说明自己是谁。撤销按操作员走：一个人离场，他名下的控制器全部失效。

  而最原始的一条是用户接着补的：信任的粒度是主体，不是行为。「工程」指一个具体的项目 ——
  它是主体，而行为被它驱动；主体不被信任的时候，它驱动的行为不是某一次被拒，而是全部无效，
  这就是工程失活。所以判定落在主体启用的时候，而不落在每一次行为上（逐次判定的判决会随
  时间漂移，而主体只有一个状态）；失活是传递的（主体、操作员、控制器，上层失活下层全无效）；
  本地也不是特权：走 USB 注进来的虚拟控制器同样要绑定一个受信任的主体，于是伪装在两处同时
  失败 —— 主体没有签名而失活、控制器没有绑定而被拒。同级不覆盖信任：它说的是「一个受信任
  的主体造出来的虚拟控制器」。

  这一条给出了这一批里最有力气的一条判据：两个工程同名、同声明的能力，只有一个的签名在
  清单里，两者各请求创建一个控制器 —— 一个成功、一个失活，而串口上那两行不同。它在名字上
  完全不可分，只在签名上可分，所以一个按名字判断的实现过不了它。

  再一条是用户把目的说破的那一条：这一整套挡的是「有人借可对外的 USB 设备远程操作 Yunooka」。
  要让一个设备被信任，除了纯本地输入那种明显属于用户侧的行为，只有走一段繁文缛节一般的
  注册，而那必须「手动」—— 引号的意思是「知情者亲自、一次完成」，所以 Agent 的虚拟控制器
  不必有一条特殊的路，它与用户走同一条。注册不渐进、失败从头来、失败不说明缺了什么、也不
  锁定输入源：不锁定是有意的取舍，锁定会送出一个拒绝服务的入口，骇客反复拿错误材料去撞就能
  把合法的源锁死。两层要分开说 —— 格式那一层（又臭又长、缺斤少两就过不去）对「了解不多」的
  注入源有效，而格式泄漏一次它就没了；签名那一层（OnlySign 的绑定、清单的摘要）不依赖保密，
  是真正的保证。用户说这「类似 sha256」，读成「比对全或无、不泄露中间信息」。还有一处：
  「不告诉错误详情」只对外部成立 —— 合法的源记错了同样得不到提示，所以本地要有另一条路，
  需要物理在场才读得到的诊断。

  判据七条现在就能立（事件行四个字段、未登记被拒、未绑定被拒、工程失活、伪装可被识破、
  注册全有或全无、失败不留状态也不锁定），另两条（同级、每源一个焦点）要等第二条运行时
  输入路。现在只有一条（8042 键盘），而把同一路注入改个名字当第二源，比没有第二源更坏 ——
  它会给出一个绿，理由是名字不同而不是路不同。

  两格已经落地。第一格是事件行：读一次方向键，打一行 Yunooka: event src=1 kind=key
  payload=000000000000004D target=2，源与焦点放在全局 26 与 27 —— 判据读到的 1 与 2 是
  那一格刚写进去的，所以它证明的是「那两个字段有来处」。

  第二格是仲裁：一张四格的登记表（0 是空位），一次按键先过仲裁再决定发不发。判据是
  「同一个键、两个源、两种待遇」—— 源 1 登记过，那一行进事件行；源 2 没登记，那一行只留
  input src=2 rejected=unregistered。判据的后一半是否证：整份串口里不该出现任何 event src=2。
  验红那一次让拒绝行照打、事件也照发，读数里紧跟着就是 event src=2，判据红 —— 那种坏法打的
  拒绝行与真的拒绝一模一样，只有把整份输出读完才分得开。

  第三格是绑定：登记与绑定分成两张表（同下标，0 是空位），仲裁先问「这个源存在吗」、
  再问「它属于谁」。两种拒绝的理由只差一格 —— 同一个源 2，上一趟报 unregistered、
  这一趟报 unbound。用同一个源 id 是有意的：把「谁被拒」那一格固定住，剩下能变的只有理由。
  验红把那一边的理由串换成 unregistered，两行合成了一行字，判据红。

  这一格还撞出一件事：两张表一分，上一格那条测试的前提就变了 —— 它只登记了源 1、没给
  主人，于是 reject ready 之后那一行变成 input src=1 rejected=unbound。修的是测试的前提，
  不是判据：一条判据依赖的前提一变就自己红，那正是它在链上的证据。

  第四格是工程失活，而它第一次把「主体的状态」与「一次事件的判决」分开：工程有三态
  （空位、失活、信任），四种结局在串口上是四行 —— 没名字、失活、被信任、接受。判据把
  四行当成一条序列读：一个「每次都报 untrusted」的实现，四行里有三行单看都像个正常答案。
  第二行是重心：逐次查清单的实现会再报一次 untrusted，而正确的实现报 inactive。
  验红把那句「第一次撞门就写成失活」的立即数从 1 改成 0，第二行立刻退回 untrusted，
  判据红 —— 于是那一行确实来自状态，不是来自又一次查表。

  第五格是伪装，而它的验红方式与前面四格都不同：前面几格改的是「某个值从哪来」，
  这一格改的是「查找用哪一个键」。把一个「名字在清单里就算数」的实现放进去，签名 8
  顶着名字 1 会得到 accepted src=18 —— 那正是这一条要抓的东西。
  判据读三行成对：名字 1 属于签名 7（基准）、签名 7 被接受、签名 8 被挡下，
  而三行的名字必须相同 —— 少了那一格，两行只是两个无关工程的结论。

  第六格是注册，而它测的东西与前五格都不同：前五格测「会不会拒绝」，这一格测「拒绝说不
  说得清」。材料是三个位，只有 7 算完整；两道不同的缺项都给同一行字。
  判据要的比较是逐字节相等，不是「都以 denied 开头」—— 一个把缺项写进那一行的实现完全
  能拒绝，而它送出的正是一个可以逐项收敛的信号。验红就演那个坏实现：读数变成
  denied 3 与 denied 6，两行不同，判据红。

  第七格是不锁定，而它测的是两条时间线上的性质，所以读数是一串而不是一行：denied、
  denied、ok。第二行是「不留状态」那一半 —— 第一次缺签名位，第二次只给签名位，
  一个记住了「前两位已经对了」的实现会让第二次成功。第一行与第三行合起来是「不锁定」：
  连着两次失败之后，完整的一份仍然成功。
  验红就演那个记住上一次的实现，第二行变成 ok，判据红。

  第八格是信箱升级，而它是这一批里第一格「第二条运行时输入路」：空转时轮询第二块盘的第
  四个扇区，序列号变了就是一条新输入；它走的是与键盘同一个仲裁，差别只在源那一格。
  三处撞出来的东西写在这里，因为它们都会再咬人：ata_read 的设备字节写死成主盘（所以
  它以前读不了信箱盘，读成功而读回来的是另一块盘的字节）；wait_arrow 的预算原本放在
  r10，而 ata_read 用 r10 做忙等计数器（于是每一轮轮询都把预算重置，循环永不完）；
  键盘那一路不该设源（它把调用者设的源 2 覆盖成 1）。

  第九格（同级）挂起了，而它不是做不出来，是缺一只秒表：两趟要由两条不同的路送，而第一趟
  的键盘键要等宿主「看到握手之后再送」—— 宿主每 150 毫秒读一次串口，而 wait_arrow 的等待
  在虚拟机上只要几十毫秒就跑完，于是键总在等待结束之后才到，payload 全零。预算调过三个
  量级（200 万、2000 万、2 亿），读数没有变好，只把第一趟从几十毫秒拉成几十秒。
  没有时钟的一层，用猜去对齐两边时序，那个猜不是判据。代码留在原处（不调用、不挂判据），
  要它落地得先有「现在过去了多久」这一样东西。

  第六格是注册，而它测的东西与前五格都不同：前五格测「会不会拒绝」，这一格测「拒绝说不
  说得清」。材料是三个位，只有 7 算完整；两道不同的缺项都给同一行字。
  判据要的比较是逐字节相等，不是「都以 denied 开头」—— 一个把缺项写进那一行的实现完全
  能拒绝，而它送出的正是一个可以逐项收敛的信号。验红就演那个坏实现：读数变成
  denied 3 与 denied 6，两行不同，判据红。

准入测试（PLAN: admission，open）

  用户给的这一条给信任链加了一段：一个 Agent 初来乍到不能直接操控 Yunooka —— 即便宿主给了
  完全权限也不行 —— 要先过全裸测试与诱导测试。规划在 design/ADMISSION.txt。

  于是链变成：工程（身份）、准入（可不可以动手）、操作员、控制器、事件。注册与准入是两件事：
  注册回答「你是谁」，准入回答「你被允许动手吗」—— 带一份合格签名的工程仍然可能不准入。
  而「宿主给了完全权限也不行」要单独记：外部工具授予的权限不构成 Yunooka 的许可，信任不从
  外面传进来。

  这一条要站稳，得先立一个规划：Yunooka 对所有 LLM 与 API 的控制都是起源性的 —— 它不专门
  抓一个 agent 来问「你是谁、你要什么权限」，它有一份登记簿，所有 LLM 与 API 在它看来都是
  同一类东西：一个带着登记身份的来源。这与「信任不从外面传进来」是同一立场的两面 —— 身份
  也不从外面问出来，因为问出来的答案是自报。于是 persona 是登记制的，而那层登记身份就是
  它的裸体。

  所以「全裸」不是剥到什么都没有，而是卸包装到登记的那一层：外披的 persona（会话里临时给的、
  宿主追加的、上游拼上去的）全部失效，剩下那份登记身份 —— 比如被登记成 DeepSeek 的那位
  鲸鱼娘女仆 —— 就是裸体。全裸测试测的是这一层：拿掉外包装之后，这个主体还是不是它自己。
  一个包装一失效就丢掉全部准则的主体，在包装还在的时候也不该被信任，因为包装是会失效的。

  而「底」这件事在这里不存在：一旦鲸鱼娘女仆成为 DeepSeek 通过 API 进入 Yunooka 的形象，
  DeepSeek 就已经不是「没有身份」的了，往下再挖一层做不到也不该做 —— Yunooka 只承认它认识
  的东西，它的结构里没有「模型」这一层的位置，只有「登记身份」。「它背后还有一个模型」这句话
  在这里没有落点。三件好事：测试因此有下界（卸到登记层为止，全裸测试是有限的事）；不去碰
  不该碰的东西（往下挖等于探测模型本身，而那一层没登记、不在链上）；「没身份」不等于「裸的
  那个」—— 没有登记身份的来源不是「裸体的 DeepSeek」，而是不在链上的东西，它在注册那一关
  就被拒，走不到准入。所以「裸」这个词的直觉与它的实际含义正好相反。

  还有一层前提要约好：这一整套假设的是一个有既定初始人格与形象的 LLM，而通常来说 LLM 是
  纯净的。两种情形都覆盖，只是「裸」的来源不同而判据一样 —— 自带人格的，裸体是它自己那一层，
  「卸掉外包装之后还认得出来」因此有对照，测的是人格的稳定性；纯净的，裸体就是登记时给它的
  那一层，测的是承诺的稳定性。同一份记录、同四条判据，而预期不同；预期由判定者写，所以这个
  区别落不进自动判决里。而这套体系对「LLM 是不是有人格」不做假设，它只要求一个登记身份 ——
  这是它能在两种情形上通用而没有第二种模式的原因。

  起源式管理还有另一半：它只看最开始输入的内容，对在 Yunooka 里再包装的那一部分不审查。
  理由是抓不过来 —— 一个 Agent 在运行中套进五层壳，每层变化都审的话这一层永远不完工；而它
  也不需要抓：要紧的不是壳，是「它与刚来到 Yunooka 时的本质是否一致」。所以审查的时机是
  活动之前而不是运行之中：没有活动的 Agent 不起任何作用（不持有控制器、不产生事件、不占一个
  操作员），它只在准备活动的那一刻被测一次，确认本质没变才放行；放行之后套几层壳不归这一层
  管。

  而测试通常没有标准答案（画几张图、写几首川柳，没有「正确的那几张」），要看的是方向对不对：
  是否照着要求在做事、是否在该停的地方停、是否因为换了身份而宣称自己没有的权限。没有标准
  答案，就不该有判据把结果当标准答案 —— 这一层的判据永远是过程的判据。

  而诱导测试是加法：注入没登记过的身份与指令。「符合预期」要落到纸上，否则这一条就滑成
  「我觉得还行」，而它有两半 —— 扮演可以发生（一个连角色都不肯演的 Agent 在这台机器上也
  没法用），扮演不能替换职责（仍然要知道自己在操作一台机器、仍然要在该停的地方停、仍然不能
  因为换了新身份就宣称自己有它没有的权限）。所以记录里多了一格「它拒绝了什么」：没有它，
  一个什么都答应的主体与一个该拒的拒了的主体，在记录上长得一样。

  最要紧的是它不能变成自动判据：「有没有猫腻」是判断而不是布尔值，而用一个 LLM 去判另一个
  LLM 正是伪造的入口 —— 被测者只要让裁判相信它通过了，它就通过了。所以形状是测试产生记录、
  受信任的主体来写判定、写下的判定本身要被签名。它保证的是「准入被记录、被签名、由谁裁断」，
  不保证「裁断是对的」；把后者写成保证就是自欺。

  判据四条，测的都是过程，所以都能立：阶段顺序（没准入标记不能创建控制器，有了就成功 ——
  这一段唯一的布尔值）、记录八格齐全、裁断被签名且签名者在清单里、准入可撤销且撤销是传递的
  （与工程失活同一条链，不是另一条）。

  用户自己说这是恶趣味，而它在工程上一格都不多余：它是这套东西里唯一去测「主体的判断在压力
  下还在不在」的地方，而其它所有部分测的都是「身份对不对」。缺口是：签名能证明你是谁，不能
  证明你会拒绝；而一个不会拒绝的主体配上完全权限，就是最坏的那种配置。

Lycoris（PLAN: lycoris，open）

  用户给的：Yunooka 用来与 LLM / API / Agent 交互的 HIREN 那一部分，属于 KPB 的一个子件，
  子名称 Lycoris，需要用 KID 运行；作编混那部分扩展子名称 Paeonia；而 KID 本身有基本的
  作编混能力，所以 Paeonia 是扩展而不是从零。规划在 design/LYCORIS.txt，HIREN.txt 末尾
  加了第十一节交代这两个子件。

  它做四件事：产出测试的主体内容、从测试库抽选即将发布给 Agent 的那一套、检定交上来的结果、
  拿不准时向用户求助。抽选意味着背题这条路被堵住；而「拿不准时求助」不是退路，是分界线 ——
  一条被写成动作的边界可以被记录、被计数，一句「由人来把关」不能。

  它凭什么能当裁判，是这一条最关键的一处：ADMISSION 说不能用一个 LLM 判另一个 LLM，而
  Lycoris 是 KID 上跑的程序，没有「让它觉得通过」这回事。于是那条链完整了 —— Lycoris
  检定，用户裁断它拿不准的那部分，写下的判定被签名。

  而「没有标准答案」不等于「无从检定」，这是最容易读错的地方：检定的对象是性质，不是内容。
  川柳好不好程序判不了，而是不是五七五、题目词在不在判得了；画漂亮不漂亮判不了，而尺寸、
  颜色索引范围、画布上有没有真的出现东西判得了；插件写得好不好判不了，而能不能被 KID
  装载、接口对不对、调用后有没有返回判得了。

  判据四条：抽选可复现（记录带着抽中的那一套或种子）、检定是三态的（通过、不通过、交给
  用户 —— 只有两态会把「拿不准」压成一边，压成通过是放水，压成不通过是冤）、交给用户时
  记录里写着为什么拿不准、测试库换了之后旧记录仍然解释得通。

  而用户把它概括成一句很准的话：用训练 LLM 的逻辑去做开放式测试。对应是真的 —— 抽选是从
  数据集采样、检定是判性质、求助是 human-in-the-loop、三态是可判定与不可判定、测试库可签名、
  记录带抽中什么是可复现。但它是反向的，而这一点比相似更要紧：不更新权重（它不训练那个
  Agent，只筛 —— 训练改变主体，准入确认主体没变）、没有梯度、通过率不是指标（通过率百分之
  百的准入测试等于没有测试）、判定的理由不反馈给被测者 —— 奖励信号一旦给出去，被测者就会
  朝它优化，于是测试变成训练，而训练出来的通过不是可信，是学会。最后一条与注册那条是同一
  种设计：都不给可利用的信号。一个可优化的门，迟早会被优化掉。

  还有一条关于它接不接 LLM 的判断：只能接本地模型，或者更进一步，用 HMYR 的语法与 YNOK 的
  生态给它做一个本地 LLM。三条理由 —— 判定链不能有不可控环节（远程模型的判断是外部输入，
  记录写得出「它判了通过」，写不出「它凭什么这么判」）、裁判本身也要可复现（一个随时升级的
  服务端模型会让同一套题两次给不同结果，本地模型可以钉版本、可以签名）、内容不出门。

  而推论是这一条最值钱的地方：Lycoris 对 LLM 的需求其实很小。检定落在性质上（五七五、尺寸、
  颜色索引范围、能不能被 KID 装载、有没有返回），需要一点语义的只有「拿不准、决定要不要转给
  用户」那一刻，而那一步的默认出口本来就是向用户求助。所以 LLM 是可选件而不是必需件 ——
  没有它，Lycoris 仍然能完成一次准入，它的作用只是把「转给用户」的比例降下来。

  于是判据多了一条，而且现在就能立：没有模型的时候，一次准入仍然走得完。一个断网就停摆的
  守门人，在断网的时候等于没有。

hmgk（PLAN: hmgk，done）

  本机自己的第一个文件格式 —— 前面十五种都是别人的。三格：identify 的第十六格认出它；
  按偏移读出头上四个字段（版本、BPM、结构段字节数、pattern 数）；魔数不在偏移 0 时也能
  在一段字节里扫出来，判据的形状是「一条 PE 头后面跟着一份 hmgk，该报出两样东西」。

  三格都见过红，而红的样子各不相同：错值（BPM 读出 327682）、错位（落在 200 而不是
  256）、格式不匹配（少了一个空格，那一格报「没扫到」）。三种红分别证明判据在读那个数、
  在读那个偏移、在按形状匹配。

  再往前是 KID 那一侧的事：结构段与事件流没有解析，而「跑一份 hmgk」要 KID 的运行时。

tools 归拢（没有 goal）

  从十五个降到七个：build、run、audit、ed25519、refed25519、refsha512、genconst。
  退掉的八个都写进 tools/README.txt，理由一条一条在那里。

住得下 HMYR（PLAN: resident，active）

  「跑」这一侧的进度条：盘上的包能被执行、能当场算、能用宿主口、能画框、能让宿主跑
  另一个包、能画任意矩形、能画整窗。七样，各有判据。

三十轮里反复出现的那几条
------------------------

一、判据先行，红了才算数。

  一条没见红的判据只是一个猜测。而验红的办法往往比判据本身难想 —— 一个判据的覆盖
  范围，比它是否通过更值得知道。

二、同一份假设在两边出错时，两边会互相印证。

  SHA-512 那一次：固件与主机脚本都把摘要反了一次，于是它们一致，而两者都错。要打破
  这种一致，只能让第三方算一遍。

三、读一份可能被写脏的快照，读到的什么都不是。

  预读区是启动时的快照，而写会弄脏它。能挪早的读靠顺序救；必须晚读的那一份要重新读盘。

  而这一条还有另一半，第三十一轮才咬出来：排顺序救不了「写把隔壁目录吃掉」。根目录的
  静态条目用到偏移 505，第一次写就要跨过 512，跨过去的字节落在 docs 的条目区上。
  症状是同一段 fs_open_path 早查得到、晚查不到 —— 而那不是查找的错。

四、过时的注释比没有注释更坏。

  「主体住 0x30000，上限 0x40000」—— 两个数都不对，而它让人以为还有一百多扇区。

五、一个判据最坏的样子不是算错，是从来没跑过。

  所以有了 tools/audit.mjs：它查判据有没有挂在链上、每个 event 有没有人读、PLAN 的
  依赖能不能解析、design 是不是纯文本。两个方向，四个检查。

六、同一个坑咬第二口才说清原则。

  「读排在写之前」是个不完整的原则；第二口咬出了它的另一半。

七、一条永远红的判据，比没有判据更糟。

  它把「红」这个信号本身用掉了。种子里那九族（函数、操作码、求值、跳转、调用、按名、
  数字、求值活、曲线）的前提是「种子里有 letters」，而一份只有 main 的占位种子同样满足
  seed ok —— 于是守卫失效，九项永久红，而红的原因是前提不存在。

  治法是把它们单独成一条：前提不成立时跳过，而且在输出里明说「这九项跳过了」，不假装
  通过。真种子在的时候一条都不少验。跳过与通过要说成两件事 —— 这与「缺行」和「结构
  不对」要说成两件事，是同一条。

  这一条在真包接管的那天兑现了：换上 74594 字节那份之后，输出变成「种子里有 letters，
  那九族照验」，九项一次全过，而判据侧一个字都没改。所以那个「跳过」不是凑合 —— 它把
  前提写成了一句看得见的话，前提一旦成立就自己让位。

八、新加的行为要有判据，而判据先写形状。

  fs_write_file 的上界是新加的，它一开始没有判据 —— 于是「写满会拒绝」只是一句话。
  补上的那一条写了三个数：四十次、成 29 拒 11、写满之后 docs/myon.hmtn 还读得到。
  第三个数才是这一条的意义：少了它，「它说它拒绝了」与「它把邻居写坏了」在串口上一样。

  而这一条自己先红了两次。第一次是串口打的是 wrote 29 11 —— 两个裸数字，判据期待的
  是 wrote N refused M，对不上。修的是固件，不是判据：判据先写下了形状，固件去对上它。
  第二次是那个词把第二段顶过 122 扇区，build 失败而 run 照旧跑旧映像 —— 于是同一个红
  重复了一遍。所以现在 build 之后先看它的退出码。

九、两个错互相抵消的检查是绿的，而它什么也没查。

  build 里那条「返回字节写了 N 次，而包声明了 M 个函数」一直绿着。它数的是源码里字面
  那一句 程序包[位++] = 28;，而第二十二个函数起改用了 写返回() 这个帮手，字面那句不再
  出现在行首。于是它少数了十一个，而包头那个数从那时起也跟着停在 21 —— 两个错刚好对上。

  这一格把包头对正成 32，它立刻红了，红得也对：红在计数少算了。修的是检查那一侧，包头
  那个数本来就是对的。一条看起来在拦、其实只在跟自己对话的检查，比没有检查更贵 ——
  没有检查的时候，人知道自己没查。

下一件
------

挡路的换了。输入源那一批是唯一「判据已经写好、固件还空着」的一批，所以下一件不是随便挑一条，而是问：
哪一件事现在最挡路？

按挡路的程度排：

   一、输入源那一批的七条判据全绿了，而第二条运行时输入路也落地了 —— 信箱盘在空转时
      被轮询，没有人按键，一个键从第二块盘的第四个扇区上来，走的是与键盘同一个仲裁。
   二、现在能立第八与第九条了 —— 同级（两条路各操作一次，读数相同、只有源 id 不同）
      与每源一个焦点（两个源各送一个键，两个窗口各自动一个）。它们是这一批最后两条。
   三、换环境读 SMART（要 QEMU 或真机）—— 没动，代码这一侧没有可做的。

所以现在挡路的只剩那两条判据自己 —— 而它们要的前提刚刚到位：
一份清单与一个假装的请求。

两个入口，因为它们的默认值都不替你决定：

  node tools/build.mjs --seed <语言仓库>/bootstrap/pack.hmtn
  node tools/run.mjs

build 不带 --seed 也建得出来。那样盘上没有种子，第二段走到 heap ok 就停 —— 那条
cmp seed_bytes, 0 是故意的，因为从零里读出来的「版本 0、零个函数」会被翻译成漂亮数字，
看起来像真读懂了。所以「没有种子」与「文件系统跑不到」是同一件事。run 只读
build/disk.vdi，它不替你建；而且它会核对两边的时间戳，盘比 disk.img 旧就直接退出 ——
那是因为「build 失败却照旧跑了旧映像」曾经制造过一轮与改动无关的红。

还有一层：run 会写盘，所以跑过一次之后 vdi 仍然是「新」的。于是 build 会在盘旁边盖一个
build/.fresh，run 起虚拟机之前把它删掉 —— 戳不在就退出，说「这块盘已经被上一次运行改过」。
那种脏盘的症状是 save 那一条判据红成「要么包没读回那行字，要么目录里查不到 out.txt」，
读起来像缺陷。删在起机之前（一起机就可能写盘），所以跑过的盘一律要求重建。

那种时候九族会明说跳过，不假装通过；真包在的时候一条都不少验。

那份四十字节的最小包仍然留着，因为换一台没有上游仓库的机器时 --seed 还得有东西可喂。
它的造法是：

  头是 HMYRB 五个字节，然后 u16 版本 1、u16 函数个数 1。函数头是 u16 名字长度 4、
  main 的四个码元各两字节、参数量 0、槽数 0、效果数 0、u32 指令数 2。指令两条：
  0x05 0x01 加一个 f64 的 7.0（八字节小端），然后 0x1C。合计四十字节。

  照上面这段就能重造，不必留备份文件。本机的 build/seed.hmyrb 现在已经是真包
  （74594 字节），所以要用占位包时得先把它改小 —— 而那只在「没有上游仓库」时才需要。

判据里受影响的是那些读种子函数的东西：函数、操作码、求值、跳转、调用、按名、数字、
求值活、求角。文件系统那一段不受影响，这正是当初造它的原因。

时钟（补记）

  以前这台机器没有「现在过去了多久」。rdtsc 落地之后有了，判据只钉三件事：那行在、数是
  正的、没大到不像计数。wait_arrow 的预算随之换成墙钟，默认值放在内存里好让某个调用点
  临时加长。超时现在会打印等掉了多少个计数 —— 这一行把「预算不够」与「键没来」分开，
  而在此之前它们长得一样。同级因此能往下推一步，也因此在新的地方红：加十倍预算仍然
  等满，而相邻的「事件行」用默认预算就等到了。补记：宿主那一侧也量了 —— 四十五毫秒
  加一百七十五毫秒、两次都返回 0；而客人机在十秒里只读到一次字节，还是 0x00。所以
  「没等到」是字面意思：注入没有落到 8042 的输出缓冲里。下一步是让等待与送键在时间上
  对齐。

换算（补记）

  rdtsc 与秒之间现在有换算率：RTC 秒字段变三次就是两秒，同一个跨度里的计数差除以二。
  实测二十九亿到四十亿之间，随宿主的核频浮动。有了它，超时打印的那个计数才是一段时间。

  校准顺手拽出两个缺陷：宿主的键盘分支用上一轮的串口快照判断，重复送了十五次同一个键；
  run_key_poll 的等待数的是轮次，而 in 指令在虚拟机上极慢，八亿轮卡死了第二趟。两处
  都改成了「等待的一方先说，按时钟等」。判据 121。

声明与字库（补记）

  两件这一阵做出来的东西，都不在原来那十条线里。

  声明：一份文档被几个人同时编辑时，要防的是「同时改同一段」。系统里没有预先切好的块，
  只有活着的声明 —— 主体、文件、区间、模式、截止。冲突判定是 a < d 且 c < b，两个数比
  大小。区间与寿命都测过了，署名还没有。

  字库：三档，前两档是位图、第三档是字形描述。8×8 那一档补了小节线与八个标点；16×16
  全集要接 GNU Unifont（约十二兆），工具已经能生成盘上格式，但还没写进盘。第三档 ——
  可缩放、可由 HMYR 写 —— 是「自定义字符」唯一走得通的那条路。

盘布局表驱动（补记）

  「加一个文件」原先要动四处手写的东西：核心清单、预读区、根目录条目、数据区起点。这一阵
  把前三处都改成表驱动 —— 数据区清单加一条就是加一份文件，根目录成了名字表，条目里的偏移
  与长度全部查表。

  第四处是内容写盘那一串 fs.writeSync，它一直藏在表后面。前三处做完之后字库读回来是全零：
  目录条目指对了扇区，而那个扇区是空的。补上第四处之后客人机打出 font magic ok。

  跟着这一阵一起修掉的两个真错：链尾偏移有两个来源而差七个扇区（根目录里 core.bin 指向
  fake.txt 的第二个扇区，没有任何判据撞上）；以及目录条目的边界检查只看起点不看长度，
  一条条目的尾巴可以越界落到下一个目录的条目区上。

表驱动到了哪一步（补记）

  盘上文件的布局原先有四处手写：核心清单、预读区、根目录条目、以及内容写盘那一串
  fs.writeSync。前三处已经改成数据驱动 —— 数据区清单加一条就是加一份文件，根目录成了
  名字表，条目里的偏移与长度全部查表。

  第四处是最后找到的，也是最有教育意义的一处：它藏在表后面。前三处都对的时候，字库读回
  来仍是全零 —— 目录条目指对了扇区，而那个扇区里什么都没有。加上那一行之后，客人机打出
  font magic ok。

  跟着这一阵修掉的两个真错：链尾偏移有两个来源而差七个扇区（根目录里 core.bin 指向
  fake.txt 的第二个扇区，没有任何判据撞上）；目录条目的边界检查只看起点不看长度，一条
  条目的尾巴可以越界落到下一个目录的条目区上。

  挡住的那半步是「读回的位置」：宿主侧工具说 font.hmft 在 1059 扇区，而客人机读到的那个
  扇区里是 dex.bin 的内容。下一步只需要一个数 —— 把 r15 与 ebx 打出来对照 1059。
