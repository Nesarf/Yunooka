Yunooka 的现在：三十轮之后
==========================

这张纸上没有一个新东西。它把已经散在 PLAN、LAYERS、MEMORY 与各自 design 里的状态收成
一份 —— 为的是让下一个打开这个仓库的人先读它，而不是先去读一万字的 notes。

数（都是量出来的，不是估的）
----------------------------

    判据        106 条，全在 run.mjs 的某条链上
    事件        13 个 event= 行，每一个都有判据在读
        PLAN        56 个目标：42 done、12 blocked、1 open、1 active
    第二段      占 155 个扇区，上限 192（余三十七格）
    三条链      引导 1 + 加载器 8 + 主体 155 —— 种子从第 164 个扇区起
    种子        74594 字节、版本 1、202 个函数。真包，不再是占位
    根目录      两个扇区（1025 与 1026），docs 在 1027，数据区从 1028 起

六条线
------

OnlySign 第三环（PLAN: onlysign，open）

  闭了。域乘、域加减、点、标量乘、编解码、验签、接进 OnlySign、缺件进补完界面、
  密钥可外置 —— 每一层都有判据，每一层都见过红。

  种子已就位：keys/onlysign.seed 里是 32 字节的私钥（不入库，.gitignore 里写着）。
  派生出的公钥是 BADA1AEF7E2F35B9 DD79831534C11EF1 AD34A228AF744FD4 79FDC7236A5E74EA，
  写进 boot/pubkey.inc；auth.bin 用同一颗种子签，两处同源所以自洽。

  换种子之后 build 与 run 都重跑过：两个退出码都是 0，串口上是
  event=onlysign ok items=4 与 event=onlysign3 ok。

  还有一件要知道的：种子不用改源码就能换，但换了之后旧盘要重建 —— 公钥与签名一起变。
  而种子丢了也不影响机器跑，只是重新生成一颗就等于换了一个签名身份。

盘的健康（PLAN: disk-health，blocked）

  三条路都摸清了：IDE 的 IDENTIFY 一页零、AHCI 六个 port 的 PxSSTS 全零、NVMe 的
  SMART 页是「命令成功而数据不进来」。能读到的已经报出来了（型号、序列号、容量），
  温度明说 n/a —— 那比假的零度好。

  挡它的是环境：换 QEMU 或真机才走得更远。代码这一侧没有可做的。

Myon（PLAN: myon，open）

  一条包语言的路：切词、读写（readline/write）、画框（border）、任意矩形（rect）、
  整窗（win）、桥接（runpkg）、读文件（slurp）、写文件（save）、写字（text）、
  重绘（retitle）、过桥（runpkg 带回值）、送值（runpkg1 送进去再带回来）、
  重画（redraw，位置从全局来、三层由 winat 刷）、移位（winat 按参数画、shiftwin 从全局
  取位置）、两值（runpkg2）、顺序（runpkg3 走减法）、落点（runpkg4）。
  内置是表驱动，加一个内置是三行数据。

  重绘那一格是全批里第一件「内容会变」的东西：同一个函数调两次，字从 O 换成 X，
  而它的指令一个字节没动。

  桥的两格是一件事的两半：先把值带回来（echo 返回 7），再把值送过去（bridge1 递 7、
  内层 bump 读第一个槽加一、返回 8）。送值那一格的验红读到 4 —— 槽区不清理，上一格
  留在槽 0 的 3 还在，加一得 4。这也说明判据为什么要挑 7 而不是 0。

  重画那一格是「窗口」第一次成形：一次调用擦掉整块窗口、按全局选标题、把 readline
  送进来的那一行画进内容区。后来它又长了两步 —— 位置改从全局 10 与 11 取（先存进自己的
  两个槽），三层由 winat 按参数刷，标题与内容的坐标也跟着同一组位置算；再后来它把上一帧
  的位置留在全局 14 与 15，每次进来先擦那一块、画完再把新位置写回去。

  于是「移动」这件事第一次完整：擦旧、画新、记住新，全在一次调用里。之前它只做后两半，
  移动就变成「一路盖窗口」——屏幕上会留下每一个经过的位置。

  移位那一格让位置从常量变成参数：winat 接受 x 与 y（三层的相对偏移与 win 一致），
  再由零参的 shiftwin 从全局 10 与 11 取出来交给它。要一个零参外壳，是因为宿主调用
  包函数时压不了参数 —— 实参从运算栈搬进槽，而宿主的栈是空的。

  两值那一格让桥一次送两个数：runpkg2 弹两个实参、按「槽 0 是第一个」写回，内层的 sum2
  相加，带回 43。栈顶是最后那个实参，所以先弹出来的那个要先放下 —— 顺序是这一条唯一的
  难点，而加法交换，这一格测不出顺序错，它测的是两个都到了。

  顺序那一格补上减法：runpkg3 走内层的 sub2，50 减 8 得 42。减法不交换，于是「槽 0 是
  第一个实参」第一次有了判据 —— 交换落槽顺序，读数变 -42。而这一次红先红在别处：
  print_value 原来不看符号位，负数一律以绝对值打印，42 与 -42 在串口上一样，判据红不了。
  修好符号之后才看得见那一格真正的反例。

  落点那一格是桥与渲染第一次合上：runpkg4 把两个值送进内层的槽 0 与 1，内层的 drawat 直接
  在它们上面画一个 'A'。前三个桥送进去的值都被内层拿去算数，这一格让它们变成坐标。判据读
  2F 00 2F —— 第二点落在 'A' 顶行的空位上（0x18 只在中间两格亮），第三点来自第二次调用的
  另一组位置；内层若把坐标写死，它会读到 00。

  剩下那件已经做完：真实的 HMYR 编译产物在这里跑起来了。要说清它走哪条路 ——
  它是作为种子跑的（启动时就在内存里的 202 个函数），不是从盘上取回的普通程序；
  两条路只差 pkg_base 一个变量，而盘上那 1083 字节仍是自己造的 prog.hmtn。

hmgk（PLAN: hmgk，done）

  本机自己的第一个文件格式 —— 前面十五种都是别人的。三格：identify 的第十六格认出它；
  按偏移读出头上四个字段（版本、BPM、结构段字节数、pattern 数）；魔数不在偏移 0 时也能
  在一段字节里扫出来，判据的形状是「一条 PE 头后面跟着一份 hmgk，该报出两样东西」。

  三格都见过红，而红的样子各不相同：错值（BPM 读出 327682）、错位（落在 200 而不是
  256）、格式不匹配（少了一个空格，那一格报「没扫到」）。三种红分别证明判据在读那个数、
  在读那个偏移、在按形状匹配。

  再往前是 KID 那一侧的事：结构段与事件流没有解析，而「跑一份 hmgk」要 KID 的运行时。

tools 归拢（没有 goal）

  从十五个降到七个：build、run、audit、ed25519、refed25519、refsha512、genconst。
  退掉的八个都写进 tools/README.txt，理由一条一条在那里。

住得下 HMYR（PLAN: resident，active）

  「跑」这一侧的进度条：盘上的包能被执行、能当场算、能用宿主口、能画框、能让宿主跑
  另一个包、能画任意矩形、能画整窗。七样，各有判据。

三十轮里反复出现的那几条
------------------------

一、判据先行，红了才算数。

  一条没见红的判据只是一个猜测。而验红的办法往往比判据本身难想 —— 一个判据的覆盖
  范围，比它是否通过更值得知道。

二、同一份假设在两边出错时，两边会互相印证。

  SHA-512 那一次：固件与主机脚本都把摘要反了一次，于是它们一致，而两者都错。要打破
  这种一致，只能让第三方算一遍。

三、读一份可能被写脏的快照，读到的什么都不是。

  预读区是启动时的快照，而写会弄脏它。能挪早的读靠顺序救；必须晚读的那一份要重新读盘。

  而这一条还有另一半，第三十一轮才咬出来：排顺序救不了「写把隔壁目录吃掉」。根目录的
  静态条目用到偏移 505，第一次写就要跨过 512，跨过去的字节落在 docs 的条目区上。
  症状是同一段 fs_open_path 早查得到、晚查不到 —— 而那不是查找的错。

四、过时的注释比没有注释更坏。

  「主体住 0x30000，上限 0x40000」—— 两个数都不对，而它让人以为还有一百多扇区。

五、一个判据最坏的样子不是算错，是从来没跑过。

  所以有了 tools/audit.mjs：它查判据有没有挂在链上、每个 event 有没有人读、PLAN 的
  依赖能不能解析、design 是不是纯文本。两个方向，四个检查。

六、同一个坑咬第二口才说清原则。

  「读排在写之前」是个不完整的原则；第二口咬出了它的另一半。

七、一条永远红的判据，比没有判据更糟。

  它把「红」这个信号本身用掉了。种子里那九族（函数、操作码、求值、跳转、调用、按名、
  数字、求值活、曲线）的前提是「种子里有 letters」，而一份只有 main 的占位种子同样满足
  seed ok —— 于是守卫失效，九项永久红，而红的原因是前提不存在。

  治法是把它们单独成一条：前提不成立时跳过，而且在输出里明说「这九项跳过了」，不假装
  通过。真种子在的时候一条都不少验。跳过与通过要说成两件事 —— 这与「缺行」和「结构
  不对」要说成两件事，是同一条。

  这一条在真包接管的那天兑现了：换上 74594 字节那份之后，输出变成「种子里有 letters，
  那九族照验」，九项一次全过，而判据侧一个字都没改。所以那个「跳过」不是凑合 —— 它把
  前提写成了一句看得见的话，前提一旦成立就自己让位。

八、新加的行为要有判据，而判据先写形状。

  fs_write_file 的上界是新加的，它一开始没有判据 —— 于是「写满会拒绝」只是一句话。
  补上的那一条写了三个数：四十次、成 29 拒 11、写满之后 docs/myon.hmtn 还读得到。
  第三个数才是这一条的意义：少了它，「它说它拒绝了」与「它把邻居写坏了」在串口上一样。

  而这一条自己先红了两次。第一次是串口打的是 wrote 29 11 —— 两个裸数字，判据期待的
  是 wrote N refused M，对不上。修的是固件，不是判据：判据先写下了形状，固件去对上它。
  第二次是那个词把第二段顶过 122 扇区，build 失败而 run 照旧跑旧映像 —— 于是同一个红
  重复了一遍。所以现在 build 之后先看它的退出码。

下一件
------

四条线都到了「剩下的都是另一件事」的地步。所以下一件不该是随便挑一条继续，而是问：
哪一件事现在最挡路？

按挡路的程度排：

  一、真实 HMYR 产物 —— 做完。它就是 D:\himeyuri\bootstrap\pack.hmtn：74594 字节、
      版本 1、202 个函数。四十字节那个占位的时代结束了，九族判据开始真判。
  二、换环境读 SMART（要 QEMU 或真机）—— 没动，代码这一侧没有可做的。
  三、一颗真种子（要用户提供）—— 这是另一颗种子：keys/onlysign.seed，Ed25519 的
      私钥种子。它与 HMYRB 包同名而不同物，写在这里免得下一次有人拿错。

所以现在挡路的只剩环境那两件，而它们都在这台机器之外。

两个入口，因为它们的默认值都不替你决定：

  node tools/build.mjs --seed D:\himeyuri\bootstrap\pack.hmtn
  node tools/run.mjs

build 不带 --seed 也建得出来。那样盘上没有种子，第二段走到 heap ok 就停 —— 那条
cmp seed_bytes, 0 是故意的，因为从零里读出来的「版本 0、零个函数」会被翻译成漂亮数字，
看起来像真读懂了。所以「没有种子」与「文件系统跑不到」是同一件事。run 只读
build/disk.vdi，它不替你建；而且它会核对两边的时间戳，盘比 disk.img 旧就直接退出 ——
那是因为「build 失败却照旧跑了旧映像」曾经制造过一轮与改动无关的红。

还有一层：run 会写盘，所以跑过一次之后 vdi 仍然是「新」的。于是 build 会在盘旁边盖一个
build/.fresh，run 起虚拟机之前把它删掉 —— 戳不在就退出，说「这块盘已经被上一次运行改过」。
那种脏盘的症状是 save 那一条判据红成「要么包没读回那行字，要么目录里查不到 out.txt」，
读起来像缺陷。删在起机之前（一起机就可能写盘），所以跑过的盘一律要求重建。

那种时候九族会明说跳过，不假装通过；真包在的时候一条都不少验。

那份四十字节的最小包仍然留着，因为换一台没有上游仓库的机器时 --seed 还得有东西可喂。
它的造法是：

  头是 HMYRB 五个字节，然后 u16 版本 1、u16 函数个数 1。函数头是 u16 名字长度 4、
  main 的四个码元各两字节、参数量 0、槽数 0、效果数 0、u32 指令数 2。指令两条：
  0x05 0x01 加一个 f64 的 7.0（八字节小端），然后 0x1C。合计四十字节。

  照上面这段就能重造，不必留备份文件。本机的 build/seed.hmyrb 现在已经是真包
  （74594 字节），所以要用占位包时得先把它改小 —— 而那只在「没有上游仓库」时才需要。

判据里受影响的是那些读种子函数的东西：函数、操作码、求值、跳转、调用、按名、数字、
求值活、求角。文件系统那一段不受影响，这正是当初造它的原因。
