第三环的地基：域算术 mod 2^255-19
================================

为什么先有这一层
----------------

Ed25519 的验签最后要回答一句话：这两个点是不是同一个点。而点运算全部由域上的加、
减、乘、平方堆出来，再加一次模逆。所以一个域乘法的错，最终表现为「验签不通过」，
而串口上「验签不通过」与「签名本来就是假的」一模一样 —— 后者正是这一层要报的那件事。

因此域算术先有自己的判据，且这条判据不与曲线一起验。两层各自先与主机对上，之后才
允许它们合流。这与 SHA-512 当初的处理是同一个道理：它先自己与 node 逐字符对，然后
才被允许参与第二环。

表示法
------

一个域元素是八个 32 位肢体，小端，每个肢体一个 dd。没有冗余位，没有延迟约简：每次
乘法之后立刻归约成唯一表示。

选它不是因为快。理由是对拍：唯一表示意味着固件打出来的十六进制与主机 BigInt 打出来
的可以逐字符比。带冗余表示的实现里同一个数有好几种写法（±x 各一份、未约简的一份、
约简后的一份），对拍就从「比一比」变成「先解释再比」，而解释错了的时候两边都不吭声。

代价是慢：验签要两次标量乘，每次约 255 轮双倍加，每轮十几次域乘，而每次域乘是 64 个
32 位乘法。总数在百万量级。这个代价在接受范围内 —— 验签一次就够，串口上等几秒不成
问题，而一次算错要花一整轮才能查。

约简的依据
----------

只有一条：p = 2^255 - 19，所以 2^256 = 2 * 2^255 = 38 (mod p)。

一个 512 位的积 N 写成 L + H * 2^256（L 是低八格，H 是高八格），就等价于 L + 38 * H。
折一次之后结果仍可能越过 256 位，所以要折第二次；第二次的溢出小到三百以内，乘 38
之后用一条短的进位传播就能吃掉。之后是一到两次条件减 p：折完一定小于 2^256，而 2p
才越过它，所以最多减两次。

乘法写成教科书式的行扫描：外层固定 a 的一个肢体，内层走 b 的八个肢体，进位在同一条
链上。每一格最多收八个 32x32 的积加上进位，最坏是 (2^32-1)^2 + 2*(2^32-1) = 2^64-1，
正好卡在 64 位之内。这条不等式不是装饰：它决定了内层可以只用一个 64 位寄存器，而
不必开 128 位累加。

一个真 bug：cmp 会把进位标志盖掉
-------------------------------

条件减里的减法链靠 CF 传借位。第一版写的是

    sbb eax, [fp_p + rcx*4]
    mov [rdi + rcx*4], eax
    inc ecx
    cmp ecx, 8
    jb .subloop

而 cmp 会写 CF：ecx 小于 8 时它恒设 CF=1。于是除第一位以外，每一位都在借位状态下减，
不管实际要不要借。inc 与 dec 都不动 CF，cmp 动。

症状极隐蔽。六组向量里五组照旧对，只有 (p-1) 的平方那一组错：(p-1)^2 约简之后是
2^255-18，减 p 该得 1，被白借之后变成一个大于等于 p 的数，于是条件减又被调用一次，
落到 0x14 ... 7FFFFFFF。

串口上看到的是「五组对、一组错」，而这个形状很容易被读成「那一组向量写坏了」。反推
是从结果倒着走的：把固件的输出加上 p，看看它等于哪个数，一加就看见 2^256 - 2^32 + 1
—— 一个明显不是约简产物的数。从那里才回到减法链，才看见 cmp。

修法是计数改用倒数：inc ecx 前进，dec r8d 倒数，jnz 收尾。三个指令都不碰 CF。

六组向量为什么是这六组
----------------------

乘一与乘小整数最平静，能过的实现很多，看不出约简。

(p-1) 的平方是唯一一个「输入最大而结果最小」的处境，它的积是 510 位，两轮折全用到，
而且需要连续借位 —— 上面那个 bug 正是被它抓住的。

(p-1) 乘二走一条不进位的减法，与上一条互补。

两个 (2^255-1) 相乘那一组，两个输入都大于 p。域元素的表示允许暂时越界，约简是乘法
之后的事；这一组专门压这条，它要求实现不要在入口处偷偷补一次约简，也不要假设输入
一定小于 p。

最后一组是基点的 x 乘 y。这是曲线代码真正会走到的数，用它把这一层的向量与后面的活儿
连上 —— 前五组都是人造的，这一组来自曲线本身。

判据挂在两个地方
----------------

stage2 里 run_fp_test 打六行，每行是完整的 32 字节：

    Yunooka: fp val=<64 个十六进制字符>

tools/run.mjs 里独立算一遍。两边各有一份向量与一份算法，这是有意的：固件那边是被测的
东西，run.mjs 那边是尺子，尺子跟着被测物走就什么也量不出。

比的是完整的 32 字节，不是前八个。约简出错时动的往往是高位，而打进串口的前几个字节
在低端 —— 只比前八个的话，一个「折不干净、高位多留了一点」的实现会安静地过去。

参考实现
--------

tools/refed25519.mjs。纯 BigInt，跑 RFC 8032 的三条向量，并且自带签名，所以能自己造
向量：长度 0 到 500 共八条，其中 len=0 那条的签名与 RFC 里那一串逐字节相同，这一条
比「验签通过」更强，它同时证明了钳位、前缀哈希与 R 的编码都对。

它也是「篡改必须验不过」这条反面判据的来源。固件那边现在还没有曲线代码，但尺子先立
着不成问题。

验红的手段
----------

把 fp_vecs 里最后一组的 b 改一位（0x66666658 改成 0x66666659），重建、重跑。串口上
六行照打，而 run.mjs 报「域算术 6 组 —— 不对」，其余每一行照旧绿。

这个形状值得记下来：一格错只报那一格。一条「改了一位就全红」的判据什么也定位不了。

加与减：宽度不变，方向相反
----------------------------

加减与乘法分开测，理由是它们各自的错法不同。乘法错在约简：乘积比输入宽一倍，错法
落在「折回来」那一步。加减错在进位与借位：宽度不变，方向相反，错法落在链上某一位
传给下一位的那一个比特。混在一起测，一组错的时候分不出是哪一层 —— 而这一层的价值
恰恰在于「错在哪一步」说得出来。

加法有两条边要压。低的那条是「和越过 p」：(p-1) 加二等于 1，条件减必须真的发生。
高的那条是「和接近八格的顶」：(p-1) 加自己是 2p-2，而 2p = 2^256 - 38，也就是说它
离「装不下」只差三十八。这一条不是多余的 —— 它决定了 fp_add 里不必处理第九格的
进位，因为两个小于 p 的数相加一定小于 2^256。那句推理就靠这一组向量撑着。

减法也有两条边。低的那条是「不够减要加 p」：二减三等于 p-1，中间量一度是 2^256-1。
高的那条是「被减数整个是零」：零减一，每一位都要往下借，借到最高一位才停。这两条
走的是同一条链的不同深度，而链上一旦有指令碰了 CF，症状会正好落在这样的组上。

减法的实现值得说清：a 小于 b 时，第一次减法留下借位，八格里装的是 a - b + 2^256；
再加 p 就折回 a - b + p，而加 p 自己在第九格产生的那一份溢出正好抵掉借位。所以结果
直接落进 [0, p)，不必再条件减。这条抵消关系是这一段的全部依靠，写错了不会报错，
只会让结果偏一个 2^256 —— 而 2^256 在八格里看不见。

判据的六组前三加后减，顺序本身是信息：run.mjs 那边按同一个顺序重算，两边的表各自
独立写着。验红的办法是把「零减一」的被减数改成二，那一趟里加减那一行红，而乘法那一
行照旧绿 —— 两条判据互不牵连，这正是把它们分开测的理由。

点运算：投影表示与一个静默的乘法
--------------------------------

坐标是 (X, Y, Z, T)，代表仿射点 (X/Z, Y/Z)，而 T = X*Y/Z。用扩展坐标而不是仿射，
因为仿射的加法与倍点各要一次模逆，而模逆是 p-2 次方，比一次乘法贵三个数量级。扩展
坐标把除法推迟到最后一刻 —— 验签全程只在编码那一步做一次逆。

点加用统一公式（add-2008-hwcd-3 那一族），点倍用 dbl-2008-hwcd。两条链各自一个子程序，
各用一组临时格，因为它们可以被单独测。点加的 T 那一格从 E*H 来，不从 x*y 算 —— 正是
这一点让整条链不必做除法。

两条公式选的比例不同：同一个点可以是 (X,Y,Z,T) 也可以是 (kX,kY,kZ,kT)，而加与倍选的
k 不一样。所以「两个点是不是同一个点」不能比坐标，要比交叉积。

二十来步用了一个宏（FPOP），把「拷两个操作数进 fp_a / fp_b、调一个域函数、把 fp_out
拷出来」收成一行。显式写出来是二十来段几乎一样的代码，而复制粘贴出来的错不会报错，
只会算出一个别的点。

这个宏的第一个版本传的是 fp_mul，而那是错的：fp_mul 只把 512 位的积写进 fp_prod，
它不写 fp_out。宏拷出去的是 fp_out，于是乘法那一步静默地什么都没做，链上每一步都在
拿上一步的结果当自己算出来的。

它的形状特别难看。域乘法自己的六组判据用的是 fp_mulmod（乘完再约简），一直是绿的；
加减那两步用的是 fp_add / fp_sub，它们直接写 fp_out，也是绿的；只有点运算错。而它
错成的样子是四份坐标全部相同 —— 因为它们拿到的是同一个旧值。

从「四格一样」倒推回「乘法没写 fp_out」走了好几步。先把八个中间量摊开打出来，看见
A 恰好等于 Y1-X1、B 恰好等于 Y1+X1 —— 也就是那两次加法的结果原样留着。那一刻才明白：
乘法没有留下任何痕迹，这也正是它的名字里那个「静默」的意思。宏的定义到第一次跑之间，
没有任何一步会抱怨。

判据是三条交叉积相等，由主机那边判，因为固件没有模逆、也不值得为判据多写一段：

  add-bb 与 dbl-b   两个公式是不是同一个群运算
  dbl2-b 与 add-4b  群运算能不能叠（两倍的两倍，与四倍的两倍）
  add-ident         加上单位元是不是真的没动

还有一条不属于交叉积：喂进去的两个点也要与基点同点。两个点都被读成零的时候，那三条
交叉积照样会相等 —— 那是假绿，而假绿比红贵，红的会有人来查，绿的不会。所以固件额外
打两行 pti，它们不参与别的判据，只证明这一层吃进去的是它该吃的东西。

验红的办法是把 2d 那个常数的第一个肢体改一位：第一条与第二条交叉积塌掉，第三条照旧
成立 —— 因为加上单位元那一路里 2d 乘的是 T2，而 T2 是零。一次改动塌掉两条、留下一条，
这个形状说明三条判据各自独立，不是同一条算两遍。

标量乘：最笨的那一种，与一个反转的跳转
--------------------------------------

从最低位往上走：acc 置单位元、base 置 P，每一位若是一就把 base 加进 acc，然后 base
翻倍、标量右移一位，直到标量变成零。每轮一次加倍加半次加法。

选它不是因为快 —— 定窗口能快一倍多 —— 而是因为它只有两个动作，而这两个动作各自已经
单独站住过。第三环走到这里，能复用的东西比能省的时间值钱。

标量右移用的是 rcr，靠 CF 把上一格的末位移下来。所以那条链与减法链是同一个规矩：
中间不许有任何碰 CF 的指令。mov 与 dec 都不碰。

第一版跑出来三组全零。原因是一个字母：pt_scalar_zero 返回零表示「标量已经是零」，
而循环写成

    call pt_scalar_zero
    test rax, rax
    jnz .done

于是非零的标量一进门就退出，acc 停在单位元上，三组读数全是 (0,0,0,0)。改成 jz 之后
就对了。

这个错值得记下来的地方不在跳转本身，而在它藏身的方式：返回值是「零」而分支要的是
「非零」，两者都是假的、都是零，凭读代码很难分。定住它的是 add-3b 那一组 —— 同样一
趟里，用 pt_add 直接算出来的 3P 是非零的，而标量乘算出来的三组全零。两件事并排放在
同一串口上，方向立刻就定了。

同点比较加了一条 Z 不为零
-------------------------

主机那边给「同点」加了一条：两边的 Z 都不许是零。没有它，一个把四份坐标都算成零的
实现会与任何点「同点」—— X1*Z2 == X2*Z1 与 Y1*Z2 == Y2*Z1 两条在两边都是零时都成立。

这不是理论上的担心。点运算那一层的第一趟，四份坐标就曾经全部变成同一个数；那时判据
离假绿只差一次运气 —— 如果那个数恰好是零，三条交叉积会一起安静地通过。

三条判据各压什么
----------------

  mul-1 与基点    标量右移与循环终止：一个把右移写成左移的实现在这里红
  mul-2 与 dbl-b  加倍那一条：标量乘里的 double 与点倍子程序必须是一回事
  mul-3 与 add-3b 加法那一条；3 的位模式是 11，加倍与加号交替发生

只测 mul-2 的话，一个「加号永远不进」的实现照样绿；只看 mul-3 的话，一个把 3 当成 2
的实现在别的组上可能碰巧撞对。三条一起，两个动作才各被问过一遍。

标量为零那一组没有放进判据：它与单位元比，而单位元的 (0,1,1,0) 在交叉积下与全零的
点也判得成同点。Z 不为零那一条已经挡住了误判，但一组只证明「循环没跑」的读数不值得
占一个向量位 —— 它写在 pt_mul 的注释里。

验红的办法是把第二个标量从 2 改成 3：mul-2 变成 3P，与 dbl-b 不再是同一个点，而那
一趟里 mul-1 与 mul-3 照旧成立。一组错只报那一组。

顺带一件小事：mul-3 与 add-3b 的四份坐标是逐字节相同的，不只是同点。两条完全不同的
代码路径（一条走双倍-加，一条直接用点加）给出同一份投影表示，这说明两条路径里每一步
选的投影比例都一样 —— 比交叉积相等更强的一个巧合。

模逆与压缩点的编码
------------------

模逆用费马小定理：a^(p-2)。p 是素数，所以 a * a^(p-2) = a^(p-1) = 1。

代价是 255 次平方加若干次乘法，比一次乘法贵两个数量级，而整条验签链只在编码时用一次。
为它写一个扩展欧几里得能省这些时间，却要多出一整段只有一种用法的代码；这一层的判据
只有五条读数，不值得为省那点时间多一处会错的地方。

指数是常量，所以写成数据段里的八格，逐位读。最高位是第 254 位 —— p-2 = 2^255 - 21，
二进制是 255 个一减去二十。

压缩点的形状：y 的三十二字节小端，最高位放 x 的最低位。x 本身不存，它由曲线方程与
那个符号位唯一确定，这就是「压缩」的意思。所以编码只做一件事：把投影坐标除回仿射
（一次逆），取 y，再看 x 的奇偶。解码才是难的那一半。

判据的覆盖：一个看似改不动的地方
--------------------------------

编码写完之后，验红的办法我选了「把 shl 7 改成 shl 6」—— 符号位往低挪一位。跑出来
**是绿的**。

原因是四个读数的 x 全是偶数。基点的 x 是 0x…d51a，末位是 0；而 2B、3B、4B 的 x 也都
是偶数。既然 x 的最低位是零，and 出一还是零，往左挪几位都是零 —— 改与不改，三十二
字节一个都不变。

这不是判据写错了，是它的覆盖少了一半：压缩点里那个唯一不来自 y 的位，全程没有被走到。
而验签那边 R 与 A 的符号位是随机的，一半的概率会用到它。

补法不是把那条判据写得更严，而是**换一组能把这一位点亮的读数**。算一遍 1 到 12 的
倍数，前四个全是偶 x，第五个是奇 x。加一组 5B 之后，同一个改动立刻红了 —— 5B 的末
字节从 0xDF 变成 0x5F，最高位掉了。

两件事值得记下来。第一，一条判据的「验红办法」如果改来改去都是绿的，先怀疑覆盖；改
一条指令不红，可能是那条指令管的事根本没有读数依赖它，而判据本身可能完全正确。第二，
奇偶这种「一半的概率」的东西，靠几个随手挑的向量是撞不到的 —— 基点的 x 恰好是偶数，
而它又是最先被写成常量的那个点。

五组读数
--------

  b    基点     与 RFC 8032 的常量串逐字节相同，这一组连主机都不需要
  2b   2B       与主机算的逐字节相同
  3b   3B       同上
  4b   4B       同上
  5b   5B       同上，而且这是唯一一组 x 为奇数的读数

前四组覆盖符号位取 0 的那一半，5B 覆盖取 1 的那一半。五组一起，编码压住的四件事
（模逆、乘法、y 的字节序、符号位取的是 x 的最低位）才各被问到过。

验红：改符号位的移位量，5B 那一组末字节从 0xDF 变成 0x5F，判据红。前四组照旧 —— 因为
它们的 x 是偶数，那一位本来就是零。

解码：从 y 解出 x
----------------

曲线方程 -x² + y² = 1 + d x² y² 整理一下就得到

    x² = (y² - 1) / (d y² + 1)

所以解码是「一次逆 + 一次开方」。

p ≡ 5 (mod 8)，所以 a^((p+3)/8) 给出 a 的一个平方根。而「一个」是这里的关键：它给出
的是某个根 —— 可能是正的那个也可能是负的，可能是 x 也可能是 x·sqrt(-1)。所以算完必须
把那一次方再平方回去验：不等于 x² 就乘 sqrt(-1) 再验一次，两次都不等于，说明这个 y
落不到曲线上，拒绝。

这一步不是防御性编程，是算法的一半。少了它，任何 y 都会被解出一个看起来像点的东西，
而那个东西会安静地一路走到验签那一步。

拒绝的三种情形：y 不小于 p（不是一个域元素）、y 不在曲线上、x 为零而符号位是一。
最后一种 RFC 8032 明确算不合法，否则单位元有两种写法，而「同一个点」这个判据就要多
一条例外。

逆与开方共用一段循环
--------------------

两者都是「底^指数」，只差指数。所以 fp_inv 与 fp_pow 共用一个核心，指数用一个指针
传递：fp_inv 把指针设到 p-2 然后跳进去，fp_pow 用调用者给的那一份。

从第 254 位往下走：高位的零只会多做几次平方，不改变结果，所以两个指数都不必各自记着
自己的位长。这一段有 255 轮，是整条链里最不该写两遍的东西。

判据是往返
----------

对 1、2、3、5 四个倍数各做一次「算出来 → 编码 → 解码」，把编码前与解码后的四份坐标
都打出来，主机成对比较。

为什么往返比期望值结实：编码与解码互为逆，而它们各自都不需要知道「正确的坐标是什么」。
一个写死的期望值只覆盖那一个点；往返覆盖每一个输入，而且想让往返通过而实现不对，比让
一个期望值通过难得多 —— 后者只要碰对一次，前者要每一个中间量都对。

1、2、3 覆盖符号位为零那一半，5 覆盖另一半。上一轮的教训在这里变成了选向量的规矩。

坏输入也占一组
--------------

y = 2 落不到曲线上（tools 那边用欧拉判据查过），解码必须拒绝。

少了这一条，一个「任何输入都接受」的实现会与正确的实现看起来一模一样 —— 它在四个
正确的输入上全对。判据里那句「坏输入必须被拒绝」不是补充说明，是这一层的另一半。

验红的办法是把开方指数改一位：第一次解码就拒绝，串口上只有一行 before、after 一行也
没有，八行往返凑不齐。这个红的形状也有信息：它说明拒绝路径与成功路径是同一条链上的
两个出口，而不是两段各自独立的代码。

验签本体：四步与一个方向
------------------------

RFC 8032 那一条式子拆开来是四步：

  一、S 必须小于 L，不小于就不是一个标量，直接拒；
  二、把 A 与 R 从压缩点解出来，两个都解不出来也直接拒；
  三、k = SHA-512(R || A || M)，按小端当整数，再对 L 取模；
  四、[S]B 与 R + [k]A 必须是同一个点。

第一步不是形式主义。签名里 S 是模 L 的，一个不检查的实现会接受同一签名的 S+L、
S+2L …… 而这些是不同字节串的「同一个签名」。放松这一条，签名的字节串就不唯一了。

约简用的是二进制长除法：从最高位往下走，每一步把 rem 左移一位、把当前位塞进最低位，
再看 rem 够不够减 L。五百一十二轮。不用 Barrett 的理由很简单：那个要预先算一个
512 位的倒数常量，而它的正确性又依赖一次多精度乘法 —— 为了省这五百轮，要多出两处
会错的地方，而这一段只在验签时跑一次。

一个只看方向就错的 bug
----------------------

第一次跑，三组向量全部失败，而「篡改之后」也全部失败 —— 串口上是六个零。一个永远
返回零的实现在这里与一个正确的实现无法区分。

于是加了一个 where：每一步成功之后记下走到第几。失败时它就是最后一个成功的那一步。

where=4。S 检查过了，两个解码过了，k 的哈希与约简也过了。卡在最后那一步比较。

接着把摘要打出来，与主机逐字节比 —— 相同。再把喂进约简的 512 位打出来 —— 也相同。
摘要对、约简的输入对，那就只剩约简本身。可约简的四个小用例（零、一、L、以及一个
小于 L 的数）全过。

所以约简的「小输入」路径是好的，而大输入不对。把那 512 位喂给主机，主机算出
5D8CEBD9……，而固件也给出 5D8CEBD9…… —— 两个都对，也就是说我之前那个「主机 k」
算错了。

错在方向。标准的哈希输出把最高有效字节放在最前面，而 RFC 8032 说把这个摘要「当作
小端整数」—— 第一个字节就是最低位。所以 sha512_out 原样拷过去即可。而固件里多反序
了一次，等于解释成大端；更要命的是，我用来对照的那份主机脚本也用了同一种反序，于是
两边一起错、一起对，谁也没揭发谁。

第一次发现两边同时错，是在把「喂进约简的 512 位」也打出来之后：固件打的是反序后的
字节，主机算的也是反序后的字节，两者相同；但我让主机直接用 BigInt 算 `n % L` 去比
固件的输出时，那份 n 是从同一串反序字节构造的 —— 也就是说，我在用同一份错误数据
验证两个方向，其中一个还被我当成了标准。

真正让它现身的是把约简单独拎出来问：四个小用例里 L 与零都过，说明约简是对的；于是
嫌疑回到「喂进去的是什么」。而那一步的判断只能靠一份独立于固件的主机实现 —— 而那份
主机实现必须自己算一遍摘要，不能拿固件打的字节。

判据
----

RFC 8032 第 7.1 节的三组向量，每组验两次：原样必须通过，第一个字节翻一位必须不通过。

两个方向缺一不可，理由与别处一样：只验通过，一个永远返回一的实现全绿；只验不通过，
一个永远返回零的实现全绿。而这两组向量来自 RFC，不是自己造的 —— 自造向量只能证明
「它与自己一致」。

三组的消息长度是 0、1、2。长消息的多块路径已经由 SHA-512 自己的六行判据压过（四个在
两块以上），这里不重复。

接进第三环：auth.bin
--------------------

验签写完之后它还是孤立的 —— 只有一组 RFC 向量在替它作证。接进 OnlySign 之后，它验
的是这台机器自己盘上的东西。

做法：build 对 `sign.bin` 的有效内容签一次名，结果写进 `auth.bin`（六十四字节）。
固件读它、读 `sign.bin`，公钥从第二段里取，然后走四步。

公钥为什么不放盘上：放上去的话，改盘的人可以把公钥与签名一起换掉，这一环就退化成
第二环 —— 而它存在的全部理由就是「比第二环多挡一手」。内嵌在第二段之后，要伪造就
必须改第二段，而第二段是从引导扇区读进来的，那一路上没有清单可改。

签名覆盖的是 `签位` 个字节，不是整个 512 字节的缓冲区。盘上那条目录条目的长度就是
`签位`，固件读到的也正是那么多。多签四十九个零不算难，但它会让「文件内容」与「被签
的内容」从此有两个定义，而这两个定义总有一天会分家。

用的是 RFC 8032 第 7.1 节第一条向量给的种子。它是公开的，所以这里的签名只能证明
「这条链接得通」，不能证明「谁签的」。生产上要换成一对没人贴过网的密钥，而那只是
换两个常量 —— build.mjs 里有一个对照检查，换了种子却没换第二段那三十二个字节，构建立刻停。

两条判据，两个方向
------------------

  正常那一趟    必须绿。否则这一环只是把一切判死。
  --authbreak   签名第一个字节翻一位，必须红。否则一个「永远通过」的实现也是绿的，
                而它与真正的验签在正常那一趟上完全一样。

破签那一趟的串口是 `event=onlysign3 bad where=2`。where 是验签自己报的「走到第几步」：
二意味着 S 检查过了、公钥解出来了，而 R 那三十二字节被翻过之后落不到曲线上，解码就
拒了。这个红带着原因，不是一个笼统的「签名不对」。

顺带一件事：破签那一趟第一次跑时，串口停在「protected mode」那一行，一百零二字节
就断了。重跑一次就通了，而前一趟的正常盘是好的 —— 那是一次偶发，记在这里，免得下次
撞上时又从头查一遍。

下一步
------

第三环到这里真的闭合了：它在系统里验的是这台机器自己盘上的 sign.bin，而不只是一组
借来的向量。

再往上还有两件：一是把密钥换成真的（换两处常量），二是让这一环在有「缺件」时也进
补完界面 —— 现在的补完界面只认核心清单那三条，不认签名缺失。

缺件也进补完界面
----------------

第二件做掉了。

在那之前，第三环在缺 auth.bin 时只打一行 noauth 就过去了 —— 而补完界面回答的正是
「现在修不了，缺什么」，auth.bin 缺了是那个问题的一种。

现在它进同一个界面：设 core_bad = 1，调 run_repair_screen。缺件的清单从此只剩一处，
而不是「核心三条一处、签名一条另一处」。

为什么直接写 core_bad 而不去问 core.bin：补完界面只用那个数报「缺几条」，而 core.bin
那一趟已经在前面跑过、已经打过自己的读数了。改这个数不会让串口上「几条」变成假话 ——
它是这一环自己的计数，而这一环缺的是一条。

验红的办法是 build --dropauth（auth.bin 不进根目录）。--drop 那个开关只认核心清单里的
名字，所以这一条要单独有 —— 而它必须是「真的缺」，不是标记一下。串口上出现了
`onlysign3 noauth` 与 `event=guard.entry`，两行都在，说明缺件确实叫出了补完界面。

剩下一件：把密钥换成真的。那只是换两处常量，而 build 里有一个对照检查挡着 —— 换了种子
却没换第二段那三十二个字节，构建立刻停。
