AHCI：一条 MMIO 的通道，走到 port 那一片就停住了

一、为什么要换这条路

盘健康那五个探测（IDENTIFY、SMART、DEV 位、DRDY、400ns 延迟）在 IDE 的 PIIX4 上
全部回一页零。那不是命令写错，是那块实现不答这两条。所以出路只有换一条通道：
SATA/AHCI。它的寄存器在 MMIO 那一片，不在 0x1F0 到 0x1F7 这几个端口上。
设计在 design/KOHANE.txt 第五层，账在 design/PLAN.json 的 disk-health 那一条。

二、已经成立的事（五件，都有串口读数撑着）

一、控制器在 PCI 上。0 号总线的 13 号槽，vendor:device 是 8086:2829。
    按 class code 0x010601（大容量存储 / SATA / AHCI）找的，不按 vendor 比 ——
    class 跟的是规范，换一台机器也一样。

二、它的六个 BAR 看清楚了。BAR0 到 BAR4 是 I/O 端口（0xD041、0xD049、0xD051、
    0xD059、0xD061），BAR5 是内存 BAR，值 0xF0804000。规范说 ABAR 在 BAR5，
    所以这个数是 ABAR，不是猜的。

三、0xF0804000 那一片进得了页表。页表原先只映前 1 GB（PML4 0x1000、PDPT 0x2000、
    PD 0x3000），而 0xF0804000 落在 PDPT[3]，那一项是空的。map_page_2m 从 0x4000
    起的池里取一页做 PD，把那个 2 MB 页映上去。这是这台机器第一次映一 GB 之外的
    物理地址，而它现在是一个普通函数。

四、PCI 命令寄存器本来就是开的。Memory Space（bit 1）与 Bus Master（bit 2）都在，
    0x100007 读写一致。这一条排除了一个很容易被当成原因的假设。

五、GHC.AE 置得上，也读得回来。写之前 GHC 是 0x8E00，写之后 0x80008E00。

三、已经排除的六条

一、PCI 命令寄存器没开 —— 见上，本来就开着。
二、按 PI 枚举 port 这条路 —— PI 读出来是零，而 VBox 的日志说 port 0 有盘。
    所以这一版直接对 port 0 做初始化，不按 PI 走。
三、COMRESET —— PxSCTL.DET 写 1，等它回 0，再等 PxSSTS.DET 变成 3。没有变。
四、HBA Reset —— 这一条最值得记：写了 HR 之后它一直不清零（GHC 从 0x80008E00
    变成 0x80000001，然后停在那里）。而 HR 期间访问 port 寄存器是非法的，
    于是不该在复位没完成时做后面的任何事。现在这一版不发 HR，把这一条记成
    「没做成的事」而不是「试过没用」。
五、AE 与 HR 的顺序 —— AE、HR、再置 AE，三种顺序都走过，PI 仍是零。
六、port 区是不是地址算错 —— port 1 的 PxCMD 读出来是零，而 port 0 的是自己写进去的
    0x11。两个 port 是两个不同的地方，所以地址算术没有错位。

四、现在卡在哪（读数的原样）

  ahci pcicmd 0x100007 0x100007        命令寄存器开着，读写一致
  ahci dev 13 0xF0804000               13 号槽，ABAR 是它
  ahci cap 0x18920F 0 0                CAP 读得出来，但 shape 可疑（见下）
  ahci ghc 0x8E00 0x80008E00           AE 置得上
  ahci pi2 0 0x80000000                HR 退出去之后：PI 仍是零，AE 还在
  ahci bar 0xD041 ... 0xF0804000       六个 BAR
  ahci timeout                         命令发出去，PxCI 的槽 0 一直不清
  ahci stuck 0 0x11 0xFFFFFFFF 0 0     sig、PxCMD、PxIS、PxTFD、PxSSTS

三个数合起来指向同一件事：port 那一片不是活的。
  PxSIG 是零（ATA 盘应当是 0x101）；
  PxIS 写 0xFFFFFFFF 就读回 0xFFFFFFFF（它是 RW1C，本来就该读回零）；
  PxSSTS 是零（DET 应当是 3）。

而 CAP 与 GHC 读得出东西。CAP 是 0x18920F —— 按规范解读，bits 4:0 是 NCS，
所以 NCS 是 0x0F（16 个命令槽）。VBox 的实现通常是 32 个槽，所以这个值可疑。
IS（偏移 8）、VS（偏移 0x10）、CAP2（偏移 0x24）三个都读成零，而 VS 是这个怀疑
最硬的一条：AHCI 1.0 的版本寄存器是 0x00010000，任何真实现都不会给零。

所以现在最可能的解释是两条之一：
  A、ABAR 那一片是 VBox 的设备模型给的，而 port 侧没有被激活（控制器停在
     IDE 兼容模式，CAP 的 bit 18 SAM 是零，也不否认这一点）；
  B、0xF0804000 上的东西根本不是 AHCI 的寄存器组 —— CAP 与 GHC 那两个读数
     来自别的什么，写 AE 能读回来只是因为那里可写。

五、下一步的三条候选（按便宜到贵）

一、换芯片组。这台 VM 是 piix3（showvminfo 里 chipset="piix3"），而它报的
    AHCI 是 ICH9 的 8086:2829 —— 一个 ICH9 的控制器住在 i440fx 上，这组合本身
    就不像被完整验过的。VBoxManage modifyvm Yunooka --chipset ich9 可以换，
    代价是引导链要重测一遍（那是这台机器上最贵的一条路，所以要放在最后）。
二、在 ICH9 之前先读清楚 GHC 的其它位与 CAP 的 SAM 位，看控制器自己说不说自己
    在 IDE 兼容模式；以及读 BOHC（偏移 0x28）看 BIOS 交接状态。
三、给 SATA 控制器换一个类型（--controller ICH6 之类），看 port 侧是否就活了。
    这一条最便宜，因为它不动芯片组、不动引导链。

六、这一块留下的两样东西

map_page_2m 是通用的：任何一 GB 之外的物理地址都能用它映进来。它不属于 AHCI，
下一次要用 MMIO 的东西（网卡、显示、别的 PCI 设备）都会用到它。

pci_write 也是通用的，在那之前这一份文件里只有 pci_read。


七、换到 NVMe：那一片是活的

AHCI 那边的最后一锤是两个实验一起给的。

第一个是对照：映一个肯定没有设备的物理地址（0x50000000，RAM 只有 32 MB），读它 —— 读出
零。而 ABAR 那一片读得出 0x18920F。所以那一片是真的设备，不是「未映射内存的残留」。
有一个更早的实验因此被判错：往 CAP 写 0xDEADBEEF 再读回 0xDEADBEEF，当时我以为那证明
它不是设备；其实 VBox 的 AHCI 只是不保护 CAP 的写入。一个读数没有对照，就只是一个数。

第二个是把六个 port 的 PxSSTS 全读出来：**六个都是零**。所以不是「port 0 上没东西」，
是这块盘在控制器眼里根本不存在 —— 而 BIOS 通过同一个控制器访问过它（VBox 日志里
AHCI 0-P#0: 0x800 sectors）。那是配置与实现之间的事，guest 侧改不动。

于是换 NVMe：它没有 IDE 兼容模式那一段历史，寄存器全在 BAR0 的 MMIO 里，而版本寄存器
VS 是必需的 —— 「那一片是不是真控制器」用 VS 一个数就答得出来。

加上去之后第一次读就答了：

  nvme dev 14.0 0xE1008000
  nvme regs 0x00010200 0x0A010FFF

VS 是 0x00010200（NVMe 1.2），CAP 的低十六位是 0x0FFF（MQES，4096 个队列项）。
两个都是合理的版本号与能力值，而那正是 AHCI 那边缺的东西（它的 VS 是零）。
所以这条通道是活的。

下一步是 NVMe 自己的那条初始化：CC.EN 清零、等 CSTS.RDY=0、写 AQA/ASQ/ACQ、
CC 里置 EN 与 CSS 与 IOSQES/IOCQES、等 RDY 起来、然后发第一条命令。

为什么这条路对盘健康更好：NVMe 的 Get Log Page（opcode 0x02，LID 0x02）一页就把
Composite Temperature、Available Spare、Percentage Used、Media Errors、
Data Units Read/Written 全给出来 —— 那是 SMART 想要的那五样，而它不需要先过
IDENTIFY 这一道门。


八、卡住的那一个位：Bus Master

初始化做完之后命令不完成，而诊断把范围缩到了一处：

  nvme diag CC=0x00460001 CSTS=0x1 ASQ=0x406000 ACQ=0x408000
  nvme stuck SQ_head=0 CQ_CID=0 CQ_status=0

CC 的 EN 起了、IOSQES 与 IOCQES 都是该有的值、CSTS 的 RDY 起了、两个队列基址读回来
也全是我写进去的。而 SQ 的 head doorbell 一动不动 —— 那是「命令根本没被取走」，
不是「取走了而没完成」。这两件事要改的地方完全不同。

原因是 PCI 命令寄存器：**这个设备的 Bus Master 位（bit 2）是零**。

  nvme pcicmd 0x100003 -> 0x100007

置上之后命令立刻完成。而这一条最难看出来，因为 CSTS 在 Bus Master 关着的时候照样报
RDY=1 —— **「控制器就绪」与「控制器能把队列读进来」是两件事**，而前者看起来像后者。
AHCI 那个设备我置过这一位，可 NVMe 是另一个设备；「上一块设备的开关」不会跟着新设备走。

第一个跑通的命令是 Get Log Page（SMART / Health），它成功完成了（status field 是零），
而 VBox 返回的那一页全是零 —— 它没有真的温度与寿命可报。所以健康那五样在这台机器上
暂时只有「形状」没有「内容」，而这件事要写清楚，不能拿零当读数。

于是换成 Identify Controller（opcode 0x06，CDW10 的 CNS 写 1），它答了：

  nvme model ORCL-VBOX-NVME-VER12
  nvme serial VB1234-56789

型号在 Identify 那一页的 offset 24（40 字节）、序列号在 offset 4（20 字节），
两段都是定长、尾部用空格补齐，所以读出来之后要自己修剪尾部。

这一条判据的原话在 design/KOHANE.txt 第五层：「型号那几个字符是盘自己报的，不是代码里
写死的」。所以 tools/run.mjs 里那条判据不只查「读到了非空的串」—— 那一条一颗打印固定
字符串的实现也能过 —— 它还查第二段的源里有没有那个型号，有就判红。验过：把型号加进
一行注释，判据报的是「型号被写进了代码（那就不是盘报的）」，退出码一。

至此 disk-health 的阻塞解除了：它原来等的是一件不存在的事（一块答 IDENTIFY 的 IDE 盘），
而真正缺的是一条能跑命令的通道。剩下的是「三件」里的另外两件 —— 能力位、以及把温度与
通电时间从有内容的设备上读出来 —— 那都是这台机器上可以继续做的事。


九、第二个来源：命名空间有多大

Identify Namespace（同一条 opcode，NSID 写 1、CDW10 的 CNS 写 0）答了：

  nvme ns 4096 9

4096 个逻辑块、每块 2 的 9 次方字节 —— 2097152 字节，而造盘时给的是 --size 2。

三个数在这里见面：我给 VBox 的配置、盘自己报的块数、以及判据那一侧认为它应当有多大。
第一个与第三个在同一个文件里，只有第二个来自盘 —— 而它是唯一能回答「盘报的对不对」
的那一个。所以这条判据的力气全在「两个独立来源对上」，而不在「读到非空的数」。

LBA 大小要绕一步：offset 26 的低四位是 FLBAS（用了哪一种格式），格式表从 offset 128
起、每项 4 字节，而 LBADS 在格式项的 byte 2。表里可能有好几种格式，挑哪一种由盘自己定，
所以不能把 512 写死。

验红的手段值得记：把 NVMe盘大小 改成 3 MB、而**不删盘文件**（run.mjs 只在文件不存在时
造盘），于是判据期望 3 MB 而盘报 2 MB —— 它红了，理由写的是「应当 3145728 字节，
实际 2097152」。

而第一次写这条判据时，打印里那句「应当 2097152」是写死的字面量，与判据用的变量不是
同一个来源：改常量那一跑，判据红了而打印还在说 2 MB。**「打印出来的数与判据用的数不是
同一个来源」这个毛病在这一份文件里出现过三次**（build.mjs 的两行、README 的那份表、
这一处），三次都是同一个形状，所以它值得单独记一句。


十、后记：这一章的证据链断了

写完第九节之后，map_page_2m 里查出一个 bug，而它把第二节到第八节的全部读数变成了假象。

那个函数有两处把入参 rdi 就地改掉（rep stosq 要用 rdi），于是：
  一、末尾「返回 rdi」交出去的是 PD 页的地址，不是入参；
  二、新建 PD 页那一支里，写 PD 项那一句取的也是 rdi —— 那一段虚拟地址被映到了堆上。

后果是：**第一次**映射某个 4 GB 区段的时候，调用者拿到的地址指向页表页或堆；而**第二次**
映射（那一格已经有 PD）走复用分支、rdi 不被改，返回值就对了。于是同一段代码里
「读得出值」与「读到的是内存」同时成立，而两者在串口上长得一样。

AHCI 那一章的所有怪读数都来自这里：CAP 是 0x18920F、往 CAP 写 0xDEADBEEF 读回自己、
三个芯片组读到同一个值、对照地址读出零、六个 port 的 PxSSTS 全零 —— 那些都是页表页与堆
里的内容，不是寄存器。

所以前面几节的**结论**要按这一条重读：
  仍然成立 —— 「控制器在 13 号槽、BAR5 是 ABAR」。那走的是 PCI 配置空间（0xCF8/0xCFC），
    不经过页表。
  全部作废 —— 「CAP 读得出」「GHC 置得上」「AE 落实」「COMRESET 没效果」
    「PI 是零」「PxSIG 是零」「六个 PxSTS 全零」，以及建立在它们上面的那六条排除。
  一半成立 —— 「换芯片组之后 ABAR 变了」用的是配置空间，成立；而「port 侧同样全零」
    是假的。

而 NVMe 那边能读到真值（VS 0x00010200、CAP 0x0A010FFF、型号 ORCL-VBOX-NVME-VER12、
容量 4096 块），恰恰是因为它在 AHCI 之后映射、走的是那个复用分支 —— 假象与真相在同一个
函数里差着一个分支。

这一章留着不删。它的价值从「AHCI 不通的证据」变成了「一个读数是怎么骗过六轮排查的」，
而后者比前者有用：这个 bug 藏得久，正是因为它让「读得出值」看起来像证据。而我在那一轮
其实做过对照实验（映一个肯定没有设备的地址，读出零），却仍然被骗 —— 因为**对照也走了
同一条错路**。

所以：如果将来要重开 AHCI 这一条，第一件事不是写驱动，是把 map_page_2m 修好之后重跑
那几个读数。在那之前，「AHCI 的 port 侧不报设备」这个结论不成立 —— 它可能只是从没被
真正读过。
