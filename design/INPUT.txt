复数控制器：YNOK 的一个特性（规划）
====================================

用户给的一条：Yunooka 允许复数键鼠等控制器的存在，而这契合「对 LLM / API / Agent 友好」
那一侧的规划。这一份把它拆成能落的东西，并且指出哪一条现在就能做、哪一条要等前提。

一、先说清楚「复数」到哪一层

物理上有两件事，它们不是同一件：

    一是多台设备。两个键盘、两个鼠标、一个键盘加一块触摸板。这在 8042 上是做不到的 ——
    那一个芯片只有一个键盘口与一个鼠标口。要多台，得有 USB 栈，那是另一件大得多的事。

    二是多个源。同一个物理键口，可以由不同来源把事件送进来：用户的键盘、一段脚本、
    一个 Agent、一条网络连接。它们各自是一个「输入源」。

这一份说的复数在第二层，而第二层是第一层的前提 —— 没有「源」这个概念，两台物理设备也只是
两个抢同一份状态的东西。反过来，源立住之后，多台设备只是多几个源。

二、源是身份，不是设备

一个源有名字、有一种信任级、有自己的事件队列。今天能指出来的三条路：

    8042 键盘（扫描码进来）    已经在用。VBoxManage controlvm keyboardputscancode 注入，
                              固件轮询 0x64 与 0x60。移窗那一格走的就是它。
    信箱（第二块盘的扇区）      已经在用，但它只在启动时读一次，不是运行时的。
    网络（将来的口子）          还不存在。

信任级这个词要小心，用户后来把它说清楚了：身份记得住来源，不决定地位。一个物理键盘按下
去，与一段脚本自称「我按了」，这件事要能分开 —— 但分开是为了说得出「是谁」，不是为了
让其中一个低一等。一个 Agent 自己造出来的虚拟键鼠与用户的真实键鼠同级，见第七节。

三、每源一个焦点

这是这一份里最要紧的一句话。焦点不再是一个全局变量 —— 每个源有自己的指向窗口。

于是两个源可以同时操作两个窗口：源 A 的方向键动窗口一，源 B 的方向键动窗口二。这正是
「窗口即任务」那句在输入这一侧的样子 —— 两个任务并排，各自有自己的手。

而它顺带解掉了 design/KOHANE.txt 里那一句：「窗口的拖动与叠加 —— 那要有『一个窗口对象』
与『焦点』，而那要进程那一层。」输入层自己的焦点不需要进程。一个窗口对象加一个每源焦点，
移动与叠加就能成立；进程那一层带来的是「另一个程序也能有这个窗口」，那是更后面的事。
所以那句话现在要读成：单源焦点不需要进程，跨源共用一个窗口才需要。

四、事件的形状

一行事件，四个字段，顺序固定：

    源 id、种类、负载、目标窗口

种类是「按下 / 放开 / 移动 / 滚轮」之一；负载随种类而定（键码，或者 x 与 y）；目标窗口是
那个源当前焦点所指的窗口，没有焦点时为空。

形状固定这件事不是洁癖：判据只认串口，而串口上能认的东西必须一行读完。同一行里带上了
源与目标，一条按键记录就不再只是「发生了什么」，而是「谁让它发生的、它落在了哪里」——
后者才是可回放的。

五、「对 Agent 友好」的四个条件

这句话容易被当成气氛，所以拆成四条能检查的：

    可寻址    每个源有名字。一个 Agent 要能说「我是 src:coder-1」。
    可注入    有一条合法的通道把事件送进来，而不必去抢用户的键盘。
    可观察    事件流能被读出来 —— 上一条的四字段行就是它。
    可仲裁    冲突规则写明，不靠时序碰运气。见下一节。

四条里缺任何一条，「友好」都只是说法：缺可寻址就没法分辨是谁、缺可注入就只能抢键盘、
缺可观察就是黑箱、缺可仲裁就是两个 Agent 互相覆盖对方的操作而没人知道为什么。

六、仲裁：先到者持有

两个源同时操作同一个窗口时的规矩，取「先到者持有」（grab）：某个源在一个窗口上按下之后，
那个窗口归它，直到它放开。后到的源的事件被挡下，而挡下要留一行。

选这一条而不是「按优先级」，理由是优先级要在配置里维护一张表，而那张表会随源的数量长；
先到者持有只用状态机就能说清，而且它有一个好性质 —— 谁在操作是看得见的。

七、虚拟与真实同级

这一节单独写，因为「注入」这个词很容易让人以为它低一等。不是这样：一个 Agent 自己造出来
的虚拟键鼠，与用户的真实键鼠同级。用户明确说过这一条。

同级的意思是五件事都一样：

    接口一样      同一套事件形状，同一组种类与负载。
    能力一样      能按的键、能做的移动，集合相同。
    焦点地位一样  也能持有窗口，也能被别的源在事件流里看见。
    位置一样      事件流里同一行、同四个字段，没有「特殊来源」这一栏。
    窗口行为一样  一个窗口不该知道这次点击是人是机。

最后一条是这一节的要点，因为它是可测的：如果窗口能区分源是人是机，Agent 就成了二等公民 ——
它得走另一条路，而两条路就会分岔。

而登记仍然要有。登记的理由与地位无关，只与可仲裁、可观察有关：两个源抢一个窗口时，得说得出
是谁；被挡下几次，得数得出来。一个没有名字的源做不到这两件事，所以它的事件被拒 —— 拒的
理由是「说不出你是谁」，不是「你低一等」。

授权在登记时一次完成，之后不再分级。这也与进程那一层同构：一个进程被启动之后，它拿到的
接口不因为「它是脚本拉起来的」而少一半。所以「能注入事件等于一只远程的手」这句警惕仍然
成立，而它落在「登记」这一关，不落在每一次事件上。

于是「同级」有了一条可测的形式（见第十二节第八条）：同一个窗口被真实键鼠与虚拟键鼠各操作
一次，两趟的行为完全相同 —— 位置变的量一样、擦旧的量一样，而串口上的事件行只在源 id
那一格不同。

而同级不覆盖信任：它说的是「一个受信任的主体造出来的虚拟控制器」。这一句原来没有写，后来
补上 —— 见第九节第四节。

八、操作员绑定：谁能用这一只手

用户给的一条，它与第七节不冲突，而且正是让第七节站得住的那一条：每一个键鼠或其他控制器
都绑定一个操作员。骇入者理论上可以在 Yunooka 里造一个新的虚拟控制器，但造出来的那个没有
绑定，于是它送来的事件被拒；而想要一个绑定，要过 volcano-separator 那一关 —— 它拒绝
不受信任的工程。

绑定是双向的：一个控制器只能以它绑定的那个操作员的身份送事件，而一个操作员的事件也只能
从它绑定的那些控制器进来。后者可以放宽，前者不能 —— 前者的坏处是「冒充」，后者的坏处
只是「不方便」。

要能验，不能自报。这里有一步代价上的取舍：给每一个按键签一次名不可行（每次事件一次
Ed25519，按键那个频率下跑不动）。所以分两层：

    登记时验一次：控制器注册的时候，操作员用 OnlySign 签一份绑定 —— 控制器 id 与操作员
    id 一对。这份绑定可验、可撤销，它住在清单里，与 core.bin 同一种做法。
    运行时只查表：事件行带控制器 id，控制器 id 到操作员的映射在内存里。签名不在每一次
    事件上，而在建立那个映射的那一次上。

这与建立会话是一回事：身份在握手时验，之后用会话本身说话。

造一个新控制器是一个特权动作，而许可的来源是「这个工程受不受信任」。这就是
volcano-separator 的位置，而且它把「不受信任的工程」落到了一个查得动的地方：盘上的一个
包想创建控制器，它的签名必须在信任清单里 —— 与 OnlySign 那一套完全重合，不需要第二套
凭据。

「真实键鼠也绑定」这一句要说清：物理键盘同样绑定到一个操作员，例如「本地操作员」。于是
第七节的「同级」与这一节的「绑定」并不冲突 —— 同级说的是两支手地位一样，绑定说的是每支
手都得先说明自己是谁。

撤销也要有：一个操作员离场，它名下的控制器全部失效。这是「按操作员绑定」的自然含义，
而它比「按设备撤销」好用 —— 换了个人，不必逐个去禁那些设备。

拒绝要分成两种，因为修法不同：没有绑定（说不出是谁）、工程不受信任（说得出，但不被允许）。
串口上那两行必须不一样，否则查错的人会先去翻登记表，而问题在信任清单里。而第二种的正式
名字是「工程失活」，它不是一次拒绝，是一个主体的状态 —— 见下一节。

九、信任的粒度是主体，不是行为

用户给的这一条比前面几条都更原始，而它要先把一个词定下来：这里说的「工程」是一个具体的
项目。它是主体，而行为是被主体驱动的。于是有一条很短的推论：主体本身不被信任的时候，它
驱动的那些行为不是「某一次被拒」，而是全部无效 —— 这就是工程失活。

这一条改变了几件事。

一、判定落在主体启用的时候，不落在每一次行为上。一个工程被装载、被绑定、被启用；此后它
的行为不再逐个判信任。所以这一层在 YNOK 上的日常形态是「这个主体还活着吗」，而「拦下这个
动作」不是它的日常形态。这不是省事，是省错：一个逐次判定的实现，其判决会随时间漂移，而
主体只有一个状态。

二、失活是传递的。一个工程被失活，它此前建立的那些虚拟控制器一起失效，不必逐个去找它们的
id。这与第八节「撤销按操作员走」是同一条链上的两级：最上面是主体，下面是操作员，再下面是
控制器。上层失活，下层全部无效。

三、本地不是特权。有人可以走本地的方式（例如 USB）把一个虚拟控制器注进来，让它看起来像
用户自己建的工程。这条路走不通，原因与 USB 无关：USB 那一层进到 YNOK 里也是一个源，也得
绑定到一个受信任的主体。于是伪装在两处同时失败 —— 主体没有签名（失活），控制器没有绑定
（被拒）。「看起来像」从来不是信任的依据。

四、于是「同级」有了它的前提，而第七节里没有写清：同级说的是「一个受信任的主体造出来的
虚拟控制器，与真实键鼠地位一样」。同级不覆盖信任 —— 读第七节时要把这一句补上。

五、日志仍然可读，而判决不在日志里。一份写着「某次按键被拒」的记录有用，但查错的人不该去
那里找判决：判决在主体的记录上。这同样是省：不必给每一次行为留下一个信任判定。

十、注册：一次性的、全有或全无

用户把这一整套的目的说破了：它挡的是「有人借可对外的 USB 设备远程操作 Yunooka」。而要一个
设备被信任，除了纯本地输入那种明显属于用户侧的行为，只有走一段繁文缛节一般的注册 —— 而那
段注册必须「手动」操作。

「手动」加引号，意思是它不是「用人手去按」，而是「知情者亲自、一次完成」。用户做得到，
Agent 也做得到，因为两边知道的是同一批东西。所以 Agent 的虚拟控制器不必有一条特殊的注册
路：它与用户走同一条，因为它拿得出同样的自证材料。这是我读这一条时唯一的疑问，而那个引号
正好回答了它 —— 注册不是一个体力活，是一次知情者的自证。

一次性的，全有或全无：不是渐进式的（对了一部分就前进一部分）；单次失败从头开始；失败不说
明缺了什么、错在哪里；也不锁定输入源，于是骇客可以一直试。

不锁定是有意的取舍，不是疏漏：锁定会送出一个「拒绝服务」的入口 —— 骇客只要反复拿错误的
材料去撞，就能把合法的源锁死。而搜空间足够大的时候，不锁定是安全的。

这里要把两层的功能分开说，否则容易记错哪一层在保证什么。

    第一层是格式。一份又臭又长的自证材料，缺斤少两就过不去。它对「对 YNOK 了解不多」的
    注入源有效，而它的作用有上限：格式只要泄漏一次，这一层就没有了。
    第二层是签名。材料里包着只有那个主体才拿得出的东西 —— OnlySign 签出的绑定、工程清单
    的摘要。这一层不依赖格式的保密，它是真正的保证。

用户说「其实也就是密钥的基本作用，只不过可能更类似 sha256 这种东西」。这句读成：比对是全或
无的，而且不泄露任何中间信息 —— 不是「拿哈希本身当密码」，而是「要么整个对上，要么什么都
得不到」。所以繁文缛节的价值首先是它把签名带进来了，顺手挡下的那些人才是第二重收益；把两
层说成一层，下一次就会去加固不该加固的那一层。

还有一处必须写下来：「不告诉错误详情」只对外部成立。一个合法的源如果记错了什么（换了一块
盘、id 变了），它同样得不到提示。所以本地要有另一条路 —— 需要物理在场才读得到的诊断。这
也是「手动」的另一面：本地有特权，外部没有。

于是设备的三个位置很清楚：内置与本地设备绑定到本地操作员就是可信的；可对外的设备（USB）
默认落在外部那一层，必须走完整注册；虚拟控制器不分来自用户还是 Agent，也走它。

十一、第二条运行时源：三条候选与各自的前提

现在只有一条运行时输入路（键盘）。要证明「每源一个焦点」，必须有第二条。三条候选：

    信箱升级    把第二块盘从「启动时读一次」改成「运行时空转时轮询」。前提最小 ——
                那块盘与读它的代码都在。代价是它慢（一轮一次读盘）且有副作用（读盘要
                让出 CPU 一小段）。
    串口双向    串口只能往外说，四条实测在 stage2 的串口一节。要它双向得换后端，而那
                一层在这台机器上没通。
    网络口子    VBox 给了 E1000，PCI 配置空间读得通（判据已经在跑）。要走完还得有收发
                描述符环与一个最小协议 —— 那是几格的事，不是一格。

所以「第二条源」的第一件是信箱升级：它最便宜，而且它正好把一条只用在启动的通道变成一条
运行时的通道 —— 那件事本身也有价值。

十二、判据的形状

现在能立七条，第八与第九条都要等第十一节：

    一、事件的形状：一次按键在串口上留下一行，四个字段都在，且目标窗口是那个源焦点所指
        的那一个。这一条今天就能立 —— 键盘源与两个窗口都在。
    二、未登记被拒：把一个没有名字的源 id 送进仲裁，事件被挡下，而串口上留一行拒绝。
    三、没有绑定的控制器被拒：拒绝行说的是「未绑定」，而它与「未登记」那一行不是同一行。
        两种拒绝的修法不同，串口上分不开就等于没分。
    四、工程失活：一个签名不在清单里的工程请求创建控制器，整个工程失活，串口上留一行。
        同一份请求在签名进了清单之后被接受 —— 两条都要验，只验前一条的话，一个「永远
        拒绝」的实现也能过。
    五、伪装可被识破：两个工程同名、同声明的能力，只有一个的签名在清单里。两者各请求
        创建一个控制器，一个成功、一个失活，而串口上那两行不同。这条判据在名字上完全
        不可分，只在签名上可分 —— 一个按名字判断的实现过不了它。
    六、注册是全有或全无：一份完整的注册材料成功；同一份删掉任意一项就失败，而失败那一
        行与「缺了哪一项」无关 —— 两种不同的缺项必须给出同一行字。这一条把「不说明缺
        什么」从一句承诺变成一次比对。
    七、失败不留状态、也不锁定：连着若干次失败的尝试之后，一份正确的材料仍然成功；而一
        次「差一点就对」的尝试不会让下一次变短。这两样合起来才是「不锁定」那个取舍的可
        测形式 —— 少了任何一样，一个把状态留在某处或者试几次就锁死的实现也能过。
    八、同级：同一个窗口被真实键鼠与虚拟键鼠各操作一次，两趟的读数完全相同，而事件行
        只在源 id 那一格不同。它要证明的正是「两条不同的路，同样的待遇」。
    九、每源一个焦点：两个源各自送一个方向键，两个窗口各自动一个。

一至七都能立，因为它们只需要固件里的一个状态机、一份清单、一份材料与一个假装的请求 ——
不必有第二台设备。第三到第七条尤其值得先立：它们把「安全」那一侧变成可数的东西，而一个
静悄悄丢掉事件的实现，看起来与「没人试过」一模一样。

第八与第九条卡在同一个前提上，而那个前提不该用「同一路改个名字」去凑。一个假的第二源比
没有第二源更坏：它会给出一个绿，而那个绿的理由是「名字不同」，不是「路不同」。

十三、这一份现在只到规划

它不建任何东西，也不改任何判据。窗口、焦点、输入这三条先稳；第十一节那条最便宜的第二源
（信箱升级）是第一件可落的事，而它落下来之前，第十二节第八与第九条判据保持不立。
